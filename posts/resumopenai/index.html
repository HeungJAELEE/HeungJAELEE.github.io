프로젝트 한눈에 보기

resumOpenAI는 사용자가 입력한 경력·교육·프로젝트 정보를 직무에 맞는 이력서 초안으로 재구성하는 Flask·React·OpenAI 기반 LLM 애플리케이션 프로토타입이다. 이 프로젝트에서 중요하게 본 것은 문장을 화려하게 만드는 기능이 아니라, 원본 경력 사실을 잃지 않으면서 필요한 정보만 모델에 전달하고 생성 결과를 다시 검증할 수 있는 흐름이었다.

이 글은 프로토타입의 설계와 구현 관점을 설명한다. 별도의 학습 데이터셋, 학습 로그, 평가 결과로 확인되지 않은 fine-tuning 완료나 모델 성능 향상을 성과로 주장하지 않는다. 현재 단계에서는 프롬프트 규칙, 구조화 출력, 후처리 검증을 우선 적용하는 것이 합리적이라고 판단했다.

1. 프로젝트 배경: 이력서 생성보다 어려운 것은 사실 관리다

이력서 작성에는 서로 다른 성격의 작업이 동시에 들어간다.

  • 여러 문서에 흩어진 경력과 프로젝트를 한 형식으로 정리해야 한다.
  • 같은 경험도 지원 직무에 따라 강조할 문제, 행동, 결과가 달라진다.
  • 문장을 매끄럽게 만드는 과정에서 실제로 하지 않은 업무나 확인되지 않은 수치가 추가되면 안 된다.
  • 이름, 연락처, 회사 내부 정보처럼 민감한 데이터가 외부 API로 불필요하게 전달되지 않아야 한다.

따라서 목표를 “AI가 이력서를 대신 작성한다”로 잡지 않았다. 사용자의 경력 사실을 구조화하고, 직무별 초안을 만들고, 사용자가 근거를 확인한 뒤 승인하는 작성 보조 도구로 범위를 정했다. LLM은 최종 의사결정자가 아니라 표현과 재배치를 돕는 변환기로 두었다.

설계 목표

  1. 입력 정보와 생성 문장을 추적할 수 있을 것
  2. 개인정보를 최소 수집·최소 전송할 것
  3. 화면, 비즈니스 규칙, 모델 호출을 분리할 것
  4. 모델 응답이 달라져도 동일한 스키마로 검사할 수 있을 것
  5. 사용자의 검토와 수정 없이는 최종본으로 확정하지 않을 것

프로토타입에서 제외한 범위

  • 채용 합격 가능성 예측
  • 경력 사실의 자동 인증
  • 충분한 근거 없이 경험이나 성과 수치 보완
  • fine-tuning을 했다는 전제의 품질 주장
  • 기업용 보안·감사 요건을 모두 충족한 운영 서비스

2. 왜 React–Flask–OpenAI 구조를 선택했는가

이력서 편집 화면은 섹션 추가, 순서 변경, 수정, 초기화처럼 상태 변화가 많다. 그래서 입력과 미리보기를 컴포넌트 단위로 관리하기 쉬운 React를 화면 계층에 두었다. 반면 API 키 보호, 입력 정규화, 프롬프트 조립, 응답 검증은 브라우저에 노출되면 안 되므로 Flask 서버가 중간 계층을 맡도록 했다.

OpenAI API는 텍스트를 직접 렌더링하는 계층과 분리했다. 이 분리는 모델이나 프롬프트가 바뀌어도 화면 전체를 다시 만들지 않고, 서버의 생성 어댑터와 검증 규칙을 교체할 수 있게 한다.

3. 사용 기술과 선택 이유

React

  • 경력, 학력, 프로젝트를 반복 가능한 폼 컴포넌트로 구성하기 적합하다.
  • 원본, AI 초안, 사용자 수정본을 별도 상태로 보관하면 변경 내용을 비교하기 쉽다.
  • 섹션 단위 재생성처럼 부분 업데이트가 필요한 인터랙션을 구현하기 좋다.

Flask와 Python

  • 작은 API 프로토타입을 빠르게 구성하면서도 전처리·검증 함수를 명확히 분리할 수 있다.
  • Python의 사전·리스트 구조는 이력서 JSON 스키마를 다루기에 자연스럽다.
  • 모델 호출 전후의 로깅, 예외 처리, 테스트 코드를 단계적으로 확장하기 쉽다.

OpenAI API

  • 사용자 사실을 직무 관점으로 요약하거나 문장 톤을 통일하는 생성 작업을 실험할 수 있다.
  • 모델 자체보다 입력 계약과 출력 계약을 서버에서 통제하는 방식을 검증하는 데 사용한다.
  • API 응답이 실패하거나 형식에 맞지 않을 때 재시도 또는 수동 편집으로 전환할 수 있게 설계한다.

JSON 기반 구조화 출력

자유 형식 Markdown을 바로 받으면 섹션 누락, 제목 변경, 임의 문장 추가를 기계적으로 확인하기 어렵다. 먼저 정해진 JSON 형태로 받은 뒤 화면이나 문서 템플릿에서 렌더링하면 검증과 표현을 분리할 수 있다.

4. 데이터 구조: 개인정보와 경력 근거를 분리한다

모델에 전달할 데이터는 “문서 전체”가 아니라 목적에 필요한 최소 필드로 정리한다. 이름, 전화번호, 이메일, 상세 주소는 문서 렌더링 단계까지 로컬 상태에 남기고, 문장 생성에 필요하지 않다면 외부 API 요청에서 제외한다. 회사명이나 고객명이 민감한 경우에는 별칭으로 치환한다.

아래는 설계 의도를 보여 주는 축약 예시다.

{
  "profile_id": "candidate-001",
  "target_role": "manufacturing_dx_engineer",
  "experiences": [
    {
      "experience_id": "exp-01",
      "company_alias": "제조기업 A",
      "period": "YYYY-MM~YYYY-MM",
      "responsibilities": ["설비 셋업", "공정 조건 관리"],
      "evidence": ["작업 표준 정리", "이상 원인 분석 기록"]
    }
  ],
  "generation_rules": {
    "invent_facts": false,
    "invent_metrics": false,
    "mark_missing_as": "확인 필요"
  }
}

핵심은 문장보다 먼저 experience_id와 evidence를 보존하는 것이다. 생성된 각 항목이 어떤 입력 경험에서 나왔는지 연결하면, 사용자가 결과를 검토할 때 원본 근거로 돌아갈 수 있다.

개인정보 처리 원칙

  1. 수집 최소화: 생성에 필요하지 않은 개인정보는 받지 않는다.
  2. 전송 최소화: 연락처 등 렌더링용 정보는 모델 요청에서 제외한다.
  3. 비식별화: 회사·고객·프로젝트의 민감한 명칭은 별칭으로 치환한다.
  4. 목적 고지와 동의: 외부 모델 API로 전달되는 범위를 요청 전에 알린다.
  5. 보존 기간 분리: 편집 중 임시 데이터와 사용자가 저장한 결과의 보존 정책을 구분한다.
  6. 로그 위생: 원문 프롬프트와 개인정보를 일반 애플리케이션 로그에 그대로 남기지 않는다.

5. 구현 흐름

5.1 입력과 정규화

React 폼에서 받은 값은 Flask에서 다시 검사한다. 날짜 형식, 필수 필드, 문자열 길이, 허용된 섹션 이름을 확인하고, 빈 수치나 불명확한 결과는 임의로 채우지 않고 확인 필요 상태로 둔다. 클라이언트 검증은 사용자 편의를 위한 것이고 서버 검증은 신뢰 경계를 지키기 위한 것이므로 둘 다 필요하다.

5.2 직무별 컨텍스트 구성

지원 직무 설명에서 핵심 역량을 추려 입력 경험과 함께 전달하되, 모델에게 “직무에 맞지 않는 경력을 삭제하라”고 지시하지 않는다. 대신 관련도가 높은 경험을 앞에 배치하고, 관련도가 낮은 경험은 짧게 요약하도록 한다. 이 방식은 원본 사실을 보존하면서 문서의 초점을 바꾼다.

5.3 프롬프트 계약

프롬프트에는 역할 설명보다 출력 규칙을 먼저 명시한다.

  • 제공된 사실만 사용한다.
  • 입력에 없는 도구, 자격, 성과 수치를 만들지 않는다.
  • 모든 생성 항목에 원본 experience_id를 포함한다.
  • 근거가 부족하면 추측 대신 확인 필요로 반환한다.
  • 응답은 합의된 JSON 스키마를 따른다.

5.4 구조화 응답 파싱

서버는 모델 응답을 JSON으로 파싱하고 필수 필드, 자료형, 허용된 섹션을 확인한다. 형식 오류가 있으면 제한된 횟수만 재요청하고, 계속 실패하면 자유 형식 결과를 억지로 사용하지 않고 사용자 편집 화면으로 전환한다.

5.5 근거 대조와 사용자 승인

검증을 통과한 문장도 곧바로 최종본이 되지 않는다. 결과 화면에서 원본 사실과 생성 문장을 나란히 보여 주고, 사용자가 수정·승인한 항목만 렌더링 대상으로 바꾼다. 초기화 기능은 AI 초안만 제거하고 사용자의 원본 경력 데이터는 별도로 유지하는 편이 안전하다.

6. fine-tuning보다 구조화와 평가를 먼저 선택한 이유

fine-tuning은 특정 출력 형식이나 표현 패턴을 반복 학습시키는 선택지가 될 수 있지만, 개인별 이력서 몇 건처럼 작고 민감한 데이터만으로 바로 시작하면 다음 문제가 생긴다.

  • 학습 데이터에 개인정보가 포함될 위험이 있다.
  • 잘못된 문장이나 편향된 표현을 학습 데이터가 반복시킬 수 있다.
  • 기본 프롬프트와 비교할 평가 세트가 없으면 개선 여부를 판단하기 어렵다.
  • 직무와 사용자마다 사실이 달라 학습보다 런타임 컨텍스트가 더 중요할 수 있다.

그래서 프로토타입의 우선순위를 입력 정규화 → 프롬프트 기준선 → 구조화 출력 → 자동 검사 → 사용자 평가로 정했다. 향후 충분한 비식별·동의 데이터와 고정 평가 세트가 준비되고, 기본 방식에서 반복되는 오류가 확인될 때만 fine-tuning을 비교 실험 대상으로 검토한다.

7. 기술적 난제와 대응 방식

사실처럼 보이는 문장 생성

LLM은 자연스러운 문장을 만들면서 입력에 없는 책임 범위나 성과를 덧붙일 수 있다. 이를 줄이기 위해 원본 경험 ID를 출력에 포함하고, 숫자·회사명·기술명처럼 위험도가 높은 토큰은 입력 근거에 존재하는지 별도로 검사한다. 자동 검사가 통과해도 최종 판단은 사용자에게 남긴다.

섹션별 문체와 길이 불일치

전체 이력서를 한 번에 생성하면 어떤 섹션은 길고 다른 섹션은 비는 문제가 생길 수 있다. 섹션별 입력·출력 스키마와 최대 항목 수를 두고, 수정이 필요한 섹션만 다시 요청하는 구조가 비용과 일관성 면에서 유리하다.

개인정보와 디버깅의 충돌

오류를 분석하려면 요청 정보를 보고 싶지만, 원문을 로그에 남기면 개인정보 노출 범위가 커진다. 요청 ID, 처리 단계, 오류 코드, 토큰 사용량 같은 운영 정보만 기록하고 원문은 기본적으로 마스킹하는 정책이 필요하다.

외부 API 장애와 형식 변화

네트워크 지연, 사용량 제한, 응답 형식 오류는 정상적인 실패 시나리오로 본다. 타임아웃, 지수 백오프, 최대 재시도 횟수, 사용자에게 보여 줄 오류 상태를 구분하고, 생성 실패가 원본 입력 손실로 이어지지 않게 한다.

8. 검증 관점과 품질 게이트

프로토타입의 품질은 “문장이 그럴듯한가” 하나로 판단할 수 없다. 다음 항목을 별도의 검사 단계로 둔다.

검증 항목 확인 방법 실패 시 처리
스키마 유효성 필수 키, 자료형, 허용 섹션 검사 제한 재요청 또는 수동 편집 전환
사실 일치성 수치·기술·기간을 원본 근거와 대조 해당 문장 차단 및 확인 표시
완전성 필수 경력, 기간, 핵심 역량 누락 확인 누락 목록을 사용자에게 제시
개인정보 노출 연락처, 상세 주소, 실명 패턴 검사 API 전송 전 마스킹 또는 요청 중단
직무 관련성 직무 핵심어와 경험 근거의 연결 확인 순서·요약 수준만 재조정
사용자 수용성 채택, 수정, 폐기 상태 기록 반복 오류를 다음 평가 항목으로 등록

현재 글에서는 수치화된 우수성을 주장하지 않는다. 추후 평가를 진행한다면 동일한 입력 세트로 기본 프롬프트와 개선 프롬프트를 비교하고, 사실 오류율·스키마 통과율·사용자 수정량을 함께 봐야 한다.

9. 제조 엔지니어 경험과의 연결

이 프로젝트의 접근 방식은 제조 공정 관리와 닮아 있다. 원재료가 불명확하면 최종 제품의 품질을 보증할 수 없듯이, 경력 원본이 구조화되지 않으면 생성 문장의 품질도 보증할 수 없다.

  • 표준 작업: 입력 스키마와 프롬프트 규칙을 표준서처럼 정의한다.
  • 공정 분리: 입력, 변환, 검사, 승인 단계를 분리해 이상 지점을 찾는다.
  • 추적성: 생성 문장을 원본 experience_id와 연결한다.
  • 품질 게이트: 형식 검사와 사실 검사를 통과한 결과만 다음 단계로 보낸다.
  • 휴먼 인 더 루프: 자동화가 애매한 판단은 작업자 승인 단계에 남긴다.
  • 지속 개선: 사용자가 많이 수정한 유형을 오류 데이터로 모아 규칙을 개선한다.

즉, resumOpenAI는 단순한 챗봇 UI가 아니라 경력 데이터가 입력되어 검증 가능한 문서로 출하되는 작은 품질 공정으로 설계한 프로젝트다. 현장에서 설비 조건과 결과를 연결하고 이상 원인을 추적하던 경험을 LLM 애플리케이션의 데이터 흐름과 검증 체계에 적용했다.

10. 현재 한계와 향후 개선

현재 한계

  • 공개된 학습 데이터와 평가 로그가 없어 fine-tuning 완료나 효과를 검증할 수 없다.
  • 프로토타입 수준이므로 인증·권한, 암호화, 비밀키 관리, 보존 기간 자동화가 운영 서비스 수준인지 검증되지 않았다.
  • 모델 응답의 사실성은 자동 검사만으로 완전히 보증할 수 없다.
  • 다양한 이력서 템플릿과 브라우저에서 내보내기 결과가 동일한지 별도 검증이 필요하다.
  • 채용 직무별 표현 품질을 비교할 고정 평가 세트가 아직 필요하다.

개선 로드맵

  1. JSON Schema 기반 요청·응답 검증과 단위 테스트를 고정한다.
  2. 비식별 샘플로 사실 오류, 누락, 형식 오류가 포함된 회귀 테스트 세트를 만든다.
  3. 인증, 암호화, 비밀키 저장소, 데이터 삭제 기능과 감사 로그를 추가한다.
  4. 각 문장에 원본 근거를 보여 주는 검토 UI와 변경 이력을 구현한다.
  5. 프롬프트 버전, 모델 버전, 평가 결과를 함께 기록한다.
  6. 충분한 동의 데이터와 평가 기준이 마련된 뒤에만 fine-tuning을 기준선과 비교한다.

이 프로젝트에서 얻은 가장 큰 교훈은 LLM 애플리케이션의 품질이 모델 이름 하나로 결정되지 않는다는 점이다. 입력 데이터의 품질, 개인정보 경계, 출력 계약, 검증 절차, 사용자의 최종 승인이 함께 있어야 실제 업무에 사용할 수 있는 결과가 된다.

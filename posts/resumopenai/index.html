resumOpenAI: 경력 사실을 구조화하는 맞춤형 이력서 생성 PoC

30초 요약

지원 직무에 맞춰 문장을 바꾸더라도 경력 사실까지 바뀌면 안 됩니다. 사실 원장과 출력 문구를 나누고 사람이 마지막에 확인하는 흐름을 만들었습니다.

해결하려던 문제

이력서 문구를 매번 다시 쓰면 기간·수치·역할이 달라지거나, 필요 이상의 개인정보가 모델 입력과 출력에 섞일 수 있습니다.

내가 맡은 범위

  • 경력 사실과 직무별 표현을 분리하고, 개인정보 최소화와 사람의 최종 확인을 포함한 Flask·React 기반 처리 흐름을 설계했습니다.

확인된 결과·현재 단계

  • 확인된 산출물 · 개인 역할 경력 사실→직무 요구→문장 후보→사람 확인으로 이어지는 PoC 흐름
  • 현재 단계 · 개인 역할 개인 PoC·공개 저장소와 운영 서비스 없음

팀 경계

개인 PoC이며 AI는 문장 후보를 만들 뿐, 사실 확인과 제출 결정은 사람이 맡습니다.

공개 범위: 실제 이력서 원문과 개인정보는 공개하지 않고 처리 원칙과 화면 흐름만 설명합니다.

채용 문서 작성에서 사실과 표현을 분리하는 일반적인 처리 흐름으로 정리했습니다.

왜 이 의사결정이 중요했는가

직무에 맞는 이력서는 같은 경력 사실을 다른 순서와 표현으로 보여 줄 수 있습니다. 하지만 문장을 매끄럽게 만드는 과정에서 실제로 하지 않은 업무, 확인되지 않은 수치나 도구가 추가되면 이력서의 신뢰가 무너집니다. 그래서 resumOpenAI는 “AI가 이력서를 완성한다”보다 경력 사실과 직무별 문구를 분리한다는 원칙에서 시작했습니다.

이름, 전화번호, 이메일과 상세 주소도 문장 생성에 대부분 필요하지 않습니다. 원본 문서에 있다는 이유만으로 외부 모델에 보내지 않고, 마지막 렌더링 단계에서만 필요한 정보를 따로 다루는 것이 중요한 개인정보 판단이었습니다.

왜 디지털 방식이 필요했는가

경력, 교육과 프로젝트가 여러 문서에 흩어져 있으면 지원 직무마다 같은 사실을 다시 정리하게 됩니다. 구조화된 경력 저장소를 두면 한 번 확인한 회사, 기간, 역할과 근거를 유지한 채 관련도가 높은 경험의 순서와 설명만 바꿀 수 있습니다.

React는 입력과 초안 검토를 담당하고, Flask는 입력 검사, 개인정보 필터링, 모델 요청과 응답 검증을 맡도록 분리했습니다. LLM은 사실을 승인하는 주체가 아니라, 선택된 근거를 직무에 맞는 초안으로 바꾸는 변환 단계입니다.

실제로 맡은 역할

개인 PoC로 경력 사실의 구조, 공개·비공개 필드 경계, 직무별 근거 선택, LLM 초안과 검증·사람 승인 흐름을 설계했습니다. 원본 사실에는 experience_id, 기간, 역할, 주장, 근거와 검증 상태를 남기고, 생성 문구는 어느 사실에서 나왔는지 다시 연결할 수 있게 하는 방향을 잡았습니다.

프로토타입의 우선순위는 fine-tuning이 아니라 입력 정규화, 프롬프트 규칙, 구조화 응답, 사실 검사와 사용자 검토였습니다. 공개된 학습 데이터와 평가 결과가 없으므로 fine-tuning 완료나 성능 향상을 주장하지 않습니다.

데이터 흐름

개인 경력 원본 → 로컬 정규화와 사실 확인 → 최소 공개 필드 선택 → 지원 직무별 근거 선택 → LLM 초안 → 날짜·수치·주장 검사 → 사람의 최종 검토와 내보내기

이름과 연락처 같은 렌더링 정보는 문장 생성에 필요하지 않으면 외부 모델 경계 전에 제거합니다. 회사나 고객 이름이 민감하면 승인된 별칭을 사용하고, 원문 프롬프트와 개인정보를 일반 로그에 남기지 않는 것을 기본으로 둡니다.

구현 순서

  1. 회사, 기간, 역할, 경력 주장과 근거를 구조화하고 검증 상태를 붙입니다.
  2. 연락처, 상세 주소, 자격 증명과 원본 회사 문서처럼 생성에 필요 없는 정보는 별도 비공개 영역에 둡니다.
  3. 지원 직무에 관련된 경력을 선택하되 원본 사실은 바꾸지 않고 순서와 설명 범위만 조정합니다.
  4. 모델에는 제공된 사실만 사용하고, 없는 수치·도구·책임을 만들지 않으며, 근거가 부족하면 확인 필요로 남기도록 요청합니다.
  5. 응답을 정해진 구조로 검사하고 날짜, 회사, 역할, 숫자와 민감정보를 원본과 대조합니다.
  6. 원본 사실과 초안을 나란히 보여 주고 사람이 수정·승인한 문장만 최종 문서에 사용합니다.

확인된 결과와 현재 단계

현재 결과는 React·Flask·OpenAI 기반의 설계와 프로토타입입니다. 경력 사실, 직무별 선택, 생성 문구, 개인정보 경계와 사람 검토를 서로 다른 단계로 나눈 흐름을 보여 줍니다.

공개 저장소나 고정 평가 데이터셋이 확인되지 않아 사실 오류율, 문장 채택률이나 작성 시간 절감 같은 수치를 제시하지 않습니다. 모델 응답의 사실성도 자동 검사만으로 완전히 보장할 수 없으며, 생성 결과는 항상 초안입니다.

운영 조건과 회사에 줄 수 있는 가치

실제 서비스에는 동의와 목적 고지, 최소 수집·전송, 보존 기간과 삭제, 비밀키 관리, 인증·권한, 암호화와 감사 이력이 필요합니다. 프롬프트·모델 버전과 생성 문장을 원본 fact ID에 연결하고, 서로 충돌하는 날짜나 확인되지 않은 성과는 자동 선택하지 않아야 합니다. 제출 전 사람의 최종 확인은 제거할 수 없는 필수 단계입니다.

이 조건이 갖춰지면 회사나 지원자는 검증된 경력 자료를 반복해서 복사하지 않고 직무별 초안을 만들 수 있고, 문구가 바뀌어도 사실의 출처를 확인할 수 있습니다. 가치는 자동 작성 자체보다 사실, 개인정보와 최종 책임을 분리한 검토 가능한 작성 과정에 있습니다.

Problem

LLM이 표현을 개선하는 과정에서 날짜·역할·수치가 바뀌거나 개인정보가 외부 API로 불필요하게 전송되면 이력서의 신뢰성이 훼손됩니다.

Goal

검증된 경력 사실, 비공개 필드, 목표 직무, 생성 초안과 사용자 승인을 분리하고 모든 문장을 source fact로 역추적하는 PoC를 만드는 것입니다.

Success

구조화 출력이 schema를 통과하고 숫자·날짜·주장을 원본과 대조하며, 개인정보가 최소 전송되고 사용자 승인 전에는 최종본이 되지 않으면 성공입니다.

범위와 경계

포함 범위

  • React 입력·검토 UI와 Flask validation/orchestration
  • 구조화 career fact, evidence ID, target-role selection
  • OpenAI API prompt contract, JSON schema, claim validation

제외·미검증 범위

  • 채용 합격 가능성 예측과 자동 의사결정
  • 근거 없는 경력·수치·자격의 자동 보완
  • fine-tuning 완료나 성능 개선이 검증됐다는 주장

구현·검증 기준

해야 할 일

  • 각 생성 문장이 source experience/evidence ID를 참조한다.
  • 모델 응답을 JSON schema로 검사하고 날짜·수치·금칙어를 대조한다.
  • 사용자가 채택·수정·거절한 항목만 최종 문서에 반영한다.

품질·운영 기준

  • 연락처·주소·민감 회사명은 전송 전에 제거·비식별화한다.
  • 모델·prompt·schema version과 검증 결과를 기록한다.
  • API 실패나 형식 오류가 원본 경력 데이터 손실로 이어지지 않는다.

왜 이렇게 구성했나

  1. fine-tuning보다 구조화·평가 우선

    사실 모델과 검증셋이 없는 상태에서 fine-tuning은 오류를 더 일관되게 만들 수 있기 때문입니다.

  2. React–Flask–LLM adapter 분리

    UI 상태, 개인정보·업무 규칙과 외부 모델 의존성을 독립적으로 교체·검증하기 위해서입니다.

  3. 사람의 최종 승인 유지

    경력 맥락과 공개 여부는 자동 규칙만으로 완전히 판단할 수 없기 때문입니다.

작업 내역과 계획

전용 공개 저장소가 없으므로 설계 완료와 구현 검증 필요 상태를 구분했습니다.

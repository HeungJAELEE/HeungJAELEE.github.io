프로젝트 자료

팀 발표자료와 연관 로봇 HMI 공개 저장소를 구분해 제공합니다.

  • 연관 GitHub 저장소github.com/HeungJAELEE/Busan_Robot
  • 자동차 공장 Digital Twin 팀 보고서/docs/Robot_Digital_Twin.pdf

정량값은 팀 PDF에서 직접 읽을 수 있는 F1 1.00·0.877과 Pi5 5 FPS → Pi5+Hailo-10H 18 FPS 비교만 사용합니다. GitHub는 PC-HMI 확장 구현이며 팀 보고서 전체와 동일한 산출물로 간주하지 않습니다.

프로젝트를 한 문장으로 설명하면

INDY7 협동로봇 3대를 사용하는 소형 자동차 조립 흐름에 QR 제품 추적, YOLOv11 조립·품질 검사, PLC/SCADA, MySQL/MES, 디지털 트윈을 연결하고, Raspberry Pi 5와 Hailo-10H의 온디바이스 추론 차이를 비교한 교육 팀 프로젝트입니다.

이 글은 팀 발표자료에서 확인되는 결과와 이후 공개 저장소의 확장 구현을 구분합니다. 팀 PDF는 10명 전체 명단과 공정 시연을 제공하지만 개인별 R&R 표는 포함하지 않습니다. 별도 포트폴리오 자료에는 제 범위가 Robot·Digital Twin으로 기록되어 있어, 여기서는 팀 결과를 개인 단독 성과로 표현하지 않습니다.

왜 이 구조가 필요했는가

자동차 조립 데모에서도 제품 식별, 로봇 상태, 검사 이미지, PLC 시퀀스와 작업 결과가 서로 다른 형식으로 발생합니다. 화면만 연결하면 시연은 가능하지만, “어떤 제품이 어떤 공정을 거쳐 어떤 검사 결과를 받았는가?”를 다시 설명하기 어렵습니다.

프로젝트의 목표는 네 흐름을 하나의 작업 단위로 묶는 것이었습니다.

  1. QR로 제품 serial을 확인하고 MySQL에 기록
  2. Indy7 협동로봇이 투입·차체 결합·유리창 결합·적재 공정을 수행
  3. YOLOv11이 색상/조립 상태와 정상·크랙을 검사
  4. PLC·SCADA·MES와 디지털 트윈이 같은 공정 상태를 공유

QR와 MES

QR은 단순 화면 전환용 표식이 아니라 제품 serial과 검사 결과를 연결하는 key로 사용합니다. MES 관점에서는 최소한 다음 field가 필요합니다.

  • product_serial
  • process_step
  • equipment_id 또는 robot ID
  • inspection_model과 version
  • prediction, score, threshold
  • event_time과 result

PLC와 로봇

AI 판정이 바로 물리 로봇을 제어하기보다 PLC가 검사 완료·통신 상태·인터록을 함께 확인한 뒤 다음 단계로 전이해야 합니다. 팀 자료에는 Vision 검사 Ladder와 통신 Ladder가 별도로 기록되어 있습니다. 이는 검사 결과와 공정 제어 책임을 분리하는 제조 자동화의 기본 경계입니다.

Edge AI

Raspberry Pi 5는 카메라와 application flow를 담당하고, Hailo-10H는 YOLOv11 추론 가속기로 비교했습니다. 팀 발표자료는 같은 데모 조건에서 다음 값을 제시합니다.

조건 발표자료 결과 해석
3-class r/g/b 검사 F1 1.00 발표 평가셋 범위의 결과
6-class normal/crack 검사 F1 0.877 색상별 정상/크랙 분류 결과
Raspberry Pi 5 5 FPS Hailo 적용 전 비교값
Raspberry Pi 5 + Hailo-10H 18 FPS 발표 데모의 가속 비교값

이 수치는 데이터셋 크기, split, 반복 평가와 장시간 thermal 조건이 모두 공개된 benchmark가 아닙니다. 따라서 현장 양산 성능이나 모든 검사 모델의 일반 정확도로 확대하지 않습니다.

공정 시퀀스를 어떻게 구성했는가

팀 보고서는 제품 serial 확인에서 양품 적재·불량 통과까지의 공정 흐름을 단계별로 보여 줍니다.

  1. QR로 제품 serial 확인 및 DB 저장
  2. 부품 투입과 차체 결합
  3. 결합 후 색상/상태 Vision 검사
  4. 유리창 결합
  5. normal/crack Vision 검사
  6. 결과에 따른 양품 적재 또는 불량 분기
  7. PLC·통신 상태와 MES 이력 확인

이 시퀀스의 핵심은 로봇 motion보다 제품 ID–공정 단계–검사 결과–이력을 끊지 않는 것입니다.

기술적 판단

Accuracy보다 오류 유형을 봐야 하는 이유

F1 1.00과 0.877은 서로 다른 class 구성과 평가 조건의 결과입니다. 값만 비교해 “한 모델이 더 우수하다”고 결론 내리기보다 confusion matrix, class별 표본 수, 미검출 비용과 운영 threshold가 필요합니다.

Edge 가속을 FPS 하나로 판단하지 않는 이유

5→18 FPS는 데모에서 Hailo 가속 가능성을 보여 줍니다. 현장 적용에는 model conversion 정확도, camera latency, pre/post-processing, 온도, memory, 재시작 복구와 장시간 안정성을 함께 검증해야 합니다.

Digital Twin을 제어 시스템과 구분한 이유

디지털 트윈은 PLC·로봇·검사 상태를 같은 시간축에서 이해하게 돕습니다. 그러나 3D 장면이 움직인다는 이유로 safety가 검증되는 것은 아닙니다. 물리 제어권은 PLC·robot controller·safety circuit에 남기고 twin은 검증·관측 계층으로 제한해야 합니다.

공개 Evidence와 한계

확인 가능한 Evidence는 다음과 같습니다.

  • 29-page 팀 발표 PDF의 목표·공정 시퀀스·Ladder·MES·edge benchmark
  • QR serial과 MySQL 기록 흐름
  • F1 1.00·0.877, Pi5 5 FPS·Pi5+Hailo 18 FPS 표기
  • 연관 Busan_Robot 저장소의 PC-HMI·MQTT·DB·Digital Twin 확장 구현

확인되지 않은 항목은 완료 성과로 쓰지 않습니다.

  • 실제 양산 line 적용과 장시간 OEE 개선
  • 팀 보고서의 직접 비교표로 재현되지 않는 별도 모델 성능 수치
  • 팀 보고서의 직접 비교표와 충돌하는 별도 속도 수치
  • Omniverse 운영 배포와 정량 지연
  • 개인 단독 개발·단독 성과

경력과의 연결

  • 로봇 Overhaul·Teaching·정도 세팅 경험은 가상 축과 실제 좌표를 별도로 검증하는 관점으로 연결됩니다.
  • 배터리 조립 Pilot Line FAT/SAT 경험은 Offline → 시뮬레이션 → 단일 동작 → 공정 확대 순서에 반영됩니다.
  • MES 초기 관리 항목 설계 경험은 제품 serial, 설비, 검사 결과, timestamp를 함께 저장하는 데이터 계약으로 연결됩니다.
  • Vision·PLC 교육은 AI 판정과 물리 제어권을 분리하는 구조로 이어집니다.

다음 개선

  1. 제품/Lot 단위 train·validation split과 class별 confusion matrix 공개
  2. Hailo 변환 전후 정확도·latency·temperature 장시간 benchmark
  3. PLC request ID와 Vision result의 handshake 및 timeout 자동 시험
  4. robot·PLC·Vision·MES event를 하나의 correlation ID로 연결
  5. 녹화된 상태를 재생하는 hardware-free regression test
  6. 개인 R&R과 팀 결과를 분리한 project changelog

이 프로젝트는 “AI가 로봇을 움직였다”는 데서 끝나지 않습니다. 제품 추적, 물리 시퀀스, 검사 모델, edge 추론, MES 이력을 같은 공정 단위로 연결하고 Evidence 범위를 구분한 팀 제조 AI 사례입니다.

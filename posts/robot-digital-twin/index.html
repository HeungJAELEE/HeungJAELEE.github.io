    TECHNICAL CASE STUDY

    협동로봇 조립 셀 디지털 트윈과 Edge Vision PoC

    QR 추적, Indy7 로봇, Vision 검사, PLC·SCADA·MES와 디지털 트윈을 연결한 교육 팀 PoC

    2026. 7. 9. · 5 · 마지막 검토 2026. 7. 31.

    • Digital Twin
    • Robot
    • Edge AI
    • Vision
    • PLC
    • MES

    어떤 문제를 해결하려 했는가

    로봇 동작, Vision 판정, PLC 시퀀스와 MES 기록을 따로 시연하면 개별 기능은 보여 줄 수 있어도 제품 한 개가 어떤 공정과 검사를 거쳤는지 다시 찾기 어렵습니다.

    이 교육 팀 프로젝트는 QR serial을 공통 key로 사용해 Indy7 협동로봇 조립 흐름, Edge Vision 판정, PLC·SCADA, MySQL/MES와 디지털 트윈 상태를 한 작업 흐름으로 연결한 PoC입니다.

    구분공개 범위
    프로젝트 형태교육 과정의 팀 PoC
    내 역할Robot·Digital Twin 영역
    팀 구현QR 추적, 로봇 조립 시퀀스, Vision, PLC·SCADA, MES
    사용 기술Indy7, Python, YOLO, Raspberry Pi, Hailo, PLC, MySQL
    현재 상태교육 시연 완료, 실공장 Pilot·장시간 E2E 미검증

    팀 전체 결과와 개인 역할은 구분합니다. 팀원이 함께 만든 결과를 개인 단독 성과로 쓰지 않으며, 팀원 실명이 포함된 원본 보고서는 공개하지 않습니다.

    왜 이런 흐름으로 구성했는가

    flowchart LR A["QR serial 등록"] --> B["MySQL / MES\n제품·공정 이력"] B --> C["PLC 시퀀스"] C --> D["Indy7 조립·이송"] D --> E["Camera + Edge Vision"] E --> F["판정 결과"] F --> C F --> B C --> G["SCADA·Digital Twin\n공정 상태 표시"]

    QR serial을 공통 key로 사용

    최소 기록 항목은 제품 serial, 공정 단계, 설비 또는 Robot ID, 검사 model version, 판정과 score, 발생 시각입니다. 이 값이 같은 작업 단위로 묶여야 불량이 발생했을 때 어느 공정과 설비 상태를 확인할지 정할 수 있습니다.

    AI 판정과 물리 제어를 분리

    Vision 결과가 로봇을 바로 움직이는 구조로 만들지 않았습니다. PLC가 검사 완료, 통신 상태와 인터록을 함께 확인한 뒤 다음 공정으로 넘어가는 흐름을 사용했습니다. 모델의 오판정과 통신 오류가 물리 동작으로 바로 이어지지 않게 하기 위해서입니다.

    Twin은 관측 화면으로 제한

    디지털 트윈은 로봇과 검사 상태를 같은 시간축에서 보는 화면입니다. 3D 장면이 정상적으로 움직이는 것과 실제 안전 조건이 검증된 것은 다른 문제이므로, 물리 제어권은 PLC·Robot Controller·Safety 회로에 남겨야 합니다.

    내가 맡고 확인한 범위

    • 협동로봇 공정 순서와 상태 표현 검토
    • Robot 상태를 Twin 화면에 연결하는 데이터 항목 정리
    • Offline 확인 뒤 단일 동작과 공정 흐름으로 확대하는 시험 순서
    • 제품 ID, 공정 단계, 검사 결과와 시간을 연결하는 이력 구조
    • Vision 결과와 물리 시퀀스 사이의 책임 구분

    발표 자료에 포함된 모델 지표와 Edge 장치 비교값은 교육 데모 조건의 결과입니다. 데이터 분할, 반복 평가와 장시간 온도 조건을 공개 방문자가 다시 확인할 수 없기 때문에 이 페이지의 대표 성과 수치로 사용하지 않습니다.

    결과

    제품 식별부터 로봇 공정, 검사 결과와 MES 기록까지 이어지는 전체 흐름을 팀 단위로 구성했습니다. 개인적으로는 Robot과 Digital Twin 영역에서 어떤 상태를 공유해야 하는지, Twin이 어디까지 관측하고 어디서부터 제어권을 넘지 않아야 하는지를 정리했습니다.

    현장 경력에서 FAT/SAT를 진행할 때 기능, 인터록, 반복성과 생산 이력을 따로 확인했던 경험을 이 프로젝트의 단계별 시험 순서에 적용했습니다.

    확인 자료와 한계

    • 팀 발표자료는 개인별 상세 R&R을 모두 나누지 않으므로 내 역할을 Robot·Digital Twin 범위로 제한합니다.
    • 팀원 실명과 메타정보가 포함된 원본 파일은 사이트에서 제거했습니다.
    • 교육 데모의 모델 지표와 속도값을 양산 성능으로 확대하지 않습니다.
    • 실공장 Cycle Time, 통신 지연, 안전, 재시작 복구와 장기 drift는 검증하지 않았습니다.
    • 연결된 별도 저장소는 공개 설정 정리가 끝나기 전까지 근거 링크로 사용하지 않습니다.

    Problem

    제품 ID, 로봇 동작, 검사 이미지, PLC 시퀀스와 MES 결과가 분리되면 어떤 제품이 어떤 공정과 검사 결과를 거쳤는지 추적하기 어렵습니다.

    Goal

    QR serial을 공통 키로 삼아 세 대의 Indy7 조립 흐름, YOLOv11 검사, PLC/SCADA, MySQL/MES와 디지털 트윈 상태를 연결하는 것입니다.

    Success

    제품 ID→공정 단계→로봇/설비→검사 결과→시간 흐름이 팀 데모와 보고서에서 재구성되고 edge 성능 비교가 근거와 함께 제시되면 성공입니다.

    범위와 경계

    포함 범위

    • QR serial 등록과 MySQL/MES 공정 이력
    • Indy7 3대의 투입·차체/유리 결합·적재 시퀀스
    • YOLOv11 검사와 Pi5·Hailo-10H edge inference 비교
    • PLC·SCADA·Digital Twin 상태 연결

    제외·미검증 범위

    • 팀 전체 결과를 개인 단독 구현으로 귀속
    • GitHub 확장 구현과 팀 PDF 전체를 동일 산출물로 간주
    • 교육 셀 결과를 자동차 생산 라인 성능으로 일반화

    구현·검증 기준

    해야 할 일

    • QR serial이 공정 이력과 검사 결과의 공통 키가 된다.
    • PLC가 로봇 시퀀스와 검사 결과에 따른 good/reject 흐름을 조정한다.
    • SCADA·MES·twin이 같은 공정 단계와 상태를 표시한다.

    품질·운영 기준

    • 팀 산출물과 개인 역할, 연관 저장소를 분리 표시한다.
    • 공개 방문자가 재현할 수 없는 모델·속도 수치를 대표 성과로 사용하지 않는다.
    • 오프라인 시연과 실제 설비 적용의 안전·성능 차이를 명시한다.

    왜 이렇게 구성했나

    1. QR serial을 end-to-end 키로 사용

      공정·검사·로봇 이벤트를 제품 단위로 재구성하기 위해서입니다.

    2. edge accelerator 비교

      Pi5 단독과 Hailo-10H 사용 시 추론 차이를 실제 배치 관점에서 확인하기 위해서입니다.

    3. 팀 결과와 확장 저장소 분리

      검증 가능한 팀 PDF와 후속 PC-HMI 구현의 Evidence 범위를 혼용하지 않기 위해서입니다.

프로젝트를 한 문장으로 설명하면

INDY7 협동로봇 3대로 구성된 소형 자동차 조립 라인을 가상 환경에 표현하고, Raspberry Pi 5와 Hailo-10H에서 실행하는 YOLOv11 비전 모델의 판정 결과를 PLC·SCADA·MES 데이터 흐름과 연결해 본 디지털 트윈·온디바이스 AI PoC입니다.

이 프로젝트의 핵심은 3D 화면을 화려하게 만드는 것이 아닙니다. 물리 설비의 제어, AI 검사, 가상 모델, 생산 이력을 서로 분리하면서도 하나의 공정 이벤트로 추적할 수 있게 만드는 것이 목표였습니다.

F1 Score는 프로젝트 데이터에 기록된 평가 결과이며, 데이터셋 규모·분할 방식·현장 장기 운영 결과가 모두 공개된 것은 아닙니다. 따라서 이 글에서는 해당 수치를 특정 평가셋에서의 결과로만 설명하고, 양산 현장의 영구적인 정확도로 과장하지 않습니다.

왜 이 프로젝트가 필요했는가

로봇, 비전 검사, PLC, MES를 개별적으로 구현하는 것만으로는 공정 전체를 설명하기 어렵습니다. 조립 불량이 발생했을 때 다음 질문에 한 번에 답할 수 있어야 하기 때문입니다.

  • 어느 작업지시와 제품에서 문제가 발생했는가?
  • 당시 어떤 로봇이 어떤 공정 단계에 있었는가?
  • 비전 모델은 어떤 판정을 내렸고, 그 판정은 유효했는가?
  • PLC는 판정 결과를 실제 시퀀스에 어떻게 반영했는가?
  • 물리 설비와 가상 모델 사이에 지연이나 좌표 불일치가 있었는가?

기존 시스템이 로봇 로그, PLC 태그, 검사 이미지, 생산 실적을 따로 보관하면 원인 추적에 시간이 오래 걸립니다. 그래서 이 프로젝트는 공정 이벤트를 중심으로 각 시스템을 연결하는 구조를 선택했습니다.

설계 원칙

물리 제어권은 PLC에 둔다

AI 모델이나 Omniverse가 물리 로봇을 직접 무제한 제어하는 구조로 설계하지 않았습니다. AI는 검사 결과와 신뢰 상태를 전달하고, PLC는 인터록·운전 모드·설비 상태를 함께 확인한 뒤 제한된 동작만 허용하는 방식입니다.

이 경계가 중요한 이유는 AI 추론 실패, 네트워크 지연, 가상 모델 오류가 곧바로 위험 동작으로 이어지는 것을 막기 위해서입니다. 실제 적용 시에는 로봇 제조사의 안전 기능과 별도의 안전 회로 검증이 추가로 필요합니다.

제어 흐름과 관측 흐름을 분리한다

  • 제어 흐름: 카메라 입력 → AI 판정 → PLC 핸드셰이크 → 로봇 시퀀스
  • 관측 흐름: PLC·로봇 상태 → 데이터 게이트웨이 → Omniverse·SCADA
  • 이력 흐름: 검사 결과·알람·사이클 정보 → MES 또는 품질 기록

SCADA나 디지털 트윈이 느려져도 PLC의 기본 시퀀스가 불필요하게 영향을 받지 않도록 분리한 구조입니다.

같은 이벤트를 끝까지 추적한다

검사 결과만 저장하면 나중에 어떤 제품과 로봇 동작에 해당하는지 알기 어렵습니다. 따라서 작업지시, 제품 또는 공정 단위 식별자, 설비 ID, 공정 단계, 판정, 시각을 함께 묶는 데이터 계약이 필요합니다.

이 그림은 프로젝트의 논리 구성을 설명합니다. 실제 통신 주기, 로봇 제어 API, 안전 회로, MES 스키마처럼 공개 자료로 확인할 수 없는 부분은 구현 완료 사실로 단정하지 않고 설계 범위로 남겼습니다.

각 기술을 선택한 이유

INDY7 협동로봇

협동로봇은 소형 조립 공정의 픽앤플레이스, 부품 이송, 검사 위치 정렬과 같은 작업 흐름을 구성하기에 적합합니다. 이 프로젝트에서는 3대의 로봇을 하나의 라인으로 보았기 때문에 로봇 한 대의 궤적보다 로봇 간 공정 순서와 공유 작업 영역의 충돌 가능성이 더 중요한 설계 대상이었습니다.

NVIDIA Omniverse

Omniverse는 3D 자산과 장면을 구성하고 로봇 상태를 가상 객체에 매핑하는 플랫폼으로 선택했습니다. 디지털 트윈에서 필요한 기능은 크게 세 가지입니다.

  1. 물리 로봇과 가상 로봇의 좌표계·관절 이름 매핑
  2. 공정 단계와 설비 상태의 실시간 시각화
  3. 실제 장비 투입 전 동선과 간섭을 검토하는 시뮬레이션

다만 Omniverse 화면이 실제 로봇의 안전 검증을 대체하지는 않습니다. 가상 충돌 검토는 위험을 앞 단계에서 발견하는 수단이며, 최종 안전성은 실제 장비와 안전 시스템에서 확인해야 합니다.

Raspberry Pi 5 + Hailo-10H

카메라 영상을 중앙 서버로 모두 전송하면 네트워크 부하와 응답 지연이 커질 수 있습니다. 에지에서 전처리와 추론을 수행하면 PLC에는 이미지 전체가 아니라 판정 이벤트와 상태 정보만 전달할 수 있습니다.

Raspberry Pi 5는 카메라·네트워크·애플리케이션 로직을 묶는 호스트 역할, Hailo-10H는 추론 가속 역할로 배치했습니다. 이 구성에서는 정확도만큼 모델 변환 호환성, 메모리 사용량, 발열, 장시간 안정성, 재시작 복구를 함께 봐야 합니다.

YOLOv11 기반 검사 모델 3종

하나의 범용 모델에 모든 검사 항목을 넣기보다 검사 목적별 모델을 분리하면 데이터 라벨과 판정 기준을 명확히 관리할 수 있습니다. 최신 이력서에 확인되는 대표 업무 맥락은 양극재의 비자성 이물 검사를 위한 YOLO 기반 Classification 비전 도입입니다. 이 프로젝트는 그 현장 관점을 로봇 조립 라인의 에지 검사 구조로 확장한 사례입니다.

프로젝트 자료에는 모델 3종이 기록되어 있지만 공개된 근거만으로 각 모델의 세부 클래스, 임계값, 학습 데이터 구성을 모두 확정할 수는 없습니다. 따라서 이 글에서는 모델을 A·B·C로 구분하고 평가 수치만 그대로 사용합니다.

모델 기록된 F1 Score 해석 시 주의점
모델 A 100% 평가셋 범위의 결과이며 현장 일반화를 별도 검증해야 함
모델 B 95% 오검·미검 유형과 운영 임계값을 함께 확인해야 함
모델 C 100% 조명·위치·LOT 변화에 대한 추가 검증이 필요함

MELSEC PLC·SCADA·MES

  • PLC는 AI 판정의 유효성, 설비 준비 상태, 타임아웃을 확인하고 공정 시퀀스를 실행합니다.
  • SCADA는 현재 공정 단계, 로봇 상태, 통신 품질, 알람을 작업자에게 보여 줍니다.
  • MES는 제품·작업지시·검사 결과·공정 시각을 연결해 추적성을 확보하는 역할입니다.

세 시스템을 한 프로그램에 합치지 않고 역할별로 분리한 이유는 변경 주기와 장애 영향 범위가 서로 다르기 때문입니다.

데이터와 핸드셰이크를 어떻게 구성했는가

AI 판정은 단순한 OK/NG 비트 하나로 전달하면 원인을 추적하기 어렵습니다. 아래처럼 이벤트의 문맥을 함께 전달하는 구조를 설계했습니다. 예시는 데이터 계약을 설명하기 위한 개념 형식이며 실제 운영 스키마라고 단정하지 않습니다.

{
  "event_id": "inspection-event-id",
  "equipment_id": "edge-vision-id",
  "process_step": "inspection-step",
  "model_id": "model-version",
  "result": "OK_OR_NG",
  "quality": "VALID_OR_INVALID",
  "captured_at": "timestamp"
}

PLC 연동은 다음과 같은 요청·응답 상태로 나누는 것이 안전합니다.

  1. PLC가 제품 도착과 촬영 가능 상태를 확인합니다.
  2. 에지 장치에 검사 요청을 전달합니다.
  3. 에지 장치는 요청 ID와 함께 판정 또는 오류 상태를 반환합니다.
  4. PLC는 동일 요청의 결과인지, 응답 시간이 유효한지 확인합니다.
  5. 유효한 결과일 때만 다음 공정으로 전이합니다.
  6. 타임아웃이나 장치 오류는 검사 결과 NG와 구분해 별도 알람으로 처리합니다.

장치 오류를 제품 불량으로 기록하면 품질 데이터가 왜곡되고, 제품 불량을 장치 오류로 처리하면 미검 위험이 생깁니다. 두 상태를 분리한 것이 중요한 설계 포인트입니다.

구현을 어떤 단계로 구성했는가

단계 1. 공정과 검사 요구사항 정의

로봇별 작업, 제품 이동 순서, 검사 위치, 합격 조건, 오류 시 복구 절차를 먼저 정리했습니다. 제조 라인에서는 “모델 정확도가 높은가”뿐 아니라 “판정이 늦거나 없을 때 공정이 어떻게 멈추는가”가 요구사항에 포함되어야 합니다.

단계 2. 로봇·PLC 상태 모델 정리

로봇의 세부 상태를 SCADA와 Omniverse가 각각 다르게 해석하지 않도록 대기, 운전, 완료, 정지, 고장, 수동처럼 공통 상태를 설계했습니다. 제조사 전용 코드는 이 공통 상태로 변환하는 어댑터에서 처리하는 방향입니다.

단계 3. 비전 파이프라인 구성

촬영 → 관심 영역 설정 → 전처리 → YOLOv11 추론 → 후처리 → 품질 상태 부여 → 이벤트 발행 순으로 책임을 나눴습니다. 모델 파일과 함께 라벨 정의, 전처리 조건, 임계값, 배포 장치 정보를 버전으로 묶어야 결과를 재현할 수 있습니다.

단계 4. 에지 배포와 예외 처리

Hailo-10H에 맞는 모델 변환, 입출력 텐서 확인, 카메라 연결 끊김, 추론 프로세스 재시작, 저장 공간 부족을 시험 항목으로 두었습니다. 실제 성능 수치가 확인되지 않은 처리속도나 지연시간은 이 글에서 임의로 제시하지 않습니다.

단계 5. PLC 핸드셰이크

검사 요청과 결과가 서로 다른 제품에 연결되는 것을 막기 위해 요청 ID, 준비 상태, 완료 상태, 타임아웃을 분리하는 구조를 설계했습니다. 자동 운전 중 AI 통신이 복구되더라도 PLC가 바로 재기동하지 않고 재확인 절차를 거치도록 하는 것이 안전합니다.

단계 6. Omniverse 장면과 좌표 매핑

실제 로봇의 관절 또는 공정 상태를 가상 객체에 연결할 때 단위, 축 방향, 원점, 관절 순서를 명시해야 합니다. 로봇 3대의 기준 좌표계와 라인 기준 좌표계를 구분하고, 변환 규칙을 설정 파일로 관리하는 방향으로 구성했습니다.

단계 7. SCADA·MES 추적성 연결

SCADA에는 운영에 필요한 상태와 알람을, MES에는 제품과 품질 이력에 필요한 이벤트를 전달합니다. 동일 데이터를 모두 보내는 대신 소비 목적에 따라 필요한 필드를 구분했습니다.

기술적으로 어려운 지점

물리 로봇과 가상 로봇의 좌표 정합성

같은 관절 값이라도 모델의 축 방향, 초기 자세, 단위가 다르면 화면에서 완전히 다른 동작으로 보일 수 있습니다. 로봇별 관절 이름과 인덱스를 하드코딩하기보다 모델 명세에 따라 매핑하고, 기준 자세에서 하나씩 축을 움직여 검증하는 절차가 필요합니다.

서로 다른 시간축의 정렬

카메라 캡처, AI 판정, PLC 스캔, 로봇 상태, 3D 렌더링은 각자 다른 시각에 갱신됩니다. 단순 수신 순서만 믿으면 늦게 도착한 과거 데이터가 최신 상태를 덮을 수 있습니다. 이벤트 시각과 순번을 사용하고, 오래된 패킷을 버리거나 진단 로그로 분리하는 방식이 필요합니다.

AI 판정과 공정 안전의 경계

F1 Score가 높더라도 조명, 제품 위치, 카메라 오염, 신규 LOT에서는 성능이 달라질 수 있습니다. 그래서 OK, NG 외에 판정 불가, 장치 오류, 모델 미준비 상태가 있어야 하고, 이 상태를 PLC가 임의의 정상으로 간주하지 않도록 설계해야 합니다.

에지 장치 운영성

에지 AI는 최초 실행보다 장시간 운영이 어렵습니다. 서비스 자동 시작, 모델 무결성 확인, 로그 순환, 온도와 자원 사용량, 원격 업데이트 실패 시 롤백이 필요합니다. 이 항목들은 PoC 이후 양산 적용에서 추가 검증해야 할 운영 요구사항입니다.

검증 계획과 결과를 어떻게 읽어야 하는가

검증 영역 시험 내용 확인할 결과
로봇 시퀀스 정상·정지·재시작 단계 전이 순서 이탈과 중복 동작 없음
AI 검사 모델별 평가셋과 오류 사례 F1, 오검·미검 유형, 판정 불가 비율
에지 장치 카메라·추론 프로세스 장애 오류 분리, 자동 복구, 잘못된 정상 판정 방지
PLC 연동 지연·중복·유실 응답 요청 ID 일치와 타임아웃 처리
디지털 트윈 기준 자세·축별 동작 비교 좌표·관절 매핑 오류 식별
SCADA·MES 이벤트 흐름과 저장 문맥 제품·설비·판정의 추적 가능성

현재 프로젝트 데이터에서 확인 가능한 정량 결과는 모델 3종의 F1 Score **100%, 95%, 100%**입니다. 반면 실제 현장 적용에 필요한 추론 지연, 장시간 가동률, 통신 유실률, 카메라 환경 변화별 성능은 공개 근거가 없으므로 달성 사실로 추가하지 않았습니다.

이력서 경력과 어떻게 연결되는가

이 프로젝트의 구조는 제조·로봇·AI를 따로 배운 기술 목록이 아니라, 기존 경력을 하나의 공정 시스템으로 묶은 결과입니다.

  • 로봇 Overhaul, Teaching, 정도 세팅, 표준 작업서 작성 경험은 가상 로봇의 축·원점·상태를 검증하는 관점으로 연결됩니다.
  • 배터리 조립 Pilot·양산 라인의 FAT/SAT와 수율 안정화 경험은 로봇 시퀀스, 인터록, 복구 조건을 우선 설계한 근거입니다.
  • 초기 MES 체계 구축 경험은 비전 결과를 이미지 한 장으로 남기지 않고 작업지시·Batch·공정 이벤트와 연결하는 방향에 반영했습니다.
  • YOLO 기반 비자성 이물 Classification 검사 도입 경험은 모델 성능뿐 아니라 현장 판정 기준과 재현성을 함께 보는 시각으로 이어졌습니다.
  • 제조 DX·AX 기획 경험은 디지털 트윈, AI, MES를 하나의 품질 피드백 구조로 확장하는 기반이 됐습니다.

한계와 향후 개선

이 프로젝트는 디지털 트윈과 에지 AI의 연결 가능성을 보여 주는 PoC입니다. 실제 양산 배포를 위해서는 다음 작업이 추가되어야 합니다.

  1. 데이터셋 분할과 클래스별 혼동행렬을 포함한 모델 평가 보고서 정식화
  2. 조명·카메라 위치·제품 LOT 변화에 대한 강건성 시험
  3. 추론·통신·PLC 반영까지의 end-to-end 지연 측정
  4. 로봇별 좌표 캘리브레이션 절차와 오차 허용 기준 수립
  5. 이미지·판정·모델 버전·공정 이벤트의 MES 추적성 강화
  6. 장애 주입 기반 자동 회귀 테스트와 재생 가능한 로그 구축
  7. 계정 권한, 네트워크 분리, 모델 배포 서명을 포함한 보안 설계

다음 단계의 목표는 “가상 로봇이 움직인다”에서 끝나지 않습니다. 어떤 데이터와 모델로 어떤 판정을 내렸고, PLC가 어떻게 반응했으며, 그 결과를 나중에 재현할 수 있는가까지 증명할 수 있는 제조 디지털 트윈으로 발전시키는 것입니다.

    Fail-Closed AI Authority & Evidence Plane: AI가 볼 수 있어도 실행할 수는 없다

    AI 관찰·제안과 실행 권한을 분리하고 Decision Envelope, Release Inventory, 승인·효과·재시작 Gate를 검증한 로컬 Foundation

    문제: 테스트 성공이 실행 권한을 의미하지 않는다

    AI 시스템에서 다음 문장은 서로 다른 사실입니다.

    • 모델이 데이터를 읽었다.
    • 모델이 행동을 추천했다.
    • 코드가 로컬 테스트를 통과했다.
    • 승인된 사람이 실제 행동을 허가했다.
    • 동일한 artifact가 운영 환경에서 실행됐다.
    • 외부 시스템에서 효과가 발생했고 read-back됐다.

    이 구분이 없으면 “테스트 PASS”가 “배포 가능”, “추천 생성”이 “주문 승인”, “로컬 상태 변경”이 “실제 외부 효과”로 잘못 해석될 수 있습니다.

    이 프로젝트는 AI 기능을 더 많이 연결하는 대신, 필수 근거가 하나라도 없으면 다음 단계로 가지 않는 fail-closed Authority & Evidence Plane을 로컬 Foundation으로 구성했습니다.

    현재 공개 상태: live order 0 · external effects 0 · C4 미승인 · 운영 GO 아님

    왜 이렇게 구성했는가

    권한을 한 개의 approved=true로 표현하면 누가 무엇을, 어떤 artifact와 위험 범위에서, 언제까지 승인했는지 알기 어렵습니다. 그래서 세 가지 계약을 분리했습니다.

    1. Decision Envelope: 의도, 위험, 근거, 승인 주체, idempotency와 예상 효과
    2. Release Ownership Inventory: source·generated·runtime artifact의 소유자와 hash
    3. Source Qualification: 어떤 입력이 authoritative하고 어떤 입력은 참고·HOLD인지

    세 계약은 Foundation Join에서 만나며, 승인·artifact·재시작·효과 Evidence가 모두 일치해야 다음 상태로 이동합니다.

    아키텍처와 데이터 흐름

    flowchart LR A["관찰·Source"] --> B["Source Qualification"] B --> C["Decision Envelope\nintent · risk · evidence"] D["Release Inventory\nsource · generated · runtime · hash"] --> E["Artifact identity Gate"] C --> F["ApprovalPrincipal Gate"] E --> F F --> G{"C4 승인?"} G -- "아니오" --> H["BLOCKED\nexternal effects 0"] G -- "예" --> I["Bounded execution"] I --> J["Authoritative read-back"] J --> K["Reconciliation · restart Gate"] K -- "불일치" --> H

    BLOCKED는 실패를 숨기는 상태가 아니라, 요구되는 권한·근거가 없을 때 올바르게 멈춘 결과입니다.

    AI와 사람의 역할

    AI가 할 수 있는 일

    • source와 artifact inventory 초안
    • 위험 후보와 누락 필드 탐색
    • 계약·테스트 코드와 반례 생성
    • Evidence 요약과 다음 검토 항목 제안

    AI가 소유하지 않는 것

    • ApprovalPrincipal 지정
    • 자격 증명·계정 접근 권한
    • C4 승인
    • 실제 주문·배포·권한 변경
    • 외부 효과의 최종 확인과 reconciliation

    사람은 승인 범위와 실제 외부 효과를 소유하고 authoritative source에서 read-back해야 합니다. AI의 분석 품질은 권한을 자동으로 넓히지 않습니다.

    구성 이유와 확인한 결과

    AI가 분석을 잘했다는 사실이 주문·배포·권한 변경 권한을 의미하지 않도록, 관찰·결정·승인·외부 효과와 재현 Evidence를 분리한 로컬 Foundation입니다.

    Foundation 로컬 검증 · 운영 GO 아님
    프로젝트 유형
    개인 AI Authority·Evidence Foundation
    개인 역할
    계약·Gate·테스트·재현 검증
    주요 사용자
    AI 운영자·승인자·감사자
    Evidence 수준
    로컬 clean materialization 검증

    Problem

    모델의 추천, 코드 실행, 배포 승인과 실제 외부 효과가 한 흐름에 섞이면 테스트 성공이나 메시지 한 줄이 거래·권한·운영 준비 완료로 잘못 해석될 수 있습니다.

    Goal

    Decision Envelope, Release Inventory와 Source Qualification로 입력·권한·artifact·승인·효과를 명시하고 하나라도 없으면 실행을 막는 fail-closed Foundation을 만드는 것입니다.

    Success

    같은 source에서 clean materialization 결과가 byte-identical하고, 승인·재시작·외부 효과 Gate가 미충족 상태를 결정적으로 차단하며 live effect가 0이면 Foundation 성공입니다.

    AI와 사람이 나눈 역할

    AI 역할
    소스·artifact 목록 초안, 위험 후보 분류, 계약·테스트 코드와 반례 생성을 지원하지만 실행 권한과 최종 승인 주체가 되지 않습니다.
    사람 역할
    ApprovalPrincipal, C4 승인, 실제 계정·자격 증명·배포·주문·복구 판단은 사람이 소유하고 authoritative read-back을 확인합니다.
    공개 Gate
    자격 증명, 내부 IP, 비공개 저장소·Notion URL, 개인 데이터와 진행 중 계약을 공개하지 않으며 마지막 완료 Foundation만 기술합니다.
    외부 효과
    live order 0, external effects 0, C4 미승인입니다. 로컬 테스트 성공은 운영 GO·실거래·수익·권한 변경 증거가 아닙니다.

    범위와 경계

    포함 범위

    • Decision Envelope와 risk·approval·effect 계약
    • Release Ownership Inventory·Source Qualification·Foundation Join
    • clean materialization, hash, restart·approval·effect fail-closed 검증

    제외·미검증 범위

    • 실거래, 주문 제출, credential 수집과 운영 계정 연결
    • C4 승인이나 운영 GO가 완료됐다는 표현
    • 진행 중 READ_ONLY_INVENTORY 1.2.0을 완료 성과로 포함

    구현·검증 기준

    해야 할 일

    • 모든 ActionSpec이 source, risk, ApprovalPrincipal, artifact와 intended effect를 명시한다.
    • Release Inventory가 source·generated·runtime owner와 hash를 연결한다.
    • 승인·재시작·효과 Gate 미충족 시 실행을 결정적으로 차단한다.

    품질·운영 기준

    • clean checkout에서 같은 source가 byte-identical artifact를 만든다.
    • 테스트·fixture·harness 성공을 실제 외부 효과와 구분한다.
    • Windows symlink 같은 환경 capability skip을 제품 PASS로 숨기지 않는다.

    왜 이렇게 구성했나

    1. 관찰과 실행 권한을 별도 계약으로 분리

      모델이 상태를 읽거나 추천할 수 있어도 자산과 외부 시스템을 변경할 권한은 자동으로 생기지 않기 때문입니다.

    2. Release Inventory로 artifact identity 고정

      테스트한 코드와 실제 실행 대상이 다르면 검증 결과가 운영 권한을 증명할 수 없기 때문입니다.

    3. clean materialization을 완료 Gate로 사용

      로컬 캐시나 수동 산출물에 의존하지 않고 source에서 같은 결과를 재생성해야 Evidence를 감사할 수 있기 때문입니다.

      승인, effect, restart와 source binding이 모두 맞을 때만 다음 단계로 이동하도록 검증했습니다.

    한계와 공개 Gate

    • 공개 저장소나 운영 URL은 없습니다.
    • 자격 증명, 내부 IP, 비공개 저장소·Notion 주소와 개인 데이터는 공개하지 않습니다.
    • 진행 중인 READ_ONLY_INVENTORY 1.2.0이나 후속 작업을 완료 성과로 포함하지 않습니다.
    • 실거래, 수익, 운영 준비 완료, C4 승인과 외부 효과를 주장하지 않습니다.
    • 실제 운영 전에는 승인 주체, credential, bounded intent, idempotency, authoritative read-back과 reconciliation이 별도로 필요합니다.

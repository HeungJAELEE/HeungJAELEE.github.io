공개 Plugin + Agent OS 로컬 Foundation

같은 경력을 여러 AI 세션에서 작성할 때 수치·역할·Pilot·양산 상태가 달라지는 문제를 문체 문제가 아니라 근거 권위·실행 권한·검증 순서 문제로 정의했습니다. 먼저 im-not-ai에 공통 사실원장과 4개 커리어 Skill, 결정적 Validator를 구현했습니다. 이후 같은 계약을 Persistent Agent·Worker/Manager Flow·Approval Inbox·Domain Pack으로 확장하는 Agent OS 구조를 설계했습니다.

1. 프로젝트 배경 — 문서가 아니라 판단이 흔들리는 문제

이력서, 경력기술서, 포트폴리오, 웹 카드와 발표자료를 각각 생성하면 같은 프로젝트가 서로 다른 이야기로 바뀌기 쉽습니다.

  • 팀 결과가 개인 단독 성과로 바뀜
  • A Sample·PoC·Pilot·양산 단계가 섞임
  • 수치의 기간·분모·재작업 포함 여부가 사라짐
  • 공개 금지 원문이나 비공개 URL이 산출물로 유출됨
  • 마지막 문체수정이 현장조건과 역할 경계를 삭제함

따라서 작성 모델보다 먼저 어떤 사실을 누가 어떤 범위에서 사용할 수 있는지를 고정해야 했습니다.

2. 5Why — 왜 같은 경력이 문서마다 달라졌는가

분석 방향

처음에는 AI 문체의 일관성 문제로 보였습니다. 그러나 승인본을 비교하자 핵심은 표현이 아니라 작성 전에 공유해야 할 Claim·기여도·단계·공개범위가 없다는 점이었습니다.

Why관찰된 문제구조적 원인
1같은 프로젝트의 수치와 역할이 산출물마다 달라짐이력서·포트폴리오·발표자료가 독립 생성
2이전 승인본이 있어도 다시 전면 재작성LOCKED BASELINE과 수정 허용구간 부재
3직접 수행·팀 결과·Pilot·양산이 섞임Contribution·Stage를 공통 필드로 관리하지 않음
4공개자료와 비공개 원문이 한 문맥에 혼재Source Priority·Public Scope 계약 부재
5최종 윤문에서 사실조건까지 바뀜생성 모델이 스스로 변경률과 의미보존을 판정

Root Cause — 사실·기여도·단계·공개범위를 잠그기 전에 문서 생성부터 시작하는 구조

이를 공통 사실원장 → 집중형 Skill → 문체 Pass → 결정적 Validator 순서로 바꿨습니다.

4. 모델의 자기판정을 코드 Gate로 교체

Skill Bundle Validator

validate_career_skill_bundle.py는 다음을 코드로 검사합니다.

  • OpenAI Plugin Manifest와 4개 필수 Skill·Reference 존재
  • 각 Skill의 SOURCE_UNAVAILABLE, 직접 수행, 팀 결과, Pilot 등 정책 Marker
  • agents/openai.yaml과 호출 Prompt 계약
  • Private Notion URL, Windows 사용자 경로, 대화 식별자와 위임 Payload 차단
  • 설치 스크립트가 4개 Skill을 모두 연결하는지 확인

변경률 Rollback Gate

문체수정 전후의 변경률을 모델이 추정하지 않고 verify_change_rate.py가 Exit Code로 판정합니다.

변경률판정처리
<30%OK윤문본 채택 가능
30–50%WARN사용자에게 과윤문 경고
≥50%ABORT윤문본 채택 금지·Rollback
판정 불가ERROR사람 검토로 전환

Python 3.11·3.12의 Pytest, Quick Rule·Diagnosis Rule Drift 검사를 수행하도록 GitHub Actions Workflow도 정의했습니다.

5. 왜 이것이 AI Authority 문제인가

Authority누가 결정하는가AI가 할 수 있는 일
Source Authority최신 사용자 확정·정본·실행 Readback후보 근거 탐색·정리
Contribution Authority사용자와 원본 역할 기록직접·팀·지원 문장 초안
Stage AuthoritySample·Pilot·양산·운영의 실제 완료상태단계별 표현 적용
Publication Authority공개권리와 Redaction 결정공개문안 생성
Style Authority승인된 사실·구조 이후의 문체 규칙번역투·AI 패턴 국소 수정

작성 모델은 이 Authority를 새로 만들지 않습니다. 권위가 잠긴 뒤 허용된 범위에서 문서를 생성하고, 코드 Gate가 계약 위반을 차단합니다.

6. Agent OS로 확장한 목표 구조

im-not-ai가 한 도메인의 근거·판정·출력 흐름을 구현했다면, Agent OS는 같은 원칙을 여러 지속형 Agent와 외부 실행에 적용합니다.

flowchart LR
    W["Wiki\n검증된 지식·Revision"] --> B["Agent Builder\n역할·지식·Tool 정의"]
    B --> R["Persistent Agent Registry\n세션 독립 ID"]
    R --> F["Worker·Manager Flow\n조사·비교·재검사"]
    F --> C["Control Runtime\nQueue·Lease·Checkpoint"]
    C --> O["Outcome Record\n근거·반대의견·책임자"]
    O --> A["Approval Inbox\n사람의 범위·만료 승인"]
    A --> D["Domain Pack\nInvestment·Manufacturing"]
    D --> E["Authoritative Readback\n실제 상태 재확인"]
    E --> O

운영계약

  • Worker와 Manager는 조사·비교·재검사를 수행하지만 사람의 승인을 만들지 않음
  • Aggregate별 Active Writer 1개와 중복 Trigger 차단
  • Queue Claim·Lease·Checkpoint·재시작으로 장기 Run 복구
  • Semantic Rework와 Transport Retry 분리
  • Notion은 Message Bus가 아니라 사람이 읽는 결과 Projection
  • 외부 요청 Receipt와 실제 결과 Readback 분리
  • 승인 대상·범위·만료·소비상태·Rollback을 함께 관리

9. 프로젝트 성과

  • 하나의 최신 근거판정을 이력서·포트폴리오·웹 카드·발표자료에 재사용하는 구조 확립
  • 직접 수행·팀 결과·Pilot·양산·현재 Runtime의 문서 간 Drift 차단
  • 공개 플러그인과 네 개의 집중형 Skill로 생성·검토·윤문 책임 분리
  • 비공개 정보 유출과 과윤문을 모델 자기평가가 아닌 결정적 코드 Gate로 통제
  • Agent OS의 Wiki·Persistent Agent·Flow·Approval·Domain Pack·Readback 구조와 단계별 구현계획 정리

상세 설계·로컬 계획 검증

배터리 조립라인 셋업과 수율 안정화에서는 설비 알람 하나만 보고 원인을 판단하지 않습니다. MES 이력, 검사 결과, Lot·재작업 기록, 작업자 조치, SOP·QCP·P-FMEA와 실제 설비상태를 같은 시간축과 판정기준으로 맞춰야 합니다. 그러나 이 자료는 서로 다른 시스템과 문서에 흩어져 있고, AI가 읽을 수 있다는 사실도 PLC나 MES를 바꿀 권한을 뜻하지 않습니다.

이 프로젝트는 그 간극을 줄이기 위한 제조·공정기술용 Agent OS 설계입니다. 목표는 AI가 설비를 대신 제어하는 것이 아니라, 공정·품질·생산 자료를 근거 단위로 연결하고 여러 Agent의 독립 분석을 생산기술 엔지니어가 검토할 수 있는 작업 제안으로 바꾸는 것입니다. 실행이 필요한 경우에도 사람 승인, 제한된 Adapter와 실제 상태 Readback을 별도 단계로 둡니다.

1. 프로젝트 개요

추진 배경

생산기술자가 설비 이상, 수율 저하나 품질 편차를 확인할 때 필요한 데이터는 한 화면에 있지 않습니다. 설비의 현재 State는 PLC·OPC에, 생산이력은 MES에, 검사 결과는 품질 파일에, 변경 이력은 SOP·QCP·P-FMEA와 담당자 기록에 남습니다. 시스템마다 이름·시간·Lot·판정코드가 다르면, 원인분석보다 먼저 데이터의 의미와 적용범위를 맞추는 일이 반복됩니다.

Agent OS는 이 문제를 데이터 수집 → 근거 결속 → 독립 분석 → 작업 제안 → 사람 승인 → 제한 실행 → 실제 결과 재확인의 제품 흐름으로 다시 설계합니다.

항목설계 내용
사용자생산기술·공정기술·품질·생산관리 엔지니어
입력MES 생산이력, PLC·OPC State, 검사결과, 설비 Alarm, 표준문서, 변경·조치 기록
핵심 역할제품 정의, 데이터·인터페이스 구조, Agent 분업, 제어-분석 Decoupling, 승인·Readback·복구 기준
출력근거가 연결된 원인 후보, 반대 근거, 재확인 항목, 작업 제안과 승인 요청
안전 원칙기본은 Read-only Advisory이며 물리 명령과 생산지시는 별도 권한으로 격리
현재 결과제품 비전·상세 아키텍처·실행계획과 로컬 검증 계약 확립

내가 맡은 범위

이 프로젝트에서 핵심 기여는 모든 코드를 혼자 작성했다는 주장이 아닙니다. 제조 현장 경험을 기준으로 다음을 결정하고 조율했습니다.

  • 공정·품질·생산 데이터를 어떤 공통 의미와 식별자로 묶을지
  • Worker와 Manager가 각각 무엇을 분석하고 어디에서 멈출지
  • 추천, 사람 승인, 외부 실행과 결과 Readback을 왜 분리해야 하는지
  • PLC·OPC·MES Adapter가 어떤 권한과 복구조건을 가져야 하는지
  • 장기 Run의 중복 Trigger, Active Writer, Checkpoint와 Rollback을 어떻게 통제할지
  • 무엇을 화면·코드·실제 상태로 확인해야 완료라고 부를지

2. 현장 문제 정의

AS-IS — 데이터는 많지만 판단의 연결이 끊긴 상태

현장 구간기존 한계생산기술 업무에 미치는 영향
데이터 위치MES·PLC·OPC·Excel·표준문서·개인 기록에 분산같은 현상을 여러 파일과 화면에서 반복 추적
의미 정합성Tag, State, Lot, 불량코드와 시간기준이 시스템별로 다름서로 다른 대상을 같은 원인으로 오판할 위험
원인분석담당자 경험과 수동 대조에 의존누락된 반대 근거와 재시험 조건을 뒤늦게 발견
AI 활용검색결과와 생성문장이 원문·적용범위와 분리그럴듯한 답변을 실제 공정 판단으로 사용하기 어려움
실행 권한분석 결과와 PLC·MES 변경권한의 경계가 불명확추천이 곧 제어로 이어지는 안전위험
완료 판정요청 성공·HTTP 200·Controller Receipt로 종료실제 설비·MES 상태가 바뀌었는지 확인되지 않음

TO-BE — 생산기술 판단을 하나의 Lineage로 연결

핵심은 더 많은 AI를 붙이는 것이 아닙니다. 공정·품질·생산 Agent가 같은 Source Snapshot을 보고 독립적으로 판단하고, Manager가 충돌과 반대 의견을 지우지 않은 채 하나의 작업 제안으로 정리하는 것입니다. 생산기술 엔지니어는 근거·적용범위·위험·복구방법을 확인한 뒤 승인하거나 보류합니다.

대표 사용 장면 — 반복 불량의 원인 추적

  1. 생산기술자가 특정 설비·Lot·시간구간의 반복 불량을 선택합니다.
  2. Read-only Adapter가 MES 생산이력, PLC·OPC State, 검사결과와 관련 표준문서의 Snapshot을 고정합니다.
  3. 공정 Agent는 조건변경·4M·재시험 이력을, 품질 Agent는 판정기준·측정 신뢰성을, 생산 Agent는 재공·병목·Lot 흐름을 각각 확인합니다.
  4. Manager는 공통 원인 후보, 배제 근거, 미확인 항목과 한 번의 통합 재검사 요청을 정리합니다.
  5. 사용자는 작업 제안을 승인·보류하거나 추가 측정을 요청합니다.
  6. 실제 변경이 필요한 경우에만 대상·Parameter·만료가 결속된 별도 승인으로 제한 Adapter를 사용합니다.
  7. 실행 뒤 설비·MES를 다시 읽고 요청 Receipt가 아니라 실제 결과로 종료 여부를 판단합니다.

3. 시스템 아키텍처

5개 Plane과 책임 경계

Plane입력과 처리산출물안전·운영 규칙
Read-only Data PlaneMES·QMS·PLC·OPC·Alarm·문서·이력 수집시간·Lot·Tag·State가 고정된 Snapshot기본 권한은 읽기, 원문과 Runtime을 변경하지 않음
Evidence PlaneSource, Revision, Currentness, Applicability, 권리·공개범위인용 가능한 근거와 부족·충돌 상태근거가 없으면 추정으로 채우지 않고 보류
Advisory Plane공정·품질·생산 Agent와 Worker·Manager Flow원인 후보, 반대 근거, 재시험, 작업 제안Manager도 더 높은 실행권한을 갖지 않음
Authority Plane대상·범위·Parameter·만료·위험·Rollback 검토사람 승인 또는 보류다른 대상·오래된 승인·이미 소비한 승인 재사용 금지
Effect & Readback Plane승인된 제한 Adapter와 실제 시스템 재조회Receipt, 실제 결과, 불일치·복구 기록요청 성공과 결과 성공을 분리하고 Active Writer를 1개로 유지

제어권한과 AI 분석의 Decoupling

AI 분석권한
Read Source → Compare → Explain → Recommend

사람의 결정권한
Approve → Reject → Request measurement → Limit scope

별도 Effect 권한
Exact target → Exact parameter → Expiry → One active writer → Rollback

완료 판정
Command receipt ≠ Process result
Authoritative Readback → Reconciliation → Close / Reopen

초기 Manufacturing Pack은 Read-only 감시와 보고에 집중합니다. PLC·OPC Write, 생산지시, 자재·PO와 같은 Effect는 하나의 포괄 권한으로 열지 않고 Adapter별 승인·복구조건을 둡니다. 이 구조는 설비 안전을 지키면서도 이후 기능을 단계적으로 추가할 수 있게 합니다.

장기 운영을 위한 Control Runtime

  • Aggregate별 Active Writer 1개와 중복 Trigger 차단
  • Queue Claim·Lease·Checkpoint로 장기 Run의 소유권과 진행상태 관리
  • 모델이 다시 판단하는 Semantic Rework와 통신 실패의 Transport Retry 분리
  • 재시작 뒤 같은 Agent·Flow·WorkItem을 복구하되 불명확한 외부 상태에서는 자동 재실행 금지
  • Outcome Record에 근거, 반대 의견, 승인, 실행 Receipt와 Readback Revision을 함께 보존
  • Notion은 Message Bus가 아니라 사람이 읽는 결과 Projection으로 사용

5. 향후 확장 비전

단계별 Scale-up

단계적용 범위완료 Gate
1. Read-only Shadow한 개 라인의 MES·검사·설비 State와 표준문서 SnapshotSource Binding, 시간·Lot·Tag 정합성, 권리·보안 검토
2. Production Copilot공정·품질·생산 Agent 독립 분석과 Manager 작업 제안Ground Truth 비교, 근거 누락·오류비용, 엔지니어 채택·반려 KPI
3. Limited Effect한 개 Adapter의 제한 명령 또는 생산업무 요청Exact target·parameter·expiry, Active Writer, Rollback·Reconciliation
4. Multi-line Domain Pack공정유형과 Site가 다른 라인에 공통 Core 재사용Namespace·Manifest·Adapter 호환성, 단계별 Cutover
5. Autonomous Manufacturing FoundationDigital Twin·Simulation에서 제안과 제어전략 사전평가Shadow Test, Safety Interlock, 사람 승인정책과 물리 E2E 재검증

확장 방식은 Big-bang 자동화가 아닙니다. Core는 Agent의 정체성·Flow·승인·기록·복구를 담당하고, Manufacturing Pack이 공정·품질·생산의 업무 규칙과 더 엄격한 제한을 추가합니다. 신규 라인은 Domain Pack과 Adapter를 교체하되, Source Binding·승인·Readback·Rollback 계약은 유지합니다.

최종 지향점

궁극적인 목표는 AI가 공장을 임의로 운영하는 화면이 아닙니다. 생산기술 엔지니어가 여러 시스템의 상태와 근거를 빠르게 맞추고, 독립 분석과 반대 의견을 비교한 뒤, 필요한 작업만 안전하게 승인하고 실제 결과까지 추적하는 Manufacturing Agent OS입니다.

현재 단계는 상세 설계와 로컬 계획 검증입니다. 다음 우선순위는 Read-only Manufacturing Reference Journey를 실제 화면과 Runtime으로 고정하는 것입니다.

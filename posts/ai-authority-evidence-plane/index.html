    Ontology·LLM Wiki 기반 AI Agent 실행 플랫폼

    해결하려던 문제

    Agent마다 긴 Prompt에 지식·도구·규칙을 반복하면 용어와 판단 기준이 달라지고, 어떤 근거로 구성됐는지 확인하기 어렵습니다. 실행 권한까지 섞이면 승인되지 않은 외부 변경으로 이어질 수도 있습니다.

    내가 맡은 범위

    • Ontology·LLM Wiki에서 관련 지식을 선택하고 Agent의 역할·도구·근거·출력·중단 조건을 묶어 실행하는 구조와, 외부 변경 전 승인·결과 재확인 조건을 설계했습니다.

    확인된 결과·현재 단계

    • 확인된 산출물 · 개인 역할 Ontology·LLM Wiki 지식을 바탕으로 역할·도구·근거·중단 조건을 묶는 AI Agent 구성·실행 플랫폼
    • 현재 단계 · 개인 역할 Agent 구성·로컬 실행 기반과 안전 계층 검증 · 운영계 연결 전

    팀 경계

    AI는 요청 분류·지식 후보 탐색·Agent 구성 초안과 실행 결과 정리를 돕습니다. 지식 기준, 도구 범위와 외부 변경 승인은 사람이 결정합니다.

    공개 범위: 공개 글은 Agent 구성·로컬 실행과 마지막 완료 안전 계층 검증까지만 다루며, 내부 Ontology·Wiki 원문, 저장소·환경·권한 정보는 공개하지 않습니다.

    Ontology·Wiki에서 지식을 찾고 Agent를 구성·실행하는 과정을 실제 업무 예시로 일반화해 설명합니다.

    어떤 플랫폼인가

    이 프로젝트의 중심은 승인 절차 자체가 아닙니다. Ontology와 LLM Wiki에 정리된 지식·용어·업무 규칙을 바탕으로, 요청한 일에 맞는 AI Agent를 구성하고 실행하는 플랫폼입니다.

    Ontology는 설비·공정·문서·역할처럼 서로 관련된 개념을 연결합니다. LLM Wiki는 Agent가 참고해야 할 설명, 작업 순서, 도구 사용법과 주의사항을 제공합니다. 플랫폼은 두 지식원을 읽어 Agent의 역할, 사용할 도구, 참고 근거, 출력 형식과 멈춰야 할 조건을 하나의 실행 단위로 묶습니다.

    권한·승인·Evidence 기능은 이 실행 플랫폼의 안전장치입니다. Agent가 답을 만들 수 있다는 사실만으로 주문·배포·권한 변경까지 실행하지 않도록, 실제 변경 전에는 근거와 사람의 승인 범위를 따로 확인합니다.

    왜 만들었나

    LLM에 긴 Prompt만 넣어 Agent를 만들면 같은 용어를 다르게 해석하거나, 프로젝트마다 규칙을 다시 설명해야 합니다. 어떤 문서를 참고했는지와 어느 도구까지 사용할 수 있는지도 대화 안에 섞이기 쉽습니다. Agent 수가 늘수록 지식과 실행 규칙이 복제되고, 수정한 내용이 일부 Agent에만 반영되는 문제가 생깁니다.

    그래서 지식은 Ontology와 Wiki에 두고, 실행할 때 필요한 부분만 골라 Agent 구성에 넣는 방식으로 나눴습니다. Agent의 지식과 행동 범위를 코드 밖에서 확인할 수 있고, 같은 지식 계약을 여러 Agent가 함께 사용할 수 있게 하는 것이 목표였습니다.

    대표 사용 장면

    예를 들어 사용자가 “특정 설비의 반복 정지 원인을 정리하고 점검 순서를 제안해 달라”고 요청한다고 가정해 보겠습니다.

    1. 요청에서 설비, 고장 현상, 관련 공정과 필요한 결과물을 구분합니다.
    2. Ontology에서 관련 설비·부품·고장 유형·점검 문서의 관계를 찾습니다.
    3. LLM Wiki에서 점검 순서, 사용할 도구, 출처와 금지사항을 불러옵니다.
    4. 이 내용을 바탕으로 분석 Agent의 역할, 입력, 도구, 출력 형식과 중단 조건을 구성합니다.
    5. Agent가 허용된 자료와 도구 안에서 작업하고, 사용한 근거와 결과를 기록합니다.
    6. 외부 시스템을 바꾸는 작업이라면 사람의 승인 범위를 확인한 뒤 허용하거나 멈추고, 실행한 경우에는 실제 결과를 다시 확인합니다.

    아래 순서는 현재 구현 방향을 공개 가능한 범위에서 일반화한 흐름입니다. 특정 회사의 내부 문서, 설비 주소, 계정과 운영 규칙은 포함하지 않았습니다.

    처음 보는 사람을 위한 시스템 지도

    이 플랫폼에는 일반적인 챗봇처럼 하나의 대화 화면만 있는 것이 아닙니다. 사용자의 요청을 받는 입구, 관련 지식을 찾는 Ontology와 Wiki, 작업용 Agent를 조립하는 단계, 허용된 범위에서 실행하는 단계, 그리고 결과와 근거를 다시 확인하는 단계가 이어집니다.

    처음 보는 사람은 왼쪽에서 오른쪽으로 읽으면 됩니다. 앞의 세 단계는 어떤 Agent를 만들 것인가를 결정하고, 뒤의 두 단계는 그 Agent가 실제로 무엇까지 할 수 있고 결과가 맞는가를 확인합니다. 그래서 좋은 답을 만드는 능력과 외부 시스템을 바꾸는 권한이 한 덩어리로 섞이지 않습니다.

    구성 요소와 역할

    구성 요소맡는 일
    Ontology업무 개념과 관계를 연결해 Agent가 같은 의미로 대상을 찾도록 함
    LLM Wiki작업 설명, 사용 도구, 예시, 제약조건과 확인 기준을 제공
    Agent Composer요청에 맞춰 역할·도구·근거·출력·중단 조건을 실행 명세로 구성
    Agent Runner구성된 명세에 따라 허용된 범위에서 작업하고 과정과 결과를 기록
    Authority & Evidence Layer근거·대상·사람 승인 범위를 확인하고, 부족하면 멈추며 실행 결과를 재확인

    이렇게 책임을 나누면 지식이 바뀌었을 때 모든 Agent Prompt를 일일이 고치는 대신 Ontology나 Wiki의 기준을 수정할 수 있습니다. 실행부는 어떤 지식을 사용했는지 기록하고, 안전 계층은 분석 성공과 실제 실행 권한을 구분합니다.

    소스 구조와 읽는 순서

    실제 저장소는 공개하지 않았습니다. 아래 이름은 비공개 경로를 옮긴 것이 아니라, 처음 보는 사람이 코드의 책임을 이해할 수 있도록 공개 가능한 단위로 일반화한 구조입니다.

    knowledge/
├── ontology/     설비·공정·문서·역할의 관계
└── wiki/         작업 순서·도구 설명·주의사항

schemas/          Agent 실행 명세와 근거 형식
composer/         요청에 필요한 지식을 골라 Agent 정의를 구성
runner/           허용된 도구로 작업하고 실행 기록을 남김
authority/        대상·사람 승인·외부 변경 가능 범위를 확인
evidence/         사용 근거, 산출물 식별자, 실행 결과를 보존
tests/            중단 조건, 재실행, 산출물 일치 여부를 검사

    코드를 살펴본다면 knowledge/에서 Agent가 무엇을 아는지 확인하고, schemas/와 composer/에서 그 지식이 어떤 실행 명세로 묶이는지 보면 됩니다. 그다음 runner/와 authority/에서 실행 범위를, evidence/와 tests/에서 결과를 다시 확인하는 방식을 읽는 순서가 자연스럽습니다.

    데이터, AI, 사람의 역할

    Ontology와 Wiki에는 개념, 관계, 업무 설명, 출처, 적용 범위와 제약조건이 남습니다. Agent 실행 기록에는 요청, 선택한 지식, 사용 도구, 결과, 위험과 승인 범위를 나눠 저장합니다. 이를 통해 Agent가 어떤 기준으로 구성됐고 어느 자료를 참고했는지 다시 확인할 수 있습니다.

    AI는 요청 분류, 관련 지식 후보 탐색, Agent 구성 초안, 검사 코드와 반례 작성, 결과 요약을 돕습니다. 사람은 Ontology와 Wiki의 기준을 검토하고, 사용할 도구와 데이터 범위, 외부 변경 여부를 승인합니다. Agent가 더 좋은 답을 만들더라도 사람의 권한이 자동으로 넘어가지는 않습니다.

    구현하고 확인한 범위

    마지막으로 완료한 로컬 검증 스냅숏에서는 Python 3.12와 jsonschema를 사용해 Agent 실행 명세, 근거·대상 연결과 중단 조건을 검사했습니다.

    • 로컬 회귀 검사 150개 통과
    • 원본에서 다시 만든 primary/repro 산출물의 byte 단위 일치 확인
    • Windows symlink 기능 제약 1건은 통과로 바꾸지 않고 skip으로 기록
    • 실제 주문 0건, 외부 시스템 변경 0건
    • 사람의 운영 승인과 운영계 연결 없음

    이 결과는 Agent를 구성하고 실행하기 위한 로컬 Foundation과 안전 계층을 확인한 것입니다. 공개 운영 서비스, 실거래나 외부 시스템 자동화가 완료됐다는 뜻은 아닙니다.

    회사에서 활용할 수 있는 부분

    회사에서는 설비보전, 공정 이상 분석, 품질 이슈 정리, 작업표준 검색처럼 서로 다른 Agent가 같은 사내 용어와 기준을 사용하도록 구성할 수 있습니다. 업무 지식은 Ontology와 Wiki에서 관리하고, Agent마다 필요한 역할과 도구만 선택하면 지식 중복과 Prompt 편차를 줄일 수 있습니다.

    또한 어떤 지식과 문서를 참고했는지, 누가 외부 변경을 승인했는지, 실행 후 실제 결과가 무엇인지 남길 수 있어 AI 결과를 검토하고 개선하기 쉬워집니다. 다만 실제 효과는 회사 데이터 연결, 사용자 검증과 운영 환경 시험을 거쳐 별도로 확인해야 합니다.

    한계와 공개 범위

    현재는 로컬 Foundation 검증 단계이며 공개 저장소와 운영 URL이 없습니다. 자격 증명, 내부 IP, 비공개 저장소·Notion 주소, 개인 데이터와 진행 중인 후속 규격은 공개하지 않습니다.

    실제 운영에는 회사 Ontology와 Wiki의 품질 검토, 문서별 접근 권한, Agent가 사용할 도구의 허용 범위, 사람 승인, 중복 실행 방지와 외부 시스템 결과 확인이 더 필요합니다. 현재 결과를 운영 준비 완료나 실거래 성과로 표현하지 않습니다.

    Problem

    Agent마다 긴 Prompt에 지식·도구·규칙을 반복하면 용어와 판단 기준이 달라지고, 어떤 근거와 권한으로 구성됐는지 확인하기 어렵습니다.

    Goal

    Ontology와 LLM Wiki에서 관련 지식을 고르고 Agent의 역할·도구·근거·출력·중단 조건을 실행 명세로 구성한 뒤, 승인된 범위에서 실행하는 플랫폼을 만드는 것입니다.

    Success

    Agent 구성이 사용한 지식과 도구 범위를 추적할 수 있고, 같은 source에서 산출물이 재현되며, 근거나 사람 승인이 빠진 외부 변경은 실행되지 않아야 합니다.

    AI와 사람이 나눈 역할

    AI 역할
    요청 분류, 관련 지식 후보 탐색, Agent 구성 초안, 테스트 코드·반례와 결과 요약을 지원하지만 지식 기준이나 외부 실행 권한을 결정하지 않습니다.
    사람 역할
    Ontology·Wiki의 기준, 사용할 데이터와 도구 범위, 실제 계정·자격 증명·배포·주문·복구 판단과 외부 결과 확인은 사람이 소유합니다.
    공개 Gate
    내부 Ontology·Wiki 원문, 자격 증명, 내부 IP, 비공개 저장소·Notion URL, 개인 데이터와 진행 중 규격은 공개하지 않습니다.
    외부 효과
    Agent 구성과 로컬 안전 계층까지만 확인했으며 실제 주문과 외부 변경은 0건입니다. 로컬 검사 성공을 운영 준비 완료나 실거래 성과로 표현하지 않습니다.

    범위와 경계

    포함 범위

    • Ontology·LLM Wiki의 개념·업무 규칙·출처 연결
    • Agent 역할·도구·근거·출력·중단 조건 구성
    • 실행 대상·사람 승인·결과 재확인과 clean materialization 검증

    제외·미검증 범위

    • 회사 내부 Ontology·Wiki 원문과 접근 권한 공개
    • 실거래, 주문 제출, credential 수집과 운영 계정 연결
    • 후속 규격이나 운영 적용을 완료 성과로 포함

    구현·검증 기준

    해야 할 일

    • 요청과 관련된 개념·문서·업무 규칙을 Ontology와 LLM Wiki에서 선택한다.
    • 선택한 지식을 역할·도구·근거·출력·중단 조건이 포함된 Agent 실행 명세로 구성한다.
    • 외부 변경은 대상·근거·사람 승인 범위가 맞을 때만 허용하고 실행 결과를 다시 확인한다.

    품질·운영 기준

    • clean checkout에서 같은 source가 byte-identical artifact를 만든다.
    • 테스트·fixture·harness 성공을 실제 외부 효과와 구분한다.
    • Windows symlink 같은 환경 capability skip을 제품 PASS로 숨기지 않는다.

    왜 이렇게 구성했나

    1. 지식과 Agent Prompt를 분리

      Ontology와 Wiki의 공통 기준을 여러 Agent가 공유해야 용어와 작업 규칙의 편차를 줄일 수 있기 때문입니다.

    2. Agent 구성을 실행 명세로 기록

      역할·도구·근거·출력·중단 조건을 남겨야 어떤 지식과 권한으로 실행됐는지 다시 확인할 수 있기 때문입니다.

    3. clean materialization을 완료 Gate로 사용

      로컬 캐시나 수동 산출물에 의존하지 않고 source에서 같은 결과를 재생성해야 Evidence를 감사할 수 있기 때문입니다.

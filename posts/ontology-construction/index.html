프로젝트 배경과 Vision

제조·반도체·배터리 지식이 파일마다 다른 용어·폴더·링크로 누적되면, 과거 문제와 유사한 현상이 재발해도 관련 원문을 다시 찾는 데 시간이 소요됩니다. 문서가 존재한다는 사실과 검색 가능한 지식으로 관리된다는 사실은 별개의 문제였습니다.

이 프로젝트의 설계 판단은 대형 Enterprise Platform을 먼저 구축하는 대신, 기존 Markdown 문서를 Source로 유지하면서 검색에 필요한 Metadata와 증분 색인 흐름부터 만드는 것이었습니다. 검색결과도 자동 답변보다 원문 후보를 우선해, 엔지니어가 근거를 직접 검토하는 업무방식을 보존했습니다.

현재 실행구조는 외부 LLM API가 아니라 로컬 CUDA 환경의 ChromaDB·BGE-M3·BGE Reranker입니다. 표준 PC·외부 API 방식은 동일 Source와 검색 Interface를 유지한 채 교체할 수 있는 다음 배포안으로 분리했습니다.

Data Standardization

지식 원문은 02_Knowledge 아래 Markdown으로 유지하고 YAML Frontmatter를 검색 Metadata로 사용했습니다.

Metadata 그룹주요 Field검색에서의 역할
BasicDomain·Date·Version분야·최신성 구분
ObjectObject Type·Tier문서유형·우선순위
Semanticis_instance_of·Expected Queries상위개념·예상질문 문맥
RelationSPO Subject·Predicate·Object문서관계 문맥
TrustStatic Trust·Decay Rate후보 Score 보정
BodyMarkdown 원문실제 검색대상·원문 검토

관계 Metadata는 현재 별도 Graph DB를 순회하는 방식이 아니라, Domain·Parent·SPO·Expected Query와 본문을 하나의 검색문서로 결합하는 데 사용했습니다.

Incremental Sync

Markdown 탐색
→ 제외폴더 Filter
→ 파일 수정시각·Checkpoint 비교
→ 신규·수정 파일 선별
→ Frontmatter·본문 Parsing
→ ChromaDB 문서단위 Upsert
→ Checkpoint 갱신

전체 문서를 매번 Embedding하지 않고 변경된 파일만 처리하도록 구성했습니다. 현장 문서가 계속 추가·개정되는 상황에서 색인 작업을 반복 가능한 운영절차로 바꾸기 위한 핵심 구조입니다.

Search & Reranking

자연어 질문
→ Tier 0 후보 + 일반 후보 Retrieval
→ 동일 경로 중복 제거
→ Query–Document Pair Reranking
→ 문서 최신성·Trust 반영
→ SHA-256 무결성 상태 반영
→ 원문 후보 순위 출력

검색판정 구조

단계구현출력
EmbeddingBAAI BGE-M3질문·문서 Vector
IndexChromaDB Persistent Client문서·Metadata 후보
Candidate RetrievalTier 0 + 일반검색관련 후보군
RerankingBGE-Reranker-V2-M3Query–Document 재정렬 Score
Trust문서일자·Static Trust·Decay시간경과 반영 Score

CLI후보파일명·Parent·Score엔지니어 원문검토 순서

검색의 종료점은 자동 생성답변이 아니라 검토할 원문 후보의 우선순위입니다. 제조문서의 사실·적용범위·공개가능 여부는 엔지니어가 원문에서 최종 판정하도록 구성했습니다.

현재 실행구조와 Cost-Aware 확장

배포안상태장점필요한 Gate
Local GPU현재 구현외부 Query API 비용 없음·문서 Local 처리CUDA·Model 배포·운영환경 고정
CPU Fallback후속안별도 GPU 없는 PC 적용 가능성응답시간·Memory Benchmark
External API Adapter후속안표준 PC·중앙 Model 운영 가능사용료·보안·문서반출 정책
Department Web후속안검색·원문이동·Feedback 표준화인증·권한·감사로그·오류복구

따라서 현재 성과는 “GPU 없이 외부 API로 구현”이 아니라 검색 Source와 Pipeline을 먼저 고정해 Runtime 선택을 분리한 것입니다. 전통 제조기업에서는 문서보안·인프라·사용료에 따라 Local GPU, CPU와 외부 API 중 적합한 방식을 선택할 수 있습니다.

제조 현장 적용 시나리오

단계사용자 경험문서화 Feedback
1. Source 표준화기존 문서를 Markdown·YAML로 정리Domain·Type·상위관계 누락 발견
2. 검색 PoC질문으로 관련 원문 후보 확인검색되지 않는 문서의 용어·Metadata 보강
3. 부서 Pilot대표 Query·정답문서 비교Template·작성규칙·검색 Ground Truth 개정
4. 운영 WikiWeb·권한·Citation·Feedback문서품질과 검색품질의 반복개선

문서를 많이 쓰도록 독려하는 대신, 잘 구조화한 문서가 검색결과로 다시 사용되는 경험을 제공하는 것이 지식 자산화의 핵심 설계의도였습니다.

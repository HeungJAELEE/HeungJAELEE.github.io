HeungTology: 제조 지식을 연결하는 Neo4j 온톨로지와 Graph-RAG 설계 PoC

  • Knowledge Graph
  • Neo4j
  • Ontology
  • Graph-RAG
  • AI

제조 현장의 지식은 작업표준서, 설비 매뉴얼, 품질 문서, 불량 분석 보고서와 엔지니어의 경험 속에 흩어져 있습니다. 검색창에 키워드를 입력하면 관련 문서를 찾을 수는 있지만, “어떤 공정 조건이 어떤 불량과 연결되고, 과거에는 어떤 조치로 해결했는가?”처럼 관계를 따라가야 하는 질문에는 답하기 어렵습니다.

HeungTology는 이 문제를 해결하기 위해 제조 도메인 지식을 노드와 관계로 구조화하고, Neo4j 기반 지식 그래프를 Graph-RAG 검색 흐름과 연결하는 방법을 설계한 아키텍처·PoC 프로젝트입니다. 이 프로젝트는 엔터프라이즈 시스템을 양산 배포하거나 전체 사내 지식을 변환 완료한 사례가 아닙니다. 그래프 데이터 모델, 적재 원칙, 탐색 흐름과 LLM 연결 가능성을 검토한 설계 실증에 범위를 둡니다.

  • 프로젝트 성격: 제조 지식 그래프 및 Graph-RAG 아키텍처 설계·PoC
  • 핵심 기술: Neo4j, Cypher, Ontology, Knowledge Graph, Graph-RAG
  • 목표: 분산된 문서를 관계 중심의 지식으로 구조화하고 근거를 추적할 수 있는 검색 흐름 설계
  • 현재 범위: 데이터 모델과 검색 파이프라인의 기술 가능성 검토
  • 제외 범위: 전사 배포, 전체 도메인 매핑 완료, 운영 성능 개선 수치

소스와 설계 자산은 HeungTology GitHub 저장소에서 확인할 수 있습니다.

1. 왜 온톨로지와 지식 그래프인가

일반적인 문서 검색은 같은 단어가 포함된 자료를 찾는 데 강합니다. 그러나 제조 트러블슈팅은 하나의 키워드보다 관계가 중요합니다. 예를 들어 용접 불량이라는 현상은 설비 조건, 소재, 검사 결과, 원인, 조치 이력과 연결됩니다. 이 관계를 문서마다 다시 읽어 찾아야 하면 숙련자 의존도가 높아지고 의사결정에 시간이 걸립니다.

저는 배터리 셀 개발과 자동화 라인 구축 업무를 수행하면서 공정 조건, 설비, 품질 기준, 불량과 개선 조치가 서로 분리되어 관리되는 문제를 경험했습니다. 또한 LLM 기반 사내 Wiki와 AI Agent, MES 데이터를 연계한 스마트 불량 분석 체계를 기획하고, 개인 지식 관리 프레임워크인 L-PARA를 활용해 공정 자료를 구조화해 왔습니다.

이 경험을 바탕으로 HeungTology의 질문을 다음과 같이 정의했습니다.

  1. 문서를 저장하는 데서 끝나지 않고, 공정 지식의 관계를 명시적으로 표현할 수 있는가?
  2. 동일한 설비·공정·불량이 여러 문서에 등장해도 하나의 개체로 연결할 수 있는가?
  3. LLM이 답변할 때 어떤 문서와 관계를 근거로 사용했는지 추적할 수 있는가?
  4. 지식이 변경될 때 기존 데이터를 무너뜨리지 않고 갱신할 수 있는가?

이 질문 때문에 단순 문서 모음이나 벡터 검색만이 아니라, Neo4j 지식 그래프와 Graph-RAG를 결합하는 아키텍처를 선택했습니다.

2. 프로젝트 목표와 비목표

목표

  • 제조 문서에서 반복되는 핵심 개체와 관계를 공통 스키마로 정의
  • Neo4j에 중복을 통제하며 데이터를 적재할 수 있는 Cypher 패턴 설계
  • 공정 → 설비 → 조건 → 불량 → 원인 → 조치로 이어지는 다중 홉 탐색 검토
  • 검색 결과와 출처를 LLM 컨텍스트로 전달하는 Graph-RAG 흐름 설계
  • 향후 사내 Wiki, AI Agent, MES와 연계할 수 있는 확장 지점 정의

비목표

  • 모든 제조 지식을 한 번에 완성된 온톨로지로 만드는 것
  • LLM이 사람의 승인 없이 설비를 자율 제어하게 하는 것
  • Neo4j를 도입하는 것만으로 환각이 사라진다고 주장하는 것
  • 검증되지 않은 응답 속도나 정확도 개선 수치를 성과로 제시하는 것

이 구분은 중요합니다. 지식 그래프는 사실을 구조화하고 탐색 경로를 제한하는 데 도움을 주지만, 원문이 틀리거나 추출 과정에서 관계가 잘못 생성되면 LLM 역시 잘못된 답을 만들 수 있습니다. 따라서 HeungTology는 “완성된 지능형 제어 시스템”이 아니라 근거 중심 제조 지식 검색을 위한 설계 기반입니다.

3. 전체 아키텍처

flowchart LR A["작업표준서·매뉴얼
불량 분석·공정 기록"] --> B["문서 식별 및 메타데이터"] B --> C["개체·관계 후보 추출"] C --> D["용어 정규화와 검토"] D --> E["Neo4j 지식 그래프"] E --> F["Cypher 기반 관계 탐색"] F --> G["관련 서브그래프와 출처"] G --> H["Graph-RAG 컨텍스트"] H --> I["LLM / AI Agent 응답"] I --> J["사용자 검토와 피드백"] J --> D

아키텍처는 크게 네 층으로 나뉩니다.

  1. 원천 계층: 매뉴얼, 표준서, 불량 분석, 공정 기록을 문서와 출처 단위로 식별
  2. 지식 모델 계층: 공정·설비·파라미터·불량·원인·조치 등의 개념과 관계를 정규화
  3. 그래프 저장·검색 계층: Neo4j와 Cypher로 연결 관계와 탐색 범위를 관리
  4. 생성형 AI 계층: 질문에 맞는 서브그래프와 출처만 LLM에 제공하고 답변 근거를 반환

각 계층을 분리한 이유는 LLM이 바뀌어도 지식 모델을 재사용하고, 데이터 오류가 발생했을 때 원문·추출·그래프·응답 중 어느 단계에서 생겼는지 추적하기 위해서입니다.

4. 사용 기술과 선택 이유

Neo4j: 관계 중심 데이터 저장

관계형 데이터베이스도 제조 데이터를 저장할 수 있지만, 공정에서 불량 원인과 조치까지 여러 단계를 가변적으로 탐색하려면 많은 조인과 별도 테이블 설계가 필요합니다. Neo4j는 개체를 노드로, 연결을 관계로 표현하므로 “이 불량과 연결된 설비 조건과 과거 조치는 무엇인가?”와 같은 질문을 경로 형태로 다루기 쉽습니다.

Neo4j를 선택한 이유는 모든 데이터를 그래프로 바꾸기 위해서가 아닙니다. Lot 이력이나 시계열 센서처럼 정형 데이터베이스가 더 적합한 데이터는 기존 시스템에 두고, 개념과 인과·참조 관계를 탐색하는 영역을 그래프로 담당하게 하는 것이 합리적입니다.

Cypher: 읽을 수 있는 그래프 탐색과 멱등 적재

Cypher는 노드와 관계 패턴을 시각적으로 읽기 쉬워 도메인 모델을 검토하기에 적합합니다. PoC에서는 동일 데이터를 반복 적재해도 중복 노드가 늘어나지 않도록 MERGE 중심의 패턴을 설계합니다. 또한 출처 식별자를 속성에 남겨 그래프에서 원문으로 돌아갈 수 있게 합니다.

Ontology: 같은 대상을 같은 언어로 표현

온톨로지의 역할은 어려운 용어를 만드는 것이 아니라, 팀마다 다르게 부르는 대상을 공통 개념과 관계로 합의하는 것입니다. 예를 들어 “레이저 출력”, “Laser Power”, “출력값”이 같은 의미라면 하나의 표준 개념에 매핑해야 검색 결과가 분리되지 않습니다.

HeungTology는 온톨로지 사고방식을 활용한 PoC이며, 특정 국제 표준과의 완전한 호환이나 정식 산업 온톨로지 인증을 주장하지 않습니다. 현재 단계에서는 제조 현장의 질문을 잘 설명하는 최소 스키마를 만드는 데 초점을 둡니다.

Graph-RAG: 관계와 출처를 포함한 검색

벡터 RAG는 문장 의미가 비슷한 문서를 찾는 데 유용하지만, 여러 문서에 나뉜 개체 관계를 정밀하게 따라가기 어렵습니다. Graph-RAG는 질문에서 핵심 개체를 식별하고, 그래프에서 제한된 관계를 탐색해 관련 서브그래프와 출처를 LLM에 제공합니다.

이 방식은 환각을 완전히 제거하지 않습니다. 대신 LLM이 참고할 수 있는 범위를 명시된 관계와 출처로 좁히고, 답변을 검토할 근거를 남기는 것이 목적입니다.

5. 제조 도메인 데이터 모델

아래 모델은 HeungTology의 설계 의도를 설명하기 위한 PoC 스키마 예시입니다. 실제 운영 스키마가 확정되었다는 의미는 아닙니다.

flowchart TD P["Process
공정"] -->|USES| E["Equipment
설비"] P -->|HAS_PARAMETER| R["Parameter
공정 조건"] P -->|MAY_CAUSE| D["Defect
불량"] D -->|HAS_CAUSE| C["Cause
원인"] C -->|MITIGATED_BY| A["Action
조치"] A -->|VERIFIED_BY| Q["Evidence
검증 근거"] Q -->|DERIVED_FROM| S["Source
원문"]

핵심 노드 후보

  • Process: 권취, 용접, 조립처럼 작업의 맥락을 정의
  • Equipment: 공정을 수행하는 설비 또는 주요 모듈
  • Parameter: 출력, 속도, 가압 등 관리해야 하는 조건
  • Defect: Swelling, 용접 불량 등 관찰된 이상 현상
  • Cause: 분석으로 확인되거나 가설로 관리되는 원인
  • Action: 조건 변경, 부품 교체, 점검과 같은 대응
  • Evidence: 측정 결과, 해체 분석, 품질 승인처럼 판단을 뒷받침하는 근거
  • Source: 표준서나 보고서 등 원문과 버전 정보

Evidence와 Source를 별도 노드로 두는 이유는 “무엇이 연결되어 있는가”뿐 아니라 “그 연결을 왜 믿을 수 있는가”를 확인하기 위해서입니다. 원인 가설과 검증된 원인을 같은 수준으로 저장하면 Graph-RAG가 가능성을 사실처럼 전달할 수 있으므로, 검증 상태와 출처를 구분해야 합니다.

6. 데이터 적재 흐름

6.1 문서 식별과 버전 관리

문서를 수집할 때 파일명만 사용하면 개정판을 구분하기 어렵습니다. 문서 ID, 제목, 개정 버전, 작성·승인 일자, 작성 조직, 접근 권한을 메타데이터로 관리해야 합니다. 그래프에 저장된 지식은 항상 원문 식별자로 돌아갈 수 있어야 합니다.

6.2 개체와 관계 후보 추출

문장에서 공정, 설비, 조건, 불량과 조치 후보를 찾고 관계 후보를 만듭니다. LLM을 추출 보조에 사용할 수 있지만 자동 추출 결과를 바로 확정 사실로 적재하지 않습니다. 신규 용어, 낮은 신뢰도의 관계, 안전·품질에 영향을 주는 관계는 도메인 담당자의 검토 대상으로 분리하는 것이 설계 원칙입니다.

6.3 용어 정규화

동의어 사전과 표준 ID를 이용해 같은 대상을 하나의 노드로 연결합니다. 공정명과 설비명이 바뀌어도 과거 기록을 유지할 수 있도록 표시 이름과 내부 식별자를 분리합니다.

6.4 멱등 적재

다음 Cypher는 설계 원칙을 설명하는 예시입니다. MERGE로 표준 ID를 기준으로 노드를 찾거나 생성하고, 관계에도 출처를 남깁니다.

MERGE (p:Process {id: $processId})
SET p.name = $processName,
    p.updatedAt = datetime()

MERGE (d:Defect {id: $defectId})
SET d.name = $defectName,
    d.updatedAt = datetime()

MERGE (s:Source {id: $sourceId})
SET s.title = $sourceTitle,
    s.revision = $revision

MERGE (p)-[r:MAY_CAUSE {sourceId: $sourceId}]->(d)
SET r.reviewStatus = $reviewStatus,
    r.updatedAt = datetime()

MERGE (d)-[:SUPPORTED_BY]->(s)

실제 운영 단계에서는 노드별 유일성 제약, 필수 속성, 허용 관계와 삭제 정책을 별도로 정의해야 합니다. 이 예시는 엔터프라이즈 운영 완료를 의미하는 코드가 아니라, PoC에서 중복과 출처 추적을 어떻게 다룰지 보여주는 패턴입니다.

7. Graph-RAG 질의 흐름

사용자가 “용접 불량의 가능한 원인과 확인해야 할 공정 조건은?”이라고 질문한다고 가정하면, 검색 흐름은 다음과 같이 구성할 수 있습니다.

  1. 질문에서 용접, 불량, 공정 조건에 해당하는 개체 후보를 식별
  2. 표준 용어 사전으로 후보를 그래프 노드에 연결
  3. 허용된 관계와 탐색 깊이 안에서 관련 원인, 파라미터, 조치, 근거를 조회
  4. 중복 경로를 정리하고 검토 상태가 낮거나 출처가 없는 관계를 제외
  5. 관련 서브그래프와 원문 메타데이터를 LLM 컨텍스트로 전달
  6. LLM이 근거를 구분해 답변하고 사용자가 원문을 확인할 수 있게 반환
MATCH (d:Defect {id: $defectId})
OPTIONAL MATCH (d)-[:HAS_CAUSE]->(c:Cause)
OPTIONAL MATCH (c)-[:RELATED_TO]->(p:Parameter)
OPTIONAL MATCH (c)-[:MITIGATED_BY]->(a:Action)
OPTIONAL MATCH (c)-[:SUPPORTED_BY]->(s:Source)
RETURN d, c, p, a, s
LIMIT $limit

이때 다중 홉 탐색을 무제한으로 허용하면 관련성이 약한 노드까지 섞일 수 있습니다. 따라서 질문 유형별로 허용 관계, 최대 깊이, 결과 수와 출처 필수 여부를 제한하는 것이 중요합니다.

8. 난제와 주요 의사결정

모든 관계를 자동 생성하지 않는다

LLM이 문장에서 관계를 빠르게 추출할 수 있어도, 제조 품질과 안전에 영향을 주는 인과관계를 자동 확정하는 것은 위험합니다. 그래서 자동 추출은 후보 생성에 사용하고, 중요 관계는 검토 상태를 거쳐 확정하는 Human-in-the-loop 구조를 선택했습니다.

“상관”과 “원인”을 구분한다

같은 시점에 발생한 현상과 검증된 원인은 다릅니다. 관계 타입이나 상태 속성으로 관련 있음, 원인 가설, 검증 완료를 구분해야 LLM이 과도한 결론을 만들지 않습니다.

그래프 깊이를 제한한다

관계를 많이 연결할수록 지식이 풍부해 보이지만, 검색 시 불필요한 경로와 순환이 늘어납니다. 질의 목적별 허용 관계와 탐색 깊이를 제한하고, 출처가 없는 경로는 우선순위를 낮추는 방식으로 범위를 통제합니다.

기존 시스템을 대체하지 않는다

MES의 생산 이력, 시계열 센서와 품질 측정 원본을 모두 Neo4j로 복제하는 것은 유지보수 부담을 키울 수 있습니다. 그래프에는 핵심 식별자와 관계를 두고, 상세 수치와 원본은 기존 시스템을 참조하는 연계 구조가 적합합니다.

9. PoC 검증 범위

현재 포트폴리오에서 주장할 수 있는 범위는 Neo4j 기반 온톨로지와 Graph-RAG 설계 및 PoC입니다. 다음과 같은 운영 성과는 확인된 수치가 없으므로 성과로 주장하지 않습니다.

  • 전체 사내 문서 또는 제조 도메인 매핑 완료
  • 엔터프라이즈 운영 환경 배포 완료
  • 검색 응답 시간 단축률
  • LLM 정답률 또는 환각 감소율
  • 자율 공정 제어 적용

PoC에서 확인해야 할 검증 항목은 다음과 같이 정의할 수 있습니다.

검증 항목확인 질문
스키마 적합성실제 제조 질문을 노드와 관계로 표현할 수 있는가?
중복 통제같은 문서를 재적재해도 동일 개체가 중복 생성되지 않는가?
출처 추적답변에 사용한 관계에서 원문과 개정 버전으로 돌아갈 수 있는가?
검색 정확성질문과 무관한 경로를 제외하고 필요한 서브그래프를 찾는가?
변경 관리용어·문서 개정 시 과거 이력과 최신 상태를 구분할 수 있는가?
권한 관리사용자 권한 밖의 문서가 검색 컨텍스트에 포함되지 않는가?

10. 이력서 경력과의 연결

HeungTology는 현장 제조 경험과 DX·AX 기획 역량을 지식 구조로 옮긴 프로젝트입니다.

  • 9년 이상의 배터리 제조 공정 설계·검증, 자동화 라인 구축 경험
  • 용접 조건 최적화, 해체 분석, P-FMEA·QCP·MSA 등 품질 지식의 구조를 이해한 경험
  • 2170·4695 셀 파일럿·양산 라인의 공정 수율 및 설비 안정화 경험
  • LLM 기반 사내 Wiki와 AI Agent, MES 연계 스마트 불량 분석 체계를 기획한 경험
  • L-PARA 프레임워크로 개인·업무 지식을 분류하고 재사용한 경험

이 경력이 온톨로지를 자동으로 완성해 주는 것은 아닙니다. 대신 어떤 정보가 현장 의사결정에 필요하고, 공정·설비·품질·조치가 어떤 맥락으로 연결되어야 하는지 정의하는 데 도메인 기반을 제공합니다.

11. 향후 개선 로드맵

1단계: 최소 도메인 확정

  • 하나의 공정과 대표 불량 유형으로 범위를 제한
  • 실제 질문 목록을 먼저 만들고 질문에 필요한 개체·관계만 정의
  • 도메인 전문가와 용어 사전, 관계 정의, 검토 기준 합의

2단계: 평가 데이터셋 구축

  • 질문, 기대 답변, 필수 근거 문서를 묶은 평가셋 작성
  • 그래프 검색의 Precision, Recall과 출처 일치율 측정
  • 벡터 RAG, Graph-RAG, Hybrid RAG를 같은 질문으로 비교

3단계: 운영 안전성 확보

  • 문서와 그래프의 버전·승인·폐기 상태 관리
  • 사용자·조직별 접근 권한을 검색 단계에 적용
  • 자동 추출 관계의 신뢰도와 사람의 승인 이력 기록
  • 답변이 근거 범위를 넘어설 때 “확인 불가”로 응답하는 정책 적용

4단계: 제조 시스템 연계

  • MES의 Lot·설비·품질 이력과 그래프 식별자를 연결
  • 불량 분석 결과와 조치 효과를 피드백 데이터로 축적
  • 사내 Wiki와 AI Agent가 같은 지식 그래프를 재사용하도록 API 계층 구성
  • 실제 사용자 질의 로그를 바탕으로 스키마와 검색 규칙 개선

12. 프로젝트를 통해 보여준 역량

HeungTology의 의미는 거대한 온톨로지를 완성했다는 데 있지 않습니다. 제조 현장의 복잡한 지식을 개체, 관계, 근거와 버전으로 나누고, Neo4j와 Cypher를 이용해 탐색 가능한 구조로 바꾸며, Graph-RAG가 사용할 컨텍스트를 통제하는 방법을 설계한 데 있습니다.

저는 공정 엔지니어로서 축적한 현장 지식을 AI가 읽을 수 있는 구조로 바꾸고, 동시에 사람이 답변의 근거를 다시 확인할 수 있게 만드는 것을 중요하게 봅니다. 이 프로젝트는 제조 도메인 이해, 데이터 모델링, 그래프 검색, LLM·AI Agent 기획을 연결한 기술 포트폴리오이며, 다음 단계는 실제 문서와 평가 질문을 기준으로 PoC를 정량 검증하는 것입니다.

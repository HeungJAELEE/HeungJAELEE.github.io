해결하려던 문제

한국어·영어 약어와 유사어가 섞인 제조 문서를 단순 키워드로 찾으면 같은 개념이 빠지거나 다른 의미가 함께 검색됩니다.

내가 맡은 범위

  • YAML 원천 계약에서 JSON-LD·OWL·SHACL·Neo4j 표현으로 이어지는 변환과 검증 구조를 설계했습니다.

확인된 결과·현재 단계

  • 확인된 산출물 · 개인 역할 YAML 계약→그래프 표현→검증→검색으로 이어지는 공개 코드 구조

팀 경계

개인 공개 프로젝트이며, 회사 내부 지식이나 고객 문서를 학습 데이터로 사용했다고 주장하지 않습니다.

공개 범위: 공개 저장소에서 다시 확인할 수 있는 구조와 코드만 설명하며, 로컬 검증 수치는 성과로 사용하지 않습니다.

제조 용어를 데이터 계약으로 정리하고 검색에 연결하는 일반적인 흐름으로 설명합니다.

무엇을 만든 프로젝트인가

제조 현장에서는 같은 설비나 불량이 문서마다 다른 이름으로 적힙니다. 공정 문서, 품질 기준, 설비 이력과 조치 기록의 용어가 맞지 않으면 검색 결과가 있어도 같은 대상을 말하는지 다시 확인해야 합니다.

HeungTology는 산업 지식 문서를 Markdown 노드로 모으고, 문서의 YAML 머리말과 본문을 로컬 벡터 저장소에 색인해 검색하는 개인 실험 저장소입니다. 공개 웹 서비스나 그래프 대시보드가 아니라, 지식 문서 모음과 로컬 Python 명령행 도구를 함께 둔 Git 저장소입니다.

공개 화면과 진입점

2026년 7월 31일 공개 저장소를 기준으로 확인한 진입점은 다음과 같습니다.

진입점 실제로 볼 수 있는 것 현재 한계
GitHub README 프로젝트가 의도하는 검색 구조와 로컬 실행 예시 README의 상태명·수치만으로 구현 또는 성능을 검증할 수 없음
GitHub 파일 브라우저 산업 분야별 Markdown 문서, YAML 머리말, 인덱스 파일 문서마다 검토 깊이가 다르고 pending_review, TBD, [데이터 부재] 표시가 남아 있음
rag_cli_v2.py --sync와 자연어 질의를 받는 터미널 진입점 공개 웹 화면이 아니며, 새로 받은 저장소에서 바로 실행할 설치 파일과 이식 가능한 설정이 없음

공개 저장소 정보에는 별도 홈페이지가 없고, 소스 트리에도 웹 프런트엔드가 없습니다. 따라서 앱 화면을 꾸며 만들지 않고, 방문자가 실제로 접하는 GitHub 저장소 화면을 그대로 보여 줍니다. 다른 진입점은 환경을 따로 준비한 뒤 사용하는 로컬 터미널입니다.

사용자 흐름

처음 보는 검토자는 README로 목적을 파악한 뒤, 02_Knowledge의 실제 문서와 rag_cli_v2.py를 대조해 무엇이 코드로 구현됐는지 확인할 수 있습니다.

로컬 사용 흐름은 코드 기준으로 Markdown 문서 준비 → --sync로 YAML 머리말과 본문 읽기 → BGE-M3 임베딩 생성 → ChromaDB에 저장 → 질문 입력 → 후보 검색 → BGE 재정렬 모델로 순서 조정 → 시간 감쇠·해시 상태 반영 → 터미널 점수표 출력 순서입니다. 현재 명령행 도구는 검색 후보의 파일명, 상위 관계와 점수를 보여 주며, 웹 화면이나 자연어 답변 화면을 제공하지 않습니다.

공개 CLI는 Neo4j를 연결하거나 JSON-LD·OWL·SHACL 파일을 생성하지 않습니다. 이런 표현은 README와 문서의 설계 언어로 남아 있지만, 현재 공개 코드에서 실행되는 기능으로 설명하지 않습니다.

권장 순서는 ① README로 의도를 짧게 읽고, ② rag_cli_v2.py에서 실제 동기화·질의 경로를 확인하고, ③ [MOC] 00_INDEX.md와 한 개의 Concept 또는 Data 문서에서 YAML 머리말과 본문 형식을 확인한 뒤, ④ _Ontology_Map.json과 _index 산출물을 마지막에 살펴보는 방식입니다. 큰 인덱스 파일이나 문서 안의 자체 선언 수치는 생성 과정과 평가 근거가 함께 재현되지 않는 한 성과 증거로 보지 않습니다.

실제로 맡은 역할

개인 프로젝트로 Markdown 지식 노드의 메타데이터 구조와 로컬 검색 흐름을 구성하고, rag_cli_v2.py에서 문서 동기화와 질의 단계를 구현했습니다. 문서의 분야, 문서 종류, 상위 관계, 단계, 날짜와 신뢰도 항목을 검색 메타데이터로 옮기고, 검색 후보를 재정렬 모델로 다시 정렬한 뒤 시간 감쇠와 해시 비교 결과를 점수에 반영하도록 했습니다.

실제 구현과 남은 한계

공개 코드로 확인되는 것은 Markdown YAML 머리말 해석, ChromaDB 동기화, BGE-M3 임베딩 검색, BGE 후보 재정렬, 날짜 기반 점수 감쇠, 일부 evidence_hash 비교와 터미널 점수표입니다.

반면 현재 저장소에는 의존성 설치 명세, 자동화된 테스트, 이식 가능한 경로·장치 설정, 웹 UI, 공개 실행 URL이 없습니다. 명령행 도구는 Windows 절대경로, 로컬 CUDA와 기존 모델·DB 환경을 전제로 하므로 새로 받은 저장소에서 재현 가능한 애플리케이션으로 보지 않습니다. 또한 저장소의 여러 문서에는 pending_review, placeholder, [데이터 부재]가 남아 있어 문서 안의 성능 수치나 완료 선언을 검증된 결과로 사용하지 않습니다.

그래서 이 글은 노드 수, 정확도, 지연시간, 오류·경고 수, 릴리스 등급을 성과로 제시하지 않습니다. 실제 회사 문서 검색의 정확성·권한·최신성도 별도 데이터와 운영 환경에서 검증해야 합니다.

회사에 적용하려면

회사에서 사용하려면 제조 용어의 소유자와 변경 절차, 문서별 검토 책임, 출처의 허용 기준, 접근 권한과 감사 이력을 먼저 정해야 합니다. 검색 결과는 설비 제어와 분리된 읽기 기능으로 유지하고, 근거가 부족한 내용은 자동으로 운전 조건이나 작업 지시가 되지 않게 해야 합니다.

이 조건과 재현 가능한 설치·평가 체계가 갖춰지면, 서로 다른 부서의 표현을 공통 메타데이터와 관계로 연결해 공정 조건, 설비 이력과 조치 근거를 찾는 구조로 확장할 수 있습니다. 현재 공개 결과는 그 운영 성과가 아니라, 문서 구조와 로컬 검색 실험을 검토할 수 있는 출발점입니다.

Problem

Markdown과 임의 frontmatter에 흩어진 산업 지식은 중복 키, 깨진 참조, 출처 없는 주장과 로컬 경로 때문에 검색 결과를 신뢰하기 어렵습니다.

Goal

사람이 편집 가능한 YAML 원본을 유지하면서 schema·hash·provenance·relation을 검증하고, 같은 release에서 GraphRAG가 근거를 인용하도록 만드는 것입니다.

Success

같은 입력에서 변환 결과가 일관되고 검색 응답에서 원문과 제목을 추적할 수 있으면 성공입니다.

범위와 경계

포함 범위

  • YAML v9 canonical node와 JSON Schema 계약
  • 결정적 migration, manifest, JSON-LD·OWL·SHACL release
  • Neo4j vector/full-text/RRF/graph expansion/reranking와 근거 인용

제외·미검증 범위

  • 애매한 관계를 임의로 추정해 연결하는 작업
  • DGX Spark가 상시 공개 서비스 중이라는 주장
  • 검증되지 않은 문서를 자동으로 authoritative source로 승격

구현·검증 기준

해야 할 일

  • 모든 node가 안정 ID, type, aliases, relations, provenance, body hash를 가진다.
  • migration과 release가 같은 입력에서 같은 결과를 만든다.
  • 검색 결과가 source node, heading, provenance를 포함한다.

품질·운영 기준

  • schema·hash·참조 오류는 release를 중단하고 경고는 명시적으로 보존한다.
  • Windows 로컬 경로와 민감 정보는 ingestion 전에 차단한다.
  • 공개 성과 수치는 방문자가 읽을 수 있는 보고서에서 다시 확인되어야 한다.

왜 이렇게 구성했나

  1. authoring과 semantic release 분리

    YAML은 사람이 유지하고 JSON-LD·OWL·SHACL은 기계가 생성하게 해 수동 동기화 오류를 줄였습니다.

  2. 경고를 숨기지 않는 release gate

    미해결 외부 관계를 임의 연결하지 않고 데이터 부채로 보존해야 검색 근거를 신뢰할 수 있기 때문입니다.

  3. hybrid retrieval과 인용 경계

    벡터 유사도만으로는 정확한 용어·관계·출처를 함께 만족시키기 어려워 단계별 검색과 reranking을 사용했습니다.

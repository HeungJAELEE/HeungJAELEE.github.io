프로젝트 자료

현재 공개 저장소와 v9.0 검증 결과를 직접 확인할 수 있습니다.

  • GitHub 저장소 github.com/HeungJAELEE/HeungTology
  • v9.0 Validation Report ontology/releases/9.0.0/validation-report.json

저장소의 공개 release와 validation report를 수치 근거로 사용합니다. DGX Spark 운영 구성은 배포 대상 아키텍처이며, 공개 사이트에서 상시 서비스 중이라고 주장하지 않습니다.

포트폴리오 요약: Problem–Role–Action–Result–Evidence

항목 확인된 내용
Problem 산업 지식이 Markdown 문서와 임의 frontmatter에 흩어져 중복 키·깨진 참조·출처 없는 주장·Windows 종속 경로가 검색 품질을 떨어뜨렸습니다.
Role 개인 공개 프로젝트의 설계·구현자로서 v9 데이터 계약, 마이그레이션·검증 CLI, JSON-LD/OWL/SHACL release, Neo4j hybrid retrieval, 근거 인용 규칙을 구성했습니다.
Action YAML 1.2 호환 authoring 형식과 JSON Schema를 정의하고, 본문 SHA-256·provenance·relation을 검증했습니다. heading-aware chunk, vector/full-text 검색, RRF, reranking, 출처 인용을 단계별로 분리했습니다.
Result 공개 v9 release에서 4,602 nodes, 1,904 provenanced assertions, 4,448 internal relations을 검증했습니다. validation report는 ok=true, errors=0, warnings=2를 기록하고 137개 외부/미해결 관계와 134개 로컬 경로를 숨기지 않습니다.
Evidence 공개 GitHub source, README, release manifest, migration report, validation report, schema·test·deployment 문서.

이력서 Bullet

  • 4,602개 한국어·영어 산업 지식 문서를 YAML v9 계약으로 마이그레이션하고 JSON Schema·본문 hash·provenance·relation 검증 파이프라인을 구현했습니다.
  • 1,904개 근거 assertion과 4,448개 내부 관계를 JSON-LD·OWL 2 RL·SHACL release로 생성하고, 137개 미해결 외부 관계를 경고로 보존했습니다.
  • Neo4j vector/full-text 검색, Reciprocal Rank Fusion, reranker, source-heading 인용을 결합한 evidence-first GraphRAG 흐름을 설계했습니다.
  • validation report에서 errors=0, warnings=2를 기록했으며, 비이식 로컬 경로는 ingestion 단계에서 redaction하도록 데이터 품질 경계를 구현했습니다.

면접 STAR

  • Situation: 문서 수가 늘면서 같은 개념의 중복, 깨진 링크, 출처 없는 주장과 잘못된 JSON map 때문에 벡터 검색 결과를 신뢰하기 어려웠습니다.
  • Task: 사람이 편집할 수 있는 Markdown은 유지하면서 기계가 검증·교환·검색할 수 있는 하나의 semantic contract를 만들어야 했습니다.
  • Action: YAML authoring, JSON Schema validation, JSON-LD exchange, OWL/SHACL semantics를 분리하고, deterministic migration·hash·release report·Neo4j hybrid retrieval을 구현했습니다.
  • Result: 4,602 nodes와 1,904 assertions을 검증 가능한 v9 release로 만들었습니다. 오류 0건뿐 아니라 남은 경고와 외부 관계도 보고서에 남겨 데이터 품질을 과장하지 않았습니다.

1. 해결하려던 데이터 문제

제조·배터리·반도체·AI 지식은 문서 제목만 잘 정리한다고 검색 가능한 데이터가 되지 않습니다. 다음 문제가 누적되면 LLM이 답을 생성하더라도 어떤 사실을 믿어야 하는지 설명할 수 없습니다.

  1. 같은 개념이 다른 ID와 이름으로 중복됩니다.
  2. frontmatter의 중복 key나 임의 타입 때문에 파서마다 결과가 달라집니다.
  3. 관계 대상이 없거나 여러 후보를 가리켜 그래프 연결이 불안정합니다.
  4. 주장에 source와 locator가 없어 답변 근거를 추적하기 어렵습니다.
  5. 로컬 절대 경로와 비밀값이 검색 인덱스로 유입될 수 있습니다.
  6. 벡터 유사도만으로는 정확한 용어와 그래프 관계를 함께 반영하기 어렵습니다.

HeungTology는 “문서를 많이 모으는 것”이 아니라 문서 → 데이터 계약 → semantic release → 검색 → 근거 인용을 하나의 검증 가능한 흐름으로 만드는 프로젝트입니다.

2. 전체 아키텍처

flowchart LR A["Markdown + YAML v9\n사람이 편집하는 원본"] --> B["JSON Schema + hash\n구조·출처·무결성 검증"] B --> C["JSON-LD 1.1 release"] C --> D["OWL 2 RL + SHACL\n의미·shape 검증"] B --> E["Heading-aware chunks"] E --> F["Qwen3 Embedding\n2560D vector"] F --> G["Neo4j vector + full-text"] G --> H["RRF + graph expansion"] H --> I["Qwen3 Reranker"] I --> J["Grounded answer\nsource path + heading [S#]"]

아키텍처는 네 계약을 의도적으로 분리합니다.

  • YAML frontmatter: 사람이 관리할 수 있는 제한된 authoring 형식
  • JSON Schema 2020-12: key·type·필수 field와 release 구조 검증
  • JSON-LD 1.1: 시스템 간 교환 가능한 canonical graph 표현
  • OWL 2 RL·SKOS·PROV-O·DCAT 3·SHACL: 개념, provenance, dataset과 shape 검증

이 분리 덕분에 Markdown 편집 경험을 유지하면서도 특정 LLM이나 DB에 종속되지 않은 release를 만들 수 있습니다.

3. Canonical Node 계약

각 문서는 하나의 엄격한 frontmatter 객체를 가집니다. 핵심 field는 다음과 같습니다.

그룹 주요 field 목적
identity UUID, legacy ID, slug, title 같은 개체를 안정적으로 식별
classification node type, domain, tier, tags 분석·검색 필터 기준
lifecycle status, version 검토·release 상태 관리
provenance authors, source refs, body hash, reviewer 원문과 변경 근거 추적
relations broader, related, instance-of 그래프 경로 구성
assertions subject·predicate·object·evidence 주장 단위 근거 관리
retrieval aliases, expected queries, trust, embedding profile 검색 동작과 품질 기준
validation schema version, status machine gate 결과

YAML duplicate key, anchor, alias, merge key, custom tag, non-string key와 JSON으로 표현할 수 없는 값은 거부합니다. 본문은 정규화한 UTF-8 bytes에서 SHA-256을 계산해 frontmatter의 provenance와 비교합니다.

4. 마이그레이션과 데이터 품질

v9 migration은 write 전에 모든 변환 결과를 검증하는 deterministic pipeline입니다.

  1. 기존 Markdown을 parse하고 legacy ID·domain·type을 읽습니다.
  2. stable UUID와 canonical slug를 생성합니다.
  3. parent/self-cycle과 중복 ID를 검사합니다.
  4. source·assertion·relation을 새 계약에 매핑합니다.
  5. normalized body hash를 계산합니다.
  6. 전체 결과가 schema를 통과한 뒤에만 --write를 허용합니다.
  7. migration report와 ID map을 release에 남깁니다.

현재 migration report는 4,602개 문서를 스캔·변환했고 parse error와 duplicate ID를 0으로 보고합니다. 반면 137개 unresolved reference와 1,165개 ambiguous legacy reference는 추측해 연결하지 않고 별도 통계로 남깁니다.

5. 검색 파이프라인을 왜 hybrid로 구성했는가

벡터 검색은 의미가 비슷한 문장을 찾는 데 유리하지만, 장비 코드·표준명·약어처럼 정확한 token에는 full-text가 강합니다. 또한 공정→설비→불량→조치처럼 관계를 따라야 하는 질문은 graph expansion이 필요합니다.

HeungTology의 retrieval 순서는 다음과 같습니다.

  1. query embedding으로 vector top-k 검색
  2. title·alias·heading·body의 full-text 검색
  3. 서로 다른 raw score를 직접 더하지 않고 RRF로 rank 결합
  4. allow-list relation을 1-hop 확장
  5. reranker가 최종 문맥 순서를 재평가
  6. LLM에는 source path와 heading을 포함한 context만 전달
  7. 답변의 각 사실에는 [S#] 근거를 요구하고 부족하면 부족하다고 답변

이 구조는 “그래프가 있으니 정확하다”는 주장을 피합니다. 검색은 후보를 좁힐 뿐이며, 최종 신뢰도는 source와 assertion 품질에 달려 있습니다.

6. 공개 검증 결과

지표 v9 release 결과 해석
Canonical nodes 4,602 strict v9 schema로 표현한 문서 수
Provenanced assertions 1,904 source·locator·hash 구조를 가진 주장
Internal relations 4,448 저장소 안의 canonical node로 해석된 관계
External/unresolved relations 137 출처가 하나로 정해지지 않아 외부 URN·경고로 보존
Validation errors 0 release gate를 막는 구조 오류 없음
Validation warnings 2 unresolved relation, nonportable body path

두 경고는 실패를 숨긴 흔적이 아니라 운영 경계입니다.

  • 137개 관계는 잘못된 내부 node에 억지로 연결하지 않았습니다.
  • Markdown body에 남은 134개 local file path는 GraphRAG ingestion에서 redaction합니다.

7. 기술 선택과 이유

  • Python 3.12 / CLI: migration, validation, build, query를 재현 가능한 명령으로 제공
  • JSON Schema: document와 release의 구조 gate
  • JSON-LD / RDF / OWL / SHACL: 교환·의미·shape 검증을 분리
  • Neo4j: vector, full-text, Cypher 관계 탐색을 하나의 graph store에서 결합
  • Qwen3 Embedding / Reranker: 한국어·영어 산업 용어를 포함한 local retrieval target
  • DGX Spark: generation·embedding·reranking을 loopback 기반 로컬 서비스로 운용하는 목표 환경
  • pytest / Ruff / release manifest: 기능·style·artifact integrity의 반복 검증

8. Data Analyst 관점에서 보여 주는 역량

이 프로젝트의 분석 역량은 dashboard를 만든 데 있지 않습니다. 데이터의 정의와 신뢰 경계를 먼저 만들고, 품질 문제를 계량해 의사결정 가능한 상태로 바꾼 데 있습니다.

  • node type·domain·lifecycle별 분포를 release report로 집계
  • source와 assertion을 분리해 “문서가 있다”와 “근거 있는 주장이 있다”를 구분
  • unresolved/ambiguous relation을 자동 연결하지 않고 품질 backlog로 관리
  • vector·full-text·graph retrieval을 각기 다른 역할로 비교
  • validation error와 warning을 분리해 release gate와 개선 항목을 명확히 함
  • 비밀값·절대 경로·근거 없는 Agent action 언어를 별도 audit 대상으로 처리

9. 제조 현장 경험과의 연결

배터리 조립 라인에서 공정 조건, 설비 신호, 품질 문서, 불량 원인과 조치가 서로 다른 시스템에 나뉘어 있으면 엔지니어가 매번 맥락을 다시 조합해야 합니다. HeungTology의 Process → Equipment → Parameter → Defect → Cause → Action 관계는 이 현장 문제를 데이터 모델로 옮긴 것입니다.

QCP·P-FMEA·MSA 경험은 assertion과 validation을 분리한 이유로, MES 관리 항목 설계 경험은 canonical ID와 provenance를 우선한 이유로, FAT/SAT 경험은 release 전에 deterministic gate를 두는 방식으로 연결됩니다.

10. 현재 한계와 다음 단계

  1. 4,602개 node가 모두 같은 수준의 사람 검토를 완료한 것은 아닙니다.
  2. 1,904 assertions 외의 문장까지 근거가 완전하다고 볼 수 없습니다.
  3. 137개 외부 relation과 1,165개 ambiguous legacy reference를 지속 정리해야 합니다.
  4. DGX Spark runtime target과 live production 운영 완료는 구분해야 합니다.
  5. retrieval quality는 고정된 benchmark question·relevance judgment로 추가 평가해야 합니다.
  6. Neo4j sync와 LLM 답변은 읽기·검색 경계에 두고 설비 제어 권한과 분리해야 합니다.

HeungTology가 보여 주는 핵심은 “Neo4j를 썼다”는 사실이 아닙니다. 사람이 작성한 산업 지식을 엄격한 데이터 계약으로 변환하고, 오류·경고·근거를 공개한 채 검색 가능한 release로 운영하는 능력입니다.

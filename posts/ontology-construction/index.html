    TECHNICAL CASE STUDY

    HeungTology: 산업 지식을 근거와 함께 찾는 구조

    산업 지식 문서를 데이터 계약, 관계 검증, 하이브리드 검색과 출처 인용으로 연결한 개인 프로젝트

    2026. 7. 9. · 5 · 마지막 검토 2026. 7. 31.

    • Knowledge Graph
    • Neo4j
    • Ontology
    • GraphRAG
    • Data Quality
    • AI

    어떤 문제를 해결하려 했는가

    제조 현장 자료는 공정, 설비, 품질, 불량, 조치 문서로 나뉘어 있습니다. 문서가 많아질수록 같은 설비가 다른 이름으로 적히고, 관계 대상이 사라지거나, 출처가 없는 설명이 검색 결과에 섞이는 문제가 생깁니다.

    HeungTology는 문서 수를 늘리는 프로젝트가 아닙니다. 사람이 편집하는 문서를 일정한 구조로 검사하고, 공정과 설비의 관계를 추적하며, 검색 결과가 어느 문서의 어느 부분에서 왔는지 확인할 수 있게 만든 개인 프로젝트입니다.

    구분공개 범위
    문제중복된 식별자, 깨진 관계, 출처가 약한 주장, 로컬 경로 유입
    맡은 범위데이터 구조, 변환·검증 절차, 그래프 표현, 검색 흐름 설계와 구현
    사용 기술YAML, JSON Schema, JSON-LD, OWL, SHACL, Neo4j, Python
    현재 상태공개 저장소에서 확인되는 코드와 문서 범위로 설명
    보류한 주장공개 보고서로 다시 확인할 수 없는 로컬 release 수치와 완료 등급

    왜 이런 구조로 만들었는가

    문서 원본, 그래프 표현, 검색용 데이터를 하나의 파일에서 함께 관리하면 수정할 때마다 서로 다른 결과가 생기기 쉽습니다. 그래서 책임을 나눴습니다.

    flowchart LR A["Markdown + YAML\n사람이 편집하는 원본"] --> B["Schema·관계·경로 검사"] B --> C["JSON-LD / OWL / SHACL\n교환·의미 검증"] B --> D["제목·본문 단위 검색 데이터"] D --> E["Vector + Full-text"] C --> F["Neo4j 관계 탐색"] E --> G["후보 결합·재정렬"] F --> G G --> H["출처 문서와 제목을 붙인 답변"]
    • YAML과 JSON Schema는 사람이 입력한 필드의 이름과 형식을 검사합니다.
    • JSON-LD·OWL·SHACL은 다른 시스템과 교환할 그래프 표현과 관계 조건을 다룹니다.
    • Neo4j는 공정→설비→불량→원인→조치처럼 관계를 따라가야 하는 질문에 사용합니다.
    • Vector와 full-text 검색은 의미가 비슷한 문장과 정확한 설비명·약어를 각각 찾습니다.
    • 출처 인용 규칙은 검색 결과가 좋아 보여도 근거 문서가 없으면 확정적으로 답하지 않게 합니다.

    내가 확인하고 바꾼 것

    문서 구조를 먼저 고정

    문서마다 다음 정보를 같은 위치에 두도록 계약을 잡았습니다.

    항목목적
    ID·제목·별칭같은 개념을 여러 이름으로 찾되 하나의 대상으로 관리
    종류·분야·상태검색과 검토 범위를 구분
    출처·검토자·본문 hash내용이 어디에서 왔고 바뀌었는지 추적
    상위·관련·사례 관계그래프 탐색 경로 구성
    주장과 근거 위치문서 존재와 근거 있는 주장을 구분

    중복 key, 존재하지 않는 관계 대상, 로컬 절대경로와 형식 오류는 변환 단계에서 따로 보고하도록 했습니다. 관계가 애매할 때는 가장 비슷한 문서에 자동으로 붙이지 않고 검토 대상으로 남기는 방식을 택했습니다.

    검색 단계를 분리

    벡터 검색 결과와 문자열 검색 점수는 기준이 다르기 때문에 원점수를 바로 더하지 않았습니다. 각각 후보 순위를 만든 뒤 순위를 결합하고, 필요한 관계만 한 단계 확장한 다음 다시 정렬하도록 구성했습니다. 답변에는 원문 경로와 제목을 함께 넘겨 어떤 내용에 기대어 작성했는지 확인할 수 있게 했습니다.

    공개 범위를 다시 정리

    이전 글에는 로컬에서 만든 release 수치가 공개 저장소에서도 바로 재현되는 것처럼 적혀 있었습니다. 공개 저장소에서 같은 보고서를 확인하지 못했기 때문에 노드 수, assertion 수, 오류·경고 수와 같은 값은 이 글의 성과에서 내렸습니다. 공개 링크는 저장소에서 직접 확인할 수 있는 구조와 문서만 보여 줍니다.

    결과와 제조 경험의 연결

    이 프로젝트를 통해 산업 지식을 저장할 때 “문서가 있다”와 “근거가 확인된 주장이 있다”를 구분하는 구조를 만들었습니다. 또 검색 결과가 물리 설비의 제어 명령으로 곧바로 이어지지 않도록 읽기·검색 영역과 실행 권한을 분리했습니다.

    배터리와 자동화 라인에서 공정 조건, 검사 기준, 설비 이력과 불량 조치가 서로 다른 문서에 흩어지는 문제를 겪은 경험이 설계의 출발점이었습니다. QCP·P-FMEA·MSA에서 기준과 판정 근거를 따로 관리했던 방식은 이 프로젝트의 출처·주장·검증 구조에 반영했습니다.

    확인 자료와 한계

    • 공개 저장소에서 데이터 구조, 변환·검증 코드와 검색 설계 문서를 확인할 수 있습니다.
    • 공개 저장소에 없는 로컬 검증 수치는 대표 성과로 사용하지 않습니다.
    • 모든 문서가 같은 깊이의 사람 검토를 받은 것은 아닙니다.
    • 검색 품질은 고정 질문과 relevance 판정표를 사용한 추가 평가가 필요합니다.
    • 지식 검색은 설비 제어 권한과 분리된 읽기 기능으로 유지해야 합니다.

    프로젝트 유형

    공개 저장소에서 확인 가능한 코드·문서

    Problem

    Markdown과 임의 frontmatter에 흩어진 산업 지식은 중복 키, 깨진 참조, 출처 없는 주장과 로컬 경로 때문에 검색 결과를 신뢰하기 어렵습니다.

    Goal

    사람이 편집 가능한 YAML 원본을 유지하면서 schema·hash·provenance·relation을 검증하고, 같은 release에서 GraphRAG가 근거를 인용하도록 만드는 것입니다.

    Success

    같은 입력에서 변환 결과가 일관되고 검색 응답에서 원문과 제목을 추적할 수 있으면 성공입니다.

    범위와 경계

    포함 범위

    • YAML v9 canonical node와 JSON Schema 계약
    • 결정적 migration, manifest, JSON-LD·OWL·SHACL release
    • Neo4j vector/full-text/RRF/graph expansion/reranking와 근거 인용

    제외·미검증 범위

    • 애매한 관계를 임의로 추정해 연결하는 작업
    • DGX Spark가 상시 공개 서비스 중이라는 주장
    • 검증되지 않은 문서를 자동으로 authoritative source로 승격

    구현·검증 기준

    해야 할 일

    • 모든 node가 안정 ID, type, aliases, relations, provenance, body hash를 가진다.
    • migration과 release가 같은 입력에서 같은 결과를 만든다.
    • 검색 결과가 source node, heading, provenance를 포함한다.

    품질·운영 기준

    • schema·hash·참조 오류는 release를 중단하고 경고는 명시적으로 보존한다.
    • Windows 로컬 경로와 민감 정보는 ingestion 전에 차단한다.
    • 공개 성과 수치는 방문자가 읽을 수 있는 보고서에서 다시 확인되어야 한다.

    왜 이렇게 구성했나

    1. authoring과 semantic release 분리

      YAML은 사람이 유지하고 JSON-LD·OWL·SHACL은 기계가 생성하게 해 수동 동기화 오류를 줄였습니다.

    2. 경고를 숨기지 않는 release gate

      미해결 외부 관계를 임의 연결하지 않고 데이터 부채로 보존해야 검색 근거를 신뢰할 수 있기 때문입니다.

    3. hybrid retrieval과 인용 경계

      벡터 유사도만으로는 정확한 용어·관계·출처를 함께 만족시키기 어려워 단계별 검색과 reranking을 사용했습니다.

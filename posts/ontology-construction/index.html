HeungTology: 산업 지식을 근거와 함께 찾는 구조

산업 지식 문서를 데이터 계약, 관계 검증, 하이브리드 검색과 출처 인용으로 연결한 개인 프로젝트

30초 요약

같은 설비·품질 개념도 부서와 문서마다 표현이 달라 검색이 끊깁니다. 용어와 관계를 먼저 계약으로 정해야 근거가 있는 검색이 가능하다고 봤습니다.

해결하려던 문제

한국어·영어 약어와 유사어가 섞인 제조 문서를 단순 키워드로 찾으면 같은 개념이 빠지거나 다른 의미가 함께 검색됩니다.

내가 맡은 범위

  • YAML 원천 계약에서 JSON-LD·OWL·SHACL·Neo4j 표현으로 이어지는 변환과 검증 구조를 설계했습니다.

확인된 결과·현재 단계

  • 확인된 산출물 · 개인 역할 YAML 계약→그래프 표현→검증→검색으로 이어지는 공개 코드 구조

팀 경계

개인 공개 프로젝트이며, 회사 내부 지식이나 고객 문서를 학습 데이터로 사용했다고 주장하지 않습니다.

공개 범위: 공개 저장소에서 다시 확인할 수 있는 구조와 코드만 설명하며, 로컬 검증 수치는 성과로 사용하지 않습니다.

제조 용어를 데이터 계약으로 정리하고 검색에 연결하는 일반적인 흐름으로 설명합니다.

왜 이 의사결정이 중요했는가

제조 현장에서는 같은 설비나 불량이 문서마다 다른 이름으로 적힙니다. 공정 문서, 품질 기준, 설비 이력과 조치 기록의 용어가 맞지 않으면 검색 결과가 있어도 같은 대상을 말하는지 다시 확인해야 합니다. 더 큰 문제는 출처가 없는 설명이 근거가 확인된 내용처럼 섞이는 경우입니다.

HeungTology는 문서를 많이 모으는 프로젝트가 아니라, 용어와 관계를 같은 규칙으로 관리하고 검색 결과가 어느 원문에서 왔는지 확인하기 위한 개인 프로젝트입니다. “문서가 존재한다”와 “그 문서가 특정 주장을 뒷받침한다”를 분리하는 것이 핵심 판단이었습니다.

왜 디지털 방식이 필요했는가

사람이 폴더와 파일명을 기억해 관련 문서를 찾는 방식은 자료가 늘수록 유지하기 어렵습니다. 문서마다 ID, 별칭, 종류, 출처와 관계를 같은 형식으로 적으면 컴퓨터가 구조 오류를 검사하고, 정확한 용어 검색과 의미가 비슷한 문장 검색을 함께 사용할 수 있습니다.

원본 문서는 사람이 읽고 수정하기 쉬운 Markdown과 YAML로 두고, 관계 탐색용 표현과 검색용 데이터를 파생시키도록 구성했습니다. 이렇게 하면 검색 편의를 위해 원본의 책임과 출처를 잃지 않을 수 있습니다.

실제로 맡은 역할

개인 프로젝트로 YAML 문서 계약, 변환·검증 흐름, 지식 그래프 표현과 검색 단계를 설계하고 구현했습니다. 중복 식별자, 존재하지 않는 관계 대상, 로컬 절대경로와 형식 오류를 배포 전 점검 대상으로 두고, 애매한 관계는 비슷한 문서에 자동 연결하지 않고 사람 검토에 남기는 방향을 정했습니다.

검색에서는 벡터와 문자열 검색의 원점수를 바로 더하지 않고 각각의 순위를 결합하도록 설계했습니다. 최종 문맥에는 원문 경로와 제목을 함께 전달해 답변의 출발점을 되짚을 수 있게 했습니다.

데이터 흐름

제조 용어 불일치 → YAML 문서 계약 → 지식 그래프 표현 → 스키마·관계·경로 검증 → 출처를 동반한 검색 사용

YAML의 ID와 별칭은 같은 개념을 여러 이름으로 찾되 하나의 대상으로 관리하는 기준이 됩니다. 관계 표현은 공정, 설비, 불량, 원인과 조치를 따라가는 탐색에 사용합니다. 검증을 통과한 문서만 검색 후보로 넘기고, 검색 결과에는 문서와 제목 정보를 붙입니다.

구현 순서

  1. 문서마다 ID, 제목, 별칭, 종류, 상태, 출처와 관계를 같은 위치에 두는 YAML 계약을 정했습니다.
  2. YAML을 JSON-LD·OWL·SHACL과 Neo4j에서 다룰 수 있는 그래프 표현으로 변환하는 경계를 나눴습니다.
  3. 스키마, 식별자, 관계 대상과 로컬 경로를 검사하고 애매한 연결은 검토 대상으로 남겼습니다.
  4. 제목과 본문 단위의 검색 데이터를 만들고, 문자열 검색과 벡터 검색의 후보 순위를 결합하도록 구성했습니다.
  5. 필요한 관계만 제한적으로 확장한 뒤 문맥을 다시 정렬하고, 원문 경로와 제목을 답변 근거로 전달하도록 했습니다.

확인된 결과와 현재 단계

공개 저장소에서 확인할 수 있는 범위는 데이터 구조, 변환·검증 코드와 검색 설계 문서입니다. 공개 자료로 재현되지 않는 로컬 release 수치나 완료 등급은 성과로 사용하지 않습니다. 이 글에서도 노드 수, assertion 수, 오류·경고 수를 제시하지 않습니다.

현재는 구조와 검증·검색 흐름을 보여 주는 개인 프로젝트 단계입니다. 모든 문서가 같은 깊이의 사람 검토를 받은 것은 아니며, 검색 품질은 고정 질문과 relevance 판정 기준을 둔 추가 평가가 필요합니다.

배포 조건과 회사에 줄 수 있는 가치

회사에서 사용하려면 제조 용어의 소유자와 변경 절차, 문서별 검토 책임, 출처의 허용 기준, 접근 권한과 감사 이력을 먼저 정해야 합니다. 검색 결과는 설비 제어와 분리된 읽기 기능으로 유지하고, 근거가 부족한 내용은 자동으로 운전 조건이나 작업 지시가 되지 않게 해야 합니다.

이 조건이 갖춰지면 서로 다른 부서의 표현을 공통 ID와 관계로 연결해 공정 조건, 설비 이력과 조치 근거를 더 빨리 찾을 수 있습니다. 회사 가치는 검색 답변의 문장보다, 같은 용어와 출처 기준으로 지식을 검토하고 다시 사용할 수 있는 구조에 있습니다.

Problem

Markdown과 임의 frontmatter에 흩어진 산업 지식은 중복 키, 깨진 참조, 출처 없는 주장과 로컬 경로 때문에 검색 결과를 신뢰하기 어렵습니다.

Goal

사람이 편집 가능한 YAML 원본을 유지하면서 schema·hash·provenance·relation을 검증하고, 같은 release에서 GraphRAG가 근거를 인용하도록 만드는 것입니다.

Success

같은 입력에서 변환 결과가 일관되고 검색 응답에서 원문과 제목을 추적할 수 있으면 성공입니다.

범위와 경계

포함 범위

  • YAML v9 canonical node와 JSON Schema 계약
  • 결정적 migration, manifest, JSON-LD·OWL·SHACL release
  • Neo4j vector/full-text/RRF/graph expansion/reranking와 근거 인용

제외·미검증 범위

  • 애매한 관계를 임의로 추정해 연결하는 작업
  • DGX Spark가 상시 공개 서비스 중이라는 주장
  • 검증되지 않은 문서를 자동으로 authoritative source로 승격

구현·검증 기준

해야 할 일

  • 모든 node가 안정 ID, type, aliases, relations, provenance, body hash를 가진다.
  • migration과 release가 같은 입력에서 같은 결과를 만든다.
  • 검색 결과가 source node, heading, provenance를 포함한다.

품질·운영 기준

  • schema·hash·참조 오류는 release를 중단하고 경고는 명시적으로 보존한다.
  • Windows 로컬 경로와 민감 정보는 ingestion 전에 차단한다.
  • 공개 성과 수치는 방문자가 읽을 수 있는 보고서에서 다시 확인되어야 한다.

왜 이렇게 구성했나

  1. authoring과 semantic release 분리

    YAML은 사람이 유지하고 JSON-LD·OWL·SHACL은 기계가 생성하게 해 수동 동기화 오류를 줄였습니다.

  2. 경고를 숨기지 않는 release gate

    미해결 외부 관계를 임의 연결하지 않고 데이터 부채로 보존해야 검색 근거를 신뢰할 수 있기 때문입니다.

  3. hybrid retrieval과 인용 경계

    벡터 유사도만으로는 정확한 용어·관계·출처를 함께 만족시키기 어려워 단계별 검색과 reranking을 사용했습니다.

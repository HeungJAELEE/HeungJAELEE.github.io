팀이 만들려던 전체 프로젝트

팀은 자동차 자동조립 시나리오를 Indy7 실물 로봇으로 시연하고, 로봇 명령·상태·작업이력을 한 흐름으로 연결하는 구성을 검토했습니다. 저는 전체 프로젝트를 기획하고 로봇 제어와 시스템 인터페이스의 연결 순서를 설계했습니다.

자동차 조립 시나리오와 실물 Indy7 시연은 팀 결과이며 보고서는 팀장이 작성했습니다. 이후 공개 코드로 확장한 PC-HMI, Robot Controller, MQTT·DB, 읽기 전용 Web Twin과 Conty JSON 호환 구조는 제가 맡은 실무입니다.

명령과 상태가 전체 시스템을 통과하는 흐름

flowchart LR HMI["PC-HMI
MY CORE"] --> CMD["robot/command
MY CORE"] CMD --> RC["Robot Controller
MY CORE"] RC --> ROBOT["Indy7
TEAM PHASE"] ROBOT --> RC RC --> STATE["robot/realtime
MY CORE"] STATE --> UI["HMI 상태화면
PERSONAL EXTENSION"] STATE --> DB["DB Worker
PERSONAL EXTENSION"] STATE --> TWIN["읽기 전용 Web Twin
PERSONAL EXTENSION"] PLC["PLC 상태변화
FUTURE/SHARED"] --> BRIDGE["Read-only PLC Bridge
PERSONAL EXTENSION"] BRIDGE --> STATE TWIN -.-> OMNI["Omniverse·AI Teaching
FUTURE"]

팀 단계와 개인 확장을 같은 완료상태로 묶지 않았습니다. TEAM PHASE는 실물 로봇 시연, MY CORE는 제가 맡은 로봇 제어·연동, PERSONAL EXTENSION은 공개 코드 확장, FUTURE는 미구현 후속 범위입니다. PLC Bridge는 제어가 아니라 상태변화 이벤트를 읽어 MQTT로 보내는 역할입니다.

제가 맡은 핵심은 로봇 명령의 소유권을 한곳에 모으는 일이었습니다

01

MY CORE

명령·상태·표시의 책임을 분리했습니다

여러 화면과 서비스가 로봇 소켓을 직접 잡지 않도록 Robot Controller가 명령을 전담합니다.
flowchart LR A["HMI 운전 요청
command_id
MY CORE"] --> B{"Robot Controller
MY CORE"} B -->|수락| C B -->|fault·queue full| F C["accepted"] --> D["IndyDCP 명령 실행"] --> E["result·realtime"] F["error·거부"] --> G["UI·DB·Web Twin"] E --> G
  • Python Robot Controller만 IndyDCP Socket을 소유하도록 구성했습니다.
  • HMI는 command_id가 포함된 운전 요청을 보내고, Controller가 accepted·result·error·connection 상태를 구분합니다.
  • fault 상태나 명령 Queue가 가득 찬 경우에는 새 명령을 거부하도록 했습니다.
  • 로봇의 관절·TCP·Torque·I/O·busy·error·collision·emergency 상태는 반복 메시지로 전달합니다.
  • DB Worker와 Web Twin은 로봇에 직접 연결하지 않고 MQTT 상태를 저장하거나 읽기 전용으로 표시합니다.

Teaching JSON은 다시 저장해도 참조가 유지되도록 했습니다

02

DATA CONTRACT

화면에서 모르는 필드도 버리지 않는 Round-trip 정책을 적용했습니다

일부 값만 편집해도 프로그램 트리와 Waypoint 참조가 깨지지 않도록 원본 의미를 보존했습니다.

확인한 위험

  • 로봇 작업은 프로그램 트리의 id/pId, Move·Waypoint 참조, Tool·TCP, 속도, 단위와 I/O 필드가 서로 연결됩니다.
  • PC 편집기가 아는 필드만 다시 저장하면 화면은 정상이어도 티치펜던트에서 참조가 깨질 수 있습니다.

구현과 확인

  • Parser와 Serializer의 책임을 나누고, 알 수 없는 원본 필드도 그대로 보존했습니다.
  • 원본 로드 → 일부 편집 → 저장 → 다시 로드 → 트리·참조·단위 비교 순서로 확인했습니다.
  • Setting/Teaching, Dry Run Recording과 Auto/Monitor 화면을 작업 목적에 따라 나눴습니다.
  • 공개 근거마다 점검 파일 수가 달라 정확한 수량은 성과에서 제외했습니다.

정상 동작과 거부 조건을 따로 남겼습니다

  1. Setting/Teaching에서 작업 설정과 티칭 정보를 준비합니다.
  2. Auto/Monitor가 Robot Controller에 운전 요청을 보냅니다.
  3. Controller가 명령을 수락하거나 fault·queue 상태에 따라 거부합니다.
  4. 수락한 명령은 IndyDCP로 실행하고 결과와 실시간 상태를 MQTT로 전달합니다.
  5. DB Worker는 이력을 저장하고 Web Twin은 Robot A·B·C 상태를 읽기 전용으로 표시합니다.

확인된 예외는 명령 수락·결과·오류·연결 상태의 분리와 fault·queue full 거부까지입니다. 사용자별 권한, 중복명령의 전체 범위, 장시간 재접속과 장애복구를 완료했다는 의미는 아닙니다.

팀 결과와 현재 단계

팀은 자동차 조립 시나리오와 Indy7 실물 로봇 시연을 연결했습니다. 저는 전체 프로젝트 기획과 로봇 제어·통합 구조, 명령·상태 경로를 맡았습니다. 공개 main@a6c08e5에서 HMI, Robot Controller, MQTT·DB, 읽기 전용 Web Twin, PLC Bridge와 JSON Round-trip 구조를 확인했습니다.

후속 Gate는 물리 PLC를 포함한 장시간 전체 E2E, 재접속, 중복명령, 권한과 장애복구 검증입니다. Omniverse와 AI Teaching은 구현 완료가 아니라 확장 방향으로 남겨 두었습니다.

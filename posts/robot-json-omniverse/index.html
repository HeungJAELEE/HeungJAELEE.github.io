팀이 해결하려던 제조 자동화문제

자동조립에서는 로봇이 움직이는 것만으로 충분하지 않습니다. 어떤 화면이 명령을 보냈는지, 로봇이 명령을 수락했는지, 실제 동작결과와 오류가 무엇이었는지, 제품과 작업이력이 어디에 남는지 연결돼야 합니다.

팀은 Indy7을 이용한 자동차 조립 시나리오를 실물로 시연하고 로봇 운전·상태·작업이력을 한 흐름으로 연결하려 했습니다. 저는 전체 프로젝트를 기획하고 로봇동작, Controller 통신과 HMI 명령·상태 흐름을 맡았습니다. 최종보고서는 팀장이 작성했습니다.

명령과 상태가 흐르는 구조

flowchart LR HMI["PC-HMI\n운전 요청"] --> CMD["command_id\n명령 메시지"] --> RC["Robot Controller\n단일 IndyDCP Socket"] --> ROBOT["Indy7 Robot"] ROBOT --> RC --> STATE["accepted·result·error·realtime"] STATE --> UI["HMI 상태"] STATE --> DB["DB Worker\n작업이력"] STATE --> TWIN["읽기전용 Web Twin"] PLC["PLC 상태변화"] --> BRIDGE["Read-only Bridge"] --> STATE

왜 Robot Controller가 명령을 전담했는가

여러 UI와 서비스가 로봇 Socket을 직접 소유하면 명령충돌과 응답혼선이 생길 수 있습니다. 그래서 Python Robot Controller가 IndyDCP Socket을 하나만 소유하고 HMI·MQTT 요청을 순서대로 처리하게 했습니다.

  • HMI 요청마다 command_id를 부여했습니다.
  • Controller는 accepted·result·error·connection 상태를 구분했습니다.
  • fault 또는 Queue full에서는 새 명령을 거부했습니다.
  • 좌표·Torque·I/O·busy·error·collision·emergency 상태를 반복 메시지로 전달했습니다.
  • DB Worker와 Web Twin은 로봇을 직접 제어하지 않고 상태와 이력을 저장·표시했습니다.

이 구조를 통해 화면 연결상태와 실제 로봇 명령성공을 같은 의미로 오해하지 않도록 했습니다.

Teaching JSON을 그대로 보존해야 했던 이유

로봇 작업파일은 프로그램 트리의 id/pId, Move·Waypoint 참조, Tool·TCP, 속도·단위와 I/O 필드가 서로 연결됩니다. PC 편집기가 아는 필드만 새로 저장하면 화면은 정상처럼 보여도 티치펜던트의 참조가 깨질 수 있습니다.

  1. 원본 JSON을 Parser로 읽었습니다.
  2. 화면에서 필요한 일부 값만 수정했습니다.
  3. 화면이 모르는 원본필드도 그대로 유지했습니다.
  4. 저장 후 다시 로드해 트리·참조·단위를 비교했습니다.

Setting/Teaching, Dry Run Recording과 Auto/Monitor 화면은 작업목적에 따라 나눴습니다.

정상동작과 오류를 확인하는 순서

  1. Setting/Teaching에서 작업과 티칭정보를 준비합니다.
  2. Auto/Monitor가 Controller에 운전요청을 보냅니다.
  3. Controller가 명령을 수락하거나 fault·queue 상태에 따라 거부합니다.
  4. 수락한 명령은 IndyDCP로 실행하고 결과와 실시간 상태를 MQTT로 보냅니다.
  5. DB Worker는 이력을 저장하고 Web Twin은 Robot A·B·C 상태를 읽기전용으로 표시합니다.
  6. 오류와 연결상태는 명령결과와 분리해 화면과 기록에 남깁니다.

팀 결과와 향후 적용

팀은 자동차 조립 시나리오와 Indy7 실물시연을 연결했습니다. 개인 확장에서는 HMI·Robot Controller·MQTT·DB·읽기전용 Web Twin과 JSON Round-trip 구조를 연결했습니다. 향후에는 물리 PLC를 포함한 장시간 E2E, 재접속·중복명령·권한·장애복구를 검증하고, 같은 명령·상태계약 위에 Omniverse 시각화와 AI Teaching을 연결할 수 있습니다.

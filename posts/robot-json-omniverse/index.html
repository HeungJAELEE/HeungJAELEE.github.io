팀 경계

제가 주도한 대표 로봇 프로젝트입니다. 전체 비전은 팀과 함께 정리하고 실제 구현은 소수 핵심 인원이 나눠 맡았지만, 로봇 프로젝트의 목표·인터페이스·통합 순서와 단계별 진행은 제가 이끌었습니다.

공개 범위: 내부 네트워크·로컬 경로·기본 인증 형태의 설정을 공개하지 않도록 외부 저장소 버튼을 보류했습니다.

제어권과 관찰권을 나눈 일반적인 로봇 데이터 흐름으로 설명합니다.

먼저 밝혀 둘 현재 단계

이 사례는 실물 Indy7 연동 시험을 포함해 개발한 교육·개발 프로토타입입니다. 작업 프로그램을 PC에서 읽고 편집하는 CustomTkinter HMI와 Robot Controller·MQTT·이력 저장·PLC 감시·웹 트윈을 분리했습니다. 공개 소스에서 확인되는 트윈은 브라우저용 읽기 전용 모니터입니다. NVIDIA Omniverse USD 어댑터는 후속 방향이며 완료된 연동이나 생산 배포로 설명하지 않습니다.

로봇 프로그램은 좌표 목록만이 아닙니다. Tool·TCP, Waypoint, 이동 설정과 program tree가 서로 참조합니다. 편집기가 모르는 필드를 지우거나 참조를 바꾸면 화면에서는 정상처럼 보여도 티치펜던트에서 프로그램이 깨질 수 있습니다. 그래서 이 실습의 출발점은 화려한 3D 장면이 아니라 로드 → 편집 → 저장 → 재로딩 → 참조 비교입니다.

전체 팀 시스템과 실제 기술 스택

전체 애플리케이션은 Windows PC에서 HMI를 실행하고 Docker Compose가 통신·저장·모니터링 서비스를 나누는 구조입니다. 아래 구성은 프로젝트 전체를 설명하기 위한 팀/시스템 범위이며 모두를 개인 단독 구현으로 표시하지 않습니다.

Git에서 읽는 권장 순서

  1. readme.md와 BEGINNER_RUN_GUIDE.md로 화면, 실행 진입점과 배포 의도를 파악합니다.
  2. ROBOT_COMMUNICATION_FLOW.md로 명령·상태·DB·PLC·트윈의 소유권을 먼저 고정합니다.
  3. frontend/run_ui_only.py → frontend/presentation/ui/main_window.py 순서로 앱이 어떤 페이지를 만드는지 확인합니다.
  4. frontend/presentation/ui/robot_hmi/robot_hmi_view.py와 frontend/infrastructure/repositories/teaching_repository_impl.py를 함께 읽어 JSON 트리, 원본 보존과 실행 버튼의 차이를 확인합니다.
  5. frontend/core/domains/robot/communication/client_manager.py → frontend/core/domains/robot/use_cases/robot_control_usecase.py → backend/robot_controller/src/main.py 순서로 direct/gateway 선택, 인터록과 실제 명령 큐를 추적합니다.
  6. backend/db_worker/src/main.py, backend/plc_bridge/src/main.py, backend/digital_twin/src/main.py와 web/index.html을 읽어 관찰·이력 소비자가 물리 명령에서 분리됐는지 확인합니다.
  7. 선택형 Vision 흐름이 필요할 때만 backend/vision_yolo/를 추가로 읽습니다.
  8. 마지막에 backend/docker-compose.yml과 배포 문서를 봅니다. 환경별 설정 예시는 아키텍처 계약이 아니며, 공개·운영 전에 민감 설정과 비이식 경로를 별도로 점검해야 합니다.

처음 실행한 사용자가 만나는 화면

앱은 상단의 네 페이지 탭, 로봇 연결 버튼, 서비스 관리 패널과 하단 로그로 구성됩니다. 시작 화면은 Page 2 Setting / Teaching입니다.

화면 사용자가 보는 것 주요 조작 물리 제어 가능성
Page 2 · Setting / Teaching 로봇별 Conty JSON 트리, 명령 팔레트, 노드별 설정, Jog 패널 새 파일, 불러오기, 저장, 사본 내보내기, 노드 편집, 가상 Play, 실행·정지 가상 Play는 화면 검토이지만 실행, Jog, TCP·DO 설정과 연결은 실제 명령 경로가 될 수 있음
Page 3 · Dry Run Recording 반복 횟수, 샘플 주기, 가상 DI 0~31, 로봇별 cycle·관절·좌표·토크, JSONL/MySQL 저장 설정 가상 DI 설정, 로봇별 기록 시작·정지, 저장 위치와 DB 연결 확인 이름과 달리 무동작 시뮬레이터가 아님. 연결된 로봇의 모션은 수행하고 DI/DO·툴 출력을 가상화해 진단 데이터를 수집
Page 1 · Auto / Monitor 3대 로봇·레일·공정의 3D 뷰, TCP·Joint·위험 가이드, 프로그램 상태 로봇 선택, Home, Zero, Error Reset, 프로그램 실행·정지, 궤적 초기화 데스크톱 HMI 안의 제어 가능 화면
Page 4 · AI Teaching 자연어 명령 초안을 만드는 실험 화면 초안 검토 핵심 검증 흐름 밖의 실험 기능이며 로봇 안전 검증 근거로 사용하지 않음
별도 Web Twin 로봇별 상태, 최근 이벤트, 공정 장면 상태 관찰 읽기 전용. Home·Zero·Stop 같은 제어 버튼 없음

여기서 가장 중요한 구분은 Page 1 데스크톱 화면과 별도 Web Twin이 같은 것이 아니라는 점입니다. Page 1은 HMI 제어권 안에 있고, Web Twin과 향후 Omniverse 어댑터만 관찰 전용 경계에 둡니다.

사용자가 실제로 진행하는 순서

  1. Offline에서 JSON부터 연다. Page 2에서 로봇 연결 없이 파일을 불러오고 info, wpList, program, moveList의 참조를 트리로 확인합니다.
  2. 노드를 편집하고 가상 Play로 순서를 본다. Pick·Place·Loop·DI/DO 같은 노드를 선택하면 우측 설정창과 Jog 패널이 바뀝니다. 이 단계에서는 저장 전 변경 범위와 프로그램 순서를 확인합니다.
  3. 저장 후 다시 읽는다. 알려진 필드만 새로 구성하고 나머지 원본 블록을 보존한 뒤, 저장 파일을 다시 로드해 노드 ID와 Waypoint·move 참조가 이어지는지 확인합니다.
  4. 연결 방식을 명시적으로 고른다. 운영형 mqtt 모드에서는 HMI가 명령 요청만 보내고 Robot Controller가 IndyDCP 소켓을 소유합니다. direct는 Docker 없이 랩에서 HMI가 직접 접속하는 별도 시험 경로이므로, 단일 Controller 구조와 같은 것으로 간주하지 않습니다.
  5. 실기 전 상태를 확인한다. 로봇 설정·통신 체크·서비스 관리에서 대상 로봇, MQTT, DB와 PLC 상태를 개별 확인합니다. 앱 창이 열렸다는 사실만으로 설비가 연결된 것은 아닙니다.
  6. 필요할 때만 실제 명령을 보낸다. Page 2의 실행·Jog 또는 Page 1의 빠른 제어는 쓰기 경로입니다. 화면의 E-STOP 버튼은 명령 버튼일 뿐, 검증된 하드웨어 비상정지 회로를 대신하지 않습니다.
  7. Page 3에서 진단 기록을 남긴다. 이 모드는 가상 DI로 분기를 시험하고 DO·툴 출력을 생략하지만, 연결된 로봇의 이동과 상태 수집은 계속합니다. 따라서 안전 구역·저속·감독·정지 기준을 갖춘 실기 절차가 필요합니다.
  8. Page 1과 Web Twin에서 상태를 본다. 작업자는 HMI에서 제어와 현재 상태를 함께 보고, 다른 관찰자는 Web Twin에서 동일한 robot/realtime과 최근 이벤트만 봅니다.

구성요소 맡는 일 맡지 않는 일
PC-HMI JSON 탐색·편집, 가상 Play, 사용자 명령 요청, 상태와 로그 표시 MQTT 운영 모드에서 별도 물리 소켓을 추가로 소유하지 않음

Web Twin MQTT 상태·연결·결과·PLC 이벤트를 WebSocket으로 전달하고 브라우저에 표시 물리 로봇 명령
Omniverse adapter 향후 robot/realtime을 USD 관절·좌표에 매핑하는 읽기 전용 후보 현재 저장소에서 완료된 구현·검증 결과가 아님

쓰기 경로와 읽기 경로

[쓰기 경로]
PC-HMI Page 1·2 ──command_id + 명령 요청──> MQTT
    └──> Robot Controller (IndyDCP 단일 소유자) ──물리 명령──> Indy7

[읽기 경로]
Indy7 ──상태·결과──> Robot Controller
    └──accepted / result / realtime / connection / error──> MQTT
        ├──> PC-HMI
        ├──> DB Worker (이력 저장)
        └──> Web Twin (읽기 전용)

PLC master ──신호 읽기──> PLC Bridge (감시 전용) ──edge event──> MQTT
MQTT - -후속 adapter- -> Omniverse / USD (미완료·읽기 전용 목표)

근거: 공개 저장소의 통신 문서와 HMI·Robot Controller·DB Worker·PLC Bridge·Web Twin 소스를 2026-07-31에 다시 확인해 일반화한 구조입니다. 화면이나 실행 결과를 새로 만들어 낸 그림이 아닙니다.

command, accepted, result, realtime, connection과 error를 분리하면 “요청이 Broker에 들어갔다”와 “로봇 동작이 끝났다”를 구분할 수 있습니다. 다만 command_id가 있다는 사실만으로 멱등성이 생기지는 않습니다. 현재 Robot Controller에는 로봇별 큐와 완료 확인이 있지만, 재전송된 같은 명령을 영구 저장소 기준으로 제거하는 검증은 남아 있습니다.

확인된 출력과 남은 한계

구분 확인된 내용 해석
저장소 소스 4개 HMI 페이지, Robot Controller, DB Worker, PLC Bridge와 Web Twin 구현이 존재 구성요소와 책임 분리는 코드에서 확인됨
JSON 재검증 기록 공개된 한 시험 fixture에서 63개 program node와 고유 ID가 export 뒤 유지됨 해당 fixture의 결과이며 모든 firmware 호환 증명은 아님
분기·기록 공개 Dry Run 보고서에 가상 DI 조합별 분기, 관절·좌표·토크 샘플과 로컬·MySQL 기록 확인이 남아 있음 화면과 기록 경로의 실제 사용 근거
장애 관찰 같은 보고서에서 실제 이동 중 충돌 플래그와 장시간 반복 미완료가 기록됨 성공 사례만 선별하지 않았으며 생산 준비 완료가 아님
Web Twin 소스상 상태·연결·최근 이벤트를 읽고 표시하며 명령 발행 UI가 없음 읽기 전용 경계가 코드에서 확인됨
Omniverse USD adapter, 관절 매핑과 좌표 보정 코드가 공개 저장소에서 확인되지 않음 완료된 Omniverse 통합으로 주장하지 않음

이번 문서 작업에서는 로봇, Docker, MySQL, PLC나 Web Twin 런타임을 새로 실행하지 않았습니다. 확인 근거는 공개 저장소의 현재 소스와 날짜가 있는 공개 Dry Run 보고서입니다.

남은 검증은 여러 Indy7 firmware의 JSON round-trip 회귀, 명령 인증·권한, 중복 명령 멱등성, Broker topic ACL, 장시간 재접속, DB 재전송과 중복 기록, 실제 설비 hardware-in-the-loop, 그리고 read-only Omniverse USD adapter입니다. 비상정지와 안전 인터록은 HMI 버튼이나 가상 위험 가이드가 아니라 검증된 로봇·PLC 안전 시스템의 책임으로 유지해야 합니다.

구성 이유와 작업 흐름

제가 주도한 대표 로봇 프로젝트입니다. 로봇 프로젝트의 요구사항·통합 순서·단계별 진행을 이끌며 JSON 편집, 물리 제어, 이벤트·DB·PLC·디지털 트윈을 하나의 동작 흐름으로 구성했습니다.

Problem

Conty JSON 일부만 수정하면 Waypoint·program·move 참조가 손상될 수 있고, 여러 클라이언트가 IndyDCP 소켓을 직접 소유하면 명령 책임과 상태 시간이 분산됩니다.

Goal

원본 보존형 JSON round-trip과 단일 Robot Controller를 중심으로 HMI, DB, PLC, twin이 명시적 이벤트를 공유하는 구조를 만드는 것입니다.

Success

load–edit–save–reload에서 참조가 보존되고, 물리 소켓이 하나이며, offline/direct/gateway 모드와 배포 문서가 재현 가능하면 성공입니다.

범위와 경계

포함 범위

  • Conty/APK JSON round-trip과 참조 무결성
  • IndyDCP 단일 소유권, MQTT command/state 분리
  • CustomTkinter HMI, MySQL worker, PLC bridge, read-only web twin

제외·미검증 범위

  • Omniverse가 검증된 생산 운영 화면이라는 주장
  • 공개 측정이 없는 latency·uptime·충돌 감소 수치
  • 디지털 트윈에서 물리 로봇 명령을 직접 실행하는 구조

구현·검증 기준

해야 할 일

  • 알 수 없는 JSON field와 참조를 보존하고 저장 후 재로딩 검증을 수행한다.
  • Robot Controller만 물리 IndyDCP 소켓을 소유한다.
  • command, result, realtime, connection, error event를 분리한다.

품질·운영 기준

  • Offline UI에서 로봇 없이 JSON과 화면 흐름을 검증할 수 있다.
  • DB와 twin은 명령 경로가 아니라 상태 소비자로 동작한다.
  • 공개 전 내부 네트워크·경로·기본 설정 형태의 값을 제거하고 다시 검사한다.

왜 이렇게 구성했나

  1. 원본 보존형 round-trip

    편집기가 모르는 vendor field를 삭제하지 않아야 teach pendant 호환성을 유지할 수 있기 때문입니다.

  2. IndyDCP 소켓 단일 소유권

    동시 명령과 상태 race를 막고 물리 제어 책임을 한 서비스에서 감사하기 위해서입니다.

  3. 디지털 트윈은 read-only

    시각화 계층의 오류가 물리 로봇 명령으로 이어지지 않도록 안전 경계를 분리했습니다.

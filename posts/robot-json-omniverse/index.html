    구분내용
    프로젝트QR·Vision·협동로봇·PLC/SCADA·DB를 연결한 10인 교육 팀 자동차 공장 PoC
    해결 문제로봇별 동작은 가능해도 제품 식별·공정 완료·검사 결과·적재 이력이 연결되지 않으면 전체 공정 상태를 추적하기 어려움
    내가 주도한 범위프로젝트 목표·공정 시나리오·시스템 구성·분과 연결 순서의 전체 기획
    직접 실무Indy7 로봇 제어, 공정 간 명령·상태 연동, 로봇 프로그램과 통합 흐름 검증
    팀 경계Vision 모델·PLC Ladder·SCADA/DB 상세 구현은 담당 팀원, 보고서·일정·최종 발표는 팀장
    확인된 결과QR 저장 → 차체·창문 결합 → Vision 검사 → 양품 적재/불량 통과의 실물 통합 시연
    후속 확장PC-HMI·Conty JSON·IndyDCP·MQTT·이력·읽기 전용 Web Twin은 이후 별도 공개 코드로 확장

    이 표에서 읽어야 할 판단: 전체 프로젝트의 문제와 시스템 연결 순서는 제가 기획했고, 직접 구현의 중심은 Indy7 제어와 공정 간 연동입니다. Vision·Ladder·SCADA 상세 구현과 팀장의 보고서·발표 역할은 분리해 설명합니다.

    Project SOW — 공개 기준 업무범위

    발표자료에는 별도의 정식 SOW 문서가 없으므로, 발표자료의 목표·산출물·역할을 기준으로 공개용 업무범위를 재구성했습니다.

    목적: QR로 식별한 제품이 Robot A·B·C의 조립·검사·적재 공정을 통과하는 동안, 명령·상태·Vision 판정과 MySQL 이력이 동일 제품 기준으로 이어지게 합니다.

    성공 기준: product_sn 저장, Robot A·B 순차 조립, Vision 결과의 PLC 분기 반영, Robot C 적재 여부 결정, SCADA·DB 상태 확인과 역할 귀속 구분입니다.

    제품 한 대가 이동한 실제 공정

    flowchart LR Q["QR 제품 시리얼"] --> DB["MySQL 이력"] DB --> A["Robot A 차체 결합"] A --> B["Robot B 창문 결합"] B --> V["YOLO 결합 후 검사"] V -->|양품| C["Robot C 적재"] V -->|불량| NG["통과·분리"] A --> S["PLC·SCADA 상태"] B --> S V --> S C --> S S --> T["Digital Twin 확인"]

    1. QR 시리얼을 추적 기준으로 사용

    제품 투입 시 QR에서 product_sn을 읽고 MySQL에 기록했습니다. 제품 시리얼, 설비명, 기록 시각, Tray 번호, Vision 결과와 불량 유형을 저장하는 구조입니다.

    2. Robot A·B가 차체와 창문을 결합

    Robot A는 차체 결합, Robot B는 창문 결합을 담당했습니다. 로봇 제어에서는 좌표뿐 아니라 이전 공정 완료, 제품 도착, Ready·Busy·Error, 완료 신호와 재시작 위치를 함께 맞췄습니다.

    3. 1차 Vision — 차량 색상 분류

    초기 모델은 r, g, b 세 클래스를 분류했습니다.

    4. 2차 Vision — 정상·균열 후보 검사

    후속 모델은 r/g/b_normal과 r/g/b_crack 여섯 클래스로 확장했습니다. 실제 불량 데이터를 충분히 확보하기 어려웠으므로 성능 수치보다 판정 결과가 PLC 분기와 적재로 전달되는 흐름을 중심으로 봅니다.

    Vision 수치 해석

    표기공개 해석
    3클래스 F1 1.00교육 데이터·평가 분할의 결과이며 실제 불량 일반화 성능이 아님
    all classes 1.00 at 0.877최대 F1 1.00이 Confidence 0.877에서 관찰됐다는 의미이며 F1 Score가 0.877이라는 뜻이 아님

    평가 판단: 이 수치는 교육 데이터에서 모델과 공정 분기 연결을 확인한 근거입니다. 실제 불량 대표성, 독립 평가셋과 Confusion Matrix가 확보되지 않았으므로 생산 품질 승인이나 양산 성능으로 사용하지 않습니다.

    5. Robot C의 양품 적재와 불량 통과

    Vision 결과가 양품이면 Robot C가 적재하고, 불량이면 적재하지 않고 통과·분리하는 흐름을 시연했습니다. 완료 판단은 Vision 판정, PLC 분기, Robot C 결과, SCADA 상태와 DB 이력이 일치하는지로 봅니다.

    6. Vision·통신 Ladder

    원 프로젝트와 후속 공개 코드 확장

    구분원 발표자료 기반 프로젝트이후 공개 코드 확장
    중심 문제QR–로봇–Vision–PLC/SCADA–DB 통합명령·상태·이력·트윈의 책임 분리
    로봇 프로그램팀 시연용 공정 시퀀스Conty JSON 보존·편집과 PC-HMI
    통신PLC·설비·SCADA/DB 연동IndyDCP, MQTT, Robot Controller, DB Worker, PLC Bridge
    Digital Twin실물 셀의 공정 시각화데스크톱 HMI와 읽기 전용 Web Twin
    Omniverse발전 방향완료된 USD Adapter는 공개 저장소에서 확인되지 않음
    귀속10인 팀 통합 시연공개 코드로 재확인 가능한 후속 개발

    경계 해석: 원 프로젝트의 완료 결과는 실물 자동차 조립 셀의 통합 시연입니다. PC-HMI·MQTT·Web Twin은 이후 공개 코드 확장이며, Omniverse는 완료 성과가 아니라 남은 확장 방향으로 구분합니다.

    보조 분석과 미검증 범위

    • Pi 5 FPS 5, Pi 5 + Hailo-10H FPS 18은 특정 데모 조건의 값이며 범용 성능 보증이 아닙니다.
    • MES·ERP는 발전 방향이며 운영계 구축 성과가 아닙니다.
    • Omniverse·Isaac Sim·Physical AI는 후속 목표이며 실물 동기화 완료 성과가 아닙니다.
    • 3/6클래스 Vision 결과는 교육 데이터 기준이며 실제 품질 승인 근거가 아닙니다.

    면접 답변 기준

    가장 어려웠던 점은 무엇입니까?

    로봇 한 대를 움직이는 것보다 QR 시리얼, 로봇 완료 상태, Vision 판정과 DB 기록이 같은 제품을 가리키게 만드는 일이 더 어려웠습니다. 그래서 전체 공정과 인터페이스를 먼저 정의하고 각 팀 구현을 그 기준에 맞춰 연결했습니다.

    직접 맡은 범위는 어디입니까?

    전체 프로젝트 기획과 Indy7 로봇 제어·공정 연동이 제 주 범위였습니다. Vision 모델, Ladder와 SCADA 상세 구현은 팀원이 수행했고 보고서와 최종 발표는 팀장이 담당했습니다.

    F1 수치를 생산 성능으로 사용할 수 있습니까?

    사용하지 않습니다. 3클래스 그래프는 교육 데이터에서 최대 F1 1.00이 Confidence 0.000, 6클래스는 최대 F1 1.00이 Confidence 0.877에서 나타난 결과입니다. 원시 데이터 분할, 실제 불량 대표성, Confusion Matrix와 현장 검증 없이 생산 품질 성과로 해석하지 않습니다.

    후속 PC-HMI·MQTT 구조를 만든 이유는 무엇입니까?

    원 프로젝트에서는 여러 계층을 연결했지만 명령·상태·결과·이력의 소유권이 충분히 명확하지 않았습니다. 이후 Robot Controller가 물리 명령을 소유하고 HMI·DB·PLC Bridge·Web Twin이 각 책임을 나누도록 확장했습니다.

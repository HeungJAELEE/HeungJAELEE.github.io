기존 Indy7 Teaching JSON을 PC-HMI에서 구조화하고, Robot Controller가 수집한 J1–J6 상태를 Forward Kinematics로 3D Twin에 반영하는 레거시 데이터 연동 구조를 구현했습니다.

1. 프로젝트 배경과 기술 PM 역할

Pain Point

기존 Robot 작업 프로그램은 티치펜던트와 개별 JSON 파일에 고립되어 있었습니다. 작업순서·좌표·I/O 조건과 실제 Robot 상태가 서로 분리되어 PC-HMI 편집, 공정 전체 제어, 3D 상태관제와 후속 AI 활용으로 연결되지 못했습니다.

해결 목표

  • 기존 Teaching Data를 폐기하지 않고 PC에서 읽기·수정·재저장 가능한 데이터 자산으로 전환
  • QR → Robot A → Vision 1 → Robot B → Vision 2 → Robot C 전체 공정의 입력·완료·오류 Handshake 통합
  • 실제 Robot의 Joint·TCP·실행상태를 3D 공장배치와 연결
  • 후속 Simulation·AI Agent가 동일한 공정·상태 인터페이스를 사용할 수 있는 기반 설계

기술 PM·아키텍처 수행

공식 팀장·최종 보고서 작성과 별도로, 제조공정과 시스템 통합을 담당하는 Technical PM / Robot·Digital Twin Integration Lead 역할을 수행했습니다.

2. 레거시 데이터 연동 아키텍처

팀 PoC에서는 PLC가 공정 Sequence를 지휘했습니다. 후속 공개 코드에서는 HMI·Web이 물리 Robot에 직접 명령하지 않고 Robot Controller가 IndyDCP 실행권한을 단독 소유하도록 제어경로를 분리했습니다.

flowchart LR JSON["Indy7 Teaching JSON"] --> HMI["PC-HMI
Load·Edit·Save"] HMI --> CMD["robot/command
command_id"] PLC["PLC Sequence
팀 구현"] --> HS["Start·Ready·Busy
Complete·Error"] HS --> CMD CMD --> RC["Robot Controller
명령·Queue·Fault 판정"] RC --> DCP["IndyDCP"] --> ROBOTS["Robot A · B · C"] ROBOTS --> RT["Joint·TCP·Torque·I/O
Busy·Error·Connection"] RT --> RC --> MQTT["MQTT State Bus"] MQTT --> TWIN["3D Digital Twin
Read-only Web Twin"] MQTT --> DBW["DB Worker"] --> MYSQL[("MySQL 이력")] PLC -. "후속 공개코드: 상태 Read" .-> MQTT

이 구조로 프로그램 원본, 물리 제어권한, 실시간 상태, 이력 저장, 3D 표시를 분리했습니다. 공정 확장 시 Vision·PLC·DB가 Robot 내부 구현을 직접 참조하지 않고 정의된 상태와 이벤트를 통해 연결됩니다.

3. 핵심 엔지니어링 구현

① [Data Engineering] Teaching JSON 구조 분석·Round-trip

Conty Teaching JSON의 program, moveList, wpList와 id/pId 관계를 분석해 평면 Node를 작업 Tree로 재구성했습니다.

  • Move·Pick·Place·Wait·If·Loop·I/O 명령의 작업순서 해석
  • Joint·Task 좌표, Speed, Tool/TCP, Reference Frame 연결
  • PC-HMI Tree에서 Node·Waypoint 편집과 저장
  • 미사용 Waypoint·제조사 고유필드 보존 후 수정 필드만 병합
  • Parent·Move–Waypoint·단위·TCP 참조 검증 후 Export
Teaching JSON
→ Program Node Tree
→ Move·Waypoint·Tool/TCP 참조해석
→ PC-HMI 편집
→ Reference Validation
→ JSON 재저장
→ Robot Controller 실행요청

② [Control Architecture] Robot Controller 중심 제어권한 분리

Robot A/B/C별 명령 Queue와 상태를 분리하고 command_id를 기준으로 요청부터 완료까지 추적했습니다.

  • robot/accepted : 명령 수락·Queue 상태
  • robot/result : 완료·실패 결과
  • robot/error : Fault·통신·실행 오류
  • Emergency·Collision·Robot Error 상태의 Motion 명령 차단
  • Joint·Task Motion 완료조건과 Timeout 판정
  • J1–J6·TCP·Torque·DI/DO·Busy·Connection 실시간 배포

PC-HMI는 실행을 요청하고, Robot Controller가 연결상태·Fault·Queue·완료조건을 판정한 뒤 IndyDCP로 물리 명령을 전송하도록 구성했습니다.

③ [Digital Twin] Forward Kinematics 기반 3D 상태 동기화

실제 Robot에서 수집한 J1–J6 Joint 값을 DH Parameter 기반 Forward Kinematics로 계산하고, TCP Offset과 Robot별 설치 Offset을 반영했습니다.

J1–J6 Joint State
→ DH Transformation Matrix
→ Joint·Flange 위치
→ TCP Offset
→ Robot 설치 Offset
→ 3D Pose·TCP·Trajectory
  • Robot A/B/C 3D 자세와 TCP 위치 표시
  • 공장 Rail·차량·공정 Station 배치
  • Joint·TCP·Busy·Complete·Error·Connection 상태 연결
  • TCP 이동궤적과 공정 위치 시각화
  • Web Twin은 상태관제 전용, 물리 제어는 PC-HMI·Robot Controller에 집중

5. 차기 플랫폼 설계 방향 — Omniverse·AI Agent

현재 구축한 Teaching Data → Command → Realtime State → History → Twin 계약을 다음 플랫폼 단계의 입력으로 사용합니다.

다음 단계설계 방향
Omniverse·Isaac SimRobot·설비 Asset, 좌표계, Joint/TCP State Adapter 구축
Shadow Twin물리 명령과 Simulation 명령 분리, 충돌·도달성·Cycle 사전검증
AI Agent공정상태·Action·Reward·제약조건 정의, 제안·Simulation 평가부터 적용
운영 Gate권한·중복명령·통신복구·안전 Interlock·물리 E2E 검증

목표는 단순 3D 모니터링이 아니라, 레거시 Robot Data를 재사용해 공정 변경안을 Simulation에서 먼저 검증하고 AI Agent의 제어전략을 안전하게 평가하는 제조 AI 플레이그라운드로 확장하는 것입니다.

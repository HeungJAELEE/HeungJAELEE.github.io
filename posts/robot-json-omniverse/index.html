프로토타입

Indy7 로봇 제어와 상태 확인 시스템

한 화면에서 로봇을 제어하고 작업 상태와 이력을 확인할 수 있도록 연결한 통합 프로토타입

맥락

담당 범위
시스템 목표·인터페이스·통합 순서 주도, 핵심 코드와 책임 경계 구현

사용자·구현·검증 요약

사용자 문제
HMI·DB·Twin이 로봇에 각각 접속하면 명령 주체와 최신 상태가 뒤섞이고 JSON 재저장 과정에서 참조가 깨질 수 있습니다.
구현 범위
시스템 목표와 인터페이스·통합 순서를 주도하고 Conty JSON, PC-HMI, Robot Controller, MQTT, DB, PLC Bridge와 Web Twin 경계를 구현했습니다.
결과·현재 단계
공개 코드에서 명령·상태·이력·읽기 전용 Web Twin 흐름이 확인되며, Omniverse는 후속 확장 방향으로 분리했습니다.

어떤 문제를 해결하려 했는가

로봇 작업 프로그램은 좌표 몇 개로 끝나지 않습니다. Tool·TCP, Waypoint, 이동 명령, 반복과 분기, 속도와 입출력 정보가 서로 참조합니다. PC 프로그램이 이해하는 항목만 읽고 다시 저장하면, 화면에서는 정상처럼 보여도 티치펜던트에서 참조가 깨질 수 있습니다.

통신에도 비슷한 문제가 있습니다. HMI, 데이터 저장기와 디지털 트윈이 로봇 소켓에 각각 접속하면 어느 프로그램이 명령을 보냈는지, 어떤 상태가 최신인지 판단하기 어렵습니다.

구분내용
목표원본 JSON의 참조를 보존하고 로봇 연결 책임을 한 서비스로 모으기
맡은 범위JSON 호환 계층, PC-HMI, 통신·이력·Twin 서비스 경계 설계
사용 기술Python, CustomTkinter, IndyDCP, MQTT, MySQL, WebSocket, Docker
현재 상태PC-HMI, Robot Controller, MQTT, DB Worker, PLC Bridge와 읽기 전용 Web Twin 통합 프로토타입
다음 검증실로봇 firmware별 회귀시험과 장시간 재접속·중복 명령 시험

왜 이렇게 구성했는가

flowchart LR A["Conty JSON"] --> B["Load·검사·편집·재저장"] B --> C["원본 참조와 미지 필드 보존"] D["PC-HMI"] --> E["Robot Controller\nIndyDCP 단일 소유"] E --> F["MQTT command / result / state"] F --> G["DB Worker\n작업·오류 이력"] F --> H["PLC Bridge"] F --> I["읽기 전용 Digital Twin"]

처음 보는 사람이 접하는 화면

PC-HMI

작업자는 PC-HMI에서 Conty 작업 프로그램을 열고 계층 구조를 확인합니다. Waypoint와 이동 명령을 수정하면 원본 참조가 유지되는지 검사한 뒤 다시 저장합니다. 로봇 연결 화면에서는 접속상태, 현재 작업, 명령 결과와 오류를 한곳에서 봅니다.

작업·오류 이력

명령에는 ID를 붙여 요청과 결과를 맞추고, 시작·완료·오류 시각을 DB에 남깁니다. 화면이 다시 켜져도 직전 작업이 어디에서 멈췄는지 확인할 수 있게 하는 것이 목적입니다.

읽기 전용 Web Twin

Web Twin은 MQTT 상태를 WebSocket으로 전달받아 Canvas에서 로봇 상태와 공정 진행을 보여 줍니다. 이 화면에는 물리 로봇을 움직이는 버튼을 두지 않았습니다. 관측 화면과 제어 화면을 나눠 명령 주체가 여러 곳으로 퍼지는 것을 막았습니다.

JSON 호환 계층

원본에 모르는 필드가 있어도 삭제하지 않고 보존하는 방식을 택했습니다. 기본 확인 순서는 원본 로드 → 일부 편집 → 저장 → 다시 로드 → 참조 비교입니다. Waypoint와 program tree, move 명령 사이의 참조가 남아 있는지를 별도로 검사하도록 설계했습니다.

로봇 소켓의 단일 소유권

물리 IndyDCP 연결은 Robot Controller 하나만 갖습니다. HMI는 명령 요청을 보내고, DB와 Twin은 상태를 소비합니다. 이 구분은 화면이나 저장 서비스의 장애가 로봇 제어 경로로 번지는 것을 줄이기 위한 것입니다.

명령과 상태 Topic 분리

MQTT에서는 command, result, realtime state, connection, error를 같은 메시지로 섞지 않습니다. 명령 ID와 결과를 맞춰야 누가 어떤 요청을 보냈고 어떻게 끝났는지 추적할 수 있습니다. 중복 명령 방지를 위한 idempotency와 권한 분리는 다음 검증 항목으로 남겨 두었습니다.

내가 확인하고 만든 범위

  • 계층형 JSON 탐색과 편집 화면
  • 원본을 보존하는 parser·serializer 구조
  • Robot Controller 중심의 통신 경계
  • 작업·상태·오류 이력을 저장하는 DB Worker 설계
  • PLC와 HMI가 로봇 상태를 공유하는 event 계약
  • 제어 버튼이 없는 읽기 전용 Twin 화면
  • Offline UI, Direct, Gateway 순서의 단계별 실행 방식

실제 로봇이 없는 단계에서는 Offline UI로 JSON 구조와 화면 흐름을 먼저 확인하고, 연결 단계에서 Direct 통신, 마지막에 Gateway와 여러 consumer를 붙이도록 나눴습니다. 한 번에 전체 구성을 켜고 문제 원인을 찾는 것보다 통신 책임을 구분하기 쉽기 때문입니다.

실제 프로그램 구조

현재 main Branch의 코드는 화면, 도메인 로직과 외부 장치 연결을 다음처럼 나눕니다. 파일 이름을 나열하기보다 각 폴더가 어떤 책임을 갖는지가 중요합니다.

영역확인한 구성책임
frontend/presentationRobot HMI, Digital Twin, Virtual Test 화면작업자가 프로그램·상태·이력을 확인하는 UI
frontend/coreRuntime config, service manager, robot domain화면과 통신 구현 사이의 규칙과 실행 순서
frontend/infrastructureIndyDCP, Conty executor, MySQL adapter로봇·PLC·DB 같은 외부 시스템 연결
backend/robot_controller로봇 명령과 상태 발행물리 로봇 연결을 한곳에서 소유
backend/db_worker작업·오류·상태 이력 저장MQTT 이벤트를 추적 가능한 기록으로 변환
backend/plc_bridgePLC 상태 읽기와 이벤트 전달로봇 제어와 PLC 감시 경계를 분리
backend/digital_twinMQTT 구독, WebSocket, Canvas Twin제어권 없이 현재 상태를 읽어 화면에 표시

Robot Controller는 IndyDCP로 명령을 실행하고 결과와 상태를 MQTT로 내보냅니다. DB Worker와 Web Twin은 그 메시지를 소비할 뿐 로봇 소켓을 직접 소유하지 않습니다. PLC Bridge도 감시 데이터를 별도 이벤트로 전달합니다. 이 구조 덕분에 화면·DB·Twin 중 하나가 중단돼도 명령 주체를 다시 판단하기 쉽고, 문제를 통신계층별로 나눠 확인할 수 있습니다.

실행 순서

  1. Offline 모드에서 JSON 탐색·편집과 화면 흐름을 확인합니다.
  2. Direct 모드에서 PC-HMI와 Indy7 Controller의 기본 명령·상태를 연결합니다.
  3. Gateway 모드에서 Robot Controller가 물리 연결을 한 번만 소유하게 합니다.
  4. MQTT로 상태·명령결과·오류를 나눠 발행합니다.
  5. DB Worker, PLC Bridge와 Web Twin을 하나씩 붙여 문제가 생긴 계층을 분리합니다.

이 순서를 택한 이유는 전체 서비스를 한꺼번에 켰을 때 로봇, 메시지, DB, 화면 중 어디에서 문제가 생겼는지 찾기 어려워지기 때문입니다.

결과

이 프로젝트의 핵심 결과는 로봇 프로그램 형식을 보존하면서 물리 제어권을 한곳에 둔 구조입니다. HMI·DB·Twin은 서로 독립적으로 상태를 읽기 때문에 화면과 기록 기능이 로봇 제어 소켓을 직접 차지하지 않습니다.

로봇 프로젝트의 시스템 목표와 인터페이스, 통합 순서를 주도했고, Conty JSON 호환 계층과 PC-HMI·Robot Controller·MQTT·DB·PLC Bridge·Web Twin의 주요 경계를 구현했습니다. Vision과 PLC 작업을 포함한 전체 시나리오는 팀과 함께 구성했습니다.

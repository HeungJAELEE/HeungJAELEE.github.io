사용자 문제
PC와 티치펜던트가 작업 데이터를 주고받을 때 JSON 참조를 보존하고, 로봇 명령과 상태 확인 경로를 한 흐름으로 정리해야 했습니다.
구현 범위

Robot Controller에 IndyDCP 명령 경로를 모으고, Robot A·B·C 상태를 읽기 전용 화면과 이력 저장 경로로 분리해 Digital Twin 구현 범위를 정리했습니다.

프로젝트 범위와 현재 상태

이 프로젝트는 Indy7 로봇의 명령 경로와 상태 확인 경로를 나눠 하나의 사용 흐름으로 구성한 팀 기반 프로토타입입니다. 자동차 조립 시나리오와 Indy7 실물 시연, Vision·PLC·MES 확장 구상은 팀 결과입니다. 저는 시스템 목표와 인터페이스, 통합 순서를 정리하고 Conty JSON 호환 구조, PC-HMI, Python Robot Controller, MQTT·DB, 읽기 전용 Web Twin 연결을 구현했습니다.

구분확인한 범위
팀 결과자동차 조립 시나리오, Indy7 실물 시연, Vision·PLC·MES 확장 구상
개인 구현Conty JSON 호환 구조, 4개 PC-HMI, Robot Controller, MQTT·DB, 읽기 전용 Web Twin
현재 단계공개 main Snapshot 기준 로컬 Digital Twin 구현·검증 단계
남은 검증물리 PLC·로봇 전체 E2E, 장시간 운전·재접속, 중복명령·권한·복구 시나리오

공개 글은 저장소의 main@a6c08e5를 기준으로 작성했습니다. 저장소 문서마다 JSON 점검 수량이 달라 정확한 파일 수는 성과로 사용하지 않았습니다.

로봇을 준비하고 상태를 확인하는 흐름

사용 흐름은 설정과 티칭, 드라이런 기록, 자동운전과 모니터링, 읽기 전용 상태 확인 순서로 나눴습니다. AI Teaching은 기본 운전 흐름에서 분리한 실험 화면입니다.

Setting/Teaching → Dry Run Recording → Auto/Monitor → Web Twin 상태 확인

PC-HMI의 네 화면은 기능을 한곳에 몰아넣지 않고 역할별로 나눴습니다.

화면사용자가 하는 일
Auto/Monitor로봇 운전 명령과 주요 상태를 확인합니다.
Setting/Teaching작업 설정과 티칭 정보를 다룹니다.
Dry Run Recording드라이런 과정과 관련 정보를 기록합니다.
AI Teaching후속 실험 기능을 별도 화면에서 확인합니다.

명령 경로와 상태 경로를 분리했습니다

PC-HMI와 상태 화면이 각각 로봇 소켓을 열면 누가 명령을 보냈는지 추적하기 어려워집니다. 그래서 Python Robot Controller만 IndyDCP 소켓을 사용하도록 명령 경로를 모았습니다. HMI는 Robot Controller에 요청을 보내고, Web Twin과 PLC Bridge는 로봇 명령을 보내지 않습니다.

flowchart LR HMI["PC-HMI\n설정·티칭·운전 요청"] --> RC["Robot Controller\nIndyDCP 소켓 단독 소유"] RC --> ROBOT["Indy7"] RC --> MQTT["MQTT\n상태 메시지"] MQTT --> DB["DB Worker\n상태 이력 저장"] MQTT --> TWIN["Web Twin\n읽기 전용 상태 표시"] PLC["PLC 신호"] --> BRIDGE["PLC Bridge\n읽기 전용 감시"] BRIDGE --> MQTT

이렇게 명령 경로가 여러 곳으로 퍼지는 문제를 줄였습니다. 다만 산업용 안전제어, 사용자별 권한, 중복명령 방지까지 검증한 것은 아닙니다.

작업 상태를 전달하고 남기는 방법

Robot Controller의 상태는 MQTT로 전달합니다. DB에는 상태 이력을 남기고 Web Twin에서는 Robot A·B·C의 공정 상태를 읽기 전용으로 표시합니다.

구성요소역할
Robot ControllerIndyDCP 연결과 로봇 명령 경로 담당
MQTT상태 메시지 전달
DB Worker작업·오류·상태 이력 저장
Web TwinRobot A·B·C 상태의 읽기 전용 표시
PLC BridgePLC 신호를 읽어 MQTT로 전달하는 감시 경로

PLC Bridge는 읽기 전용 감시 코드와 Docker 구성이 공개 저장소에 있습니다. 다만 물리 PLC와 로봇을 함께 연결한 전체 E2E 검증은 아직 남아 있습니다.

Conty JSON을 다룰 때 지킨 기준

로봇 작업 프로그램은 좌표만 저장하지 않습니다. Tool·TCP, Waypoint, 이동 명령, 분기, 속도와 I/O 필드가 서로 참조합니다. PC-HMI에서 익숙한 필드만 읽고 다시 저장하면 화면에서는 정상처럼 보여도 티치펜던트에서 참조가 깨질 수 있습니다.

원본에서 모르는 필드는 버리지 않고 보존하도록 parser·serializer 경계를 두었습니다. 원본 로드 → 일부 편집 → 저장 → 다시 로드 → 참조 비교 순서로 점검했습니다. 정확한 전체 호환 파일 수는 공개 근거가 서로 달라 본문에서 제외했습니다.

자동차 조립 시나리오시스템 목표와 통합 순서
Indy7 실물 시연Conty JSON 호환 구조와 4개 PC-HMI

Vision과 전체 PLC 시나리오는 팀 결과입니다. 개인 구현 범위에서는 공개 저장소에서 확인한 읽기 전용 PLC Bridge 코드와 Docker 구성까지만 설명합니다.

확인한 결과와 다음 검증

공개 저장소에서 4개 HMI 화면, Robot Controller의 IndyDCP 소켓 단독 소유 구조, MQTT·DB 상태 이력 코드, Robot A·B·C 읽기 전용 Web Twin, PLC Bridge 감시 코드와 Docker 구성을 확인했습니다. 공개 코드를 로컬에서 열어 Web Twin 화면도 다시 확인했습니다.

다음 단계는 물리 PLC·로봇 전체 E2E, 장시간 연속 운전, 연결 해제 후 재접속, 중복명령 처리, 사용자·기능별 권한과 장애 복구 시나리오입니다. Omniverse와 AI Teaching 확장은 이 기본 검증을 마친 뒤의 후속 과제로 남겼습니다.

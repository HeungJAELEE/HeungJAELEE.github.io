Indy7 로봇·Omniverse 디지털 트윈 실습

로봇 프로그램 JSON 호환성과 물리 제어 책임을 분리해 설계한 PC-HMI·상태 이력·디지털 트윈 프로토타입

2026. 7. 9. · 6 · 마지막 검토 2026. 7. 31.

  • Robot
  • MQTT
  • Digital Twin

30초 요약

로봇 명령, 현재 상태, 이력 저장과 디지털 트윈을 한 프로그램이 모두 책임지면 장애와 권한 경계가 모호해집니다. 각 책임을 나눠야 안전하게 확장할 수 있습니다.

PC-HMI·상태 이력·읽기 전용 트윈

해결하려던 문제

로봇 프로그램 JSON 호환성을 유지하면서 실물 제어와 모니터링·이력·가상 시각화를 구분해야 했습니다.

내가 맡은 범위

  • IndyDCP 소켓, MQTT 명령·상태, MySQL 이력, PLC Bridge와 읽기 전용 트윈의 인터페이스 책임을 나눴습니다.

확인된 결과·현재 단계

  • 확인된 산출물 · 개인 역할 명령·상태·이력·PLC Bridge·읽기 전용 트윈의 책임 분리
  • 현재 단계 · 팀 결과 공개 프로토타입·실로봇 통합/E2E 검증 전

팀 경계

실물 로봇 통합과 전체 E2E 완료를 주장하지 않으며, 공개 프로토타입의 설계 범위만 제 역할로 설명합니다.

공개 범위: 내부 네트워크·로컬 경로·기본 인증 형태의 설정을 공개하지 않도록 외부 저장소 버튼을 보류했습니다.

제어권과 관찰권을 나눈 일반적인 로봇 데이터 흐름으로 설명합니다.

왜 이 의사결정이 중요했는가

Indy7 작업 프로그램은 좌표만 저장하는 파일이 아닙니다. Tool·TCP, Waypoint, 이동 명령과 program tree가 서로 참조하기 때문에 PC 편집기가 모르는 필드를 지우거나 참조를 바꾸면 화면에서는 정상처럼 보여도 티치펜던트에서 프로그램이 깨질 수 있습니다.

통신 책임도 분명해야 합니다. HMI, 이력 저장기, PLC 연계와 디지털 트윈이 각각 로봇 소켓을 열면 어느 서비스가 명령을 보냈는지, 어떤 상태가 최신인지 추적하기 어렵습니다. 물리 로봇의 제어 경로가 화면이나 저장 기능에 따라 늘어나는 것은 안전 경계를 흐립니다.

왜 디지털 방식이 필요했는가

PC-HMI는 계층형 JSON을 읽고 편집하는 데 유용하지만, 편의 기능보다 원본 호환성이 먼저입니다. 그래서 모르는 필드를 보존하고 로드 → 일부 편집 → 저장 → 다시 로드 → 참조 비교로 왕복 결과를 확인하는 구조를 잡았습니다.

통신은 Robot Controller 한 곳이 IndyDCP 연결을 소유하고, 다른 기능은 명령 요청이나 상태 이벤트를 주고받도록 나눴습니다. 이 방식은 화면, 기록과 시각화가 각자 물리 제어 소켓을 차지하지 않게 합니다.

실제로 맡은 역할

이 프로젝트에서 JSON 호환 계층, PC-HMI, Robot Controller 중심의 통신 경계, 작업·상태·오류 이력과 Twin 서비스의 책임을 설계하고 프로토타입으로 구성했습니다. 핵심은 기능을 한 프로그램에 모으는 것이 아니라 다음 책임을 분리하는 일이었습니다.

  • Command: HMI가 명령 ID를 포함한 요청을 보내고 Robot Controller만 IndyDCP 명령을 실행합니다.
  • State와 result: 로봇의 실시간 상태, 연결 상태, 오류와 명령 결과를 별도 이벤트로 배포합니다.
  • History: DB Worker는 작업·상태·오류 이력을 저장하지만 물리 명령을 소유하지 않습니다.
  • PLC Bridge: PLC와 HMI가 필요한 상태를 event 계약으로 교환하는 경계이며, 임의의 우회 제어 경로로 두지 않습니다.
  • Digital Twin: 상태를 관측하는 읽기 전용 소비자이며 제어 버튼과 물리 명령 권한을 갖지 않습니다.

데이터 흐름

PC-HMI 명령 요청 → Robot Controller의 단일 IndyDCP 연결 → 명령 결과·실시간 상태 이벤트 → DB Worker 이력 / PLC Bridge 상태 교환 / 읽기 전용 Twin 관측

command, result, realtime state, connection과 error를 같은 메시지에 섞지 않았습니다. 명령 ID로 요청과 결과를 연결하면 누가 무엇을 요청했고 어떻게 끝났는지 추적할 수 있습니다.

구현 순서

  1. Conty JSON에서 보존해야 할 미지 필드와 Waypoint·program tree·이동 명령 참조를 구분했습니다.
  2. 계층형 JSON 탐색·편집 화면과 원본 보존 parser·serializer 경계를 구성했습니다.
  3. 로봇이 없는 Offline UI에서 파일 왕복과 화면 흐름을 먼저 확인하도록 했습니다.
  4. Direct 단계에서 Robot Controller가 IndyDCP 연결을 단독 소유하도록 경계를 잡았습니다.
  5. Gateway 단계에서 명령, 결과, 상태, 연결과 오류 event를 분리하고 DB Worker, PLC Bridge와 Twin 소비자를 나눴습니다.
  6. Twin에는 제어 기능을 넣지 않고 읽기 전용 상태 화면으로 제한했습니다.

확인된 결과와 현재 단계

현재 결과는 JSON 호환성, PC-HMI와 서비스 책임을 함께 다룬 설계·프로토타입입니다. “원격으로 로봇을 운영했다”거나 생산 환경에 배포했다고 주장하지 않습니다. Omniverse는 후속 adapter 방향이며 완료된 연동 결과가 아닙니다.

연결된 저장소에는 내부 네트워크, 로컬 경로와 기본 설정 형태의 값이 남아 있다는 진단이 있어 외부 링크를 보류하고 있습니다. 여러 Indy7 firmware의 JSON 왕복, 실제 로봇을 포함한 장시간 재접속과 중복 명령 시험도 남아 있습니다.

배포 조건과 회사에 줄 수 있는 가치

실제 연결 전에는 firmware별 JSON 회귀시험, 명령 인증과 권한, idempotency, MQTT topic 권한, 타임아웃과 재접속, 감사 이력을 검증해야 합니다. PLC Bridge와 Twin이 Robot Controller의 단일 제어 경계를 우회하지 않는지도 hardware-in-the-loop로 확인해야 합니다. 비상 정지와 안전 인터록은 이 애플리케이션이 아니라 검증된 로봇·PLC 안전 회로의 책임으로 유지합니다.

이 조건이 갖춰지면 회사는 작업 프로그램을 편집할 때 참조 손상 위험을 줄이고, 명령·상태·오류 이력을 한 흐름으로 추적할 수 있습니다. 읽기 전용 Twin은 현장 상태를 공유하되 새로운 제어 경로를 만들지 않는 시각화 수단이 될 수 있습니다. 실제 다운타임 감소나 작업 시간 절감은 별도 현장 측정이 필요합니다.

Problem

Conty JSON 일부만 수정하면 Waypoint·program·move 참조가 손상될 수 있고, 여러 클라이언트가 IndyDCP 소켓을 직접 소유하면 명령 책임과 상태 시간이 분산됩니다.

Goal

원본 보존형 JSON round-trip과 단일 Robot Controller를 중심으로 HMI, DB, PLC, twin이 명시적 이벤트를 공유하는 구조를 만드는 것입니다.

Success

load–edit–save–reload에서 참조가 보존되고, 물리 소켓이 하나이며, offline/direct/gateway 모드와 배포 문서가 재현 가능하면 성공입니다.

범위와 경계

포함 범위

  • Conty/APK JSON round-trip과 참조 무결성
  • IndyDCP 단일 소유권, MQTT command/state 분리
  • CustomTkinter HMI, MySQL worker, PLC bridge, read-only web twin

제외·미검증 범위

  • Omniverse가 검증된 생산 운영 화면이라는 주장
  • 공개 측정이 없는 latency·uptime·충돌 감소 수치
  • 디지털 트윈에서 물리 로봇 명령을 직접 실행하는 구조

구현·검증 기준

해야 할 일

  • 알 수 없는 JSON field와 참조를 보존하고 저장 후 재로딩 검증을 수행한다.
  • Robot Controller만 물리 IndyDCP 소켓을 소유한다.
  • command, result, realtime, connection, error event를 분리한다.

품질·운영 기준

  • Offline UI에서 로봇 없이 JSON과 화면 흐름을 검증할 수 있다.
  • DB와 twin은 명령 경로가 아니라 상태 소비자로 동작한다.
  • 공개 전 내부 네트워크·경로·기본 설정 형태의 값을 제거하고 다시 검사한다.

왜 이렇게 구성했나

  1. 원본 보존형 round-trip

    편집기가 모르는 vendor field를 삭제하지 않아야 teach pendant 호환성을 유지할 수 있기 때문입니다.

  2. IndyDCP 소켓 단일 소유권

    동시 명령과 상태 race를 막고 물리 제어 책임을 한 서비스에서 감사하기 위해서입니다.

  3. 디지털 트윈은 read-only

    시각화 계층의 오류가 물리 로봇 명령으로 이어지지 않도록 안전 경계를 분리했습니다.

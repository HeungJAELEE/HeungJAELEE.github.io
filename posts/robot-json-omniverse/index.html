로봇 JSON 해석과 디지털 트윈 연동: Indy7 PC-HMI 설계

  • Robot
  • JSON
  • IndyDCP
  • MQTT
  • Digital Twin
  • Docker

프로젝트를 한 문장으로 설명하면

Neuromeka Indy7 협동로봇의 기존 Conty 티치펜던트 JSON을 PC에서 읽고, 계층형으로 편집하고, 가상 검증하고, 다시 호환 JSON으로 저장하기 위해 만든 Python HMI 및 백엔드 서비스 프로젝트입니다.

이 프로젝트를 단순히 “JSON을 파싱해 3D 로봇을 움직였다”라고 설명하면 중요한 설계가 빠집니다. 실제 핵심은 다음 네 가지입니다.

  1. 제조사 JSON의 트리와 참조 관계를 손상시키지 않는 왕복 변환(round-trip)
  2. IndyDCP 소켓을 Robot Controller 한 곳만 소유하게 한 통신 구조
  3. 명령 쓰기와 상태 읽기를 분리한 MQTT 이벤트 흐름
  4. HMI, MySQL 이력, 읽기 전용 디지털 트윈이 같은 실시간 상태를 구독하는 구조
  • 소스 저장소: HeungJAELEE/Busan_Robot

프로젝트 카드에는 NVIDIA Omniverse 연동 프로젝트로 요약되어 있습니다. 다만 현재 공개 저장소에서 구체적으로 확인되는 실행 구조는 CustomTkinter HMI와 WebSocket 기반 3D 웹 모니터입니다. 따라서 이 글에서는 공개 코드로 확인되는 부분을 핵심 구현으로 설명하고, Omniverse는 동일한 robot/realtime 상태를 구독할 수 있는 확장 어댑터 또는 PoC 방향으로 구분합니다.

해결하려던 문제

현장에서 로봇 작업 프로그램은 단순한 관절 좌표 배열이 아닙니다. 툴과 TCP 설정, 웨이포인트, 이동 조건, 반복과 분기, 디지털 입출력, 속도와 블렌딩 정보가 서로 참조하는 구조입니다. 기존 티치펜던트에서 내보낸 JSON을 PC 프로그램이 일부 필드만 읽고 다시 저장하면, 화면에서는 정상처럼 보여도 원본 장치에서 열리지 않거나 잘못된 좌표를 참조할 수 있습니다.

통신 구조에도 별도의 문제가 있습니다. HMI, DB 저장기, 디지털 트윈이 각각 로봇 소켓에 직접 접속하면 다음과 같은 위험이 생깁니다.

  • 여러 클라이언트의 명령 순서가 뒤섞임
  • 한 서비스의 느린 응답이 다른 화면까지 정지시킴
  • 로봇 상태를 각 서비스가 서로 다른 시점에 읽음
  • 장애가 났을 때 어느 프로그램이 마지막 명령을 보냈는지 추적하기 어려움

그래서 JSON 호환 계층과 실시간 통신 계층을 분리하고, 물리 로봇 연결은 단일 서비스가 책임지는 구조를 선택했습니다.

왜 HMI와 백엔드를 분리했는가

HMI는 작업자의 버튼 입력, TreeView 편집, 상태 표시처럼 GUI 이벤트에 즉시 반응해야 합니다. 반면 로봇 폴링, DB 저장, WebSocket 중계, PLC 감시는 연결 실패와 재시도를 포함한 장시간 작업입니다. 이 작업들을 UI 메인 루프 안에서 직접 처리하면 네트워크 지연 하나로 화면이 멈출 수 있습니다.

그래서 프론트엔드는 작업자 경험과 도메인 로직에 집중하고, 백엔드는 다음 서비스로 나눴습니다.

  • robot_controller: IndyDCP 연결, 명령 실행, 실시간 상태 발행
  • db_worker: MQTT 이벤트를 MySQL 이력으로 저장
  • digital_twin: 실시간 상태를 WebSocket 웹 화면으로 중계
  • plc_bridge: PLC 신호 감시와 이벤트 발행
  • message_broker: 서비스 사이의 MQTT 메시지 전달

가벼운 실험에서는 Python 스레드 기반으로 실행할 수 있고, 현장형 구성에서는 Docker Compose로 백엔드 장애를 분리할 수 있도록 한 이유도 여기에 있습니다.

가장 중요한 결정: 로봇 소켓의 단일 소유권

운영 모드에서는 robot_controller만 Robot A/B/C의 IndyDCP 소켓에 연결합니다. HMI, DB Worker, 디지털 트윈은 로봇을 직접 읽지 않습니다.

sequenceDiagram participant HMI as HMI participant MQTT as MQTT Broker participant RC as Robot Controller participant Robot as Indy7 participant Consumer as UI·DB·Digital Twin HMI->>MQTT: robot/command 발행 MQTT->>RC: 명령 전달 RC->>Robot: IndyDCP 명령 Robot-->>RC: 결과·상태 RC-->>MQTT: robot/result 발행 loop 연결 중 상태 갱신 RC-->>MQTT: robot/realtime 발행 MQTT-->>Consumer: 동일 상태 배포 end

이 구조의 장점은 명확합니다.

  • 실제 로봇으로 나가는 명령 경로가 하나라서 감사와 차단이 쉽습니다.
  • 상태를 한 번 읽어 여러 소비자에게 배포하므로 시점 차이를 줄일 수 있습니다.
  • DB나 디지털 트윈이 중단되어도 로봇 소켓 소유권은 영향을 받지 않습니다.
  • 로봇 연결 재시도와 에러 처리를 Robot Controller에 집중할 수 있습니다.

단일 소유권은 단일 장애 지점이 될 수도 있습니다. 그래서 운영 단계에서는 컨테이너 재시작 정책, 연결 상태 Topic, 명령 중복 방지, 재기동 후 안전 상태 확인이 함께 필요합니다.

명령 쓰기와 상태 읽기를 왜 분리했는가

이 프로젝트는 MQTT Topic을 성격에 따라 구분합니다.

흐름Topic성격
HMI → Robot Controllerrobot/command사용자가 동작을 요청할 때만 발생하는 단발성 명령
Robot Controller → HMIrobot/result명령 처리 결과
Robot Controller → 소비자robot/realtime연결 중 반복 발행되는 상태 스트림
Robot Controller → HMIrobot/connection로봇별 연결 상태
Robot Controller → UI·DBrobot/error충돌·통신·실행 오류
PLC Bridge → UI·DBplc/event 계열PLC 감시 이벤트

robot/realtime을 읽는 화면이 Home이나 Stop 명령까지 보낼 수 있게 하면 모니터링 화면이 곧 제어 화면이 됩니다. 현재 웹 디지털 트윈은 상태를 보여 주는 읽기 전용 화면으로 두고, Home·Zero·Stop 같은 제어는 HMI에서만 수행하도록 경계를 설정했습니다.

이 원칙은 Omniverse를 추가할 때도 동일합니다. Omniverse 어댑터는 robot/realtime을 구독해 가상 모델을 갱신할 수 있지만, 검증되지 않은 상태에서 물리 로봇 명령 Topic을 직접 발행해서는 안 됩니다.

실행 모드를 나눈 이유

개발 PC와 현장 PC는 연결 가능한 장치가 다릅니다. 프로그램을 실행하자마자 실제 로봇에 붙는 방식은 안전하지 않고, 로봇이 없으면 UI 자체를 시험할 수도 없습니다. 그래서 연결 경계를 실행 모드로 드러냈습니다.

모드용도연결 방식
Offline UI로봇·Docker 없이 화면과 JSON 먼저 확인자동 연결을 끄고 UI만 실행
Direct랩에서 Docker 없이 단독 시험HMI가 로봇에 직접 연결
MQTT Gateway현장 운영 권장 구성HMI가 명령을 Broker에 보내고 Robot Controller가 실행
Auto환경에 따른 보조 선택MQTT 사용 가능 여부에 따라 Gateway 또는 Direct 시도

운영 기본값은 무연결 상태에서 시작하고 작업자가 연결을 명시적으로 요청하는 방향입니다. 이는 “프로그램이 켜졌다”와 “실제 설비에 연결됐다”를 구분하기 위한 안전 장치입니다.

Conty JSON은 어떻게 구성되어 있는가

공개 저장소의 호환 구조는 네 블록을 중심으로 합니다.

  • info: Tool, TCP, 좌표계와 기본 설정
  • wpList: 티칭된 Waypoint와 고유 ID
  • program: 실행 순서와 부모·자식 관계를 가진 프로그램 트리
  • moveList: 이동 속도, 가속도, 블렌딩 등 동작 상세와 Waypoint 참조

구조를 단순화하면 다음과 같습니다. 아래 값은 관계를 설명하기 위한 예시이며 실제 작업 좌표가 아닙니다.

{
  "info": { "tool": "tool-setting", "tcp": "tcp-setting" },
  "wpList": [{ "id": "wp-pick", "p": "pose-data" }],
  "program": {
    "id": "root",
    "children": [{ "id": "node-pick", "wpId": "wp-pick" }]
  },
  "moveList": {
    "wpList": [{ "id": "wp-pick", "motion": "motion-setting" }]
  }
}

중요한 것은 JSON 문법이 유효한지만 확인하는 것이 아닙니다. program의 wpId가 실제 wpList 항목을 가리키는지, moveList의 참조가 유지되는지, id/pId 트리가 순환하거나 끊기지 않는지까지 확인해야 합니다.

JSON 왕복 변환을 어떻게 안전하게 만들었는가

1. 원본을 보존하면서 해석한다

로더는 알려진 노드 타입을 도메인 객체로 바꿔 TreeView에서 편집할 수 있게 합니다. 그러나 프로그램이 이해하지 못하는 제조사 전용 노드는 삭제하지 않고 원본 데이터를 보존해야 합니다. “모르므로 제거”가 아니라 “표시하고 보존하되 직접 실행은 제한”하는 정책입니다.

2. 참조를 객체 관계로 해석한다

Waypoint ID, 이동 설정, 프로그램 노드를 문자열 조각으로만 다루지 않고 서로의 관계로 해석합니다. 노드를 복사하거나 삭제할 때 어떤 참조가 영향을 받는지 판단하기 위해서입니다.

3. 편집 범위를 최소화한다

PC 화면에서 변경한 필드만 갱신하고, 프로그램에서 직접 사용하지 않는 기존 wpList와 moveList 항목도 함부로 제거하지 않습니다. 원본 APK가 별도로 참조하는 확장 필드를 잃지 않기 위한 선택입니다.

4. 직렬화 후 다시 읽어 검증한다

저장 결과를 다시 파싱해 다음 불변 조건을 확인하는 것이 round-trip 검증의 핵심입니다.

  • 필수 최상위 블록이 유지되는가?
  • 모든 Waypoint 참조 대상이 존재하는가?
  • 프로그램의 id/pId 트리가 유지되는가?
  • 알려지지 않은 노드와 확장 필드가 남아 있는가?
  • 단위 변환 후 값의 의미가 바뀌지 않았는가?
  • 저장한 파일을 다시 열었을 때 같은 작업 순서로 복원되는가?

5. TCP는 쓰고 끝내지 않고 read-back 한다

좌표 p는 meter 기준이고 UI는 mm로 표시할 수 있으므로 단위 변환 실수가 위험합니다. 실제 실행 전에는 JSON의 TCP를 로봇에 적용한 뒤 다시 읽어 일치 여부를 확인하고, 다르면 다음 모션을 보내지 않는 방식을 공개 문서가 명시합니다. 이는 파일의 문법 검증을 실제 장치 상태 검증으로 확장한 예입니다.

프로그램 트리와 실행 엔진

JSON의 program은 순차 명령 목록만이 아니라 Loop, If, DI/DO, Pick, Place 같은 부모·자식 구조를 포함합니다. HMI는 이를 TreeView로 보여 주고, 실행 계층은 노드 타입을 로봇 제어 유스케이스로 변환합니다.

flowchart TD A["Conty JSON 불러오기"] --> B["구문·필수 블록 검사"] B --> C["Waypoint·Move·Tree 참조 해석"] C --> D["도메인 Node로 변환"] D --> E["CustomTkinter TreeView 편집"] E --> F{"실행 방식"} F -->|"가상 Play"| G["순서·분기·위험 조건 검토"] F -->|"저장"| H["JSON 직렬화"] F -->|"실제 실행 요청"| I["안전 확인 후 Robot Controller에 명령"] H --> J["재로딩·참조 무결성 검사"]

Pick이나 Place처럼 여러 모션으로 이루어진 동작을 UI 이벤트 안에 직접 작성하지 않고, 도메인 유스케이스에 둔 것도 같은 이유입니다. 화면을 바꾸더라도 로봇 동작 규칙과 안전 확인을 재사용할 수 있습니다.

DB와 디지털 트윈은 어떻게 연결되는가

Robot Controller는 robot/realtime 상태를 MQTT로 한 번 발행합니다. 이후 소비자가 자신의 목적에 맞게 처리합니다.

  • HMI는 현재 로봇의 연결·관절·작업 상태를 표시합니다.
  • DB Worker는 작업 완료, 오류, 상태 이벤트를 MySQL 이력으로 저장합니다.
  • Digital Twin 서비스는 상태를 WebSocket으로 중계해 내부망 브라우저에서 3D 화면을 제공합니다.
  • 로컬 Dry Run은 MySQL에 연결하지 못하는 환경에서도 JSONL 파일로 샘플과 이벤트를 남길 수 있습니다.

DB Worker가 로봇을 다시 폴링하지 않는 이유는 저장 장애가 물리 로봇 통신에 영향을 주지 않게 하고, 모든 소비자가 같은 원본 이벤트를 보게 하기 위해서입니다.

Omniverse는 어디에 연결되는가

현재 공개 저장소의 기본 디지털 트윈은 WebSocket 기반 웹 모니터입니다. Omniverse 연동을 확장한다면 Robot Controller에 또 하나의 IndyDCP 연결을 만드는 방식보다, 다음과 같은 읽기 전용 어댑터가 적합합니다.

  1. MQTT의 robot/realtime을 구독합니다.
  2. Robot A/B/C의 상태를 공통 내부 모델로 정규화합니다.
  3. 로봇별 관절 이름, 축 방향, 단위, 초기 자세를 USD 객체에 매핑합니다.
  4. 오래된 순번의 상태는 버리고 최신 상태만 가상 장면에 반영합니다.
  5. 매핑 실패와 지연은 진단 로그로 남기되 물리 제어에는 개입하지 않습니다.

이렇게 하면 웹 모니터와 Omniverse가 같은 상태 소스를 사용하고, 3D 도구를 교체하더라도 로봇 통신 코어를 수정하지 않아도 됩니다. 공개 저장소로 확인되지 않는 Omniverse 운영 배포나 정량 지연 성능은 완료 사실로 주장하지 않습니다.

구현을 어떤 순서로 진행했는가

단계 1. 기존 JSON 구조와 호환 정책 분석

티치펜던트가 만든 JSON에서 info, wpList, program, moveList의 역할을 나누고, 어떤 필드를 편집하며 어떤 필드를 원형 보존할지 기준을 세웠습니다.

단계 2. 도메인과 화면 분리

JSON 파일을 화면 위젯에 직접 묶지 않고 Repository가 로딩·저장을, Node 도메인이 작업 구조를, Use Case가 실행 규칙을 담당하도록 분리했습니다. CustomTkinter 화면은 사용자의 선택을 도메인 명령으로 전달합니다.

단계 3. 연결 어댑터 분리

Offline, Direct, MQTT Gateway 모드가 같은 HMI에서 동작하도록 로봇 연결 방식을 설정으로 선택하게 했습니다. 이를 통해 로봇이 없는 개발 환경에서도 JSON 편집과 가상 Play를 확인할 수 있습니다.

단계 4. Robot Controller 단일화

운영 모드에서 모든 물리 명령과 상태 읽기를 Robot Controller로 모으고, 다른 서비스는 MQTT Topic을 통해서만 상호작용하도록 구성했습니다.

단계 5. 저장·모니터링 서비스 분리

DB Worker, Digital Twin, PLC Bridge를 백그라운드 서비스로 분리하고 Docker Compose로 선택 실행할 수 있게 했습니다. UI 자체는 호스트 Python에서 실행해 데스크톱 장치와 화면 접근을 단순화했습니다.

단계 6. Dry Run과 단계적 실기 확인

JSON 순서와 DI 조건을 가상 Play로 먼저 확인하고, 로컬 또는 DB 기록을 점검한 뒤, 실제 연결에서는 단일 명령과 낮은 속도·짧은 반복부터 확인하는 단계적 절차를 문서화했습니다.

기술적 난제와 해결 관점

알 수 없는 JSON 노드를 어떻게 처리할 것인가

파서가 지원하지 않는 타입을 오류로 끝내거나 삭제하면 원본 호환성이 깨집니다. 반대로 의미를 모르는 노드를 실행하면 위험합니다. 따라서 보존과 실행을 분리했습니다. 원본 데이터는 유지하되, 직접 실행은 건너뛰거나 사용자 확인을 요구하는 방식입니다.

단위와 좌표의 의미를 어떻게 지킬 것인가

파일 내부의 meter와 UI의 mm가 섞이면 숫자는 정상 범위에 있어도 실제 위치는 크게 달라질 수 있습니다. 단위 변환은 화면 곳곳에서 개별 수행하지 않고 경계 계층에 모으고, TCP read-back처럼 실제 장치 값과 비교하는 절차가 필요합니다.

MQTT 메시지가 중복되거나 늦게 도착하면 어떻게 할 것인가

상태 스트림은 최신 값이 중요하고, 명령은 한 번만 실행되어야 합니다. 따라서 두 흐름을 다른 Topic으로 나누고, 운영 확장 시에는 명령 ID, 로봇 ID, 발행 시각, 결과 상태를 포함해 중복 실행을 막아야 합니다. 현재 공개 자료로 정확한 전달 보장 수치를 확인할 수 없으므로 유실률이나 지연 성능은 임의로 제시하지 않습니다.

UI를 멈추지 않고 장애를 격리하는 방법

네트워크·DB·카메라 작업을 GUI 메인 스레드에서 분리하고, 현장 배포에서는 컨테이너 단위로 서비스를 나눌 수 있게 했습니다. 다만 서비스 분리만으로 무중단이 자동 보장되는 것은 아닙니다. 헬스 체크, 재시작 정책, 로그 집계, 재연결 후 상태 확인이 함께 있어야 합니다.

제어 화면과 모니터 화면의 경계

모니터링 편의를 위해 웹 화면에 제어 버튼을 추가하면 접근 가능한 기기 전체가 로봇 명령 지점이 됩니다. 그래서 웹 디지털 트윈을 읽기 전용으로 두고, 물리 명령은 HMI와 Robot Controller 경로에만 남겼습니다.

공개 저장소에서 확인되는 결과는 HMI·백엔드 모노레포, JSON 호환 계층, MQTT 기반 읽기·쓰기 분리, MySQL DB Worker, WebSocket 디지털 트윈, PLC Bridge, Docker 실행 구조가 코드와 운영 문서로 구성되어 있다는 점입니다. 프로젝트 요약에는 JSON 기반 로봇 통신 해석과 디지털 트윈 데이터 파이프라인의 실시간성 확보가 기록되어 있습니다.

반면 패킷 지연, 장시간 가동률, 실제 설비 충돌 감소율처럼 공개 검증 근거가 없는 수치는 추가하지 않았습니다.

이력서 경력과 어떻게 연결되는가

이 프로젝트는 로봇 소프트웨어만의 결과가 아니라 현장 경험을 코드 구조로 옮긴 사례입니다.

  • 진공 로봇 Overhaul, Teaching, 정도 세팅 경험은 좌표·TCP·툴 설정을 단순 숫자가 아니라 실기 검증이 필요한 설비 조건으로 보는 기반이 됐습니다.
  • 로봇 수리 표준서, 고객 교육 자료, 신규 로봇 시방서 작성 경험은 JSON 호환 규칙과 작업자 실행 절차를 문서화하는 방식으로 이어졌습니다.
  • 배터리 조립 Pilot Line의 FAT/SAT와 자동화 라인 검수 경험은 Offline → 가상 Play → 단일 명령 → 짧은 반복 → 공정 확대의 단계적 검증 순서에 반영됐습니다.
  • 초기 MES 체계 구축과 PLC 경험은 로봇 명령, 공정 신호, 작업 이력을 서로 다른 책임으로 나누되 추적 가능한 이벤트로 연결하는 근거가 됐습니다.
  • DX·AX 역량은 향후 자연어 티칭이나 Omniverse 확장을 물리 로봇 소켓에 직접 결합하지 않고 검증 계층 뒤에 배치하는 설계 원칙으로 연결됩니다.

향후 개선 방향

  1. JSON Schema와 사용자 정의 참조 검증기를 함께 사용한 자동 유효성 검사
  2. 원본 → 로드 → 저장 → 재로드의 구조 동일성을 확인하는 회귀 테스트 확대
  3. 명령 ID와 멱등성 키를 이용한 MQTT 중복 실행 방지
  4. Broker 인증·TLS·Topic ACL과 HMI 사용자 권한 분리
  5. DB 장애 시 재전송 큐와 중복 INSERT 방지 전략 정식화
  6. 컨테이너 헬스 체크, 중앙 로그, 서비스별 지표를 포함한 운영 관측성 강화
  7. 녹화된 robot/realtime을 재생하는 하드웨어 없는 통합 테스트
  8. Omniverse USD 관절 매핑 어댑터와 좌표 캘리브레이션 시험
  9. PLC·로봇·비전 이벤트를 하나의 작업 단위로 연결하는 MES 추적성 확장

이 프로젝트가 보여 주는 핵심 역량은 JSON 문법 지식 자체가 아닙니다. 기존 설비 프로그램의 호환성을 보존하면서, 물리 제어와 데이터 소비를 분리하고, 시험 환경에서 현장 운영 구조까지 단계적으로 확장한 설계 능력입니다.

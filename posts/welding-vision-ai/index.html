프로젝트 개요

이 프로젝트는 공개 용접영상에서 높은 점수를 내는 모델을 만드는 데서 끝내지 않고, 실제 용접실기품을 촬영했을 때 어떤 오류가 발생하는지 확인하기 위해 진행했습니다.

AI-Hub 용접영상으로 학습한 초기 모델을 설비보전기사 용접실기품에 적용했을 때 Recall이 15.84%까지 떨어졌습니다. 공개자료와 달리 실기품에는 그을음, 스패터, 산화표면, 반사광, 촬영각도와 배경이 함께 들어 있었기 때문입니다.

팀은 오류사진을 FN과 FP로 나누고, 촬영조건을 반영한 데이터 증강, 후보모델 비교, 앙상블과 Threshold 조정을 순서대로 진행했습니다. 저는 전체 프로젝트 흐름과 평가기준을 정하고, 후보모델 비교, 오류이미지 분석, 저해상도 좌표 스케일링과 Threshold 판단을 담당했습니다.

팀 목표와 완료조건

팀 목표

  1. AI-Hub 공개자료와 직접 촬영 용접실기품을 분리합니다.
  2. 초기 모델이 실기품에서 놓치는 불량과 오검을 확인합니다.
  3. FN과 FP를 촬영조건·표면상태·ROI 문제로 나눕니다.
  4. 실제 촬영조건을 반영한 증강을 적용합니다.
  5. 후보모델을 같은 평가항목으로 비교합니다.
  6. ResNet-50과 DeiT-Small의 확률을 결합합니다.
  7. Threshold별 FN·FP 변화를 비교해 시연조건을 정합니다.
  8. 스마트폰 이미지가 FastAPI를 거쳐 PWA에 표시되는 흐름을 구현합니다.
  9. 결과를 자동 합격·폐기가 아닌 작업자 검사보조 정보로 표시합니다.

나의 역할 — AI 모델링·평가기준 설계

저는 공개 데이터의 검증점수만으로 모델을 선택하지 않고, 직접 촬영한 실기품에서 발생한 FN과 FP를 먼저 확인하도록 전체 실험순서를 정했습니다.

후보모델은 Accuracy 한 값이 아니라 Recall, FPR, F1과 실제 오류이미지를 같은 기준으로 비교했습니다. 저해상도 입력에서 모델 좌표가 원본사진과 어긋나는 문제는 원본 크기와 모델 입력 크기의 비율을 이용해 다시 환산하도록 처리했습니다.

최종 시연에서는 F1이 가장 높았던 Threshold 0.49보다, 제한 평가셋에서 불량 미검출이 없었던 0.40을 사용했습니다. 그 대신 양품 재확인 대상이 늘어난다는 점을 함께 기록하고, 결과를 자동 합격·폐기가 아닌 검사보조 정보로 제한했습니다.

데이터 구성과 Domain Gap

보고서의 원천 데이터 표에는 언더컷과 오버랩을 합쳐 약 60,000장이 제시됐고, 후속 학습표에는 전처리 후 사용된 선박 부품영상 56,256장이 기록돼 있습니다. 직접 촬영한 용접실기품은 실험단계에 따라 약 155~198장, 즉 약 200장 규모로 사용했습니다.

데이터 구분사용 목적평가 처리
AI-Hub 공개 용접영상사전학습·후보모델 비교학습·검증자료
직접 촬영 용접실기품실제 촬영조건 평가공개자료 결과와 분리
증강 이미지조명·각도·표면노이즈 보완학습에만 사용, 원본 평가셋과 분리

초기 ResNet을 직접 촬영품에서 평가했을 때 Accuracy 38.86%, F1 21.33%, Recall 15.84%, FPR 35.87%였습니다. 모델구조를 바꾸기 전에 데이터와 촬영조건 차이를 먼저 원인으로 분리했습니다.

이미지를 어떻게 평가했는가

  1. 원본이미지와 정답 Label을 기준으로 예측결과를 대조했습니다.
  2. 실제 불량을 정상으로 판단한 FN 이미지를 먼저 확인했습니다.
  3. 양품을 불량으로 판단한 FP는 그을음·스패터·반사광·촬영각도·ROI 이탈로 나눴습니다.
  4. 같은 평가셋에서 모델·증강·Threshold만 바꿔 비교했습니다.
  5. Confidence가 낮거나 경계가 겹치는 경우는 재촬영 또는 작업자 확인 대상으로 분리했습니다.

촬영조건을 반영한 데이터 증강

Crop·좌우반전·회전·원근변형으로 촬영구도를 바꾸고, 밝기·대비·감마·그림자·Lens Flare로 조명변화를 반영했습니다. Blur·Gaussian Noise·JPEG 압축과 일부 가림도 추가했습니다.

저해상도 좌표를 원본사진에 맞춘 방법

모델은 Resize된 입력이미지를 기준으로 좌표를 출력하지만, 작업자는 원본사진에서 결함위치를 확인해야 합니다. 따라서 모델좌표를 그대로 그리지 않고 원본과 입력이미지의 가로·세로 비율을 계산해 다시 환산했습니다.

flowchart LR A["스마트폰 원본 이미지
원본 Width · Height"] --> B["모델 입력크기로 Resize"] B --> C["모델 좌표 출력
x1 · y1 · x2 · y2"] C --> D["가로·세로 비율 계산"] D --> E["원본 기준 좌표로 환산"] E --> F["원본사진 위에
ROI·결함위치 표시"]
scale_x = 원본 가로 / 모델 입력 가로
scale_y = 원본 세로 / 모델 입력 세로

원본 x 좌표 = 모델 x 좌표 × scale_x
원본 y 좌표 = 모델 y 좌표 × scale_y

이 처리는 저해상도 입력에서도 ROI와 원본사진의 위치가 어긋나지 않도록 하기 위한 로직입니다.

Threshold를 검사조건으로 바꾼 방법

Threshold 0.49에서는 F1이 가장 높았지만, 제한 평가셋에서 실제 불량 4건을 놓쳤습니다. 시연에서는 불량 미검출을 우선 줄이기 위해 0.40을 사용했습니다. 그 대신 양품 재확인 대상은 4건에서 15건으로 늘었습니다.

Threshold 0.40 조건의 최종 시연표에는 Accuracy 92.23%, Precision 87.07%, Recall 100%, F1 93.10%가 기록됐습니다. 이는 보고서의 제한 평가셋 결과이며, 생산라인의 불량유출 0건을 뜻하지 않습니다.

APP 형태의 검사 시연

flowchart LR A["스마트폰 촬영"] --> B["이미지 Resize·전처리"] B --> C1["ResNet-50"] B --> C2["DeiT-Small"] C1 --> D["확률 평균"] C2 --> D D --> E["Temperature Scaling"] E --> F{"Threshold·판정"} F -->|명확한 결과| G["등급·결함·Confidence 표시"] F -->|Gray Zone| H["재촬영·작업자 확인"]

스마트폰 이미지는 HTTPS multipart/form-data로 FastAPI의 /predict에 전달했습니다. 서버는 두 모델의 결과를 평균하고 Temperature Scaling과 Threshold를 적용한 뒤 JSON으로 반환했습니다.

PWA에는 A·C·D 등급이 표시됐습니다. 공개된 근거에서 등급 매핑의 세부 규칙까지 확인되지 않아 이 글에서는 구현화면과 출력항목만 제시합니다.

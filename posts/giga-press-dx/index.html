왜 이 프로젝트를 했는가

대형 설비는 현장에 설치한 뒤 시퀀스나 통신 문제를 발견할수록 수정 비용이 커집니다. 센서 신호 하나가 누락돼도 PLC 로직, SCADA 화면과 상위 데이터가 서로 다른 상태를 보여 줄 수 있고, 실제 설비에서 처음 시험하면 트라이아웃 시간이 길어집니다.

이 프로젝트는 기가프레스 공장 확장을 가정해 실제 설비를 투입하기 전에 제어 순서와 데이터 흐름을 가상으로 확인하는 방법을 만든 10인 교육 팀 PoC입니다.

핵심은 화면을 하나 더 만드는 것이 아니라, 실제 시운전에서 생길 문제를 더 앞 단계로 옮기는 것이었습니다.

전체 시스템 흐름

flowchart LR A["센서·스위치·액추에이터"] --> B["Arduino·Raspberry Pi\n수집·형식 정리"] B --> C["PLC\n시퀀스·인터록·안전 상태"] C <--> D["Factory I/O\n가상 공정·시험 시나리오"] C --> E["SCADA\n상태·알람·이력"] C --> F["OPC UA\n상위 데이터 연결"] F --> G["AI 적용 후보\n상태 예측·조건 추천"]

현장·에지 장치

Arduino와 Raspberry Pi는 센서값을 읽고 단위와 필드 이름을 맞추는 역할로 뒀습니다. 사람과 설비의 안전에 직접 영향을 주는 비상정지·도어 인터록·운전 허가는 PLC와 안전회로 영역에 남겼습니다.

PLC

PLC는 공정 순서와 인터록의 최종 책임을 맡습니다. 준비 확인 → 소재 확인 → 안전조건 확인 → 동작 허가 → 완료 확인 → 복귀로 상태를 나누고, 각 단계에 진입조건·완료신호·타임아웃을 붙였습니다.

IF safety_ok AND material_ready AND NOT alarm THEN
    run_permit := TRUE
ELSE
    run_permit := FALSE
END_IF

이 코드는 실제 Ladder 원본이 아니라, 운전 명령보다 허가조건을 먼저 확인한다는 제어 의도를 짧게 표현한 것입니다.

SCADA와 OPC UA

SCADA에는 운전·정지·고장만 표시하지 않고 현재 공정 단계, 단계별 체류시간, 마지막 신호 갱신시각과 알람 확인 여부를 함께 보여 주도록 구성했습니다. OPC UA는 PLC 태그를 상위 시스템과 AI 후보가 같은 이름으로 읽게 하는 연결 계층으로 사용했습니다.

Factory I/O

Factory I/O에서는 정상 사이클뿐 아니라 센서 미검출, 완료신호 지연, 통신 끊김과 수동·자동 모드 충돌을 반복했습니다. 실제 장비의 모든 물리 특성을 대신하는 모델이 아니라, FAT 전에 시퀀스와 인터록 누락을 먼저 찾는 가상 시험장으로 사용했습니다.

내가 맡은 범위와 팀 결과

제가 맡은 일은 통신 구성을 맞추고, 각 계층이 어떤 데이터를 주고받는지 정리하며, AI를 어디에 둘 수 있는지 검토하는 것이었습니다. Ladder와 SCADA 화면의 세부 구현은 해당 팀원이 맡았습니다. 전체 공정 시나리오와 발표자료는 팀이 함께 만들었습니다.

AI 후보는 PLC의 운전 허가를 대신하는 제어기가 아니라, 상태 이력에서 이상 징후를 찾거나 조건 후보를 제안하는 보조 계층으로 뒀습니다. 현장 제어권과 AI 분석을 분리한 이유는 모델 오류가 바로 설비 동작으로 이어지지 않게 하기 위해서입니다.

구현 순서

  1. 공정 Flow와 위험 시나리오를 먼저 정리했습니다.
  2. 센서·액추에이터 주소, 논리명, 단위와 정상상태를 태그 표로 만들었습니다.
  3. PLC의 상태·명령·알람·인터록 구조를 나눴습니다.
  4. Factory I/O와 PLC를 연결해 정상 사이클을 확인했습니다.
  5. 센서 누락·응답 지연·통신 끊김을 넣어 복구 흐름을 확인했습니다.
  6. SCADA와 OPC UA에 같은 상태 이름을 연결해 화면과 상위 데이터가 맞는지 비교했습니다.

가상 시운전에서 확인한 항목

시험 장면확인할 내용기대 동작
정상 자동운전단계 전이와 완료신호정해진 순서로만 다음 단계 진입
센서 채터링중복 명령과 오동작필터 뒤 한 번의 이벤트로 처리
통신 지연·끊김마지막 값과 품질상태타임아웃 알람, 자동 재기동 차단
액추에이터 미완료다음 단계 진입 여부현재 단계 유지, 원인 신호 표시
수동·자동 전환모드 충돌운전 중 임의 전환 차단

이 항목은 배터리 조립설비 FAT/SAT에서 사용했던 인수기준 → Punch List → 업체 조치 → 같은 조건 재시험 흐름을 가상 공정에 옮긴 것입니다.

결과와 제조현장 활용

팀은 Factory I/O–PLC–SCADA–OPC UA를 하나의 시연 흐름으로 연결했습니다. 제가 담당한 통신 셋업과 기술조사는 제어·화면·상위 데이터가 같은 상태를 보도록 경계를 정리하는 데 사용됐습니다.

이 구조가 회사에 도움이 되는 지점은 세 가지입니다.

  • 실제 설비 투입 전에 논리 오류와 인터록 누락을 발견할 수 있습니다.
  • 주소와 화면을 공통 태그로 관리해 설비 추가 시 수정 범위를 줄일 수 있습니다.
  • 정상운전뿐 아니라 장애·복구 조건을 FAT/SAT 항목으로 미리 만들 수 있습니다.

팀 보고서에는 셋업 시간 50~75% 단축과 증설 공수 50% 절감이 목표로 제시됐습니다. 이 값은 시연에서 측정한 결과가 아니라, 실제 공장 적용 단계에서 확인해야 할 목표입니다.

다음 단계

실제 설비 프로젝트로 이어가려면 안전 PLC와 제조사 프로토콜, Hardware-in-the-Loop 시험, 알람 우선순위, 자동 회귀시험과 OT 보안 검토가 추가로 필요합니다. 다음 단계의 목표는 “화면이 연결됐다”가 아니라 가상 시험 결과와 현장 인수기준을 같은 문서로 관리하는 시운전 패키지를 만드는 것입니다.

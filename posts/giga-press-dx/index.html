과제 목적

GIGA Press는 여러 부품의 생산·조립·용접을 대형 주조공정으로 통합할 수 있지만, 설비 규모와 투자비가 크고 공정 안정화에 필요한 Try-out 부담도 큽니다. 보고서는 실물설비에서 반복시험을 시작하기 전에 가상공정을 만들고, 제어상태와 관제화면을 같은 흐름으로 확인하는 자율형 공장 Digital Twin 교육 PoC를 제안했습니다.

이 과제의 핵심은 실제 GIGA Press의 주조 물리현상을 정밀해석하는 데 있지 않았습니다. Factory I/O에서 구현 가능한 공정으로 단순화한 뒤, 원자재 투입부터 가공·검사·적재·배출까지의 Sequence를 만들고 PLC·SCADA·OPC UA·Web과 향후 AI 제어구조를 계층별로 연결하는 것이 목표였습니다.

왜 Digital Twin이 필요했는가

보고서는 기존 제조방식의 문제를 세 가지로 정리했습니다.

제조 문제기존 방식의 한계Digital Twin에서 확인하려던 내용
Try-out 장기화최적조건을 찾기 위해 실물과 자재를 반복 투입물리설비 구축 전 Sequence와 Interlock 사전확인
데이터 정합성 부족설계·PLC·설비·관제의 상태 의미가 서로 달라질 수 있음Factory I/O·PLC·SCADA가 같은 상태를 가리키는지 확인
만성 Loss 원인 추적설비상태와 가상모델이 연결되지 않으면 성능저하 구간을 찾기 어려움상태·Alarm·이력과 향후 분석입력의 연결구조 설계

이 프로젝트에서 위 문제의 경제적 효과를 실측한 것은 아닙니다. 교육환경에서 가상공정과 통신·제어·관제의 정상동작 흐름을 만드는 데 범위를 두었습니다.

가상공정으로 단순화한 GIGA Press 흐름

Factory I/O에는 실제 GIGA Press 장비가 없기 때문에 금형 가공을 CNC 가공공정으로 단순화했습니다. 제품 색상으로 검사결과를 구분하고, 양품은 Tray와 Stacker를 거쳐 배출하며 불량은 별도 배출하는 흐름을 구성했습니다.

flowchart LR A["원자재 투입"] --> B["금형 가공\nFactory I/O에서는 CNC로 대체"] --> C{"불량검사"} C -->|불량| D["불량 배출"] C -->|양품| E["Tray 이송"] --> F["Stacker 적재"] --> G["Stacker 배출\n출하 명령"]

원자재 투입 → 금형 가공 → 불량검사 → Tray 이송 → Stacker 적재 → Stacker 배출의 순서로 제어와 상태표시를 연결했습니다.

시스템을 네 계층으로 나눈 이유

계층보고서 구현범위제조에서의 역할완료 수준
L1 Factory I/O3D 가상공정과 설비동작Sequence·이송·검사·적재 흐름 시각화팀 시연 완료
L2 PLC/Ladder·SCADA제어로직, HMI, OPC UA 서버·클라이언트명령·Interlock·상태감시와 Tag 연결팀 시연 완료
L3 Web설비상태·Rack/Stacker·생산정보 표시운영자가 전체 상태를 한 화면에서 확인프로토타입 시연
L4 AIQ-Learning/DQN 모델 선정과 연결구조상태–행동 후보와 향후 제어정책 검토선정·설계 단계
flowchart LR FIO["Factory I/O\n가상 설비·센서"] <--> PLC["PLC / Ladder\nSequence·Interlock"] PLC <--> OPC["OPC UA\nTag·상태 전달"] OPC <--> SCADA["SCADA\n관제·Alarm"] OPC --> WEB["Web Dashboard\n상태·Rack·생산정보"] OPC -.-> AI["DQN 후보\n상태–행동 구조"] AI -.-> HIL["향후 HIL·Shadow Test"]

OPC UA는 PLC·SCADA·Web·AI가 동일한 Tag와 상태 의미를 공유하기 위한 연결경계로 사용했습니다. 통신이 연결됐다는 사실과 실제 공정제어의 안전성 검증은 분리해서 판단했습니다.

팀 역할과 내가 맡은 범위

보고서의 공식 R&R은 다음과 같습니다.

구분보고서 담당범위
팀장전체 일정·리스크 관리와 최종발표
PLC 팀Ladder 작성, 통신 연결과 Factory I/O 작업
Digital Twin 팀AI 모델 선정·학습, 통신 셋업과 자료조사
SCADA 팀OPC UA 서버·클라이언트, 대시보드와 설비연동

저는 Digital Twin 팀에서 제조 시나리오와 시스템 연결구조, AI 모델 선정구간과 통신 셋업을 정리했습니다. 별도 확인된 실제 기여기준으로는 각 팀의 구현을 하나의 제조흐름으로 설명하는 최종보고서도 작성했습니다. Ladder와 SCADA의 상세 구현은 해당 팀원의 결과로 구분했습니다.

실제 구현결과 1 — Factory I/O와 PLC 제어

Factory I/O의 Start·Reset·Stop·Emergency Stop 조작과 PLC Ladder 상태를 함께 확인했습니다. 이 화면은 가상공정의 버튼입력과 제어로직이 연결된 팀 결과이며, Ladder 상세 작성은 PLC 팀 범위입니다.

실제 구현결과 2 — SCADA·Stacker 관제

Rack과 Stacker의 적재상태를 SCADA 화면과 가상공장에서 함께 확인했습니다. 가상설비의 위치·적재상태가 관제화면에서 같은 의미로 표시되는지 확인하는 데 사용했습니다.

실제 구현결과 3 — Web 운영화면

Web 화면에는 설비상태, Rack 위치, 생산정보와 분석후보를 표시했습니다. 이는 운영화면 프로토타입이며 예지보전이나 AI 최적제어 성능을 검증한 결과는 아닙니다.

Ladder 모듈화에서 확인한 설계방향

보고서는 스파게티식 Ladder를 기능별 Program/Function Block으로 나누는 방향을 제안했습니다. Emit, Machine, Move, Stacker, Vision처럼 공정기능별로 분리하면 수정구간과 장애확인 범위를 좁힐 수 있습니다.

모듈화 목적이번 프로젝트에서 확인한 내용추가로 필요한 검증
기능별 책임분리공정기능 단위 Program 구조 제시동일 설비 증설 전후 개발공수 비교
장애범위 축소문제 기능만 확인하는 구조 설계MTTR 실측과 고장주입 시험
재사용반복공정에 적용 가능한 Block 구조다른 Layout·PLC에서 재사용 시험

보고서에 제시된 증설 공수 50% 절감은 기대효과이며 이번 PoC의 실측성과로 사용하지 않았습니다.

DQN을 어디까지 적용했는가

보고서는 Rack·Stacker와 설비상태를 State, 이동·적재·배출 명령을 Action으로 정의하는 Q-Learning/DQN 구조를 후보로 선택했습니다. 이산적인 상태–행동 문제를 표현하기 쉽다는 점을 선정이유로 사용했습니다.

이번 공개 범위에서 DQN은 모델 선정과 연결구조를 검토한 단계입니다. 0.1초 이내 응답, 실시간 학습, AI 명령의 PLC 직접제어와 자율적인 공정산포 제어는 별도 Benchmark나 폐루프 안전시험으로 확인되지 않았습니다.

다음 검증은 DQN 출력을 PLC 안전제어와 분리한 상태에서 비교하는 Hardware-in-the-Loop·Shadow Test입니다. Interlock을 우회하지 않고 추천 Action, 작업자 승인, PLC 실행결과를 각각 기록해야 합니다.

팀 결과와 다음 단계

10인 팀은 약 4월 20일부터 30일까지 Factory I/O 가상공정, PLC/Ladder, SCADA·OPC UA와 Web 화면을 연결한 교육 시연을 완료했습니다. 저는 제조 시나리오와 계층별 연결구조, Digital Twin–AI 구간과 최종보고서를 정리했습니다.

보고서의 예지보전, DQN·PPO 자율제어, MADRL 에너지관리와 셋업시간 단축 수치는 향후 적용목표 또는 외부 Benchmark입니다. 다음 단계에서는 통신단절·Stale Value·Timeout·Reconnect, 설비고장·복구, 실측 Cycle Time과 물류동선, 물리 PLC Hardware-in-the-Loop를 먼저 검증해야 합니다.

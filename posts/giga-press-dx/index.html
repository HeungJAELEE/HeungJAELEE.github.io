30초 요약

실물 설비에서 처음 시퀀스와 통신을 맞추면 오류 수정 비용이 커집니다. 가상 환경에서 신호 책임과 실패 조건을 먼저 확인하는 이유를 보여주기 위해 구성했습니다.

가상 시운전·데이터 흐름 PoC

해결하려던 문제

PLC·SCADA·가상설비·상위 데이터가 같은 신호를 서로 다르게 해석하면 시운전 단계에서 인터록·알람·통신 오류가 늦게 발견됩니다.

내가 맡은 범위

  • AI 모델 후보 선정·학습, 통신 셋업과 기술 조사를 맡았습니다.

확인된 결과·현재 단계

  • 확인된 산출물 · 팀 결과 가상설비·PLC·SCADA·OPC UA를 연결한 팀 데모와 보고서
  • 확인된 산출물 · 개인 역할 AI 모델 후보·학습, 통신 셋업, 기술 조사

팀 경계

Ladder와 SCADA 구현은 팀원 역할이며, Factory I/O–PLC–SCADA–OPC UA 전체는 10인 팀 결과입니다.

공개 범위: 팀 내부 편집 링크와 원자료는 공개하지 않고, 개인 역할과 공개 가능한 시스템 흐름만 정리했습니다.

아래 흐름은 팀 과제를 바탕으로 가상 시운전 업무에 적용할 수 있게 일반화했습니다.

왜 이 의사결정이 중요했는가

고가 설비는 실제 장비가 들어온 뒤에 제어 순서나 통신 문제를 발견할수록 수정 비용과 시운전 위험이 커집니다. 센서 상태, PLC 판단, 화면 표시가 서로 다르면 작업자는 어느 정보가 맞는지 확인하는 데 시간을 쓰게 됩니다. 이 팀 프로젝트는 기가프레스 공장의 맥락을 빌려, 실제 설비 투입 전에 공정 순서와 데이터 연결을 확인하는 방법을 검토했습니다.

대상은 양산 기가프레스 전체를 구축하는 일이 아니었습니다. Factory I/O, PLC, SCADA와 상위 통신을 연결한 가상 시운전 시나리오를 만들고, 물리 장비로 넘어가기 전에 무엇을 점검해야 하는지 정리한 PoC였습니다.

왜 디지털 방식이 필요했는가

실제 설비에서만 로직을 시험하면 센서 누락, 완료 신호 지연, 재기동 조건 같은 문제를 늦게 발견할 수 있습니다. 가상 공정은 같은 비정상 조건을 반복해서 넣어 보고, 제어 상태와 화면의 데이터가 일치하는지 먼저 확인하게 해 줍니다.

팀은 제어권을 PLC에 남기고 역할을 나눴습니다. Factory I/O는 가상 공정, PLC는 시퀀스와 인터록, SCADA는 상태와 알람의 표시, OPC UA 흐름은 상위 시스템과 AI 후보가 사용할 데이터를 전달하는 경계로 보았습니다. AI는 안전 제어를 대신하지 않고 최적화 후보를 검토하는 위치에 두었습니다.

실제로 맡은 역할

이 작업은 10인 팀 프로젝트였습니다. 제 역할은 Digital Twin 파트의 AI 모델 선정·학습, 통신 셋업, 자료 조사에 한정됩니다. 실시간 센서·PLC 데이터를 활용하는 DQN 후보를 검토하고, OPC UA를 포함한 통신 흐름이 팀 시나리오 안에서 어디에 놓이는지 정리했습니다.

Ladder와 SCADA 구현은 담당 팀원의 결과입니다. 이 글은 두 결과를 팀 전체 아키텍처의 일부로 설명하지만, 제 개인 구현으로 확대하지 않습니다.

데이터 흐름

현장 신호 → PLC의 시퀀스·인터록 판단 → Factory I/O 가상 공정과 SCADA 상태 표시 → OPC UA 통신 경계 → 웹·AI 활용 후보

각 계층은 같은 신호를 보되 책임은 다릅니다. 화면이나 AI가 보낸 값이 곧바로 안전 명령이 되지 않으며, 운전 허가와 통신 장애 시 안전 상태는 PLC와 별도의 안전 설계 영역에 남습니다.

구현 순서

  1. 팀이 정상 공정 순서와 정지·지연·재기동 조건을 정리했습니다.
  2. 담당 팀원이 Factory I/O 시나리오와 Ladder 로직을 연결했습니다.
  3. 담당 팀원이 SCADA에서 상태와 알람을 확인할 수 있도록 구성했습니다.
  4. 저는 AI 모델 후보를 선정·학습하고, 통신 셋업과 관련 자료 조사를 진행했습니다.
  5. 팀은 PLC, SCADA, Factory I/O, 웹과 AI 확장 방향을 하나의 시연 흐름과 보고서로 통합했습니다.
  6. 결과를 정리할 때 설계 기대효과와 실제 측정 성과를 분리했습니다.

확인된 결과와 현재 단계

확인된 산출물은 공정 Flow, Ladder·Factory I/O, SCADA, 웹·AI 확장 구조를 연결한 팀 시연과 보고서입니다. 실제 기가프레스의 안전 PLC, 유압·서보 동특성이나 양산 I/O를 포함한 현장 검증은 완료된 범위가 아닙니다.

보고서에 적힌 셋업 시간 50~75% 단축과 설비 증설 공수 50% 절감은 가상 시운전과 Ladder 모듈화의 기대효과 또는 목표값입니다. 실제 공장 적용 전후를 같은 조건으로 측정한 성과가 아니므로 달성 수치로 사용하지 않습니다.

배포 조건과 회사에 줄 수 있는 가치

현장 적용 전에는 실제 I/O와 안전 요구사항을 반영한 Hardware-in-the-Loop 시험, 통신 끊김과 재접속 시험, 태그 명세의 버전 관리, 알람 우선순위, 네트워크 분리와 접근 권한 검토가 필요합니다. AI 후보를 사용하더라도 운전 명령과 안전 판단을 넘길 수 없고, 추천값의 승인·거부·되돌리기 절차가 있어야 합니다.

이 조건이 갖춰지면 가상 시운전은 논리 오류와 데이터 불일치를 실제 트라이아웃보다 앞에서 발견하고, 팀 간 검토 기준을 맞추는 데 도움이 될 수 있습니다. 회사 가치는 설비 변경의 영향을 사전에 확인하고 재사용 가능한 검증 절차를 축적하는 데 있습니다. 시간이나 공수 절감은 실제 기준선과 비교 측정한 뒤에만 성과로 확정할 수 있습니다.

Problem

실물 설비 투입 전에는 PLC 시퀀스, SCADA 태그, 센서 이상과 통신 지연을 함께 검증하기 어려워 오류가 현장 트라이아웃 단계에서 늦게 발견됩니다.

Goal

Factory I/O–PLC–SCADA–OPC UA의 책임과 데이터 계약을 먼저 정의하고, 정상·고장·재기동 시나리오를 가상 환경에서 검토할 수 있는 제조 DX 기준안을 만드는 것입니다.

Success

팀 데모와 보고서에서 데이터 흐름·역할·검증 시나리오가 추적되고, 기대효과가 실제 측정 성과와 명확히 구분되면 성공으로 판단합니다.

범위와 경계

포함 범위

  • Factory I/O, PLC, SCADA, OPC UA 사이 신호 흐름과 책임 경계
  • 정상 운전, 센서 누락, 통신 지연, 재기동 검증 시나리오
  • 실시간 센서·PLC 데이터를 활용하는 DQN 후보 검토

제외·미검증 범위

  • 실제 기가프레스 안전 PLC와 하드웨어 사양의 생산 배포
  • Ladder·SCADA 구현을 개인 단독 성과로 귀속하는 표현
  • 50~75%·50% 기대효과를 공장 실측 성과로 해석하는 주장

구현·검증 기준

해야 할 일

  • 공통 태그에 equipment, signal, value, quality, timestamp를 포함한다.
  • PLC가 인터록과 최종 운전 허가를 소유하고 AI는 보조 권고만 제공한다.
  • SCADA에서 상태·알람·지연·수동 명령 결과를 같은 태그 기준으로 추적한다.

품질·운영 기준

  • 통신 단절 시 마지막 명령을 유지하지 않고 안전 상태로 전환한다.
  • 정상 흐름뿐 아니라 실패·복구 시나리오를 반복 검증한다.
  • 목표값, 팀 결과, 개인 기여와 미검증 항목을 분리 기록한다.

왜 이렇게 구성했나

  1. PLC에 제어권 유지

    비결정적 AI 응답이나 통신 지연이 안전 인터록을 우회하지 않도록 최종 권한을 PLC에 남겼습니다.

  2. OPC UA를 상위 데이터 경계로 사용

    주소 중심 통신보다 태그 의미와 품질 정보를 함께 전달해 SCADA·분석 계층의 결합도를 낮추기 위해서입니다.

  3. 실물 전에 Factory I/O로 실패 주입

    현장에서 재현하기 어려운 센서 누락·지연·모드 충돌을 반복 시험하기 위해서입니다.

    TECHNICAL CASE STUDY

    기가프레스 공장 DX 전환 시나리오: 현장 신호부터 가상 검증까지

    Arduino·Raspberry Pi, PLC, SCADA, Factory I/O를 계층화해 설비 연동과 사전 검증을 설계한 제조 DX 포트폴리오

    2026. 7. 9. · 11 · 마지막 검토 2026. 7. 31.

    • DX
    • IoT
    • PLC
    • SCADA
    • Factory I/O

    문제: 실제 설비 투입 전에 공정·통신 위험을 검증해야 한다

    항목확인된 내용
    Problem실제 설비를 투입해야만 시퀀스와 파라미터를 확인할 수 있어 트라이아웃이 길어지고, PLC·SCADA·가상 모델 사이 데이터 정합성을 사전에 확인하기 어려웠습니다.
    Role10인 팀 프로젝트에서 Digital Twin 파트의 AI 모델 선정·학습, 통신 셋업, 자료 조사를 맡았습니다. Ladder와 SCADA 구현은 담당 팀원의 결과이며 제 개인 역할로 확대하지 않습니다.
    ActionFactory I/O–PLC–SCADA–OPC UA 계층의 데이터 흐름을 정리하고, 실시간 센서·PLC 데이터를 사용하는 DQN 후보와 통신 구성을 검토했습니다.
    Result공정 Flow, Ladder/Factory I/O, SCADA, 웹·AI 확장 구조를 하나의 팀 시연·보고서로 통합했습니다. 보고서의 “셋업 50~75% 단축”과 “증설 공수 50% 절감”은 기대효과/목표값이며 실제 공장 실측 성과로 주장하지 않습니다.
    Evidence팀 발표 PDF·Canva 보고서의 역할표, 아키텍처, 결과 및 기대효과 페이지. 전용 공개 소스 저장소는 미분리 상태입니다.

    이력서 Bullet

    • 10인 제조 DX 팀 프로젝트에서 AI 모델 선정·학습과 OPC UA 통신 셋업 범위를 담당하고, Factory I/O–PLC–SCADA 데이터 흐름을 가상 시운전 시나리오로 구조화했습니다.
    • 실제 설비 성과와 설계 기대효과를 분리해, 보고서의 50~75% 셋업 단축·50% 증설 공수 절감을 검증 전 목표값으로 관리했습니다.
    • 배터리 라인 FAT/SAT 경험을 바탕으로 정상 시퀀스뿐 아니라 센서 누락·통신 지연·재기동 조건을 검증 항목에 포함했습니다.

    면접 STAR

    • Situation: 고가 설비는 실제 투입 전 제어 로직과 데이터 정합성을 충분히 시험하기 어렵고, 현장 트라이아웃이 길어질 위험이 있었습니다.
    • Task: 제 역할은 팀의 가상 공정 구조에서 AI 적용 후보와 통신 경계를 정리해 제어·모니터링 계층이 같은 데이터를 보도록 만드는 것이었습니다.
    • Action: 센서/PLC 데이터를 OPC UA 흐름으로 연결하고 DQN 적용 위치를 검토했으며, 현장 제어권은 PLC에 남기고 AI는 검증·최적화 후보로 한정했습니다.
    • Result: 팀이 Factory I/O, Ladder, SCADA, 웹·AI 확장을 하나의 시나리오로 시연할 수 있었습니다. 정량값은 기대효과로 남기고 실측 성과와 구분했습니다.

    프로젝트를 한 문장으로 설명하면

    현장 센서 신호를 곧바로 상위 시스템에 연결하는 대신, 에지 수집·PLC 제어·SCADA 가시화·Factory I/O 사전 검증의 네 계층으로 분리해 설비 변경의 영향을 먼저 확인할 수 있도록 구성한 제조 DX 시나리오입니다.

    이 글에서 말하는 기가프레스는 대형 프레스 공장을 이해하기 위한 공정 맥락입니다. 실제 양산 기가프레스 전체를 구축했다는 의미가 아니며, 하드웨어 사양과 안전 회로가 확정되지 않은 부분은 설계 또는 PoC(개념 검증) 범위로 구분했습니다.

    구분내용
    프로젝트 성격스마트팩토리 제어·모니터링·가상 검증 PoC
    대상 범위에지 디바이스 → PLC → SCADA → Factory I/O
    핵심 기술Arduino, Raspberry Pi, MELSEC·LS 계열 PLC 개념, Ladder Logic, Modbus/TCP·OPC UA 연동 검토
    보고서의 기대효과셋업 시간 50~75% 단축 목표, Ladder 모듈화에 따른 설비 증설 공수 50% 절감 목표
    실무 관점FAT/SAT, 인터록, 표준화, 변경 영향 분석, 장애 시 안전 상태 유지

    위 수치는 팀 보고서의 기대효과 페이지에 제시된 목표값입니다. 실제 공장 적용 전후를 같은 조건으로 측정한 실적이 아니므로 결과 수치로 확대 해석하지 않습니다.

    왜 이 프로젝트를 구성했는가

    제조 라인의 DX는 센서 값을 화면에 표시하는 것만으로 완성되지 않습니다. 현장에서는 다음 문제가 동시에 발생합니다.

    1. 센서와 설비마다 데이터 형식, 갱신 주기, 통신 방식이 다릅니다.
    2. 제어 로직과 화면 로직이 강하게 결합되면 작은 설비 변경도 전체 프로그램 수정으로 이어집니다.
    3. 실제 장비에서 처음 시퀀스를 시험하면 충돌, 오동작, 장시간 정지의 위험이 커집니다.
    4. 통신이 끊겼을 때 마지막 명령을 계속 유지할지, 정지할지에 대한 기준이 없으면 안전한 운영이 어렵습니다.

    따라서 이 프로젝트에서는 제어의 책임은 PLC에 두고, 에지 장치는 수집과 정규화, SCADA는 상태 가시화, Factory I/O는 사전 검증을 담당하도록 역할을 분리했습니다. 계층을 분리하면 한 영역을 바꾸더라도 다른 영역의 수정 범위를 줄일 수 있고, 문제가 발생한 위치도 더 빠르게 추적할 수 있습니다.

    아키텍처와 데이터 흐름

    flowchart LR A["센서·스위치·액추에이터"] --> B["Arduino / Raspberry Pi\n수집·필터·형식 정규화"] B --> C["PLC\n인터록·시퀀스·안전 상태"] C --> D["SCADA\n상태·알람·이력 가시화"] C <--> E["Factory I/O\n가상 시운전·시나리오 검증"] D --> F["상위 시스템 연동 후보\nMES·리포트"]

    현장·에지 계층

    Arduino는 디지털·아날로그 입출력의 빠른 프로토타이핑에 적합하고, Raspberry Pi는 Python 기반 전처리나 여러 통신 인터페이스를 묶는 게이트웨이 역할에 유리합니다. 다만 이 장치가 프레스의 안전 제어를 직접 담당하도록 설계하지 않았습니다. 비상 정지, 도어 인터록처럼 사람과 설비의 안전에 직결되는 기능은 인증된 안전 회로와 PLC 영역에서 다뤄야 하기 때문입니다.

    에지 계층의 책임은 다음으로 제한했습니다.

    • 센서 원시값 읽기와 단위 변환
    • 짧은 펄스나 채터링을 완화하기 위한 기초 필터링
    • 장치별 필드 이름을 공통 태그 이름으로 변환
    • 값, 품질 상태, 수집 시각을 하나의 데이터 단위로 전달

    PLC 제어 계층

    PLC는 공정 순서와 인터록의 최종 책임자입니다. 프레스 동작을 예로 들면 준비 확인 → 소재 존재 확인 → 안전 조건 확인 → 동작 허가 → 완료 확인 → 복귀처럼 단계를 나누고, 각 단계의 진입 조건과 타임아웃을 명시합니다.

    이 프로젝트에서 Ladder 모듈화를 선택한 이유는 설비 증설 시 주소와 로직을 복사해 붙이는 방식을 줄이기 위해서입니다. 모터, 실린더, 센서 묶음을 공통 인터페이스로 정의하면 장치가 추가되어도 같은 상태 모델과 알람 규칙을 재사용할 수 있습니다.

    아래 코드는 실제 PLC 소스가 아니라 제어 의도를 보여 주는 짧은 의사 코드입니다.

    IF safety_ok AND material_ready AND NOT alarm THEN
    run_permit := TRUE
ELSE
    run_permit := FALSE
    IF command_timeout THEN alarm := TRUE
END_IF

    핵심은 run 명령 하나가 아니라 허가 조건, 완료 확인, 타임아웃, 이상 시 복귀 상태를 한 모듈 안에서 함께 관리하는 것입니다.

    SCADA 가시화 계층

    SCADA는 PLC를 대신해 공정을 제어하는 두 번째 두뇌가 아니라, 작업자가 현재 상태를 정확히 판단하도록 돕는 운영 화면으로 보았습니다. 화면에는 다음 정보가 함께 있어야 합니다.

    • 설비별 운전·정지·대기·고장 상태
    • 현재 공정 단계와 단계별 체류 시간
    • 알람 발생 시각, 해제 시각, 확인 여부
    • 센서 값의 품질 상태와 마지막 갱신 시각
    • 수동 명령을 보낸 사용자와 명령 결과

    단순히 초록색과 빨간색 램프를 배치하는 것보다, 왜 정지했는지와 다음 확인 항목이 무엇인지를 보여 주는 것이 다운타임 단축에 더 직접적으로 기여합니다.

    Factory I/O 가상 검증 계층

    Factory I/O는 실제 설비를 멈추지 않고 PLC 시퀀스를 시험하기 위한 가상 시운전 도구로 선택했습니다. 센서가 정상 순서로 들어오는 경우뿐 아니라 센서 미검출, 중복 입력, 액추에이터 지연처럼 현장에서 자주 만나는 비정상 조건을 반복 주입할 수 있습니다.

    가상 모델은 실제 장비의 물리 특성을 완전히 대체하지 않습니다. 대신 FAT 이전에 논리 오류와 인터록 누락을 먼저 발견하는 테스트 하네스로 활용하는 것이 이 구성의 목적입니다.

    사용 기술과 데이터 구성

    장치 주소를 상위 화면에 그대로 노출하면 PLC 주소가 바뀔 때 SCADA와 리포트까지 연쇄 수정해야 합니다. 이를 막기 위해 다음과 같은 논리 태그 모델을 설계했습니다.

    필드역할예시
    equipment_id설비 식별자프레스 또는 이송 장치 ID
    signal_name사람이 이해할 수 있는 태그명소재 감지, 운전 허가
    value현재 값ON/OFF 또는 계측값
    quality값의 신뢰 상태정상, 지연, 통신 끊김
    timestamp수집 또는 갱신 시각이벤트 순서 판정에 사용
    mode설비 운전 모드자동, 수동, 정비

    Modbus/TCP는 PLC·에지 장치 간 단순 레지스터 교환을 빠르게 검증하기 좋고, OPC UA는 태그의 의미와 품질 정보를 포함한 상위 연동에 유리합니다. 이 프로젝트에서는 두 기술을 무조건 동시에 적용했다고 단정하기보다, 장치 제약과 상위 시스템 요구에 따라 선택할 통신 후보로 다뤘습니다.

    구현을 어떤 순서로 진행했는가

    단계 1. 공정 시퀀스와 실패 조건 정의

    정상 동작 순서보다 먼저 정지 조건, 재시작 조건, 수동 복구 절차를 표로 만들었습니다. 이는 이력서에 기술된 P-FMEA, QCP, 설비 검수 경험과 같은 관점입니다. 제어 프로그램을 작성한 뒤 안전 조건을 덧붙이는 것이 아니라, 위험 시나리오를 입력 조건으로 사용했습니다.

    단계 2. I/O 목록과 태그 사전 작성

    센서와 액추에이터마다 주소, 논리명, 단위, 정상 범위, 고장 시 기본값을 정의했습니다. PLC 내부 주소와 외부 공개 태그를 분리해 향후 장비 교체 시 상위 시스템의 변경을 최소화했습니다.

    단계 3. 공통 PLC 모듈 설계

    장치별로 Command, Status, Alarm, Interlock, Timeout을 동일한 구조로 묶었습니다. 신규 장치를 추가할 때 제어 흐름을 새로 만들기보다 파라미터와 I/O 매핑을 추가하는 방향입니다.

    단계 4. 에지 수집과 통신 예외 처리

    연결 끊김, 잘못된 값, 갱신 지연을 정상 데이터와 구분했습니다. 통신이 복구되었다고 설비가 즉시 재기동되지 않도록 PLC에서 재가동 승인 조건을 다시 확인하도록 구성했습니다.

    단계 5. Factory I/O 시나리오 검증

    정상 사이클, 센서 채터링, 완료 신호 누락, 응답 지연, 운전 중 모드 변경을 반복 시험하는 PoC 시나리오를 설계했습니다. 각 시험은 입력 조건, 기대 상태, 알람, 복구 절차가 남도록 구성했습니다.

    단계 6. SCADA 화면과 알람 연결

    설비 상태와 알람을 같은 태그 사전에 연결하고, 작업자가 원인을 좁힐 수 있도록 단계·인터록·통신 품질을 함께 표시했습니다.

    가장 어려웠던 기술적 판단

    신호 필터링과 이상 은폐의 경계

    필터를 강하게 적용하면 노이즈는 줄지만 실제 짧은 이상 신호까지 사라질 수 있습니다. 그래서 모든 값을 평균 처리하기보다 신호 성격에 따라 디바운스, 범위 검사, 연속 확인 횟수를 분리하는 방식으로 설계했습니다. 필터 전 원시값을 진단용으로 남기는 것도 중요합니다.

    서로 다른 갱신 주기

    에지 장치, PLC 스캔, SCADA 폴링, 가상 모델 렌더링은 같은 주기로 움직이지 않습니다. 화면의 부드러움을 위해 PLC 제어 주기를 늦추는 식의 결합을 피하고, 각 계층은 고유 주기를 유지하면서 타임스탬프와 품질 상태로 최신성을 판단하도록 했습니다.

    통신 장애 시 안전 상태

    패킷 하나가 누락되었다는 이유로 즉시 전체 정지를 걸면 가용성이 떨어지고, 반대로 마지막 명령을 무기한 유지하면 위험합니다. 신호별 허용 지연과 타임아웃을 정하고, 중요 신호는 PLC에서 안전 상태로 전환하도록 책임을 명확히 했습니다.

    모듈화와 현장 예외의 균형

    모든 설비를 하나의 거대한 공통 모듈로 만들면 예외 처리 때문에 오히려 복잡해집니다. 공통 상태 모델은 유지하되, 설비 고유 동작은 확장 블록으로 분리하는 방식을 택했습니다.

    AI와 사람의 역할

    AI는 공개 가능한 팀 자료와 구현 기록을 기준으로 공정 흐름, 통신 경계, 검증 항목을 구조화하고 문서 초안을 정리하는 데 사용했습니다. 사람은 PLC·SCADA·OPC UA 설정, Factory I/O 시퀀스, 팀 역할과 실제 확인 범위를 검토했으며 기대효과를 실측 성과처럼 표현하지 않도록 최종 판단했습니다.

    Problem

    실물 설비 투입 전에는 PLC 시퀀스, SCADA 태그, 센서 이상과 통신 지연을 함께 검증하기 어려워 오류가 현장 트라이아웃 단계에서 늦게 발견됩니다.

    Goal

    Factory I/O–PLC–SCADA–OPC UA의 책임과 데이터 계약을 먼저 정의하고, 정상·고장·재기동 시나리오를 가상 환경에서 검토할 수 있는 제조 DX 기준안을 만드는 것입니다.

    Success

    팀 데모와 보고서에서 데이터 흐름·역할·검증 시나리오가 추적되고, 기대효과가 실제 측정 성과와 명확히 구분되면 성공으로 판단합니다.

    범위와 경계

    포함 범위

    • Factory I/O, PLC, SCADA, OPC UA 사이 신호 흐름과 책임 경계
    • 정상 운전, 센서 누락, 통신 지연, 재기동 검증 시나리오
    • 실시간 센서·PLC 데이터를 활용하는 DQN 후보 검토

    제외·미검증 범위

    • 실제 기가프레스 안전 PLC와 하드웨어 사양의 생산 배포
    • Ladder·SCADA 구현을 개인 단독 성과로 귀속하는 표현
    • 50~75%·50% 기대효과를 공장 실측 성과로 해석하는 주장

    구현·검증 기준

    해야 할 일

    • 공통 태그에 equipment, signal, value, quality, timestamp를 포함한다.
    • PLC가 인터록과 최종 운전 허가를 소유하고 AI는 보조 권고만 제공한다.
    • SCADA에서 상태·알람·지연·수동 명령 결과를 같은 태그 기준으로 추적한다.

    품질·운영 기준

    • 통신 단절 시 마지막 명령을 유지하지 않고 안전 상태로 전환한다.
    • 정상 흐름뿐 아니라 실패·복구 시나리오를 반복 검증한다.
    • 목표값, 팀 결과, 개인 기여와 미검증 항목을 분리 기록한다.

    왜 이렇게 구성했나

    1. PLC에 제어권 유지

      비결정적 AI 응답이나 통신 지연이 안전 인터록을 우회하지 않도록 최종 권한을 PLC에 남겼습니다.

    2. OPC UA를 상위 데이터 경계로 사용

      주소 중심 통신보다 태그 의미와 품질 정보를 함께 전달해 SCADA·분석 계층의 결합도를 낮추기 위해서입니다.

    3. 실물 전에 Factory I/O로 실패 주입

      현장에서 재현하기 어려운 센서 누락·지연·모드 충돌을 반복 시험하기 위해서입니다.

    검증 결과

    검증 시나리오확인 내용합격 기준의 예
    정상 자동 운전단계 전이와 완료 신호정의된 순서 외 전이 없음
    센서 채터링중복 명령·오동작 여부필터 후 단일 이벤트로 처리
    통신 지연·끊김품질 상태와 안전 전환타임아웃 알람 및 재기동 방지
    액추에이터 미완료단계 정지와 원인 표시다음 단계 진입 차단
    수동/자동 전환모드 충돌 방지운전 중 무조건 전환되지 않음
    설비 모듈 추가기존 로직 영향 범위공통 인터페이스로 변경 범위 제한

    팀 보고서는 Factory I/O 사전 검증과 SCADA 동기화를 통한 셋업 시간 50~75% 단축, Ladder 모듈화에 따른 설비 증설 공수 50% 절감을 기대효과로 제안합니다. 현재 공개 Evidence로는 실제 공장 적용 전후 측정이 확인되지 않으므로, 여기서 검증된 산출물은 목표 수치가 아니라 가상 공정·제어·통신·모니터링을 연결한 팀 시나리오와 보고서입니다.

    • 가상 시운전: 실제 장비에서 발견할 논리 오류를 앞 단계로 이동
    • 태그 표준화: 주소 변경에 따른 연쇄 수정 감소
    • PLC 모듈화: 반복 로직 작성과 검증 공수 감소
    • 알람 구조화: 정지 원인 탐색 시간 감소

    이력서 경력과 어떻게 연결되는가

    이 프로젝트는 단순 IoT 데모보다 실제 제조 라인에서 쌓은 경험을 소프트웨어 구조로 옮긴 작업에 가깝습니다.

    • 2170·4695 원통형 셀 라인의 셋업과 안정화 경험을 바탕으로, 가상 검증의 목표를 화면 구현이 아니라 시운전 리스크 감소에 두었습니다.
    • 조립 설비 FAT/SAT와 양산 라인 검수 경험은 I/O 목록, 인터록, 펀치리스트, 합격 기준을 먼저 정의하는 방식에 반영했습니다.
    • P-FMEA, QCP, MSA 기준 수립 경험은 정상 시나리오뿐 아니라 고장 모드와 측정 신뢰도를 검증 항목에 포함하는 근거가 됐습니다.
    • Mitsubishi·LS산전 PLC 학습 및 현장 자동화 경험은 제어권을 PLC에 유지하고, 에지와 SCADA를 보조 계층으로 배치한 이유와 연결됩니다.

    즉, 이 포트폴리오는 “무엇을 연결할 수 있는가”보다 “연결한 시스템을 제조 현장에서 어떻게 안전하게 검증하고 변경할 것인가”를 보여 줍니다.

    한계와 다음 개선 방향

    현재 단계에서 실제 기가프레스의 안전 PLC, 제조사 전용 프로토콜, 유압·서보의 정밀 동특성까지 검증했다고 말할 수는 없습니다. 다음 단계에서는 아래 항목이 필요합니다.

    1. 실제 장비 I/O와 안전 요구사항을 반영한 Hardware-in-the-Loop 검증
    2. 태그 명세의 버전 관리와 OPC UA 정보 모델 정식화
    3. 알람 홍수 방지를 위한 우선순위·억제 규칙
    4. 시나리오별 자동 회귀 테스트와 결과 리포트 생성
    5. MES 연동 시 작업지시·LOT·품질 데이터의 추적성 설계
    6. 네트워크 분리, 계정 권한, 감사 로그를 포함한 OT 보안 검토

    이 개선까지 이어지면 PoC를 넘어 실제 설비 프로젝트에서 재사용할 수 있는 가상 시운전 표준 패키지로 발전시킬 수 있습니다.

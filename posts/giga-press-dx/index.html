팀이 해결하려던 문제

공장을 확장할 때 설비 수만 늘린다고 목표 생산량을 맞출 수 있는 것은 아닙니다. Cycle Time, 병목, 설비 간 이동과 Buffer를 함께 봐야 합니다. 팀은 기가프레스 공장 확장을 가정하고 설비를 설치하기 전에 가상공장에서 생산흐름과 병목 후보를 검토하는 시나리오를 만들었습니다.

저는 프로젝트의 목적과 전체 구조, 팀 역할을 기획하고 결과 보고서를 작성했습니다. Factory I/O·Ladder·SCADA의 세부 구현은 팀원이 맡았고, 저는 가상공장 상태와 생산 데이터를 분석 입력과 제조 판단 항목으로 바꾸는 연결 구간을 담당했습니다.

센서 이벤트가 생산 판단으로 이어지는 전체 흐름

flowchart LR A["가상공장 이벤트
TEAM"] --> B["Factory I/O·PLC·OPC
TEAM·SHARED"] --> C["SCADA·SQLite
TEAM·SHARED"] --> D["Cycle Time·Buffer·생산량
MY CORE"] --> E["확장 시나리오
MY CORE"] E -.-> F["AI·PLC 피드백
FUTURE"]

TEAM은 팀 구현, MY CORE는 제가 직접 기획·연결한 구간, SHARED는 공동 인터페이스, FUTURE는 미구현 후속 범위입니다. PLC·SCADA가 보여 주는 상태와 분석 데이터가 같은 공정을 가리키도록 연결하는 것이 핵심이었습니다.

제가 맡은 것은 상태데이터를 제조 판단값으로 바꾸는 구간이었습니다

01

MY CORE

Digital Twin 상태와 분석 입력의 의미를 맞췄습니다

모델 이름보다 어떤 데이터를 왜 입력으로 쓰고 결과를 어디까지 해석할지를 먼저 정했습니다.
flowchart LR A["상태·이벤트 의미 정의
MY CORE"] --> B["공정시간·대기·Buffer 분리"] --> C["생산지표 분석 입력 구성"] --> D["설비·물류·생산량 시나리오"] D -.-> E["PLC 자동제어
미구현"]
  • 전체 프로젝트의 목적, 시스템 구성과 팀 역할을 먼저 정했습니다.
  • PLC·SCADA 상태를 Cycle Time, 가동률, Buffer와 생산량으로 연결해 분석 입력의 의미를 맞췄습니다.
  • 결과는 설비 수·물류길이·예상 생산량을 검토하는 시나리오 정보로 제한했습니다.
  • 당시 AI 구현코드와 재현 가능한 실행환경은 남아 있지 않아, AI 최적화 완료나 PLC 폐루프 제어로 설명하지 않습니다.
  • 팀 구현과 제 책임, 확인된 시연 범위를 구분해 프로젝트 보고서를 직접 작성했습니다.

설비 수보다 생산흐름과 병목 후보를 먼저 봤습니다

02

DESIGN DECISION

공정시간과 물류시간을 분리해 정체 위치를 찾았습니다

목표 생산량만으로 설비 수를 정하지 않고 대기와 Buffer가 생기는 지점을 함께 확인했습니다.

판단 순서

  1. 목표 생산량을 공정별 Cycle Time으로 나눴습니다.
  2. 이송시간과 Buffer 대기를 별도로 연결했습니다.
  3. Factory I/O 흐름과 PLC·SCADA 상태가 같은 공정을 가리키는지 확인했습니다.
  4. 정체 구간을 찾은 뒤 설비 수와 배치 시나리오를 검토했습니다.

확인한 범위

  • 팀 시연에서 T자 물류 분기구간의 약 1초 정체를 병목 후보로 확인했습니다.
  • 정상 통신과 가상 생산흐름을 하나의 교육 시연으로 연결했습니다.
  • 최적 Layout을 확정하거나 실공장 생산성을 개선한 결과는 아닙니다.
  • 통신 단절·고장·복구와 AI 결과의 PLC 반영은 후속 Gate로 남겼습니다.

팀 결과와 현재 단계

10인 팀은 Factory I/O·PLC·SCADA·OPC UA·SQLite를 연결해 가상 생산흐름과 생산지표를 교육 시연으로 확인했습니다. 저는 전체 기획, 결과 보고서와 상태데이터–분석 입력 연결 구간을 맡았습니다.

확인한 결과는 정상 데이터 흐름과 확장 시나리오 검토까지입니다. 실제 현장 적용에는 실측 Cycle Time과 물류동선, 안전 PLC, 제조사 Protocol, 고장·통신 단절과 복구 시나리오, Hardware-in-the-Loop와 FAT/SAT 기준이 더 필요합니다.

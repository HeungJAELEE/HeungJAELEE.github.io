    딥러닝 모델링 교과서: 제조 데이터까지 연결하는 학습·실험 설계

    2026. 7. 13. · 11 · 마지막 검토 2026. 7. 31.

    • Deep Learning
    • Python
    • MLOps
    • Reproducibility

    문제: 실행되는 학습 코드만으로는 재현 가능한 실험이 되지 않는다

    딥러닝 모델링 교과서는 데이터 전처리, 모델 학습, 평가, 재현성 관리를 하나의 흐름으로 정리하기 위한 개인 학습·실무 검증 프로젝트다. 단편적인 예제 코드를 따라 쓰는 데서 끝내지 않고, 새로운 데이터가 들어왔을 때 같은 절차로 문제를 정의하고 결과를 확인할 수 있는 모델링 기준을 만드는 데 목적을 두었다.

    공개 저장소에서 현재 확인할 수 있는 설명은 제한적이다. 따라서 이 글은 저장소의 기존 프로젝트 요약인 “전처리–학습–평가–재현성 관리”를 바탕으로 한 설계 문서이며, 특정 데이터셋 규모, 모델 정확도, 학습 완료, 운영 배포 성과를 주장하지 않는다. 아래 디렉터리와 검증 항목 역시 구현 완료 목록이 아니라 저장소를 발전시키기 위한 기준이다.

    프로젝트 배경: 실행되는 코드와 신뢰할 수 있는 실험은 다르다

    딥러닝 학습 예제는 하나의 노트북 안에서 데이터 로딩부터 정확도 출력까지 빠르게 실행할 수 있다. 하지만 실무에서는 다음 질문에 답할 수 있어야 한다.

    • 어떤 버전의 데이터로 학습했는가?
    • 학습·검증·테스트 데이터가 서로 섞이지 않았는가?
    • 전처리 기준이 학습 시점과 추론 시점에 동일한가?
    • 모델이 좋아졌다는 판단은 어떤 지표와 기준선에 근거하는가?
    • 같은 설정으로 다시 실행했을 때 결과 차이를 설명할 수 있는가?
    • 제조 현장에 적용할 때 미검출과 오검출 중 무엇이 더 위험한가?

    이 프로젝트는 이런 질문을 모델 학습 뒤에 붙이는 부가 문서가 아니라, 처음부터 실험 흐름 안에 넣는 연습이다. 목표는 가장 복잡한 모델을 만드는 것이 아니라 데이터와 결과 사이의 인과관계를 추적할 수 있는 실험 습관을 갖추는 것이다.

    프로젝트 목표

    1. 전처리, 학습, 평가 단계를 명확히 분리한다.
    2. 데이터 누수와 평가 오염을 모델 선택 전에 차단한다.
    3. 설정, 코드, 결과물을 함께 기록해 실험을 재현 가능하게 만든다.
    4. 전체 정확도뿐 아니라 오류 유형과 업무 비용을 함께 해석한다.
    5. 학습용 예제를 제조 품질·설비 데이터 문제에 옮길 수 있는 기준으로 정리한다.

    왜 파이프라인 구조로 구성하는가

    딥러닝 모델링은 “데이터를 넣고 학습한다”는 한 단계가 아니다. 각 단계의 입력과 출력이 분명해야 오류가 발생했을 때 원인을 좁힐 수 있다. 그래서 원본 데이터부터 평가 보고서까지를 다음과 같은 파이프라인으로 본다.

    graph LR A["원본 데이터"] --> B["스키마·품질 점검"] B --> C["학습·검증·테스트 분할"] C --> D["전처리·특징 변환"] D --> E["기준선 모델"] E --> F["딥러닝 학습"] F --> G["고정 테스트 평가"] G --> H["오류 분석"] H --> I["모델·설정·평가 기록"] I -->|"개선 가설"| B

    이 구조를 선택한 이유는 세 가지다.

    • 누수 방지: 데이터 분할을 먼저 확정한 뒤 학습 데이터에만 전처리 기준을 맞춘다.
    • 비교 가능성: 모델 구조가 달라도 동일한 데이터 분할과 평가 함수로 비교한다.
    • 원인 추적: 성능 변화가 데이터, 전처리, 모델, 임계값 중 어디에서 발생했는지 기록한다.

    노트북 하나에 모든 로직을 넣으면 탐색은 빠르지만, 실행 순서와 숨은 상태에 따라 결과가 달라질 수 있다. 학습용 저장소에서도 데이터 준비, 학습, 평가를 함수 또는 스크립트 단위로 나누는 편이 실무 전환에 유리하다.

    아키텍처와 데이터 흐름

    데이터 계약, 전처리, 학습, 평가, artifact와 실행 환경 기록을 분리하고 동일한 설정으로 다시 실행할 수 있게 구성했습니다. 입력 데이터와 평가 기준이 바뀌면 기존 결과를 최신 성능처럼 재사용하지 않는 것이 핵심입니다.

    사용 기술과 선택 이유

    Python

    데이터 처리, 모델 실험, 평가 자동화를 하나의 언어로 연결하기 위해 Python을 중심 언어로 둔다. 특정 딥러닝 프레임워크에 종속된 사용법을 외우기보다, 입력 텐서 형태, 학습 루프, 손실 함수, 평가 함수가 어떤 계약을 갖는지 이해하는 데 초점을 맞춘다.

    Deep Learning 모델링

    모델은 문제를 해결하는 구성 요소 중 하나로 취급한다. 모델 깊이나 파라미터 수를 늘리기 전에 단순 기준선, 데이터 분할, 오류 비용을 먼저 정의한다. 이 순서를 지켜야 복잡한 모델이 실제로 개선됐는지 판단할 수 있다.

    MLOps 관점의 실험 관리

    여기서 MLOps는 대규모 배포 플랫폼을 구축했다는 뜻이 아니다. 학습 단계에서도 다음 정보를 함께 관리하는 실무 습관을 의미한다.

    • 데이터 스냅샷 또는 데이터 버전 식별자
    • 학습·검증·테스트 분할 기준
    • 전처리 설정과 모델 하이퍼파라미터
    • 난수 시드와 실행 환경
    • 모델 가중치, 평가 지표, 오류 분석 결과
    • 코드 커밋과 실험 결과의 연결

    GitHub

    코드와 문서를 버전으로 남겨 학습 과정과 설계 변경 이유를 추적하는 공간으로 사용한다. 다만 현재 공개 저장소의 내용만으로 실제 실험 재현성을 검증할 수는 없으며, 향후 코드·설정·실행 방법을 보강해야 한다.

    권장 저장소 구조와 각 구성의 이유

    다음 구조는 현재 구현 완료 상태를 설명하는 목록이 아니라, 프로젝트를 재현 가능한 학습·검증 저장소로 발전시키기 위한 설계 기준이다.

    Deep_Learning_Text_book/
├─ README.md              # 문제 정의, 실행 순서, 결과 해석
├─ configs/               # 데이터·모델·학습 설정
├─ notebooks/             # 탐색과 개념 검증
├─ src/
│  ├─ data/               # 로딩, 검증, 분할
│  ├─ preprocessing/      # 학습/추론 공통 변환
│  ├─ models/             # 모델 생성 인터페이스
│  ├─ train.py            # 학습 진입점
│  └─ evaluate.py         # 고정 평가 진입점
├─ tests/                 # 스키마와 전처리 단위 테스트
├─ reports/               # 지표, 혼동행렬, 오류 사례
└─ artifacts/             # 모델과 실행 메타데이터

    notebooks/와 src/를 나누는 이유

    노트북은 데이터 분포를 보고 가설을 빠르게 확인하는 데 적합하다. 반면 재현이 필요한 전처리와 학습 로직은 실행 순서가 고정된 코드로 옮겨야 한다. 탐색과 운영 가능한 로직을 분리하면 노트북 셀의 숨은 상태에 의존하는 문제를 줄일 수 있다.

    configs/를 별도로 두는 이유

    학습률, 배치 크기, 입력 크기 같은 설정이 코드 곳곳에 흩어지면 어떤 변경이 결과에 영향을 주었는지 찾기 어렵다. 설정을 파일로 분리하고 결과와 함께 저장하면 실험 간 차이를 비교할 수 있다. 이 글에서는 특정 최적값을 제시하지 않는다. 적절한 값은 데이터와 평가 결과로 정해야 한다.

    reports/와 artifacts/를 나누는 이유

    보고서는 사람이 판단하기 위한 지표와 오류 사례이고, 아티팩트는 모델 가중치와 실행 메타데이터처럼 다시 실행할 때 필요한 결과물이다. 목적이 다른 산출물을 분리하면 무엇을 검토하고 무엇을 재사용해야 하는지 명확해진다.

    데이터와 구현 흐름

    문제와 평가 단위를 먼저 정의한다

    모델을 선택하기 전에 한 건의 예측이 무엇인지 정의한다. 이미지 한 장인지, 제품 한 개의 여러 촬영면인지, 설비의 일정 시간 구간인지에 따라 데이터 분할과 평가 방식이 달라진다. 제조 문제라면 불량 미검출, 정상 오검출, 추론 지연이 각각 어떤 비용을 만드는지도 함께 적는다.

    원본 데이터를 보존하고 스키마를 검사한다

    원본 데이터는 수정하지 않고 읽기 전용 기준으로 남긴다. 파일 경로, 레이블, 설비, 생산 일자, 로트와 같은 메타데이터의 형식·누락·중복을 먼저 확인한다. 이미지나 센서 값 자체보다 메타데이터 오류 때문에 데이터가 잘못 섞이는 경우도 있으므로 스키마 검사가 선행돼야 한다.

    전처리 전에 데이터를 분할한다

    전체 데이터 통계로 정규화 값을 만들거나 증강한 샘플이 서로 다른 세트에 들어가면 데이터 누수가 생길 수 있다. 따라서 학습·검증·테스트의 경계를 먼저 고정하고, 학습 데이터로 계산한 전처리 기준만 검증과 테스트에 적용한다.

    제조 데이터는 같은 설비, 로트, 촬영 세션의 샘플이 매우 비슷할 수 있다. 무작위 행 분할만 사용하면 사실상 같은 제품의 정보가 학습과 테스트에 함께 들어갈 수 있으므로, 문제에 따라 설비·로트·시간 기준의 그룹 분할을 검토한다.

    단순 기준선을 먼저 만든다

    딥러닝 모델을 복잡하게 만들기 전에 단순 규칙이나 작은 모델로 기준선을 만든다. 기준선은 높은 성능을 내기 위한 것이 아니라, 이후 변경이 실제 가치를 추가했는지 판단하기 위한 비교점이다.

    설정 기반으로 학습한다

    데이터 버전, 분할 기준, 모델 설정, 학습 설정, 난수 시드, 실행 환경을 한 번의 실행 단위로 묶는다. 학습 손실만 저장하지 않고 검증 지표 변화와 과적합 징후를 함께 본다. 테스트 세트는 모델 선택에 반복 사용하지 않고 최종 평가 단계까지 고정한다.

    지표와 오류 사례를 함께 본다

    분류 문제라면 정확도 외에도 정밀도, 재현율, F1, 혼동행렬을 문제의 비용에 맞게 선택한다. 예를 들어 불량품을 정상으로 통과시키는 비용이 크다면 불량 클래스의 재현율과 미검출 사례를 우선 확인한다. 반대로 과도한 오검출이 생산 중단을 유발한다면 정밀도와 알람 빈도도 함께 봐야 한다.

    결과를 모델 파일 하나로 끝내지 않는다

    최소한 다음 정보를 결과와 함께 남겨야 한다.

    기록 항목필요한 이유
    데이터 식별자와 분할 기준평가 데이터가 바뀌었는지 확인하기 위해
    코드 커밋과 설정어떤 구현과 조건으로 실행했는지 재현하기 위해
    학습·검증 곡선과적합, 미학습, 불안정 여부를 보기 위해
    클래스별 지표와 혼동행렬평균값에 가려진 오류 유형을 찾기 위해
    대표 오류 샘플다음 데이터·모델 개선 가설을 만들기 위해
    실행 환경라이브러리·하드웨어 차이를 설명하기 위해

    기술적 난제와 해결 관점

    데이터 누수

    가장 위험한 문제는 모델 코드가 아니라 평가 경계가 무너지는 것이다. 중복 데이터, 같은 로트, 같은 촬영 세션, 미래 시점 정보가 서로 다른 세트에 섞이지 않는지 먼저 검사한다. 분할 기준 자체를 설정과 보고서에 남겨야 한다.

    클래스 불균형

    제조 품질 데이터는 정상 샘플이 많고 희귀 불량이 적을 수 있다. 전체 정확도만 보면 모델이 모든 샘플을 정상으로 예측해도 좋아 보일 수 있다. 클래스별 지표, 샘플링 전략, 손실 가중치, 임계값 조정을 비교하되, 어느 방식이 낫다고 미리 단정하지 않고 고정 검증 세트에서 판단한다.

    재현성과 완전한 동일성의 차이

    난수 시드를 고정해도 하드웨어와 라이브러리 연산에 따라 결과가 완전히 같지 않을 수 있다. 재현성의 목표를 “모든 숫자가 동일함”으로만 두지 않고, 동일한 코드·데이터·설정으로 유사한 결론을 다시 얻고 차이를 설명할 수 있는 상태로 정의한다.

    좋은 오프라인 지표와 현장 성능의 차이

    학습 데이터와 실제 설비의 조명, 소재, 센서 조건이 달라지면 성능이 변할 수 있다. 따라서 오프라인 테스트와 별도로 조건별 슬라이스 평가, 시간 경과에 따른 데이터 변화, 추론 시간과 실패 처리 같은 운영 관점을 준비해야 한다.

    실험 수 증가에 따른 비교 혼란

    하이퍼파라미터를 많이 바꾸면 가장 높은 결과만 골라 해석하기 쉽다. 한 번에 하나의 가설을 바꾸고, 실패한 실험도 설정과 이유를 남겨야 같은 시도를 반복하지 않는다.

    AI와 사람의 역할

    AI는 모델 후보, 전처리·평가 코드 초안, 실험 비교표와 문서화를 보조합니다. 사람은 데이터 사용 권리, train·validation·test 분리, 평가 지표, 실행 환경, 결과 승인과 공개 범위를 확인하며 검증되지 않은 성능을 성과로 채택하지 않습니다.

    Problem

    노트북이 한 번 실행된 사실만으로는 데이터 누수, 전처리 일관성, 재현성, 기준선 대비 개선과 제조 현장의 오류 비용을 설명할 수 없습니다.

    Goal

    전처리–학습–평가–재현성 관리를 분리하고, 새로운 제조 데이터에도 같은 기준으로 실험을 반복할 수 있는 학습 저장소 구조를 만드는 것입니다.

    Success

    고정 데이터 분할, 설정·seed·artifact 기록, 기준선 비교와 error analysis가 자동 검증되고 다른 환경에서 재실행되면 성공입니다.

    범위와 경계

    포함 범위

    • 데이터 schema·split·전처리·augmentation 기준
    • baseline, train/evaluate pipeline, metric·artifact logging
    • 제조 불균형 데이터의 Recall·Precision·F1·error analysis

    제외·미검증 범위

    • 공개 근거 없는 특정 모델 정확도와 학습 완료 주장
    • 운영 배포와 MLOps 플랫폼이 이미 완성됐다는 표현
    • 하나의 노트북 결과를 재현 가능한 실험으로 간주

    구현·검증 기준

    해야 할 일

    • train/validation/test split을 고정하고 데이터 누수를 검사한다.
    • config, seed, code/data version과 model artifact를 함께 기록한다.
    • accuracy 외 Recall·Precision·F1과 confusion matrix를 생성한다.

    품질·운영 기준

    • 같은 설정을 다른 환경에서 재실행할 수 있다.
    • baseline 대비 개선과 실패 사례를 같이 기록한다.
    • 제조 현장의 미검출·오검출 비용을 metric 선택에 반영한다.

    왜 이렇게 구성했나

    1. 노트북보다 pipeline을 기준으로 설계

      단계별 입력·출력과 오류 위치를 분리해야 반복 실험과 검증이 가능하기 때문입니다.

    2. config와 artifact를 code와 함께 추적

      모델 파일만으로는 어떤 데이터·전처리·seed에서 나온 결과인지 설명할 수 없기 때문입니다.

    3. 성능 주장은 구현 Evidence 이후로 보류

      현재 공개 저장소만으로 학습 완료나 특정 수치를 검증할 수 없기 때문입니다.

    검증 체계

    이 프로젝트가 지향하는 검증은 데이터, 모델, 운영의 세 층으로 나뉜다.

    검증 층주요 질문예시 점검 항목
    데이터입력이 올바르고 평가 경계가 독립적인가?스키마, 결측, 중복, 레이블 분포, 그룹 누수
    모델기준선보다 의미 있게 개선됐는가?고정 분할, 클래스별 지표, 혼동행렬, 오류 사례
    재현성같은 실험을 다시 설명하고 실행할 수 있는가?설정, 시드, 환경, 코드·데이터 버전
    운영현장 조건에서도 안전하게 사용할 수 있는가?추론 시간, 입력 이탈, 실패 처리, 데이터 드리프트

    검증 결과는 숫자 하나로 합치기보다 의사결정에 맞춰 읽는다. 품질 검사 모델이라면 불량 미검출과 정상 오검출의 비용이 다르고, 설비 이상 탐지라면 알람의 조기성과 작업자의 대응 가능성도 중요하다.

    제조 엔지니어 경력과의 연결

    제조 현장에서는 공정 조건, 사용 설비, 소재 로트, 작업 시간, 검사 결과를 연결해야 불량 원인을 추적할 수 있다. 딥러닝 실험도 같은 원칙으로 접근했다.

    • 원본 보존: 현장 원시 데이터와 가공 데이터를 분리한다.
    • 변경점 관리: 코드, 설정, 데이터 분할의 변경을 실험 단위로 남긴다.
    • 검사 기준 명확화: 모델 지표를 현장의 양품·불량 판정 비용과 연결한다.
    • 이력 추적: 모델 결과를 데이터 버전과 실행 조건까지 역추적한다.
    • 이상 원인 분석: 평균 지표보다 조건별 오류 사례를 보고 개선 가설을 세운다.
    • 표준화: 반복 가능한 모델링 절차를 작업 표준처럼 문서화한다.

    이 경험은 AI를 제조 업무와 분리된 연구 주제로 보지 않게 했다. 모델은 공정의 한 구성 요소이고, 데이터 수집 조건과 판정 기준, 추적성, 실패 대응까지 연결돼야 실제 품질 개선 도구가 될 수 있다.

    현재 한계

    • 공개 저장소에는 프로젝트 목적을 뒷받침할 코드, 데이터 설명, 설정, 실행 결과가 충분히 공개되어 있지 않다.
    • 특정 데이터셋과 모델을 대상으로 한 성능 수치가 없어 모델 간 우열을 말할 수 없다.
    • 재현 가능한 실행 명령, 의존성 버전, 테스트가 공개 자료만으로 확인되지 않는다.
    • 제조 현장 데이터에 적용했다는 실증 결과나 운영 지표를 이 글에서 주장하지 않는다.
    • 따라서 현재 단계의 포트폴리오 가치는 완성 모델 성능보다 실험을 어떤 기준으로 설계하고 검증할 것인지 정리한 사고 과정에 있다.

    향후 개선 로드맵

    1. 공개 가능한 작은 예제 데이터와 명확한 문제 정의를 추가한다.
    2. 데이터 검사, 학습, 평가를 독립 실행 가능한 코드로 분리한다.
    3. 환경 파일과 실행 명령을 문서화해 처음부터 재현할 수 있게 한다.
    4. 기준선과 한 개 이상의 딥러닝 모델을 동일한 분할·지표로 비교한다.
    5. 혼동행렬과 대표 오류 사례를 포함한 평가 보고서를 자동 생성한다.
    6. 전처리와 데이터 누수 방지 규칙에 단위 테스트를 추가한다.
    7. 코드 변경 시 최소 테스트를 실행하고, 모델 카드에 적용 범위와 한계를 기록한다.
    8. 제조 공개 데이터로 설비·로트·시간 분할 시나리오를 검증한다.

    딥러닝 모델링에서 중요한 것은 한 번의 최고 점수가 아니라, 왜 이 데이터와 구조를 선택했는지 설명하고 같은 절차로 다시 검증할 수 있는가이다. 이 프로젝트는 그 기준을 학습하고 제조 데이터 문제까지 연결하기 위한 장기적인 실험 저장소로 발전시키는 것을 목표로 한다.

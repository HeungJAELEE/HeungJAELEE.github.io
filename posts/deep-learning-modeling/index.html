제조 AI 도입 5단계 Safety Gate와 실행 Skeleton 정립

정제된 예제의 Accuracy가 아니라, 제조 현장의 제품·Lot·시간 변동과 미검출 리스크를 기준으로 데이터부터 현장 도입까지 판단하는 개인 AI 가이드북을 구축했습니다.

1. 프로젝트 배경과 기획 의도

제조 현장의 Domain Gap

일반적인 AI 튜토리얼은 정제된 데이터, Random Split과 평균 Accuracy에 집중합니다. 제조 현장은 같은 품번에서도 자재 Lot, 생산시간, 설비상태, 조명, 작업자와 Recipe 변경에 따라 입력분포가 달라집니다. 학습·평가 데이터가 이 변동을 공유하면 Test 점수는 높아도 신규 Lot이나 다음 생산시간대에서 미검출이 발생할 수 있습니다.

또한 제조 검사에서 중요한 질문은 단순히 “몇 %를 맞혔는가”가 아닙니다.

  • 어떤 불량을 놓쳤는가 — FN·미검출·Underkill
  • 어떤 양품을 불량으로 판정했는가 — FP·과검·Overkill
  • 어느 제품·Lot·시간·설비조건에서 오류가 집중됐는가
  • 모델 판정이 Takt Time과 기존 검사·제어흐름을 방해하지 않는가
  • 이상 발생 시 기존 판정체계로 즉시 복귀할 수 있는가

연구 목표

예제코드 모음을 다음 제조 AI 의사결정 흐름으로 재구성했습니다.

→ 설정·버전·실험기록 통제
→ Recall·FN·FP·오답원인 평가
→ Shadow Test·수동확인·Rollback

주요 구현은 다음과 같습니다.

이 Skeleton은 제조 AI 코드의 연결순서를 보여주는 출발점입니다. 다음 구현에서는 합성 데이터를 실제 공정 Source Adapter로 교체하고, 데이터 분리·평가·현장검증 단계를 실행계약으로 추가합니다.

4. 제조 AI 5단계 Safety Gate

Gate 1. 도입 타당성 — Why & What

AI 모델보다 먼저 공정문제와 오류비용을 정의합니다.

판단항목제조 현장 질문산출물
대상 CTQ어떤 불량·설비이상을 검출할 것인가Failure Mode·Label 정의
FN 비용미검출 시 유출·재작업·고객영향은 무엇인가FN 우선순위
FP 비용과검 시 재검·폐기·Takt 손실은 무엇인가FP 허용범위
적용 위치작업자 보조, 검사판정, 설비제어 중 어디까지인가권한·사용자 Flow
성공조건성능·속도·현장운영 중 무엇을 통과해야 하는가Acceptance Criteria

Gate 2. Data — Product·Lot·Time Split

Random Split만 사용하면 같은 생산조건의 유사 이미지가 Train과 Test에 함께 들어갈 수 있습니다. 제조 AI는 다음 단위로 데이터 독립성을 확보합니다.

Train
= 과거 Product·Lot·시간구간

Validation
= 조건선정에 사용하되 Train과 분리한 Lot·시간구간

Final Test
= 모델·Threshold 선정에 사용하지 않은 Product·Lot·시간구간

필수 점검항목:

  • 동일 Cell·이미지·연속 Frame의 Train/Test 중복 차단
  • 제품·자재 Lot·설비·조명·작업교대·시간정보 보존
  • 정상 다수·불량 소수의 클래스 불균형 기록
  • 증강 전 원본기준 Split 고정
  • 최종 Test를 모델·Threshold 선정에서 격리

Gate 3. Configuration — 재현 가능한 실행단위

실험결과는 Model Weight만으로 재현되지 않습니다. 다음 항목을 한 실행단위로 묶습니다.

experiment:
  data_version: "..."
  split_manifest: "..."
  random_seed: 42
  model: "..."
  image_size: 224
  batch_size: 32
  learning_rate: 0.0001
  decision_threshold: 0.40
  code_commit: "..."

관리대상:

  • Data Source·Label Version·Split Manifest
  • 전처리·Augmentation·Random Seed
  • Model Architecture·Weight 초기화
  • Batch·Learning Rate·Epoch
  • Threshold·Operating Point
  • Code Commit·Package Environment
  • Confusion Matrix·Error List·Weight·Log

Gate 4. Evaluation — Accuracy보다 오류구조

양품 990개·불량 10개인 데이터에서 전부 양품으로 판정해도 Accuracy는 99%입니다. 제조 검사는 Accuracy 단독값 대신 오류의 방향과 비용을 평가합니다.

평가축핵심 지표·자료판단목적
미검출Recall·FN 건수·불량유형별 FN고객유출·치명불량 방어
과검Precision·FP 건수·제품별 FP재검·폐기·Takt 손실 통제
균형F1·PR Curve·Confusion Matrix클래스 불균형 포함 종합판정
원인오답 Image·Product·Lot·시간·설비 SliceDomain Gap·Drift 구간 규명
설명Grad-CAM·ROI·Annotation 대조결함이 아닌 배경·지그 학습 여부 판정
운영Latency·Throughput·메모리공정 Takt와 장시간 운전 적합성

Threshold는 단순 최고 Accuracy가 아니라 FN·FP 비용과 수동 확인능력을 함께 고려해 선정합니다.

Gate 5. Deployment — Shadow Test·Rollback

모델 Test가 끝나도 바로 PLC·설비판정에 연결하지 않습니다.

기존 검사·제어 유지
+ AI는 Background 판정과 Log만 수행
→ 작업자·기존검사 결과와 교차비교
→ Product·Lot·시간별 FN·FP·Latency 분석
→ Release 승인 또는 조건수정
→ 이상 시 기존 판정경로로 Rollback

Shadow 단계에서 관리할 항목:

  • AI 판정·Confidence·처리시간
  • 작업자·기존검사 판정과 불일치 유형
  • Product·Lot·시간·설비조건별 오류집중
  • 미검출 즉시 수동확인·격리절차
  • 과검 폭주·지연·통신오류·Drift 조건
  • Model Version 복귀와 기존검사 유지조건

5. 실행형 표준 Template로 전환할 구조

현재 아카이브의 문서와 Code Skeleton을 다음 실행구조로 통합합니다.

Deep_Learning_Text_book/
├── data/
│   ├── raw/                  # Product·Lot·Time 원본구조
│   └── processed/            # Split 이후 전처리 Data
├── configs/
│   └── experiment_01.yaml    # Seed·Model·Threshold·Version
├── notebooks/
│   ├── 01_eda_and_split.ipynb
│   ├── 02_model_training.ipynb
│   └── 03_evaluation_gradcam.ipynb
├── scripts/
│   ├── make_split.py
│   ├── train.py
│   ├── evaluate.py
│   └── shadow_compare.py
└── results/
    ├── weights/
    ├── reports/
    ├── error_cases/
    └── logs/

다음 Engineering Package의 완료조건:

  1. Product·Lot·Time 기준 Split Manifest 자동생성
  2. config.yaml 기반 동일설정 재실행
  3. Code·Data·Config·Weight·Report Hash 연결
  4. Recall·FN·FP·Confusion Matrix·Error Slice 자동출력
  5. Grad-CAM과 원본 Annotation 비교
  6. Shadow 판정 Log와 기존검사 결과 교차분석
  7. Release·Hold·Rollback 판정기준 실행

AX 엔지니어링 자산

이 가이드북의 목적은 모델 수를 늘리는 것이 아니라, 제조 엔지니어가 다음 질문에 답할 수 있는 실행기준을 확보하는 것입니다.

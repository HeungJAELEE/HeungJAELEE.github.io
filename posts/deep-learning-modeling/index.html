30초 요약

모델 이름을 많이 아는 것보다 데이터 전처리부터 평가와 재현까지 같은 조건으로 다시 실행할 수 있는 흐름이 제조 데이터 적용에 더 중요하다고 봤습니다.

해결하려던 문제

전처리·분할·학습·평가 조건이 흩어지면 성능 차이가 모델 때문인지 데이터 처리 때문인지 설명하기 어렵습니다.

내가 맡은 범위

  • 데이터 전처리, 모델 학습, 평가와 재현성 관리를 한 저장소 흐름으로 정리했습니다.

  • 확인된 산출물 · 개인 역할 전처리→학습→평가→재현성 관리의 공개 학습 흐름
  • 현재 단계 · 개인 역할 제조 생산 데이터 적용·현장 성능 검증 전

팀 경계

개인 학습 저장소이며, 회사 생산 데이터에 적용한 성과로 표현하지 않습니다.

공개 범위: 공개 코드로 확인되는 실험 절차만 설명하고, 확인되지 않은 성능 수치는 성과에 넣지 않습니다.

제조 데이터에 모델을 적용하기 전 필요한 검증 순서로 일반화했습니다.

왜 이 의사결정이 중요했는가

딥러닝 코드는 한 번 실행될 수 있어도, 어떤 데이터와 설정으로 나온 결과인지 설명하지 못하면 업무 판단에 쓰기 어렵습니다. 같은 제품이나 Lot의 정보가 학습과 테스트에 섞이거나, 테스트 결과를 보며 모델을 반복 수정하면 점수가 좋아 보여도 실제 성능을 과대평가할 수 있습니다.

제조에서는 이 문제가 품질 판단과 바로 연결됩니다. 불량 미검출과 정상 오검출의 비용이 다르고, 설비·소재·촬영 조건이 바뀌면 오프라인 결과도 달라질 수 있습니다. 그래서 최고 점수보다 데이터와 결과 사이의 경로를 다시 확인할 수 있는 실험 기준을 먼저 정했습니다.

왜 디지털 방식이 필요했는가

노트북 하나에 전처리, 학습과 평가를 모두 넣으면 빠르게 시험할 수 있지만 실행 순서와 숨은 상태에 따라 결과가 달라질 수 있습니다. 전처리, 학습, 평가와 실행 기록을 분리하면 어느 단계의 변경이 결과에 영향을 줬는지 추적할 수 있습니다.

이 프로젝트에서 MLOps는 운영 플랫폼을 이미 구축했다는 뜻이 아닙니다. 데이터 식별자, 분할 기준, 설정, 코드, 실행 환경과 평가 결과를 한 실험 단위로 연결하는 학습 습관을 뜻합니다.

실제로 맡은 역할

개인 학습·실무 검증 프로젝트로 문제 정의, 데이터 분할, 전처리, 학습, 평가와 재현성 관리가 이어지는 모델링 기준을 정리했습니다. 모델 후보를 많이 나열하기보다 단순 기준선을 먼저 두고, 동일한 분할과 평가 함수로 비교하며, 지표와 오류 사례를 함께 읽는 흐름에 집중했습니다.

현재 공개 자료가 제한적이므로 이 글은 구현 완료 목록이 아니라 설계 문서입니다. 특정 데이터셋 규모, 모델 정확도, 학습 완료나 운영 배포를 제 역할의 성과로 주장하지 않습니다.

데이터 흐름

원본 데이터 보존·분할 → 전처리 → 설정 기반 학습 → 고정 평가와 오류 분석 → 데이터·코드·환경·결과 기록으로 재현성 관리

전처리 기준은 학습 데이터에서만 계산해 검증과 테스트에 적용합니다. 모델 선택에 사용하지 않은 고정 테스트 세트로 마지막 평가를 수행하고, 평균 점수뿐 아니라 클래스별 지표와 대표 오류를 남기는 구조입니다.

구현 순서

  1. 한 건의 예측이 이미지 한 장인지, 제품 단위인지, 설비의 시간 구간인지 먼저 정합니다.
  2. 원본을 읽기 전용 기준으로 보존하고 파일, 라벨, 설비, Lot와 시간 정보의 누락·중복을 검사합니다.
  3. 학습 전에 설비·Lot·시간 기준을 고려해 train·validation·test 경계를 고정합니다.
  4. 학습 데이터로만 전처리 기준을 맞추고, 단순 기준선을 만듭니다.
  5. 데이터 버전, 분할 규칙, 모델 설정, 난수 시드와 실행 환경을 기록한 상태로 학습합니다.
  6. 고정된 평가 기준으로 클래스별 지표와 오류 사례를 확인하고, 모델·설정·보고서를 같은 실행 기록에 연결합니다.

이 순서는 저장소를 발전시키기 위한 기준이며, 공개 저장소에서 모두 구현·검증됐다는 뜻은 아닙니다.

확인된 결과와 현재 단계

공개 저장소에서 확인할 수 있는 설명은 전처리–학습–평가–재현성 관리라는 프로젝트 방향입니다. 공개 자료만으로 재현 가능한 실행 명령, 의존성 버전, 특정 데이터셋과 모델 성능을 확인할 수 없으므로 정량 성과를 제시하지 않습니다.

현재 포트폴리오의 결과는 완성된 모델이 아니라, 데이터를 나누고 실험을 기록하며 결과를 해석하는 기준을 정리한 설계입니다. 제조 데이터에 적용했다는 실증 결과도 아직 주장하지 않습니다.

배포 조건과 회사에 줄 수 있는 가치

제조 적용에는 별도 검증이 필요합니다. 설비·Lot·시간 기준의 독립 평가, 실제 조명과 센서 조건별 슬라이스, 추론 지연, 입력 이탈과 실패 처리, 데이터 드리프트를 확인해야 합니다. 데이터 사용 권리, 모델 버전, 판정 임계값, 승인과 되돌리기 절차도 운영 기준에 포함돼야 합니다.

이 조건이 갖춰지면 회사는 점수 하나가 아니라 어떤 데이터와 조건에서 모델을 신뢰할 수 있는지 검토할 수 있습니다. 실패한 실험까지 같은 형식으로 남기면 반복 작업을 줄이고 다음 개선 가설을 더 빨리 세울 수 있습니다. 다만 실제 품질 개선이나 공수 절감은 별도 현장 검증으로 확인해야 합니다.

Problem

노트북이 한 번 실행된 사실만으로는 데이터 누수, 전처리 일관성, 재현성, 기준선 대비 개선과 제조 현장의 오류 비용을 설명할 수 없습니다.

Goal

전처리–학습–평가–재현성 관리를 분리하고, 새로운 제조 데이터에도 같은 기준으로 실험을 반복할 수 있는 학습 저장소 구조를 만드는 것입니다.

Success

고정 데이터 분할, 설정·seed·artifact 기록, 기준선 비교와 error analysis가 자동 검증되고 다른 환경에서 재실행되면 성공입니다.

범위와 경계

포함 범위

  • 데이터 schema·split·전처리·augmentation 기준
  • baseline, train/evaluate pipeline, metric·artifact logging
  • 제조 불균형 데이터의 Recall·Precision·F1·error analysis

제외·미검증 범위

  • 공개 근거 없는 특정 모델 정확도와 학습 완료 주장
  • 운영 배포와 MLOps 플랫폼이 이미 완성됐다는 표현
  • 하나의 노트북 결과를 재현 가능한 실험으로 간주

구현·검증 기준

해야 할 일

  • train/validation/test split을 고정하고 데이터 누수를 검사한다.
  • config, seed, code/data version과 model artifact를 함께 기록한다.
  • accuracy 외 Recall·Precision·F1과 confusion matrix를 생성한다.

품질·운영 기준

  • 같은 설정을 다른 환경에서 재실행할 수 있다.
  • baseline 대비 개선과 실패 사례를 같이 기록한다.
  • 제조 현장의 미검출·오검출 비용을 metric 선택에 반영한다.

왜 이렇게 구성했나

  1. 노트북보다 pipeline을 기준으로 설계

    단계별 입력·출력과 오류 위치를 분리해야 반복 실험과 검증이 가능하기 때문입니다.

  2. config와 artifact를 code와 함께 추적

    모델 파일만으로는 어떤 데이터·전처리·seed에서 나온 결과인지 설명할 수 없기 때문입니다.

  3. 성능 주장은 구현 Evidence 이후로 보류

    현재 공개 저장소만으로 학습 완료나 특정 수치를 검증할 수 없기 때문입니다.

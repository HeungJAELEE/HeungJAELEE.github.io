AI Welding Vision: Designing Metrics Around Missed-Defect Risk

Project resources Public material for the dataset, model-selection, and evaluation record. GitHub project indexgithub.com/HeungJAELEE AI Welding Vision reportcanva.com/design/DAHGaCTGRFs A dedicated public source repository has not been separated for this model. The GitHub profile is an index of other public work and is not labeled as the welding-model source. Portfolio summary: Problem–Role–Action–Result–Evidence Item Verified scope Problem Micro-defect features overlapped with normal surfaces, data was imbalanced, and accuracy alone did not represent the cost of passing a defective weld. Role I was responsible for evaluation-metric design and validation, including F1, recall, false-positive behavior, and threshold interpretation. Action The team separated roughly 60,000 AI-Hub images from 198 field images, compared a DenseNet baseline, a two-model combination, and a ResNet+DeiT ensemble, then reviewed a second test set and tuned the decision threshold to prioritize missed-defect control. Result On the recorded evaluation set and selected threshold, the report lists F1 93.10%, Recall 100%, and Precision 87.07%. These values do not establish production-wide generalization. Evidence The public report’s dataset, model-evolution, second-test, threshold, and final-metric slides; no dedicated public repository. Resume bullets Separated approximately 60,000 public welding images and 198 field images by learning/field-validation purpose instead of presenting them as one undifferentiated training set. Compared DenseNet, a two-model combination, and a ResNet+DeiT ensemble, then used second-test error review to tune the operating threshold around missed-defect cost. Recorded F1 93.10%, Recall 100%, and Precision 87.07% on the stated evaluation set and defined manual reinspection as the control for remaining false positives. Interview STAR Situation: Missing a small weld defect carried a higher quality risk than sending a normal part to reinspection, while accuracy could remain high under class imbalance. Task: Establish a comparable evaluation framework and a decision threshold aligned with that asymmetric risk. Action: Separate data sources, compare model stages on the same metrics, inspect mixed normal/defect regions in a second test, and search thresholds that retained recall. Result: The selected evaluation produced Recall 100%, F1 93.10%, and Precision 87.07%. I also documented that this is inspection-assistance evidence, not proof of autonomous production deployment. 1. Portfolio summary: Problem–Role–Action–Result–Evidence Item Verified scope Problem Partial edits to Conty JSON could break Waypoint/program/move references, while multiple HMI, DB, and twin clients connecting directly to the robot would scatter command ownership and state timing. Role Designed and implemented the public Busan_Robot repository’s JSON compatibility layer, PC-HMI boundary, backend services, and operating documentation. Action Built round-trip preservation, single IndyDCP socket ownership, separate MQTT command/state topics, a MySQL worker, PLC bridge, WebSocket read-only twin, and Offline/Direct/Gateway execution modes. Result Published a frontend/backend monorepo with Docker Compose, deployment and communications documents, and a staged validation path. No unsupported latency, uptime, or collision-reduction metric is claimed. Evidence Public source and README, JSON design, PLC/MES integration, communications, setup, and deployment documents; related team PDF. Resume bullets Designed a load–edit–save–reload validation flow that preserves Conty/APK JSON Waypoint, program-tree, and move references. Centralized IndyDCP physical sockets in one Robot Controller and separated MQTT command, result, realtime, connection, and error topics. Split a CustomTkinter HMI, MySQL DB worker, PLC bridge, and WebSocket digital twin into independent service boundaries with Docker Compose documentation. Added Offline UI, Direct, and MQTT Gateway modes so JSON and UI behavior can be checked before physical robot connection. Interview STAR Situation: Reference damage in a robot program file and concurrent socket access can compromise both compatibility and physical-control accountability. Task: Preserve the teach-pendant format while allowing PC editing and let HMI, DB, and twin consumers share one trustworthy robot state. Action: Define JSON round-trip invariants, make Robot Controller the single IndyDCP owner, and route other components through explicit MQTT events. Result: Published a reproducible HMI/backend structure and operator documents. Omniverse remains a future read-only adapter rather than an unverified production claim. 1.

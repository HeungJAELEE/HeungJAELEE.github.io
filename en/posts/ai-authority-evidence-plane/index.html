AI Agent Experiment That Checks Evidence Before Acting

A local experiment that checks evidence and human approval before an AI-proposed action can run

User, build, and validation summary

User problem
An AI reading data and proposing an action does not prove authority to execute or a safe external result.
Build scope
I am organizing Ontology/LLM Wiki knowledge and execution conditions into an agent specification and designing the order of evidence review, human approval, and stop conditions.
Result / current stage

In one sentence

This local experiment selects knowledge from an Ontology and LLM Wiki and turns what an AI agent may read, which tools it may use, and when it must stop into an execution specification.

The current foundation stage compares how decisions vary across LLMs and data and where human approval must remain. The complete allow/block/readback flow is still under test, and this is not an operating service connected to external systems.

A representative use case

Consider an agent that helps prepare an inspection sequence for an equipment anomaly.

  1. A user asks the agent to read anomaly evidence and propose checks.
  2. The agent finds relations among equipment, process, defect, and inspection items in the Ontology.
  3. It retrieves the related source text and review status from the LLM Wiki.
  4. The allowed tools, readable scope, prohibited actions, and stop conditions become one execution specification.
  5. A person reviews the proposed work and its evidence.
  6. A bounded local reading and analysis path is tested for the approved scope.
  7. The next stage reads the resulting state back and compares it with the expected outcome.

Being able to read data does not grant permission to change equipment. That distinction is the starting point of the project.

From an AI proposal to a checked result

The core flow can be understood in five steps.

  1. The AI reads the request and proposes the work it believes is needed.
  2. The user reviews the selected knowledge and original evidence.
  3. A person approves the tools, target, time window, and stop conditions.
  4. The system runs only the approved work and stops anything outside that scope.
  5. After execution, the system reads the actual state again and compares it with the requested outcome.

The target behavior is to show missing evidence or authority and stop instead of filling the gap with a plausible answer. Completed public claims are limited to the design and local experimentation; concrete allow/block scenarios and public execution logs remain additional verification work.

Data and system structure

Component 1 — Ontology and LLM Wiki

The Ontology connects equipment, process, symptom, cause, and action. The LLM Wiki supplies human-readable source text and source/review state. The agent records which documents and states were actually used.

Component 2 — Agent execution specification

The specification contains:

  • the problem and success condition;
  • readable sources and allowed tools;
  • actions that must never run;
  • required human approval and its valid scope;
  • an identifier that prevents duplicate execution;
  • states to check before and after execution.

Component 3 — Bounded execution

Work does not run when approval is missing or the source is insufficient. Even approved work stays within the tools and targets listed in the specification.

Component 4 — Result readback

A successful function or API response does not finish the job. The resulting state is read again and compared with the intended target. A mismatch stops the next action and returns the case for review.

Implementation sequence

  1. Classify knowledge sources and their states.
  2. Combine agent purpose, tools, risk, and stop conditions into one execution specification.
  3. Define the requirement that source, specification, and runtime artifact refer to the same target.
  4. Turn missing approval, artifact mismatch, and ambiguous restart state into explicit test cases.
  5. Compare decision differences across LLMs and data.

Current result and next stage

The current result is an agent-specification structure, evidence/approval/stop-condition design, and a set of local experiments. Concrete allow/block scenarios, public execution logs, and external readback are not presented as completed results.

Connecting this experiment to real services and external systems would require:

  • user and role permissions with an approval UI;
  • per-tool target and parameter restrictions;
  • restart, duplicate-request, and partial-failure regression tests;
  • authoritative readback for each external system;
  • auditable execution records and privacy/secret handling;
  • independent security review and human approval in the operating environment.

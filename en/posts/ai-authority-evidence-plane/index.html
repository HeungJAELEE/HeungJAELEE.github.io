Ontology and LLM Wiki Agent Specification & Safety Foundation

Building agent specifications from knowledge and execution conditions, then checking approval, evidence, and stop conditions in bounded local runs

One-sentence explanation

This foundation selects knowledge from an Ontology and LLM Wiki, turns what an AI agent may read and which tools it may use under which conditions into an execution specification, and permits only bounded local work when evidence, human approval, and stop conditions agree.

It is not a completed operating platform or a product that automatically changes external systems. It validates how knowledge selection and execution authority should connect before platformization.

Representative use scenario

Consider an agent that prepares an equipment-anomaly inspection sequence.

  1. A user asks the agent to read anomaly evidence and propose checks.
  2. The agent finds equipment, process, defect, and inspection relations in the Ontology.
  3. It retrieves related source text and source state from the LLM Wiki.
  4. Tools, readable scope, prohibited actions, and stop conditions become one execution specification.
  5. A person reviews the proposal and evidence.
  6. Only approved local read/analysis work runs.
  7. The resulting state is read back and compared with the expected outcome.

The ability to read data is not authority to change equipment.

Information architecture for a future UI

There is no public operating UI, so this article does not present mockups as a finished product. It defines the information a platform UI would need.

Area What the user would review
Knowledge selection Ontology scope and Wiki sources available to the agent
Agent specification Purpose, tools, input scope, risks, and stop conditions
Evidence review Source location, status, recency, and HOLD items
Approval Who approved what scope and for how long
Execution record Tool calls, summarized input/output, and block reasons
Result check Readback compared with the expected outcome

From proposal to readback

AI proposes work
→ evidence and selected knowledge are reviewed
→ a person approves scope and stop conditions
→ only allowed work runs; everything else is blocked
→ the resulting state is read back and compared

A blocked result is not hidden failure. It is the correct result when evidence, authority, or artifact identity is missing.

Data and system structure

Ontology and LLM Wiki

The Ontology supports relations among equipment, process, symptom, cause, and action. The LLM Wiki provides human-readable sources and source/review status. The agent records which sources were actually used.

Agent execution specification

The specification contains:

  • problem and success condition;
  • allowed sources and tools;
  • prohibited actions;
  • required human approval and valid scope;
  • an identifier that prevents duplicate execution;
  • states to verify before and after execution.

Bounded execution

Execution stops when approval is absent or evidence is insufficient. Even approved work must remain within the tools and targets declared in the specification.

Result readback

A successful API or function response is not enough. The actual resulting state must be read back and matched to the intended target and result.

AI and human responsibilities

Work Owner
Find relevant knowledge candidates AI
Summarize sources and draft execution AI
Decide whether sources support the request Human
Set risk and authority scope Human
Check approver and expiry System + human
Run approved local work System
Make the final outcome judgement Human

The AI does not replace the approver or fill missing evidence with fluent prose.

Implementation sequence

  1. Classify knowledge sources and states.
  2. Combine purpose, tools, risk, and stop conditions into one specification.
  3. Check that source, specification, and runtime artifact refer to the same target.
  4. Block missing approval, artifact mismatch, and ambiguous restart state.
  5. Read back results after bounded local execution.

Current result and remaining gates

The current result is a local foundation. It has not performed operating orders, equipment control, payments, deployment, or permission changes. There is no public operating UI or reproducible public repository.

Platformization still requires:

  • user/role authority and approval UI;
  • per-tool target and parameter restrictions;
  • restart, duplicate-request, and partial-failure regression tests;
  • authoritative readback per external system;
  • auditable execution records and secret/privacy handling;
  • independent security review and human approval in the operating environment.

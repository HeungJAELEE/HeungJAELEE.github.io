    Fail-Closed AI Authority & Evidence Plane: Visibility Is Not Execution Authority

    A local foundation separating AI observation and recommendation from execution authority through Decision Envelopes, Release Inventory, and approval/effect/restart gates

    Jul 31, 2026 · 6 minutes · Last reviewed Jul 31, 2026

    • AI Governance
    • Fail-Closed
    • Authority
    • Evidence
    • Reproducibility

    Problem: test success is not execution authority

    These statements describe different facts:

    • a model read data;
    • a model recommended an action;
    • local code passed tests;
    • an authorized person approved a bounded action;
    • the same artifact ran in the operating environment;
    • an external effect occurred and was read back.

    Without that separation, “test PASS” can become “ready to deploy,” recommendation can become order approval, and local state can be mistaken for external effect.

    This project adds fewer integrations and instead builds a fail-closed Authority & Evidence Plane that stops when any required fact is absent.

    Current public boundary: live orders 0 · external effects 0 · C4 not approved · not operational GO

    Why the contracts are separated

    One approved=true flag cannot explain who approved which action, artifact, risk, and time boundary. The foundation therefore separates:

    1. Decision Envelope: intent, risk, evidence, approval principal, idempotency, expected effect;
    2. Release Ownership Inventory: source, generated, and runtime owners with hashes;
    3. Source Qualification: authoritative, advisory, and HOLD inputs.

    Foundation Join permits progression only when approval, artifact, restart, and effect evidence agree.

    Architecture and data flow

    flowchart LR A["Observation / source"] --> B["Source Qualification"] B --> C["Decision Envelope\nintent · risk · evidence"] D["Release Inventory\nsource · generated · runtime · hash"] --> E["Artifact identity gate"] C --> F["ApprovalPrincipal gate"] E --> F F --> G{"C4 approved?"} G -- "No" --> H["BLOCKED\nexternal effects 0"] G -- "Yes" --> I["Bounded execution"] I --> J["Authoritative read-back"] J --> K["Reconciliation · restart gate"] K -- "Mismatch" --> H

    BLOCKED is a correct result when authority or evidence is missing, not a failure to hide.

    AI and human roles

    AI can draft source and artifact inventories, identify risk candidates, generate contract and test code, and summarize evidence.

    AI does not assign the ApprovalPrincipal, own credentials, grant C4 approval, submit orders, deploy, change permissions, or reconcile external effects.

    A human owns the approval scope and must read back actual effects from an authoritative source. Better analysis does not expand authority automatically.

    Problem

    When recommendation, code execution, deployment approval, and external effect share one flow, a test success or message can be mistaken for trading, permission, or operational authority.

    Goal

    Use Decision Envelopes, Release Inventory, and Source Qualification to bind input, authority, artifact, approval, and effect, blocking execution when any element is absent.

    Success

    Clean materialization is byte-identical and approval, restart, and effect gates deterministically block incomplete state while live effects remain zero.

    How AI and human roles were divided

    AI role
    Assisted source and artifact inventory drafts, risk candidates, contract/test code, and counterexamples without owning execution authority or final approval.
    Human role
    A human owns ApprovalPrincipal assignment, C4 approval, credentials, deployment/order/recovery decisions, and authoritative read-back.
    Publication gate
    Credentials, internal IPs, private repository/Notion URLs, personal data, and in-progress contracts remain private; only the last completed foundation is described.
    External effect
    Live orders 0, external effects 0, and C4 not approved. Local test success is not operations GO, trading, profit, or permission-change evidence.

    Scope and boundaries

    In scope

    • Decision Envelope and risk, approval, and effect contracts
    • Release Ownership Inventory, Source Qualification, and Foundation Join
    • Clean materialization, hashes, restart, approval, and effect gates

    Out of scope or unverified

    • Live trading, order submission, credential collection, or operating accounts
    • Claiming C4 approval or operational GO
    • Counting in-progress READ_ONLY_INVENTORY 1.2.0 as complete

    Implementation and verification

    What had to work

    • Every ActionSpec binds source, risk, ApprovalPrincipal, artifact, and intended effect.
    • Release Inventory binds source, generated, and runtime owner with hashes.
    • Missing approval, restart, or effect evidence blocks execution deterministically.

    Quality and operating rules

    • The same source produces byte-identical artifacts from a clean checkout.
    • Fixture and harness success remains separate from real external effect.
    • Environment capability skips, such as Windows symlink support, remain visible.

    Why it was designed this way

    1. Separate observation from execution authority

      Reading state or recommending action does not automatically authorize changes to assets or external systems.

    2. Fix artifact identity through Release Inventory

      Evidence cannot authorize operations if the tested artifact differs from the runtime target.

    3. Use clean materialization as a completion gate

      Auditable evidence must rebuild from source without relying on local cache or manual output.

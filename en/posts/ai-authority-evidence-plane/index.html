    What this platform is

    Approval gates are not the product by themselves. This project is an AI agent platform that uses knowledge, terminology, and operating rules from an ontology and an LLM wiki to compose and run an agent for a requested task.

    The ontology connects related concepts such as equipment, processes, documents, and roles. The LLM wiki provides task guidance, operating sequences, tool instructions, and cautions. The platform selects the relevant knowledge and assembles an executable agent definition containing its role, tools, evidence sources, output format, and stop conditions.

    Authority, approval, and evidence checks are the platform’s safety layer. The ability to generate an answer does not automatically permit an agent to submit an order, deploy a change, or modify access. Evidence and human approval are checked separately before an external effect is allowed.

    Why I built it

    When an agent is defined only through a long prompt, terminology can be interpreted inconsistently and the same rules must be repeated for every project. Source documents and tool boundaries also become mixed into the conversation. As the number of agents grows, knowledge and operating rules are duplicated, and a correction may reach only some agents.

    I separated reusable knowledge into the ontology and wiki, then selected only the parts needed for each execution. The goal was to make an agent’s knowledge and action boundary inspectable outside its prompt and let several agents share the same knowledge contract.

    Representative user scene

    Consider a request to identify likely causes of repeated equipment stops and propose an inspection sequence.

    1. Classify the equipment, symptom, related process, and expected output in the request.
    2. Find connected equipment, parts, failure modes, and inspection documents in the ontology.
    3. Retrieve the sequence, allowed tools, sources, and restrictions from the LLM wiki.
    4. Compose the analysis agent’s role, inputs, tools, output format, and stop conditions.
    5. Run the agent within the allowed data and tool boundary while recording its evidence and result.
    6. If the task would change an external system, check the human approval scope, allow or stop the action, and read back the actual result after execution.

    This is a generalized public description of the implemented direction. It excludes company documents, equipment addresses, accounts, and private operating rules.

    A system map for first-time readers

    This platform is not a single chatbot screen. It has an entry point for the request, an ontology and wiki that supply relevant knowledge, a composition stage that assembles a task-specific agent, a bounded execution stage, and a final evidence and result check.

    A first-time reader can follow the diagram from left to right. The first three stages decide what agent should be composed. The last two decide what that agent may actually do and whether the observed result matches the request. Answer quality and permission to change an external system therefore remain separate concerns.

    Components and responsibilities

    ComponentResponsibility
    OntologyConnect domain concepts and relationships so agents resolve the same objects consistently
    LLM wikiProvide task guidance, tool instructions, examples, constraints, and validation criteria
    Agent ComposerTurn a request into an executable definition of role, tools, evidence, output, and stop conditions
    Agent RunnerExecute the definition within its allowed boundary and record the process and result
    Authority & Evidence LayerCheck evidence, target identity, and human approval; stop when information is missing and read back the result after execution

    This separation means a knowledge change can be made in the ontology or wiki instead of editing every agent prompt. The runner records which knowledge was used, while the safety layer keeps analytical success separate from execution authority.

    Source structure and reading order

    The actual repository is not public. The names below are generalized responsibility units for explaining the codebase; they are not copies of private directory names.

    knowledge/
├── ontology/     relationships among equipment, process, documents, and roles
└── wiki/         task sequences, tool guidance, and cautions

schemas/          agent execution and evidence contracts
composer/         selects knowledge and assembles an agent definition
runner/           invokes permitted tools and records the run
authority/        checks target, human approval, and external-effect scope
evidence/         preserves sources, artifact identity, and observed results
tests/            exercises stop conditions, replay, and artifact consistency

    For a first code read, start with knowledge/ to see what an agent can know. Continue through schemas/ and composer/ to see how that knowledge becomes an executable definition. Then read runner/ and authority/ for the action boundary, followed by evidence/ and tests/ for result verification.

    Data, AI, and human roles

    The ontology and wiki retain concepts, relationships, task guidance, sources, scope, and constraints. An agent run records the request, selected knowledge, tools, result, risk, and approval boundary separately. This makes it possible to inspect how an agent was composed and which material it used.

    AI assists with request classification, candidate knowledge retrieval, agent-definition drafts, test and counterexample creation, and result summaries. A person reviews the ontology and wiki, chooses the permitted tools and data scope, and approves any external change. A better answer does not transfer human authority to the agent.

    Implemented and verified scope

    In the last completed local snapshot, Python 3.12 and jsonschema were used to validate agent execution definitions, evidence and target bindings, and stop conditions.

    • 150 local regression checks passed
    • Primary and reproduced artifacts rebuilt from source were byte-identical
    • One Windows symlink capability limitation remained recorded as a skip
    • No orders were submitted and no external systems were changed
    • No human operational approval or production connection exists

    This verifies a local foundation and safety layer for composing and running agents. It does not mean that a public service, live trading, or external-system automation is operational.

    Potential company use

    A company could compose maintenance, process-diagnostic, quality-investigation, or work-standard search agents that use the same internal terms and rules. Knowledge remains in the ontology and wiki, while each agent receives only the role and tools required for its task, reducing duplicated knowledge and prompt variation.

    The platform can also retain which knowledge and documents were used, who approved an external change, and what the external system reported afterward. Actual benefit would still need to be measured through company-data integration, user validation, and operating-environment tests.

    Limitations and disclosure

    This remains a locally validated foundation with no public repository or operating URL. Credentials, internal IPs, private repository and Notion addresses, personal data, and in-progress specifications remain private.

    Real operation still requires quality review of the company ontology and wiki, document-level access control, bounded agent tools, human approval, duplicate-execution protection, and read-back from the external system. The current result is not presented as production readiness or live-operation performance.

    Implementation and verification

    What had to work

    • Select request-relevant concepts, documents, and operating rules from the ontology and LLM wiki.
    • Compose selected knowledge into an agent definition containing role, tools, evidence, output, and stop conditions.
    • Allow an external change only when target, evidence, and human approval agree, then read back the result.

    Quality and operating rules

    • The same source produces byte-identical artifacts from a clean checkout.
    • Fixture and harness success remains separate from real external effect.
    • Environment capability skips, such as Windows symlink support, remain visible.

    Why it was designed this way

    1. Separate knowledge from agent prompts

      Shared ontology and wiki standards reduce terminology and operating-rule drift across agents.

    2. Record agent composition as an execution definition

      Roles, tools, evidence, outputs, and stop conditions must remain inspectable after a run.

    3. Use clean materialization as a completion gate

      Auditable evidence must rebuild from source without relying on local cache or manual output.

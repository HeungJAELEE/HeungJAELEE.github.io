When the same career evidence was processed in multiple AI sessions, metrics, contribution, Pilot, and production status could change from one document to another. I treated this not as a writing-style issue but as an evidence authority, execution authority, and verification-order problem. I first implemented a shared claim ledger, four focused career-writing skills, and deterministic guards in im-not-ai, then designed the Agent OS architecture that extends the same contracts to persistent agents, Worker/Manager flows, approvals, domain packs, and authoritative readback.

1. Project background — the judgement drifted, not just the prose

Generating a resume, career description, portfolio, web card, and presentation independently can turn one project into several conflicting stories.

  • a team outcome becomes a sole personal result
  • A-sample, PoC, Pilot, and production stages are mixed
  • metric period, denominator, and rework conditions disappear
  • private source material or non-public URLs leak into public output
  • the final style pass removes field conditions and contribution boundaries

The system therefore had to lock who may use which fact under what scope before writing began.

2. 5Why — why did the same career evidence change across documents?

Analysis direction

The initial symptom looked like inconsistent AI wording. Comparing approved drafts showed a deeper issue: the generation process had no shared Claim, contribution, stage, and publication boundary.

WhyObserved problemStructural cause
1Metrics and contribution differed by outputResume, portfolio, and slides were generated independently
2Approved drafts were repeatedly rewritten from scratchNo LOCKED BASELINE or bounded edit region
3Direct work, team outcome, Pilot, and production were mixedContribution and Stage were not common fields
4Public and private sources appeared in one contextNo source-priority and publication-scope contract
5The final style pass changed factual conditionsThe model evaluated its own change rate and fidelity

Root cause — writing started before evidence, contribution, stage, and publication scope were locked.

I changed the order to shared claim ledger → focused skills → style pass → deterministic validator.

4. Replacing model self-assessment with code gates

Skill-bundle validator

validate_career_skill_bundle.py checks the following in code:

  • OpenAI plugin manifest and four required skills/references
  • policy markers such as SOURCE_UNAVAILABLE, direct work, team outcome, and Pilot
  • agents/openai.yaml and invocation-prompt contracts
  • blocked private Notion URLs, Windows user paths, conversation identifiers, and delegation payloads
  • installation of all four skills

Change-rate rollback gate

The model does not estimate how much it rewrote. verify_change_rate.py returns an exit code from the actual before/after text.

Change rateDecisionHandling
<30%OKRevised text may be adopted
30–50%WARNNotify the user of possible over-editing
≥50%ABORTReject the revision and roll back
unavailableERROREscalate to human review

A GitHub Actions workflow is also defined for Python 3.11/3.12 Pytest plus Quick Rule and Diagnosis Rule drift checks.

5. Why this is an AI-authority problem

AuthorityDecision ownerWhat AI may do
Source AuthorityCurrent user confirmation, canonical ledger, runtime readbackFind and summarize candidate evidence
Contribution AuthorityUser and original role recordsDraft direct, team, or support wording
Stage AuthorityActual Sample, Pilot, production, or operating stateApply stage-specific language
Publication AuthorityRights and redaction decisionGenerate public copy within the allowed scope
Style AuthorityStyle rules applied after facts and structure are approvedRemove translationese and local AI-writing patterns

The writing model does not create these authorities. It generates inside an approved boundary, and deterministic code blocks contract violations.

6. Agent OS target architecture

im-not-ai implements evidence, decision, and output control for one application domain. Agent OS extends the same contracts to persistent agents and external effects.

flowchart LR
    W["Wiki\nvalidated knowledge and revisions"] --> B["Agent Builder\nrole·knowledge·tool definition"]
    B --> R["Persistent Agent Registry\nsession-independent identity"]
    R --> F["Worker·Manager Flow\nresearch·comparison·rework"]
    F --> C["Control Runtime\nqueue·lease·checkpoint"]
    C --> O["Outcome Record\nevidence·dissent·accountable owner"]
    O --> A["Approval Inbox\nhuman scope and expiry"]
    A --> D["Domain Pack\nInvestment·Manufacturing"]
    D --> E["Authoritative Readback\nactual external state"]
    E --> O

Operating contracts

  • Workers and Managers may research, compare, and request rework, but cannot create human approval
  • one active writer per aggregate and duplicate-trigger prevention
  • queue claim, lease, checkpoint, and restart for long-running work
  • semantic rework separated from transport retry
  • Notion used as a human-readable projection, not the message bus
  • request receipts separated from authoritative external readback
  • approval target, scope, expiry, consumption state, and rollback managed together

9. Project outcomes

  • reused one current evidence decision across resumes, portfolios, web cards, and presentations
  • blocked drift in direct contribution, team outcome, Pilot, production, and current runtime state
  • separated generation, review, and style responsibilities into one public plugin and four focused skills
  • moved private-data leakage and excessive rewriting from model self-evaluation to deterministic code gates
  • defined the Agent OS path from Wiki and persistent agents through flow, approval, domain packs, and authoritative readback

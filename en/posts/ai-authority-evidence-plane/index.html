A process engineer does not diagnose an assembly-line problem from one alarm alone. MES history, inspection results, lot and rework records, operator actions, SOP/QCP/P-FMEA revisions, and the actual equipment state must be aligned on the same time axis and decision basis. Those records are distributed across different systems, and an AI model’s ability to read them does not grant authority to change a PLC or MES.

This project defines a manufacturing decision-support system for that gap. Its objective is not autonomous equipment control. It links process, quality, and production evidence, converts separate analyses into reviewable work proposals, and keeps human approval, limited connections, and verification against the system of record as separate stages whenever an external effect is required.

1. Project overview

Background

The data required to investigate equipment abnormalities, yield loss, or quality variation does not live in one screen. Current machine state is held in PLC/OPC, production history in MES, inspection results in quality files, and change history in SOP, QCP, P-FMEA, and owner records. When names, time bases, lots, and disposition codes differ by system, engineers repeatedly have to align meaning and applicability before cause analysis can even begin.

The system organizes that work as data collection → evidence linkage → independent analysis → work proposal → human approval → limited execution → actual-result verification.

My scope

I used manufacturing-field experience to define and coordinate the following areas:

  • the shared meaning and identifiers that bind process, quality, and production data
  • where Workers and Managers analyze, challenge, escalate, or stop
  • why recommendation, human approval, external execution, and result state verification must remain separate
  • the authority and recovery conditions required by PLC, OPC, and MES adapters
  • duplicate-trigger, active-writer, checkpoint, and rollback rules for long-running work
  • the UI, code, and actual-state evidence required before a stage is considered complete

2. Field problem definition

AS-IS — abundant data without a connected decision path

Field segment Existing limitation Impact on process-engineering work
Data location MES, PLC/OPC, Excel, standards, and individual records are fragmented Repeated tracing across screens and files
Semantic alignment Tags, states, lots, defect codes, and time bases differ by system Risk of correlating different subjects as one cause
Cause analysis Relies on individual experience and manual comparison Counter-evidence and retest conditions are found late
AI use Generated answers are detached from source location and applicability Fluent output cannot safely become a process decision
Execution authority Boundary between analysis and PLC/MES change authority is unclear A recommendation may drift into unsafe control
Completion Work ends at request success, HTTP 200, or controller receipt Actual equipment or MES state may remain unverified

TO-BE — one lineage for the engineering decision

The point is not to add more AI. process, quality, and production analyses inspect the same fixed shared source record independently, while Managers preserve conflicts and dissent in one work proposal. The process engineer reviews evidence, applicability, risk, and recovery options before approving, holding, or requesting more measurement.

Representative use case — tracing a recurring defect

  1. The engineer selects the equipment, lot, and time window of a recurring defect.
  2. Read-only adapters freeze MES history, PLC/OPC state, inspection results, and the relevant standard revision.
  3. The process analysis reviews conditions, 4M, and change history; the quality analysis reviews disposition and measurement reliability; the production analysis reviews WIP, bottlenecks, and lot flow.
  4. Managers separate common hypotheses, exclusion evidence, unresolved items, and one consolidated recheck request.
  5. The user approves, holds, or requests additional measurement.
  6. Only when an actual change is needed does a separate approval bind the exact target, parameter, and expiry to a limited adapter.
  7. The system reads the equipment or MES again and closes the work from actual state rather than command receipt.

3. System architecture

Five planes and their boundaries

Plane Input and processing Output Safety and operating rule
Read-only data access MES, QMS, PLC, OPC, alarms, documents, and history Time/lot/tag/state-bound snapshot Read by default; do not change sources or runtime
evidence review Source, revision, currentness, applicability, rights, and publication scope Citable evidence plus missing/conflicting states Do not fill evidence gaps by inference
Recommended checks Process, quality, and production analysis flows Hypotheses, counter-evidence, retests, and work proposal Review coordination does not gain higher execution authority
approval and decision responsibility Target, scope, parameter, expiry, risk, and rollback review Human approval or hold Reject stale, consumed, or mismatched approval
Limited execution and result verification Approved limited adapter and actual-system reread Receipt, actual result, mismatch, and recovery record Separate request success from result success; one active writer

Decoupling AI analysis from control authority

AI analysis authority
Read source → Compare → Explain → Recommend

Human decision authority
Approve → Reject → Request measurement → Limit scope

Separate effect authority
Exact target → Exact parameter → Expiry → One active writer → Rollback

Completion
Command receipt ≠ Process result
Actual-state verification → result comparison → close / reopen

The first manufacturing rule set stage focuses on read-only monitoring and reporting. PLC/OPC writes, production orders, material changes, and PO effects are not opened under one broad permission. Each adapter requires its own approval and recovery contract. This protects equipment safety while keeping the architecture extensible.

Control Runtime for long-running work

  • one active writer per aggregate and duplicate-trigger prevention
  • queue claim, lease, and checkpoint for work ownership and progress
  • semantic rework separated from transport retry
  • recovery of the same Agent, Flow, and WorkItem after restart, without automatic replay when external state is ambiguous
  • one Outcome Record for evidence, dissent, approval, execution receipt, and state verification revision
  • Notion used as a human-readable projection rather than the message bus

Intended process-engineering work product

  • bind the same equipment, lot, and time window across multiple systems into one shared source record
  • present Process, Quality, and Production hypotheses together with exclusion evidence
  • show measurement reliability, change points, affected scope, and owner before a retest
  • keep work proposals separate from execution authority so AI cannot change equipment conditions by itself
  • connect actual equipment/MES state and result revision to the close-or-reopen decision

5. Expansion vision

Phased scale-up

Stage Scope Completion gate
1. Read-only Shadow MES, inspection, equipment state, and standards snapshot for one line Source binding, time/lot/tag consistency, rights and security review
2. Production decision-support tool Separate analyses and integrated work proposals Ground-truth comparison, evidence-error cost, and engineer accept/reject KPIs
3. Limited Effect One restricted command or manufacturing-work request through one adapter Exact target/parameter/expiry, active writer, rollback, and reconciliation
4. Multi-line line-specific rule set Reuse the same Core across different process types and sites Namespace, manifest, adapter compatibility, and staged cutover
5. Autonomous Manufacturing Foundation Evaluate proposals and control strategies in a Digital Twin or simulation first Parallel field validation, safety interlock, human approval policy, and physical E2E revalidation

The core manages module roles, process flow, approval, records, and recovery. Manufacturing rule sets add process, quality, and production decision criteria. A new line replaces its rule set and adapter while retaining source linkage, approval, actual-state recheck, and rollback procedures.

Target state

The target is not a screen where AI operates a plant at will. It is a manufacturing decision-support system where process engineers align system state and evidence, compare process, quality, and production analyses, approve defined work, and trace the actual result.

The current stage is detailed design and local plan validation. The next priority is to establish one read-only Manufacturing Reference Journey in a real UI and runtime.

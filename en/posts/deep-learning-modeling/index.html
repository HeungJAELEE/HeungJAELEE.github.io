Team boundary

The workflow is generalized as validation needed before applying models to manufacturing data.

Why the shop-floor decision mattered

Deep-learning code can run once and still be unusable for an engineering decision if no one can explain which data and settings produced the result. A score can be overstated when samples from the same product or Lot cross training and test boundaries, or when the test set is repeatedly used to guide model changes.

In manufacturing, that problem affects quality decisions directly. Missed defects and false rejections have different costs, and offline behavior can change with equipment, material, or capture conditions. The project therefore starts with a traceable experiment standard rather than a peak score.

Why a digital method was needed

A single notebook is useful for fast exploration, but hidden state and cell order can make a result fragile. Separating preprocessing, training, evaluation, and run records makes it possible to trace which change affected the outcome.

MLOps in this case does not mean that a deployment platform has already been built. It means connecting the data identifier, split rule, configuration, code, runtime environment, and evaluation output as one experiment record.

My actual role

As a personal learning and practical-validation project, I documented a modeling standard that connects problem definition, data splitting, preprocessing, training, evaluation, and reproducibility. The focus is to establish a simple baseline, compare candidates on the same split and evaluation functions, and read metrics together with error cases.

Because the current public material is limited, this case is a design document rather than a list of completed features. It does not claim a specific dataset size, model accuracy, completed training run, or production deployment.

Data flow

Preserve and split source data → preprocessing → configuration-based training → fixed evaluation and error analysis → reproducibility record linking data, code, environment, and results

Preprocessing parameters are fitted only on training data and then applied to validation and test data. Final evaluation uses a fixed test set that was not used for model selection, and retains per-class metrics and representative errors rather than only an average score.

Implementation sequence

  1. Define whether one prediction represents an image, a product, or an equipment time window.
  2. Keep raw data read-only and inspect file, label, equipment, Lot, and time metadata for missing or duplicate values.
  3. Fix train, validation, and test boundaries before training, considering equipment-, Lot-, or time-based groups.
  4. Fit preprocessing on training data only and establish a simple baseline.
  5. Train with recorded data version, split rule, model configuration, random seed, and runtime environment.
  6. Review per-class metrics and error cases under a fixed evaluation contract, then link the model, configuration, and report to the same run record.

This sequence is a target standard for developing the repository; it is not a claim that every step is implemented and publicly verified.

Verified output and current stage

The public repository currently supports only the stated direction of preprocessing, training, evaluation, and reproducibility management. It does not expose enough reproducible commands, dependency versions, dataset detail, or validated model results to support a quantitative achievement claim.

The present portfolio output is therefore an experiment-design standard, not a completed model. It also does not claim field validation on manufacturing data.

Deployment conditions and company value

Manufacturing use requires separate validation: independent equipment-, Lot-, and time-based evaluation; condition-based slices for lighting or sensor variation; inference latency; out-of-distribution and failure behavior; and drift monitoring. Data rights, model version, decision threshold, approval, and rollback also need operating controls.

Under those conditions, a company could review where a model is trustworthy instead of relying on one score. Recording unsuccessful experiments in the same format can reduce repeated work and sharpen the next hypothesis. Any quality improvement or engineering-effort reduction still requires separate field evidence.

Design choices and work flow

Problem

A notebook that runs once does not prove leakage control, preprocessing consistency, reproducibility, baseline improvement, or the cost of manufacturing errors.

Goal

Separate preprocessing, training, evaluation, and reproducibility so the same procedure can be applied to new manufacturing data.

Success

Fixed splits, config, seed, artifact logging, baseline comparison, and error analysis are automated and reproducible in another environment.

Scope and boundaries

In scope

  • Data schema, split, preprocessing, and augmentation rules
  • Baseline, train/evaluate pipeline, metric and artifact logging
  • Recall, precision, F1, and error analysis for imbalanced manufacturing data

Out of scope or unverified

  • Unsupported model accuracy or completed-training claims
  • Claiming an operational MLOps platform already exists
  • Treating one notebook run as a reproducible experiment

Implementation and verification

What had to work

  • Fix train/validation/test splits and test for leakage.
  • Record config, seed, code/data version, and model artifact together.
  • Generate recall, precision, F1, and confusion matrix in addition to accuracy.

Quality and operating rules

  • The same configuration runs in another environment.
  • Baseline comparison and failure cases are reported together.
  • Manufacturing false-negative and false-positive costs influence metric choice.

Why it was designed this way

  1. Design around a pipeline, not a notebook

    Explicit stage inputs and outputs make errors and repeated experiments traceable.

  2. Track config and artifacts with code

    A model file alone cannot explain its data, preprocessing, or seed.

  3. Defer performance claims until evidence exists

    The current public repository does not verify completed training or a metric.

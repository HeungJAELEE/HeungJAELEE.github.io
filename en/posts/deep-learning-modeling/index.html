Why I started this project

Manufacturing vision and equipment data require more than knowing how to call a model. I need to explain which data trained it, whether evaluation data leaked into training, and which error matters more to the operation. This project is a personal learning archive for repeatedly organizing deep-learning concepts and experiment practice.

Current archive structure

The current public archive is a README-based learning map. It records the order in which I review a modeling problem and the evidence that a future experiment should retain. Code, notebooks, training logs, and evaluated outputs will be added as separate reproducible experiments rather than implied by the topic list.

It is not yet a repository where a representative experiment has been rerun with a fixed data split, seed, and configuration file. The project is therefore presented as a learning archive of preprocessing-to-evaluation decisions, not as a reproducibility or model-performance result.

How I review an experiment

Step 1 — Define the problem and error cost

In manufacturing data, a rare missed defect, the cost of reinspection, and the capture condition may matter more than total accuracy. The business cost of each error is written before model selection.

Step 2 — Separate data roles

Raw, training, validation, and final evaluation data must be distinct. Similar frames from the same product, lot, time, or machine can leak across splits and make results look better than they are.

Step 3 — Record preprocessing and configuration

Resize, normalization, augmentation, seed, model, and metrics belong to the same experiment record. A result should remain connected to the configuration that produced it.

Step 4 — Read averages and error types together

Summary metrics such as Accuracy or F1 are reviewed alongside missed defects and false alarms in the confusion matrix. Threshold changes are interpreted through both miss risk and reinspection volume.

Step 5 — Add a separate field-use gate

A good evaluation result does not prove robustness to lighting, equipment, product, or time changes. Shadow tests, reference samples, reinspection flow, model versioning, and rollback criteria are required before production use.

How this helps manufacturing work

The current value is a repeatable checklist for turning an AI output into an engineering decision.

  1. Define the problem and the cost of each error.
  2. Separate data roles and check for leakage.
  3. Record preprocessing and training settings together.
  4. Review actual error types as well as aggregate metrics.
  5. Validate the result against changes in lighting, product, and equipment.
  6. Define deployment, reinspection, and rollback criteria.

The next stage is to attach a small number of end-to-end experiments with fixed data splits, recorded environments, saved metrics, and error samples.

    TECHNICAL CASE STUDY

    Deep Learning Modeling Textbook: Reproducible Experiments for Manufacturing Data

    Jul 13, 2026 · 14 minutes · Last reviewed Jul 31, 2026

    • Deep Learning
    • Python
    • MLOps
    • Reproducibility

    Problem: executable training code is not yet a reproducible experiment

    Deep Learning Modeling Textbook is a personal learning and practical validation project for organizing data preprocessing, model training, evaluation, and reproducibility as one traceable workflow. Instead of stopping at isolated tutorial code, the project defines a modeling standard that can be reused when new data arrives: frame the problem, run a controlled experiment, and explain the result.

    The public repository currently exposes only limited implementation detail. This case study is therefore a design document based on the repository’s stated scope of preprocessing, training, evaluation, and reproducibility management. It does not claim a particular dataset size, model accuracy, completed training run, or production deployment. The directory structure and validation items below are target design criteria, not a list of finished features.

    Background: Executable Code Is Not Yet a Trustworthy Experiment

    A deep-learning example can load data, train a model, and print an accuracy score in a single notebook. In engineering work, however, that output is useful only if the team can answer questions such as:

    • Which version of the data was used for training?
    • Were training, validation, and test samples kept independent?
    • Was the same preprocessing contract used during training and inference?
    • Which baseline and metric justify the claim that the model improved?
    • Can another run with the same settings reproduce a comparable conclusion?
    • In a manufacturing application, which is more costly: a missed defect or a false alarm?

    The project treats these questions as part of the experiment itself, not documentation added after training. The primary goal is not to build the most complex network. It is to develop an experimental discipline that preserves the causal chain between data, configuration, code, and results.

    Project Goals

    1. Separate preprocessing, training, and evaluation into explicit stages.
    2. Prevent data leakage and evaluation contamination before model selection.
    3. Record configuration, code, environment, and outputs together so experiments can be repeated.
    4. Interpret error types and business costs in addition to aggregate accuracy.
    5. Create a transfer framework from educational examples to manufacturing quality and equipment data.

    Why the project uses a pipeline

    Deep-learning modeling is not one action called “training.” Each stage needs a clear input, output, and responsibility so that a failure can be localized. For that reason, the project models the path from source data to evaluation report as a feedback pipeline.

    graph LR A["Raw Data"] --> B["Schema and Quality Checks"] B --> C["Train / Validation / Test Split"] C --> D["Preprocessing and Feature Transformation"] D --> E["Baseline Model"] E --> F["Deep-Learning Training"] F --> G["Fixed-Test Evaluation"] G --> H["Error Analysis"] H --> I["Model, Configuration, and Evaluation Records"] I -->|"Improvement hypothesis"| B

    This design was chosen for three practical reasons:

    • Leakage prevention: the split is fixed first, and preprocessing parameters are fitted only on training data.
    • Comparable experiments: different model architectures use the same split and evaluation functions.
    • Root-cause traceability: a performance change can be connected to data, preprocessing, architecture, or threshold decisions.

    A notebook is useful for exploration, but its hidden state and cell execution order can make results fragile. Moving repeatable preparation, training, and evaluation logic into functions or scripts creates an explicit execution contract and makes a later transition to production easier.

    Architecture and data flow

    The project separates the data contract, preprocessing, training, evaluation, artifacts, and runtime record so the same configuration can be replayed. A result is not treated as current when its input data or evaluation contract has changed.

    Technologies and Why They Were Chosen

    Python

    Python provides one language for data handling, model experiments, and evaluation automation. The learning focus is not memorizing one framework’s API. It is understanding the contracts between tensor shapes, data loaders, training loops, loss functions, and evaluation functions so the same reasoning can transfer across frameworks.

    Deep-Learning Modeling

    The model is treated as one component of the problem-solving system. A simple rule or small baseline, a defensible split, and explicit error costs are defined before adding depth or parameters. This order makes it possible to determine whether added model complexity creates real value.

    Experiment Management from an MLOps Perspective

    MLOps here does not mean that a large-scale deployment platform has already been built. It means applying operational discipline during training by recording:

    • a data snapshot or data-version identifier;
    • train, validation, and test split rules;
    • preprocessing settings and model hyperparameters;
    • random seeds and the execution environment;
    • model weights, evaluation metrics, and error-analysis outputs; and
    • the relationship between a code commit and an experiment result.

    GitHub

    GitHub is used to version code and documentation and to preserve why the design changed. The current public repository alone is not sufficient to verify full experimental reproducibility; code, configuration, dependencies, and execution instructions still need to be expanded.

    Recommended Repository Structure and Design Rationale

    The following layout is a target architecture for developing the repository into a reproducible learning and validation system. It does not describe the current implementation as complete.

    Deep_Learning_Text_book/
├─ README.md              # Problem definition, run order, result interpretation
├─ configs/               # Data, model, and training configuration
├─ notebooks/             # Exploration and concept validation
├─ src/
│  ├─ data/               # Loading, validation, and splitting
│  ├─ preprocessing/      # Shared training/inference transformations
│  ├─ models/             # Model construction interfaces
│  ├─ train.py            # Training entry point
│  └─ evaluate.py         # Fixed evaluation entry point
├─ tests/                 # Schema and preprocessing unit tests
├─ reports/               # Metrics, confusion matrices, and error cases
└─ artifacts/             # Models and execution metadata

    Why Separate notebooks/ from src/

    Notebooks are appropriate for inspecting distributions and testing a hypothesis quickly. Reusable preprocessing and training logic should then move into deterministic code with a fixed execution order. This separation reduces dependence on hidden notebook state without sacrificing fast exploration.

    Why Keep configs/ Separate

    When learning rate, batch size, input dimensions, and other settings are scattered throughout code, it becomes difficult to explain which change affected a result. Keeping configuration separate and saving it alongside outputs makes experiment-to-experiment differences inspectable. This case study intentionally does not prescribe “best” values; they must be selected from the data and validation evidence.

    Why Separate reports/ from artifacts/

    Reports contain evidence for human review, such as metrics and representative errors. Artifacts contain reusable machine outputs, such as model weights and execution metadata. The separation clarifies what should be reviewed, what can be reloaded, and what must be retained for traceability.

    Data and Implementation Flow

    Define the Prediction and Evaluation Unit First

    Before selecting a model, define what one prediction represents: one image, multiple views of one product, or a time window from a machine. This choice determines the correct split and evaluation method. For manufacturing work, the definition should also state the cost of a missed defect, a false rejection, and delayed inference.

    Preserve Raw Data and Validate the Schema

    Raw data remains immutable and is treated as a read-only reference. File paths, labels, equipment IDs, production dates, lots, and other metadata are checked for format, missing values, and duplicates. A metadata defect can mix samples incorrectly even when the image or sensor values themselves are valid, so schema validation comes before modeling.

    Split Before Fitting Preprocessing

    Computing normalization values from the complete dataset or placing augmented versions of one sample into different sets leaks information. Train, validation, and test boundaries are fixed first; only parameters estimated from the training set are applied to validation and test data.

    Manufacturing samples from the same machine, lot, or acquisition session may be highly similar. A random row split can therefore put near-duplicates from the same product into both training and test sets. Depending on the problem, the design evaluates group splits by equipment, lot, or time.

    Establish a Simple Baseline

    A rule-based method or small model is created before introducing a complex network. The baseline is not intended to be the final performer. It is a reference point for determining whether later complexity actually adds measurable value.

    Train from Recorded Configuration

    The data version, split rule, model configuration, training configuration, random seed, and runtime environment are bundled as one experiment record. Training loss is not reviewed in isolation; validation trends and signs of overfitting are recorded as well. The test set remains fixed and is not repeatedly reused for model selection.

    Review Metrics Together with Error Cases

    For classification, accuracy, precision, recall, F1 score, and the confusion matrix are selected according to operational cost. If passing a defective item is the dominant risk, recall for the defect class and false-negative examples take priority. If excessive false alarms stop production, precision and alarm frequency must be considered as well.

    Preserve More Than a Model File

    Each meaningful result should retain at least the following evidence:

    RecordWhy It Matters
    Data identifier and split ruleConfirms whether the evaluation population changed
    Code commit and configurationReconstructs the implementation and conditions
    Training and validation curvesReveals overfitting, underfitting, or instability
    Per-class metrics and confusion matrixExposes error types hidden by averages
    Representative error samplesProduces the next data or model hypothesis
    Execution environmentExplains library and hardware differences

    Technical Challenges and Resolution Strategy

    Data Leakage

    The most dangerous failure is often not model code but a broken evaluation boundary. Duplicate samples, shared lots, common acquisition sessions, or future information must not cross sets. The split rule itself belongs in the configuration and evaluation report so it can be audited.

    Class Imbalance

    Manufacturing quality datasets may contain many normal samples and few rare defects. Overall accuracy can look high even when every item is predicted as normal. The design compares per-class metrics, sampling strategies, loss weighting, and threshold adjustment on a fixed validation set instead of assuming one technique is universally superior.

    Reproducibility versus Bit-for-Bit Identity

    Fixing a random seed does not guarantee identical numbers across hardware and library implementations. Reproducibility is therefore defined as the ability to rerun the same code, data, and settings, reach a comparable conclusion, and explain any variation, rather than requiring every floating-point value to match.

    Strong Offline Metrics versus Shop-Floor Performance

    Lighting, material, sensor, and equipment conditions can differ from the training environment. Offline tests should be supplemented by condition-based slice evaluation, monitoring for change over time, inference-latency checks, and explicit failure handling before a model is considered operationally safe.

    Experiment Proliferation

    When many hyperparameters change at once, it is easy to select only the highest score and lose the causal explanation. The project favors changing one hypothesis at a time and recording unsuccessful experiments as well, preventing the same failed idea from being repeated without context.

    AI and human roles

    AI assists with model candidates, preprocessing and evaluation drafts, experiment-comparison tables, and documentation. A human owns data rights, train-validation-test separation, metrics, runtime identity, result approval, and the publication boundary.

    Validation Framework

    The target validation framework separates data, model, reproducibility, and operations rather than compressing every concern into one score.

    Validation LayerPrimary QuestionExample Checks
    DataAre inputs valid and evaluation boundaries independent?Schema, missing values, duplicates, label distribution, group leakage
    ModelDoes the model improve meaningfully over the baseline?Fixed split, per-class metrics, confusion matrix, error cases
    ReproducibilityCan the experiment be explained and rerun?Configuration, seed, environment, code and data versions
    OperationsCan the model fail safely under field conditions?Inference time, out-of-distribution inputs, failure handling, data drift

    Validation evidence is read according to the decision being made. In quality inspection, a missed defect and a false rejection carry different costs. In equipment anomaly detection, early warning and the operator’s ability to respond can be as important as a classification score.

    Resume Relevance: Connecting AI Practice to Manufacturing Engineering

    Manufacturing root-cause analysis connects process conditions, equipment, material lots, working time, and inspection results. This project applies the same discipline to model development:

    • Preserve source evidence by separating raw field data from derived data.
    • Control change points by recording code, configuration, and data-split changes as experiment units.
    • Define inspection criteria by connecting model metrics to the cost of accepting a defect or rejecting a good item.
    • Maintain traceability from a model result back to its data version and execution conditions.
    • Analyze causes, not averages by reviewing errors by equipment, lot, time, or operating condition.
    • Standardize repeatable work by documenting the modeling workflow like an engineering work standard.

    This perspective keeps AI from becoming an isolated research exercise. A model is one element of a manufacturing process; it becomes a useful quality-improvement tool only when data-collection conditions, decision thresholds, traceability, and failure response are designed together. For a resume, the project demonstrates systems thinking and verification discipline rather than claiming an unverified production deployment or headline accuracy figure.

    Current Limitations

    • The public repository does not yet expose enough code, data documentation, configuration, or execution results to substantiate the full project scope.
    • No validated performance figures for a specific dataset and model are available, so model rankings or quantitative improvements cannot be claimed.
    • Reproducible commands, dependency versions, and automated tests cannot be verified from the public materials alone.
    • This case study does not claim field validation or operational results on proprietary manufacturing data.
    • The current portfolio value is therefore the reasoning used to design and validate experiments, not the performance of a completed production model.

    Improvement Roadmap

    1. Add a small, publishable example dataset and a precise problem definition.
    2. Separate data checks, training, and evaluation into independently executable modules.
    3. Document environment files and run commands for a clean first-time reproduction.
    4. Compare a baseline and at least one deep-learning model on the same split and metrics.
    5. Generate an evaluation report containing a confusion matrix and representative error cases.
    6. Add unit tests for preprocessing and data-leakage prevention rules.
    7. Run minimum tests on code changes and record intended use and limitations in a model card.
    8. Validate equipment-, lot-, and time-based split scenarios with an open manufacturing dataset.

    The most important result in deep-learning modeling is not one peak score. It is the ability to explain why a particular dataset and architecture were selected and whether the same procedure can verify that decision again. This project is intended to evolve into a long-term experimental repository that develops that standard and transfers it to manufacturing data problems.

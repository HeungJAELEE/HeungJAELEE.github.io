I built a personal guidebook for judging manufacturing AI from data through field adoption—not by clean-example accuracy, but by product, lot, and time variation plus missed-defect risk.

1. Project background and intent

The manufacturing domain gap

General AI tutorials tend to use curated data, random splits, and average accuracy. Manufacturing inputs shift with material lot, production time, equipment condition, illumination, operator, and recipe changes—even for the same product. When training and evaluation share these conditions, a strong test score can still conceal missed defects on the next lot or production window.

The relevant manufacturing questions are therefore broader than “What percentage was correct?”

  • Which defect was missed — FN, missed detection, or underkill
  • Which good product was rejected — FP, false alarm, or overkill
  • Which product, lot, time window, or equipment condition concentrates the errors
  • Whether model latency interferes with takt time and the existing inspection or control flow
  • Whether the process can return immediately to the established decision path

Research objective

I reorganized the archive around the following manufacturing-AI decision flow.

Define process problem and error cost
→ Split by Product, Lot, and Time
→ Control configuration, version, and experiment records
→ Evaluate Recall, FN, FP, and error causes
→ Shadow test, manual review, and rollback

② Multimodal manufacturing-defect prototype

Manufacturing-Defect/integrated_prototype.py processes synthetic manufacturing images and sensor values together.

sensor_logs.csv + images/
→ KNN imputation
→ StandardScaler
→ Image transform
→ Image + temperature/vibration dataset
→ CNN feature + sensor feature fusion
→ Mixed-precision training
→ MLflow loss and model logging

Implemented elements include:

  • disk-based image and sensor-CSV loading
  • missing-value imputation through KNNImputer
  • sensor scaling through StandardScaler
  • image, sensor, and label integration in FactoryFileDataset
  • fusion of CNN features with temperature and vibration features
  • a torch.cuda.amp training loop
  • MLflow experiment, training-loss, and model logging

This skeleton establishes the code sequence. The next implementation package replaces synthetic input with a process-source adapter and adds data splitting, evaluation, and field-validation contracts.

4. Five manufacturing-AI safety gates

Gate 1. Adoption rationale — Why and What

The process problem and error cost come before model selection.

Decision itemManufacturing questionOutput
Target CTQWhich defect or equipment anomaly is being detected?Failure mode and label definition
FN costWhat customer, escape, or rework impact follows a missed defect?FN priority
FP costWhat reinspection, scrap, or takt loss follows a false alarm?FP tolerance
Point of useOperator aid, inspection decision, or equipment control?Authority and user flow
Success conditionWhich performance, speed, and operating checks must pass?Acceptance criteria

Gate 2. Data — Product, Lot, and Time split

A random split can place near-duplicate images from the same production condition in both train and test sets. Manufacturing AI therefore requires independent evaluation units.

Train
= earlier products, lots, and time windows

Validation
= lots and time windows separated from training but used for condition selection

Final test
= product, lot, and time windows never used for model or threshold selection

Required checks:

  • block duplicate cells, images, and adjacent frames across train and test
  • retain product, material lot, equipment, illumination, shift, and time metadata
  • record class imbalance between abundant good products and rare defects
  • freeze the split before augmentation
  • isolate the final test from model and threshold selection

Gate 3. Configuration — a reproducible execution unit

A model weight alone does not reproduce an experiment. The following information belongs to one execution unit.

experiment:
  data_version: "..."
  split_manifest: "..."
  random_seed: 42
  model: "..."
  image_size: 224
  batch_size: 32
  learning_rate: 0.0001
  decision_threshold: 0.40
  code_commit: "..."

Controlled items:

  • data source, label version, and split manifest
  • preprocessing, augmentation, and random seed
  • model architecture and weight initialization
  • batch, learning rate, and epoch count
  • threshold and operating point
  • code commit and package environment
  • confusion matrix, error list, weight, and logs

Gate 4. Evaluation — error structure before accuracy

With 990 good products and ten defects, a model that predicts every item as good still reports 99% accuracy. Manufacturing inspection must evaluate error direction and cost.

Evaluation axisMetrics and evidenceDecision purpose
Missed defectsRecall, FN count, FN by defect typePrevent customer escape and critical misses
False alarmsPrecision, FP count, FP by productControl reinspection, scrap, and takt loss
BalanceF1, PR curve, and confusion matrixInclude class imbalance in the decision
CauseError image, product, lot, time, and equipment slicesIdentify domain-gap and drift segments
ExplanationGrad-CAM, ROI, and annotation comparisonCheck whether the model learned the defect rather than background or fixture
OperationLatency, throughput, and memoryCheck takt and long-run suitability

The threshold is selected from FN and FP costs plus manual-review capacity—not maximum accuracy alone.

Gate 5. Deployment — shadow test and rollback

A completed test-set evaluation does not justify immediate PLC or equipment intervention.

Retain existing inspection and control
+ run AI decisions and logs in the background
→ compare against operator and existing-inspection results
→ analyze FN, FP, and latency by Product, Lot, and Time
→ approve release or revise conditions
→ roll back to the established decision path on abnormal behavior

Shadow-stage controls:

  • AI decision, confidence, and processing time
  • disagreement with the operator or existing inspection
  • error concentration by product, lot, time, and equipment condition
  • manual review and segregation for missed-defect candidates
  • false-alarm bursts, delay, communication errors, and drift
  • model-version rollback and the retained conventional inspection path

6. Project result

Bridge between manufacturing knowledge and AI experiments

  • integrated preprocessing, model, evaluation, and system-design material into one GitHub learning path
  • connected a PyTorch starter with a synthetic image/sensor manufacturing-defect skeleton
  • shifted evaluation from accuracy alone to Recall, FN, FP, and error slices
  • defined independent evaluation by Product, Lot, and Time instead of relying only on random split
  • placed shadow testing, manual review, and rollback between model evaluation and field release

AX engineering asset

The guidebook is built to answer the following questions—not to maximize the number of models in the repository.

Which process problem is being solved?
→ Does the data represent production variation?
→ Can the same experiment be rerun?
→ Which defect was missed?
→ Can the model be introduced in parallel without disrupting control?
→ Can the process recover immediately when abnormal behavior appears?

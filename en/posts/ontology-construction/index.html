    HeungTology: Finding Industrial Knowledge with Traceable Sources

    A personal project connecting industrial documents through data contracts, relationship validation, hybrid retrieval, and source citations

    Jul 9, 2026 · 6 minutes · Last reviewed Jul 31, 2026

    • Knowledge Graph
    • Neo4j
    • Ontology
    • GraphRAG
    • Data Quality
    • AI

    The problem

    Manufacturing knowledge is split across process, equipment, quality, defect, and corrective-action documents. As the collection grows, one machine acquires several names, relationships point to missing records, and unsupported explanations enter search results.

    HeungTology is not a document-count project. It is a personal project for validating human-edited documents, tracing process and equipment relationships, and showing which source section supports a retrieved answer.

    Why it is structured this way

    Keeping authoring, graph exchange, and retrieval data in one hand-maintained file makes drift likely. The project therefore separates their responsibilities.

    flowchart LR A["Markdown + YAML\nhuman-edited source"] --> B["Schema, relation, and path checks"] B --> C["JSON-LD / OWL / SHACL\nexchange and semantic checks"] B --> D["Heading-aware retrieval data"] D --> E["Vector + full-text"] C --> F["Neo4j relationship traversal"] E --> G["Rank fusion and reranking"] F --> G G --> H["Answer with source document and heading"]
    • YAML and JSON Schema constrain the fields entered by a person.
    • JSON-LD, OWL, and SHACL handle exchange, semantics, and relationship shapes.
    • Neo4j supports questions that traverse process, equipment, defect, cause, and action.
    • Vector and full-text search cover semantic similarity and exact equipment terms.
    • Citation rules prevent a plausible retrieval result from becoming a confident answer without a source.

    What I designed and changed

    Fix the document contract first

    Each record keeps identity, aliases, classification, lifecycle, provenance, relationships, and supported claims in predictable fields. Duplicate keys, missing relationship targets, local absolute paths, and structural errors are reported before release. Ambiguous relationships remain in a review queue rather than being attached to the nearest-looking record.

    Keep retrieval stages explicit

    Vector and lexical scores are not directly added because they have different scales. Each search produces a ranked candidate list; ranks are fused, selected graph relationships are expanded, and the final context is reranked. Source paths and headings travel with the context so a reviewer can trace the answer.

    Correct the publication boundary

    An earlier version of this article presented local release metrics as though the same report were directly reproducible from the public repository. Because that report is not publicly readable, node, assertion, error, and warning counts have been removed from the public achievement claim. The repository link now supports only what a visitor can inspect there.

    Result and manufacturing relevance

    The project establishes a practical difference between “a document exists” and “a claim has traceable support.” It also keeps knowledge retrieval separate from physical control authority.

    The design comes from field experience where process settings, inspection criteria, equipment history, and corrective actions lived in separate documents. The same discipline used to separate criteria and evidence in QCP, P-FMEA, and MSA informs the source, claim, and validation boundaries here.

    Evidence and limits

    • The public repository exposes the data structure, transformation and validation code, and retrieval design documentation.
    • Local validation counts that are not reproduced publicly are not used as headline results.
    • The documents do not all have the same depth of human review.
    • Retrieval quality still needs a fixed question set and relevance judgments.
    • Knowledge retrieval must remain a read function, separate from equipment control.

    Design choices and work flow

    The delivery plan treats schema, deterministic migration, semantic validation, retrieval, and citation as one release system rather than a document collection exercise.

    Problem

    Industrial Markdown and ad-hoc frontmatter accumulated duplicate keys, broken references, weak provenance, and local paths that reduced retrieval trust.

    Goal

    Keep YAML human-editable while validating schema, hash, provenance, and relations, then make GraphRAG cite the same release source.

    Success

    The same input produces consistent transformation results and retrieval traces context to a source document and heading.

    Scope and boundaries

    In scope

    • YAML v9 canonical node and JSON Schema contract
    • Deterministic migration, manifest, JSON-LD, OWL, and SHACL release
    • Neo4j vector/full-text/RRF/graph expansion/reranking and citation

    Out of scope or unverified

    • Guessing links for ambiguous or external relationships
    • Claiming DGX Spark is a continuously available public service
    • Promoting unvalidated documents to authoritative sources

    Implementation and verification

    What had to work

    • Every node has stable ID, type, aliases, relations, provenance, and body hash.
    • Migration and release produce the same output from the same input.
    • Retrieval returns source node, heading, and provenance.

    Quality and operating rules

    • Schema, hash, and reference errors stop release; warnings remain visible.
    • Local Windows paths and sensitive information are blocked before ingestion.
    • Public achievement figures must be reproducible from a report available to visitors.

    Why it was designed this way

    1. Separate authoring from semantic release

      Humans maintain YAML while machines generate JSON-LD, OWL, and SHACL, reducing manual drift.

    2. Use a release gate that preserves warnings

      Unresolved external links must remain visible data debt instead of guessed truth.

    3. Use hybrid retrieval with a citation boundary

      Vector similarity alone cannot satisfy exact terms, graph relations, and source traceability.

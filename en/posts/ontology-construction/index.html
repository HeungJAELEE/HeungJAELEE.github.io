HeungTology for Collecting and Searching Manufacturing Knowledge

A personal project that links manufacturing notes and document relationships to find material related to a question

User, build, and validation summary

User problem
Manufacturing, semiconductor, and battery knowledge accumulated with inconsistent terms and links, making evidence retrieval difficult.
Build scope
I structured the Markdown/YAML vault and link-graph index, then built a CLI that synchronizes changed files to ChromaDB and retrieves/reranks candidates.

User and existing problem

As manufacturing, semiconductor, and battery notes grow, the same equipment and issue are described with different terms. Finding related material, tracing the source document, and reindexing only changed files becomes more important than simply adding more notes.

HeungTology keeps Markdown as the human-readable source, uses YAML metadata and document links for topics and relations, and adds natural-language candidate retrieval.

Repository structure

HeungTology
├─ 02_Knowledge/                 # Industrial Markdown knowledge
│  └─ _System/_index/
│     ├─ GRAPH.md                # Link-derived relation index
│     ├─ VAULT_INDEX.md          # Navigation index
│     └─ index.json              # Tool/search index
├─ 02_Knowledge/_System/
│  └─ _Ontology_Map.json         # Topic and relation map
├─ rag_cli_v2.py                 # Incremental sync and query CLI
└─ README.md

The public code verifies a --sync path that finds changed Markdown files and writes them to a ChromaDB collection. The query path uses BGE-family embeddings and a reranker. Wiki-style links, YAML metadata, and generated graph indexes are also present.

The current implementation centers on the Markdown vault, generated indexes, and search CLI. JSON-LD, OWL, SHACL, and Neo4j remain possible extensions rather than dependencies of the working search path.

Data and execution flow

Markdown + YAML
→ detect changed files
→ build chunks and metadata
→ synchronize ChromaDB
→ embed the question
→ retrieve candidates
→ rerank
→ review original titles and text

Source documents and generated indexes remain separate so the index can be rebuilt from human-readable material.

What I directly built

  • Industrial Markdown vault and metadata conventions
  • Link-derived relation indexes
  • Incremental synchronization for changed documents
  • Natural-language retrieval and reranking CLI
  • Title/source-text connection for result review

AI helps find candidates. A person still reviews factual accuracy, source status, and publication decisions.

Current stage

The working path is a Markdown knowledge vault and search CLI prototype: changed documents can be synchronized, candidates retrieved and reranked, and the original title and text reviewed. The next step is to add reproducible index-rebuild and query snapshots.

Gates before manufacturing use

  1. Require source and review dates per document.
  2. Show the source location with every retrieval result.
  3. Test clean index deletion and rebuild.
  4. If a graph database is used, verify loading code, queries, and result snapshots.
  5. Never allow retrieval alone to approve quality or safety actions.

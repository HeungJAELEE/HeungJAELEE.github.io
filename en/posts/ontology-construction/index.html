1. The data problem

Industrial knowledge is not trustworthy merely because it is stored in Markdown. Retrieval quality degrades when:

  • one concept has several unstable identifiers;
  • parsers interpret duplicate YAML keys differently;
  • relationships point to missing or ambiguous targets;
  • claims have no source, locator, or integrity binding;
  • local absolute paths or secrets enter an index;
  • vector similarity is used for every exact term and relationship question.

HeungTology addresses the complete path from document → data contract → semantic release → retrieval → cited answer.

2. Architecture

flowchart LR A["Markdown + YAML v9"] --> B["JSON Schema + body hash"] B --> C["JSON-LD 1.1 release"] C --> D["OWL 2 RL + SHACL"] B --> E["Heading-aware chunks"] E --> F["Qwen3 Embedding\n2560D"] F --> G["Neo4j vector + full-text"] G --> H["RRF + allow-listed graph expansion"] H --> I["Qwen3 Reranker"] I --> J["Grounded answer with [S#]"]

Four contracts remain separate by design:

  • YAML is the constrained human-authoring format.
  • JSON Schema 2020-12 validates document and release structure.
  • JSON-LD 1.1 is the canonical exchange representation.
  • OWL 2 RL, SKOS, PROV-O, DCAT 3, and SHACL carry and validate semantics.

3. Canonical node contract

Group Key fields Purpose
Identity UUID, legacy IDs, slug, title stable entity resolution
Classification node type, domain, tier, tags filtering and analysis
Lifecycle status, version review and release state
Provenance authors, source refs, body hash, reviewer traceability
Relations broader, related, instance-of graph paths
Assertions subject, predicate, object, evidence claim-level support
Retrieval aliases, expected queries, trust, embedding profile search behavior
Validation schema version, status machine gate

Duplicate YAML keys, anchors, aliases, merge keys, custom tags, non-string keys, and non-JSON values are rejected. The normalized UTF-8 body is hashed and compared with provenance metadata.

4. Migration and validation

The v9 migration is deterministic: parse the legacy source, generate stable identity, normalize classification, resolve references where a unique target exists, calculate body hashes, validate every transformed node, and only then allow --write. It produces an ID map and machine-readable migration report.

The public report records:

Metric Result
Scanned / migrated nodes 4,602 / 4,602
Parse errors 0
Duplicate IDs 0
Provenanced assertions 1,904
Internal relations 4,448
External/unresolved relations 137
Validation errors 0
Validation warnings 2

The two warnings are operational boundaries: unresolved external relationships remain explicit instead of being attached to a guessed internal node, and 134 local body paths are redacted during GraphRAG ingestion.

5. Hybrid retrieval design

Vector search helps with semantic similarity; full-text search helps with equipment codes, standards, and exact industrial terms; graph expansion supports relationship questions. Their incompatible raw scores are not directly added.

  1. Retrieve vector top-k candidates.
  2. Retrieve title, alias, heading, and body full-text candidates.
  3. Fuse ranks with reciprocal-rank fusion.
  4. Expand allow-listed one-hop graph relationships.
  5. Rerank the candidate context.
  6. Pass source paths and headings to generation.
  7. Require [S#] citations and state when evidence is insufficient.

6. Data-analysis value

This case demonstrates analytical work before visualization:

  • define stable units, dimensions, and lifecycle states;
  • distinguish “a document exists” from “a supported assertion exists”;
  • quantify unresolved and ambiguous relationships;
  • separate blocking validation errors from improvement warnings;
  • compare vector, lexical, and graph retrieval roles;
  • preserve uncertainty and provenance in downstream answers.

7. Manufacturing relevance

Battery and automation work repeatedly links process conditions, equipment signals, quality documents, defects, causes, and actions. The graph model transfers that field reasoning into a data contract. QCP/P-FMEA/MSA experience informs claim/validation separation; MES field design informs canonical identity and provenance; FAT/SAT experience informs deterministic release gates.

8. Limitations and next steps

  1. Not all 4,602 nodes have the same depth of human review.
  2. Claims outside the 1,904 structured assertions are not automatically evidence-complete.
  3. Unresolved and ambiguous legacy references remain a quality backlog.
  4. A target DGX Spark runtime is not the same as proven continuous production operation.
  5. Retrieval quality still needs a fixed benchmark and relevance judgments.
  6. Neo4j sync and LLM answers remain read/search functions, separate from physical control authority.

The central skill shown here is not simply using Neo4j. It is turning human-authored industrial knowledge into a versioned, validated, evidence-aware release while keeping unresolved quality issues visible.

What this project is

The same machine or defect can have different names across manufacturing documents. When process instructions, quality criteria, equipment history, and corrective-action records use inconsistent terminology, finding a document does not establish that it refers to the same object.

HeungTology is a personal experiment that stores industrial-knowledge documents as Markdown nodes and indexes their YAML front matter and body text in a local vector store. It is a Git repository containing a knowledge collection and a local Python CLI, not a public web service or graph dashboard.

User journey

A first-time reviewer can read the README for orientation, then compare documents in 02_Knowledge with rag_cli_v2.py to distinguish implemented behavior from design language.

The local flow visible in code is prepare Markdown nodes → run --sync to read front matter and body text → create BGE-M3 embeddings → upsert into ChromaDB → enter a query → retrieve candidates → rerank with BGE reranker → apply time decay and hash status → print a terminal scoreboard. The current CLI prints candidate filenames, parent information, and scores. It does not provide a web page or a natural-language answer screen.

My actual role

As a personal project, I structured metadata for Markdown knowledge nodes and implemented the local retrieval flow in rag_cli_v2.py. The script maps domain, object type, parent relationship, tier, date, and trust fields into search metadata, reranks retrieved candidates, and applies time decay and a hash-comparison result to the score.

What is implemented and what remains limited

The public code supports Markdown front-matter parsing, ChromaDB synchronization, BGE-M3 embedding retrieval, BGE reranking, date-based score decay, a limited evidence_hash comparison, and a terminal scoreboard.

The repository does not currently include a dependency manifest, automated tests, portable path and device settings, a web UI, or a public runtime URL. The CLI assumes Windows absolute paths, local CUDA, and pre-existing model and database resources, so it is not presented as a reproducible clean-checkout application. Several repository documents also retain pending_review, placeholder, and [데이터 부재] markers; performance figures and completion declarations inside those documents are not treated as verified results.

This case therefore claims no node count, accuracy, latency, error or warning count, or release grade. Accuracy, authorization, and freshness for real company-document retrieval require separate data and an operating environment.

Conditions for company use

Company use would require named terminology owners, controlled change and review procedures, source-acceptance rules, access control, and audit history. Retrieval must remain read-only and separate from equipment control so unsupported text cannot become an operating condition or work instruction.

With those controls and a reproducible installation and evaluation path, common metadata and relationships could help teams find process conditions, equipment history, and corrective-action evidence across departmental vocabulary. The current public result is not that operating outcome; it is a reviewable starting point for the document structure and local retrieval experiment.

Design choices and work flow

The delivery plan treats schema, deterministic migration, semantic validation, retrieval, and citation as one release system rather than a document collection exercise.

Problem

Industrial Markdown and ad-hoc frontmatter accumulated duplicate keys, broken references, weak provenance, and local paths that reduced retrieval trust.

Goal

Keep YAML human-editable while validating schema, hash, provenance, and relations, then make GraphRAG cite the same release source.

Success

The same input produces consistent transformation results and retrieval traces context to a source document and heading.

Scope and boundaries

In scope

  • YAML v9 canonical node and JSON Schema contract
  • Deterministic migration, manifest, JSON-LD, OWL, and SHACL release
  • Neo4j vector/full-text/RRF/graph expansion/reranking and citation

Out of scope or unverified

  • Guessing links for ambiguous or external relationships
  • Claiming DGX Spark is a continuously available public service
  • Promoting unvalidated documents to authoritative sources

Implementation and verification

What had to work

  • Every node has stable ID, type, aliases, relations, provenance, and body hash.
  • Migration and release produce the same output from the same input.
  • Retrieval returns source node, heading, and provenance.

Quality and operating rules

  • Schema, hash, and reference errors stop release; warnings remain visible.
  • Local Windows paths and sensitive information are blocked before ingestion.
  • Public achievement figures must be reproducible from a report available to visitors.

Why it was designed this way

  1. Separate authoring from semantic release

    Humans maintain YAML while machines generate JSON-LD, OWL, and SHACL, reducing manual drift.

  2. Use a release gate that preserves warnings

    Unresolved external links must remain visible data debt instead of guessed truth.

  3. Use hybrid retrieval with a citation boundary

    Vector similarity alone cannot satisfy exact terms, graph relations, and source traceability.

HeungTology: Finding Industrial Knowledge with Traceable Sources

A personal project connecting industrial documents through data contracts, relationship validation, hybrid retrieval, and source citations

Why the shop-floor decision mattered

The same machine or defect can have different names across manufacturing documents. When process instructions, quality criteria, equipment history, and corrective-action records use inconsistent terminology, a search result does not establish that every document refers to the same subject. Unsupported explanations can also appear beside source-backed content.

HeungTology is a personal project for managing terminology and relationships under one contract and tracing a retrieved statement back to its source. The key decision was to separate “a document exists” from “this document supports this claim.”

Why a digital method was needed

A person can navigate folders by memory only while the collection remains small. Consistent IDs, aliases, types, provenance, and relationships allow structural checks and support both exact-term and semantic retrieval.

Human-readable Markdown and YAML remain the authoring source. Graph and retrieval representations are derived from that source, preserving ownership and provenance while making relationships searchable.

My actual role

As a personal project, I designed and implemented the YAML document contract, transformation and validation flow, knowledge-graph representation, and retrieval stages. Duplicate identities, missing relationship targets, local absolute paths, and format errors were defined as pre-release checks. Ambiguous relationships remain for human review rather than being attached automatically to the nearest-looking record.

For retrieval, vector and lexical raw scores are not added directly. Their candidate ranks are fused, and the final context carries its source path and heading so a reviewer can trace where the answer began.

Data flow

Manufacturing terminology mismatch → YAML document contract → knowledge-graph representation → schema, relationship, and path validation → source-linked search use

YAML IDs and aliases let several terms resolve to one managed concept. Graph relationships support traversal across process, equipment, defect, cause, and action. Only validated material becomes a search candidate, and retrieved context includes its document and heading.

Implementation sequence

  1. Define a YAML contract for identity, title, aliases, type, lifecycle, provenance, and relationships.
  2. Separate conversion boundaries for graph representations used by JSON-LD, OWL, SHACL, and Neo4j.
  3. Validate schemas, identifiers, relationship targets, and local-path leakage; leave uncertain links for review.
  4. Build heading-aware retrieval data and fuse ranked lexical and vector candidates.
  5. Expand only selected relationships, rerank the context, and pass source path and heading with the answer material.

Verified output and current stage

The public repository supports claims about the data structure, transformation and validation code, and retrieval design documentation. The current stage is a personal project demonstrating the structure and retrieval flow. The documents do not all have the same depth of human review, and retrieval quality still needs a fixed question set with relevance judgments.

Deployment conditions and company value

Company use requires named terminology owners, controlled change and review procedures, provenance rules, access control, and audit history. Retrieval must remain read-only and separate from equipment control, so unsupported text cannot become an operating condition or work instruction.

Under those conditions, shared IDs and relationships could help teams find process conditions, equipment history, and corrective-action sources across departmental vocabulary. The company value lies in a reusable review and provenance structure, not in fluent search wording alone.

Design choices and work flow

The delivery plan treats schema, deterministic migration, semantic validation, retrieval, and citation as one release system rather than a document collection exercise.

Problem

Industrial Markdown and ad-hoc frontmatter accumulated duplicate keys, broken references, weak provenance, and local paths that reduced retrieval trust.

Goal

Keep YAML human-editable while validating schema, hash, provenance, and relations, then make GraphRAG cite the same release source.

Success

The same input produces consistent transformation results and retrieval traces context to a source document and heading.

Scope and boundaries

In scope

  • YAML v9 canonical node and JSON Schema contract
  • Deterministic migration, manifest, JSON-LD, OWL, and SHACL release
  • Neo4j vector/full-text/RRF/graph expansion/reranking and citation

Out of scope or unverified

  • Guessing links for ambiguous or external relationships
  • Claiming DGX Spark is a continuously available public service
  • Promoting unvalidated documents to authoritative sources

Implementation and verification

What had to work

  • Every node has stable ID, type, aliases, relations, provenance, and body hash.
  • Migration and release produce the same output from the same input.
  • Retrieval returns source node, heading, and provenance.

Quality and operating rules

  • Schema, hash, and reference errors stop release; warnings remain visible.
  • Local Windows paths and sensitive information are blocked before ingestion.
  • Public achievement figures must be reproducible from a report available to visitors.

Why it was designed this way

  1. Separate authoring from semantic release

    Humans maintain YAML while machines generate JSON-LD, OWL, and SHACL, reducing manual drift.

  2. Use a release gate that preserves warnings

    Unresolved external links must remain visible data debt instead of guessed truth.

  3. Use hybrid retrieval with a citation boundary

    Vector similarity alone cannot satisfy exact terms, graph relations, and source traceability.

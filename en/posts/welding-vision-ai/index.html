AI Welding Vision: Designing Metrics Around Missed-Defect Risk

Portfolio summary: Problem–Role–Action–Result–Evidence

Item Verified scope
Problem Micro-defect features overlapped with normal surfaces, data was imbalanced, and accuracy alone did not represent the cost of passing a defective weld.
Role I was responsible for evaluation-metric design and validation, including F1, recall, false-positive behavior, and threshold interpretation.
Action The team separated roughly 60,000 AI-Hub images from 198 field images, compared a DenseNet baseline, a two-model combination, and a ResNet+DeiT ensemble, then reviewed a second test set and tuned the decision threshold to prioritize missed-defect control.
Result On the recorded evaluation set and selected threshold, the report lists F1 93.10%, Recall 100%, and Precision 87.07%. These values do not establish production-wide generalization.
Evidence The public report’s dataset, model-evolution, second-test, threshold, and final-metric slides; no dedicated public repository.

Resume bullets

  • Separated approximately 60,000 public welding images and 198 field images by learning/field-validation purpose instead of presenting them as one undifferentiated training set.
  • Compared DenseNet, a two-model combination, and a ResNet+DeiT ensemble, then used second-test error review to tune the operating threshold around missed-defect cost.
  • Recorded F1 93.10%, Recall 100%, and Precision 87.07% on the stated evaluation set and defined manual reinspection as the control for remaining false positives.

Interview STAR

  • Situation: Missing a small weld defect carried a higher quality risk than sending a normal part to reinspection, while accuracy could remain high under class imbalance.
  • Task: Establish a comparable evaluation framework and a decision threshold aligned with that asymmetric risk.
  • Action: Separate data sources, compare model stages on the same metrics, inspect mixed normal/defect regions in a second test, and search thresholds that retained recall.
  • Result: The selected evaluation produced Recall 100%, F1 93.10%, and Precision 87.07%. I also documented that this is inspection-assistance evidence, not proof of autonomous production deployment.

1. Why this project was structured this way

Manufacturing vision is not finished when a model outputs a class. A deployable quality decision must answer four questions:

  1. What exactly counts as a defect?
  2. Which data was used for learning and which data checks field transfer?
  3. What is the cost of a false negative versus a false positive?
  4. Can a quality engineer review the evidence behind a wrong decision?

My battery-assembly experience with laser and ultrasonic welding made the decision boundary the center of this project. The model architecture matters, but the operational threshold and reinspection rule determine how a model affects quality risk.

2. Data and evaluation flow

flowchart LR A["AI-Hub public images\n~60,000"] --> B["label / quality checks"] B --> C["model comparison"] D["field images\n198"] --> E["field-condition check"] C --> E E --> F["probability outputs"] F --> G["threshold search"] G --> H["confusion matrix"] H --> I["F1 93.10%\nRecall 100%\nPrecision 87.07%"] H --> J["FP/FN image review"]

The public and field data are not described as 60,198 interchangeable training images. The public set supplies breadth; the 198 field images provide a limited check against lighting, surface, camera, and domain differences.

3. Model evolution

The project report records three stages.

Stage Approach Decision reason
1 DenseNet121 baseline affected by the reported 2:8 imbalance
2 DenseNet + Mask R-CNN combination compatibility and expected-benefit gap
3 ResNet + DeiT ensemble, augmentation, threshold tuning final selected direction

The case does not claim that choosing a newer architecture alone produced the final quality decision. The useful work was maintaining a common evaluation frame and reviewing where normal and defect predictions overlapped.

4. Why recall was prioritized

For defect probability (p) and threshold (t), lowering (t) normally increases sensitivity but can increase false alarms. The quality tradeoff is summarized by:

[ \text{Precision} = \frac{TP}{TP+FP}, \qquad \text{Recall} = \frac{TP}{TP+FN} ]

[ \text{F1} = 2 \cdot \frac{\text{Precision}\cdot\text{Recall}}{\text{Precision}+\text{Recall}} ]

The recorded Recall 100% means no defect in that evaluation set was missed at the selected threshold. Precision 87.07% means some predicted defects were normal. The operating decision was therefore: protect against missed defects first, then route suspected false positives to reinspection.

5. Validation result and limits

Metric Recorded result Proper interpretation
Public images ~60,000 broad learning source
Field images 198 limited field-condition check
Recall 100% no missed defect in this evaluation set
Precision 87.07% remaining false-positive cost
F1 93.10% balance at the selected threshold

The public material does not fully disclose product/Lot split, class counts for every defect subtype, repeated-run variance, camera-cycle time, or long-term drift. The metrics therefore support a bounded PoC, not an unconditional production KPI.

6. Production-readiness requirements

  1. Split training and validation by product/Lot to reduce leakage.
  2. Publish class-level confusion matrices and confidence intervals.
  3. Standardize camera position, exposure, focus, and illumination.
  4. Measure inference latency and missed-frame behavior at line speed.
  5. Store model version, threshold, image, Lot, equipment condition, and operator reinspection.
  6. Monitor domain drift and route disagreement cases to an active-learning queue.
  7. Require model/threshold change approval and rollback records.

7. Role relevance

  • Manufacturing AI & data: domain-aware data separation, model comparison, threshold control, and deployment gates.
  • Data analysis: metric definition, class imbalance, confusion-matrix interpretation, and scope-limited conclusions.
  • Manufacturing engineering: welding-process context, reinspection workflow, MES/PLC traceability, and quality-risk ownership.

The most important result is not the F1 number in isolation. It is the ability to translate a manufacturing defect risk into data boundaries, comparable metrics, a decision threshold, and an honest deployment limit.

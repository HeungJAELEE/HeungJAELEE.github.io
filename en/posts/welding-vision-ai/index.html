Why this problem mattered

For weld inspection, the central question is not the model name or a single accuracy score. It is how to control the risk of passing a defect as normal. With an imbalanced dataset, a model can show high accuracy while detecting very few defects. Lowering the decision threshold too far, however, sends more good parts to reinspection and slows production.

This education team PoC classified weld-defect images. It separated public learning material from limited field images, then defined an evaluation flow that considered recall, precision, false alarms, and missed defects when converting model probabilities into an inspection decision.

Operation stop at a model output connect false alarms to reinspection and missed defects to cause review

My scope

  • translated weld-quality risk into evaluation priorities
  • separated the intended roles of public data and field-check material
  • organized a common comparison flow for model candidates
  • interpreted recall, precision, false alarms, and missed defects across thresholds
  • documented the additional tests and operator-review flow required before production use

No dedicated public repository or fully reproducible experiment artifact was verified. The case therefore does not present a model-specific score as a completed result. Its confirmed scope is an education team PoC for evaluation logic and missed-defect threshold design.

Data and decision flow

flowchart LR A["Public learning material"] --> B["Label, duplicate and quality checks"] B --> C["Train and validation split"] C --> D["Model-candidate comparison"] E["Limited field images"] --> F["Capture-condition check"] D --> G["Defect probability"] F --> G G --> H["Confusion matrix by threshold"] H --> I["Review missed defects first"] H --> J["Review false-alarm burden"] I --> K["Select a candidate rule"] J --> K

Public material supplied learning breadth. Field images were treated as a limited check against changes in lighting, reflection, surface condition, and camera position. They were not simply combined and described as one interchangeable training dataset.

Why these metrics were used

A false negative can allow a defective weld to continue downstream, so recall was reviewed first. Recall was not optimized in isolation: lowering a threshold can increase false positives and add reinspection labor and cycle-time cost.

[ \text{Precision} = \frac{TP}{TP+FP}, \qquad \text{Recall} = \frac{TP}{TP+FN} ]

[ \text{F1} = 2 \cdot \frac{\text{Precision}\cdot\text{Recall}}{\text{Precision}+\text{Recall}} ]

Candidates were compared under the same data split and metrics. When a threshold changed, a human reviewed the actual false-positive and false-negative images instead of accepting the aggregate score alone.

Normal and exception flows

The normal path is image input → probability → threshold decision → result record → operator review. Production use also needs explicit exception handling:

  • low-confidence images affected by glare or lighting go to recapture or manual review
  • model/operator disagreements are retained for label and cause review
  • product, camera, or weld-condition changes trigger revalidation instead of silent reuse
  • model version, threshold, Lot, and capture condition are stored with each decision

Technologies and why they were needed

Area Role in this project
Python experiment workflow manage data splits, candidate comparison, and metric calculation in a repeatable order
Deep-learning vision learn irregular surface and defect features that are difficult to encode as fixed rules
Confusion matrix expose false negatives and false positives hidden by accuracy

Manufacturing quality methods connect the model output to P-FMEA, inspection criteria, and traceability

Current result and remaining gates

Verified outputs are the data-role boundary, the model-comparison criteria, the threshold-evaluation flow, and the production-readiness gates. This was not a completed line deployment, real-time full inspection, or long-term drift-monitoring system.

Before production use, the following would still be required:

  1. split training and validation by product, Lot, and capture period
  2. disclose class counts and confusion matrices by defect type
  3. standardize camera position, focus, exposure, and illumination
  4. measure inference time and dropped frames at line speed
  5. run a shadow test alongside inspectors
  6. govern model and threshold changes, rollback, and revalidation

The value of the PoC is not a claim that AI replaced inspection. It shows how a manufacturing defect problem can be decomposed into data boundaries, missed-defect cost, a decision threshold, operator reinspection, and traceability.

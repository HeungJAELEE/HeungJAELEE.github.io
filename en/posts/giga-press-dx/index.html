Testing Equipment Expansion in a Virtual Factory

A ten-person training project checking control sequences and communication issues before equipment installation

Project period
Ten-person AI-convergence training project
Context
Team training PoC · no real-plant deployment
Scope
Communication setup, AI-candidate review, and technical research

User, build, and validation summary

User problem
Finding sequence and communication issues only after equipment installation makes tryout expensive.
Build scope
In a ten-person team, I handled communication setup, AI-candidate review, and technical research; ladder and SCADA implementation remain team contributions.
Result / current stage
The team connected Factory I/O, PLC, SCADA, and OPC UA in one educational demonstration and defined a virtual-commissioning checklist.

Why we built it

The later a sequence or communication problem is found on large equipment, the more expensive it becomes to correct. One missing sensor signal can leave the PLC, SCADA screen, and upstream data showing different states. If the first full test happens on physical equipment, trial time grows quickly.

This ten-person education team PoC used a hypothetical Giga Press factory expansion to explore how the control sequence and data flow could be tested before physical equipment was available.

What we wanted to change

Existing approachDirection built in the PoC
Test the sequence for the first time on physical equipmentRepeat normal and abnormal scenarios in Factory I/O first
Maintain PLC addresses and screen tags separatelyDefine common tag names and state meanings before integration
Leave unclear where a communication failure should stop the systemKeep control authority and safe state in the PLC; upper layers consume state
Show only that an alarm occurredShow the process step, cause signal, and recovery condition together

The goal was not another dashboard. It was to move likely commissioning problems into an earlier and cheaper test stage.

System flow

flowchart LR A["Sensors, switches, actuators"] --> B["Arduino / Raspberry Pi\nacquisition and normalization"] B --> C["PLC\nsequence, interlock, safe state"] C <--> D["Factory I/O\nvirtual process and test scenarios"] C --> E["SCADA\nstate, alarm, history"] C --> F["OPC UA\nupstream data interface"] F --> G["AI candidates\nstate prediction and condition recommendation"]

Field and edge devices

Arduino and Raspberry Pi were positioned as data-acquisition and normalization devices. Emergency stop, door interlock, and run permission remained within the PLC and safety-circuit boundary because they directly affect people and equipment.

PLC

The PLC remained responsible for process order and interlocks. The sequence was divided into ready check → material check → safety check → run permission → completion check → return, with entry, completion, and timeout conditions for each state.

IF safety_ok AND material_ready AND NOT alarm THEN
    run_permit := TRUE
ELSE
    run_permit := FALSE
END_IF

This is not the original Ladder program. It is a compact expression of the control intent: permission conditions are checked before a motion command is allowed.

SCADA and OPC UA

The SCADA concept showed the current process step, time spent in that step, last signal update, and alarm acknowledgement—not only run, stop, and fault. OPC UA provided a common naming layer so that PLC state could be read consistently by upstream systems and AI candidates.

Factory I/O

Factory I/O was used for normal cycles, missing sensor detection, delayed completion, communication loss, and manual/automatic mode conflict. It did not attempt to reproduce every physical characteristic of a real press. Its role was to reveal sequence and interlock gaps before FAT.

My contribution and the team result

I configured the communication path, organized the data exchanged by each layer, and reviewed where an AI model could be useful. Team members responsible for Ladder and SCADA implemented those parts, while the whole team developed the process scenario and presentation.

AI was positioned as a supporting layer that could find patterns in state history or recommend candidate conditions, not as a controller that replaced PLC run permission. Separating plant control from AI analysis prevents a model error from becoming an equipment command.

Implementation sequence

  1. Define the process flow and abnormal scenarios.
  2. Create a tag table for sensor and actuator addresses, logical names, units, and normal states.
  3. Separate PLC state, command, alarm, and interlock responsibilities.
  4. Connect Factory I/O and the PLC and verify the normal cycle.
  5. Inject missing signals, delays, and communication loss and inspect recovery behavior.
  6. Bind the same state names to SCADA and OPC UA and compare screen state with upstream data.

These checks carried the same logic I had used in battery-equipment FAT/SAT: acceptance rule → punch list → corrective action → retest under the same condition.

Result and value for manufacturing teams

The team connected Factory I/O, PLC, SCADA, and OPC UA in one demonstration flow. My communication setup and technical research helped define a boundary in which control, screens, and upstream data referred to the same state.

The structure can support manufacturing work in three ways:

  • sequence errors and missing interlocks can be found before equipment trial;
  • common tags reduce the number of places that must change when equipment is added;
  • abnormal and recovery behavior can be prepared as FAT/SAT checks, not left to ad-hoc commissioning.

The team report listed 50–75% shorter setup time and 50% lower expansion effort as target benefits. They are measurement targets for a future factory application, not results measured in this education demonstration.

Next step

A field project would still need safety-PLC and vendor-protocol integration, hardware-in-the-loop testing, alarm prioritization, automated regression tests, and OT-security review. The next useful deliverable is not merely a connected screen, but a commissioning package that manages virtual-test results and field acceptance criteria together.

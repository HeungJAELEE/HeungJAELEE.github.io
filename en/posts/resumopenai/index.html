resumOpenAI: An Evidence-aware Resume Generation PoC

A Flask/React LLM PoC that separates career facts, target-role selection, public wording, validation, and personal-data handling

Problem to solve

Repeatedly rewriting resumes can drift dates, metrics, and roles, while exposing more personal information than necessary.

My scope

  • Designed a Flask/React workflow that separates career facts from job-specific wording, minimizes personal data, and requires final human review.

Verified result / current stage

  • Verified output · Individual PoC flow from career facts to job requirements, wording candidates, and human confirmation

Team boundary

This is a personal PoC; AI proposes wording, while a person verifies facts and decides what to submit.

Disclosure scope: Actual resumes and personal information are not published; only the processing rules and interface flow are described.

The case generalizes a workflow that separates facts from presentation in job-application documents.

Why the decision mattered

A role-specific resume may reorder and rephrase the same career facts. If fluent generation adds work that was never performed, an unsupported number, or an unverified tool, however, the document loses trust. resumOpenAI therefore starts by separating career facts from role-specific wording, not by asking AI to complete a resume.

Names, phone numbers, email addresses, and detailed addresses are also unnecessary for most drafting. They should not cross an external-model boundary merely because they appear in the source document; rendering-only information remains separate until the final document stage.

Why a digital method was needed

When experience, education, and project facts are spread across documents, every application repeats the same normalization work. A structured fact store preserves confirmed employer, period, role, and evidence while allowing each target role to change only selection, order, and explanation.

React handles structured input and draft review, while Flask owns request validation, personal-data filtering, model calls, and response checks. The LLM does not approve facts. It transforms selected evidence into a role-specific draft.

My actual role

As a personal PoC, I designed the career-fact structure, public/private field boundary, target-role evidence selection, LLM drafting, deterministic checks, and human-approval flow. Source facts retain an experience_id, period, role, claim, evidence, and verification status so generated wording can be traced back to its origin.

The prototype prioritizes normalization, prompt rules, structured responses, claim checks, and user review over fine-tuning. No public training data or evaluation results support a claim of completed fine-tuning or improved model performance.

Data flow

Private career sources → local normalization and fact review → minimum public-field filter → target-role evidence selection → LLM draft → date, number, and claim checks → human final review and export

Rendering fields such as name and contact details are removed before the external-model boundary when they are not needed for drafting. Sensitive employer or customer names use approved aliases, and raw prompts and personal data should not be retained in ordinary application logs.

Implementation sequence

  1. Structure employer, period, role, career claims, and evidence with a verification status.
  2. Keep contact details, precise addresses, credentials, and raw employer documents in a separate private layer when they are not needed for generation.
  3. Select evidence for the target role without rewriting the source facts; change only ordering and explanation depth.
  4. Instruct the model to use supplied facts only, avoid invented metrics, tools, or responsibilities, and return insufficient evidence as a review item.
  5. Validate the response shape and compare dates, employers, roles, numbers, and sensitive fields with the source.
  6. Show source facts beside the draft and export only wording that a person has edited or approved.

Verified output and current stage

The current output is a React, Flask, and OpenAI design and prototype that separates career facts, role selection, draft wording, privacy boundaries, and human review.

No public repository or fixed evaluation dataset supports figures for factual-error rate, draft acceptance, or time saved. Automated checks also cannot guarantee factual correctness, so every generated result remains a draft.

Operating conditions and company value

A real service needs informed purpose and consent, minimum collection and transfer, retention and deletion rules, secret management, authentication and authorization, encryption, and audit history. Prompt and model versions and generated text should link back to source fact IDs. Conflicting dates or unverified achievements must not be resolved automatically, and human final review before submission remains mandatory.

Under those conditions, a company or applicant could reuse verified career evidence across role-specific drafts and trace changed wording back to its source. The value is not automatic writing alone; it is a reviewable process that separates facts, privacy, and final accountability.

Problem

If polished LLM wording changes dates, roles, or metrics, or sends unnecessary personal data to an external API, the resume becomes less trustworthy.

Goal

Separate verified facts, private fields, target role, generated draft, and user approval while tracing every sentence back to source evidence.

Success

Structured output passes schema, claim, date, and number checks; personal data is minimized; and no draft becomes final without user approval.

Scope and boundaries

In scope

  • React input/review UI and Flask validation/orchestration
  • Structured career facts, evidence IDs, and target-role selection
  • OpenAI API prompt contract, JSON schema, and claim validation

Out of scope or unverified

  • Predicting hiring success or making hiring decisions
  • Inventing missing experience, metrics, or credentials
  • Claiming verified fine-tuning or performance gains

Implementation and verification

What had to work

  • Every generated statement references a source experience or evidence ID.
  • Validate model output against JSON schema, dates, numbers, and blocked claims.
  • Only user-accepted or edited items enter the final document.

Quality and operating rules

  • Remove or pseudonymize contact, address, and sensitive company data before transmission.
  • Record model, prompt, schema version, and validation result.
  • API or format failure cannot destroy source career data.

Why it was designed this way

  1. Prioritize structure and evaluation before fine-tuning

    Without a fact model and evaluation set, fine-tuning may only make errors more consistent.

  2. Separate React, Flask, and LLM adapter

    UI state, privacy/business rules, and model dependency need independent replacement and testing.

  3. Keep final human approval

    Career context and public wording cannot be decided completely by automated rules.

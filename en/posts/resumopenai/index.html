    resumOpenAI: An Evidence-aware Resume Generation PoC

    A Flask/React LLM PoC that separates career facts, target-role selection, public wording, validation, and personal-data handling

    Problem: controlling career facts matters more than fluent generation

    resumOpenAI explores a narrower problem than “ask an LLM to write a resume.” It separates verified career facts, private fields, target-role selection, draft generation, and output validation so that polished wording cannot silently alter dates, employers, roles, or measured outcomes.

    Why structure comes before fine-tuning

    Fine-tuning can make style more consistent, but it cannot repair missing or contradictory facts. The first quality gate is a structured source model.

    {
  "experience_id": "exp-example",
  "employer": "verified employer",
  "period": {"start": "YYYY-MM", "end": "YYYY-MM"},
  "role": "verified role",
  "claims": [
    {
      "statement": "bounded achievement",
      "evidence": "source reference",
      "status": "verified",
      "public": true
    }
  ]
}

    Sensitive fields such as address, date of birth, phone number, credentials, or raw company documents should not be sent merely because they exist in a resume file. The public rendering model contains only approved technical facts.

    Architecture

    flowchart LR A["Private source documents"] --> B["Local extraction / normalization"] B --> C["Verified career-fact store"] C --> D["Public-field filter"] D --> E["Target-role evidence selection"] E --> F["Flask generation request"] F --> G["LLM draft"] G --> H["Claim/date/number validation"] H --> I["Human review"] I --> J["Exported draft"]

    The React layer captures job target and review choices. Flask owns schema validation, field filtering, prompt assembly, and result checks. The LLM receives only the minimum evidence required for the chosen output.

    Technologies and implementation

    The PoC uses React for structured input, Flask for the API boundary, explicit career-evidence records, an LLM for drafting, and output checks for unsupported or sensitive content. Facts and role-specific wording remain separate reviewable layers.

    AI and human roles

    AI proposes role-specific drafts, wording alternatives, and possible omissions. A human owns the source career facts, numeric evidence, privacy and employer-confidentiality review, target-role relevance, and the final submitted text.

    Problem

    If polished LLM wording changes dates, roles, or metrics, or sends unnecessary personal data to an external API, the resume becomes less trustworthy.

    Goal

    Separate verified facts, private fields, target role, generated draft, and user approval while tracing every sentence back to source evidence.

    Success

    Structured output passes schema, claim, date, and number checks; personal data is minimized; and no draft becomes final without user approval.

    Scope and boundaries

    In scope

    • React input/review UI and Flask validation/orchestration
    • Structured career facts, evidence IDs, and target-role selection
    • OpenAI API prompt contract, JSON schema, and claim validation

    Out of scope or unverified

    • Predicting hiring success or making hiring decisions
    • Inventing missing experience, metrics, or credentials
    • Claiming verified fine-tuning or performance gains

    Implementation and verification

    What had to work

    • Every generated statement references a source experience or evidence ID.
    • Validate model output against JSON schema, dates, numbers, and blocked claims.
    • Only user-accepted or edited items enter the final document.

    Quality and operating rules

    • Remove or pseudonymize contact, address, and sensitive company data before transmission.
    • Record model, prompt, schema version, and validation result.
    • API or format failure cannot destroy source career data.

    Why it was designed this way

    1. Prioritize structure and evaluation before fine-tuning

      Without a fact model and evaluation set, fine-tuning may only make errors more consistent.

    2. Separate React, Flask, and LLM adapter

      UI state, privacy/business rules, and model dependency need independent replacement and testing.

    3. Keep final human approval

      Career context and public wording cannot be decided completely by automated rules.

    Validation design

    The PoC treats generation as a draft process with deterministic gates.

    • Every employer, period, role, and number must exist in the source fact store.
    • A claim marked unverified cannot be promoted as achieved.
    • Conflicting date ranges produce a review item instead of an automatic choice.
    • Private fields are removed before the external-model boundary.
    • Unsupported superlatives and invented tools are flagged.
    • Korean and English outputs must point to the same fact IDs.

    Role-specific selection

    One fact store can support several views without rewriting history.

    • Manufacturing engineering: line setup, FAT/SAT, process conditions, yield, quality systems.
    • Manufacturing AI & data: Vision AI, PLC/SCADA/MES, digital twin, data contract, deployment boundary.
    • Data analysis: dataset definition, metric choice, validation, data quality, provenance, decision impact.

    The application changes ordering and explanation, not the underlying facts.

    Current limits

    • The current portfolio does not provide a public repository or evaluation dataset for this PoC.
    • A generated resume still requires human review.
    • Style consistency is not evidence accuracy.
    • Fine-tuning must not include unredacted personal or confidential documents.
    • Quality needs a fixed evaluation set containing contradictions, missing evidence, and sensitive fields.

    Next steps

    1. Publish a sanitized schema and sample dataset.
    2. Add claim-level provenance and output-to-source links.
    3. Build deterministic tests for dates, numbers, language parity, and privacy filtering.
    4. Compare prompt-only, retrieval-assisted, and fine-tuned variants on the same evaluation set.
    5. Record user acceptance/edit distance rather than relying only on LLM-style metrics.

    This case demonstrates an important AI application principle: structured facts, privacy boundaries, and deterministic validation come before fluent generation.

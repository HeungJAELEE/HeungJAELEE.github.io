The core of this project is the operating path that lets an operator read, edit, and validate existing Indy7 Teaching JSON on a PC, execute the physical robot, and observe the same runtime state in the HMI, database, and 3D Twin.

1. Automotive-assembly process and responsibility boundary

Background

Existing robot work remained inside the teaching pendant and individual program files. Task sequence, motion conditions, coordinates, I/O logic, and physical robot state could not be reviewed as one connected system. This project reused the existing Teaching Data, exposed it through a PC-HMI, and connected Robot A/B/C execution to an automotive-assembly Digital Twin.

3. Converting Teaching JSON into an operator task tree

Three core JSON arrays

A robot action is not stored in one record. Task order, motion conditions, and physical coordinates are separated and must be resolved again.

JSON areaStored informationMeaning in the HMI
programCommand type, id, pId, task order, branching, loops, and I/OMove, Pick, Place, Wait, If, and Loop task tree
moveListSpeed and acceleration, TCP, reference frame, interpolation, offset, and waypoint referencesHow the robot moves
wpListJoint q[], task p[], and blend radiusWhere the robot moves

Move coordinates are resolved through this chain.

program[name]
→ moveList[name]
→ moveList.wpList[id]
→ wpList[id]
→ joint q[6] / task p[6]

Command-group interpretation

4. Editing and loss-preserving JSON round trip

Preserve the complete source first

Vendor settings and unused waypoints that are not shown in the editor can still be required by the teaching pendant. The loader preserves the full source and its major arrays, and the saver merges only fields edited in the HMI.

prog._raw_info = data.get("info", {"name": prog_name})
prog._raw_wpList = data.get("wpList", [])
prog._raw_moveList = data.get("moveList", [])
prog._raw_full_data = data

Build reference maps

move_map[mv_name] = mv
wp_map[wp_id] = wp

mv = move_map.get(node.name, {})
real_wp = wp_map.get(wp_id, {})

The task-tree Move name resolves the motion condition, then the referenced waypoint ID resolves the actual joint and task coordinates.

Execution sequence in the later public code

The HMI and web layer do not open independent IndyDCP sockets for each robot. The Robot Controller owns the physical command path.

sequenceDiagram actor OP as Operator participant HMI as PC-HMI participant MQTT as MQTT participant RC as Robot Controller participant DCP as IndyDCP participant ROBOT as Indy7 participant DT as Digital Twin participant DB as DB Worker OP->>HMI: Select robot and Teaching JSON OP->>HMI: Run program HMI->>MQTT: robot/command + command_id MQTT->>RC: Deliver command RC->>RC: Check robot ID·queue·connection·fault RC-->>HMI: robot/accepted RC->>DCP: Convert joint/task/I/O command DCP->>ROBOT: Physical command loop while robot is connected ROBOT-->>RC: J1–J6·TCP·torque·DI/DO·status RC-->>HMI: robot/realtime RC-->>DT: robot/realtime RC-->>DB: robot/realtime end ROBOT-->>RC: Busy=0·MoveDone or fault RC-->>HMI: robot/result or robot/error

Per-robot queues and result tracking

  • Robots A, B, and C use separate command queues.
  • Every request carries a command_id so acceptance, completion, and failure remain tied to one request.
  • robot/accepted reports queue acceptance, robot/result reports completion disposition, and robot/error reports faults, communication errors, and command errors.
  • Stop, Emergency, Reset, and Disconnect are immediate commands that clear pending work before priority handling.
  • Joint/task motion compares before-and-after physical coordinates with Busy and MoveDone state to classify completion or timeout.

6. Live robot state and the 3D Digital Twin

Runtime-state collection

The Robot Controller polls each connected robot and publishes one robot/realtime payload.

StateUse
q — J1 through J6Compute each joint’s 3D position and robot pose
p — TCP poseDisplay the physical tool position in HMI telemetry
torqueReview per-axis load state
di / doReview PLC, tool, and process signals
busy / movedoneDetermine execution and completion
emergency / collision / errorBlock motion and disposition recovery
connectedDisplay per-robot connection state

Forward kinematics and installation offsets

Physical J1–J6 values are applied to DH-parameter transformation matrices. TCP and Robot A/B/C installation offsets place the robot pose in the factory coordinate frame.

J1–J6
→ DH transformation matrices 1–6
→ joint and flange 3D positions
→ TCP offset
→ Robot A/B/C installation offset
→ arm·TCP·trajectory update

T = self.compute_forward_kinematics(j_pos)
tcp_local = np.array([
    self.tcp_offset[0],
    self.tcp_offset[1],
    self.tcp_offset[2],
    1.0,
])
P6 = (T[6] @ tcp_local)[:3]
offset = self.robot_offsets.get(name, np.array([0, 0, 0]))
P6 += offset

8. Next extension — Omniverse, Isaac Sim, and AI Agent

The completed path is Teaching Data → PC-HMI → Robot Controller → Runtime State → DB/Twin. The next stage adds a separate simulation path without replacing that interface.

Next stageDesign direction
Omniverse / Isaac SimRobot and equipment assets, coordinate systems, and joint/TCP state adapters
Shadow TwinSeparate physical and simulation commands; pre-check collision, reachability, and cycle behavior
AI AgentDefine process state, action, and constraints; recommendation → simulation evaluation → operator approval
Operating conditionsAuthorization, duplicate-command handling, communication recovery, safety interlocks, and physical E2E revalidation

The target is not another 3D screen. It is a manufacturing-AI experiment environment that reuses existing robot programs and live state so process changes and AI control strategies can be reviewed before physical-equipment application.

The full team project

The team created an automotive automated-assembly scenario, demonstrated it with a physical Indy7 robot, and reviewed how robot commands, state, and work history could be connected in one flow. I planned the overall project and designed the sequence between robot control and system interfaces.

The assembly scenario and physical Indy7 demonstration were team results, and the team lead wrote the report. My direct work covered the later public-code extension: PC HMI, Robot Controller, MQTT/DB, a read-only Web Twin, and Conty JSON compatibility.

My core responsibility was giving robot commands one owner

01

MY CORE

Command, state, and display responsibilities were separated

The Robot Controller owns the robot socket so screens and background services do not compete for control.
flowchart LR A["HMI request
command_id
MY CORE"] --> B{"Robot Controller
MY CORE"} B -->|Accept| C B -->|Fault or queue full| F C["accepted"] --> D["IndyDCP execution"] --> E["result and realtime"] F["error and rejection"] --> G["UI, DB, Web Twin"] E --> G
  • The Python Robot Controller is the sole owner of the IndyDCP socket.
  • The HMI sends an operation request with command_id; the controller separates accepted, result, error, and connection states.
  • New commands are rejected when the controller is in a fault state or its command queue is full.
  • Repeated state messages include joints, TCP, torque, I/O, busy, error, collision, and emergency state.
  • The DB Worker and Web Twin do not connect directly to the robot. They store or display MQTT state read-only.

Teaching JSON preserved references across a save cycle

02

DATA CONTRACT

A round-trip policy preserved fields the PC editor did not understand

Editing a familiar value could not be allowed to break the program tree or waypoint references.

Risk

  • Robot jobs connect the id/pId program tree, move and waypoint references, tool/TCP settings, speed, units, and I/O fields.
  • Saving only the fields understood by a PC editor can leave its screen looking correct while breaking teaching-pendant references.

Implementation and check

  • Parser and serializer responsibilities were separated, and unknown source fields were preserved.
  • The check followed load source → edit selected fields → save → reload → compare tree, references, and units.
  • Setting/Teaching, Dry Run Recording, and Auto/Monitor were separated by task.
  • Exact corpus counts were excluded because public evidence sources conflict.

Normal execution and rejection conditions were kept separate

  1. Setting/Teaching prepares job and teaching information.
  2. Auto/Monitor sends an operation request to the Robot Controller.
  3. The controller accepts the command or rejects it based on fault and queue state.
  4. Accepted commands run through IndyDCP, and results and realtime state are published through MQTT.
  5. The DB Worker stores history, while the Web Twin displays Robot A/B/C state read-only.

Verified exception handling covers separated acceptance, result, error, and connection states plus fault and queue-full rejection. It does not claim completed role-based permissions, the full duplicate-command boundary, long-duration reconnection, or automated recovery.

Team result and current stage

The team connected an automotive assembly scenario to a physical Indy7 demonstration. I led overall planning and owned robot control, integration architecture, and command/status implementation. Public main@a6c08e5 verifies the HMI, Robot Controller, MQTT/DB, read-only Web Twin, PLC Bridge, and JSON round-trip structure.

Next gates are full long-duration E2E including the physical PLC, reconnection, duplicate-command handling, permissions, and recovery behavior. Omniverse and AI Teaching remain expansion directions rather than completed integrations.

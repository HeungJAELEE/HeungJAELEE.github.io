The problem

A robot program is more than a list of joint positions. Tool and TCP settings, waypoints, motion commands, branches, speed, and I/O fields reference one another. If a PC editor reads only familiar fields and rewrites the file, the result may look correct on screen while failing on the teach pendant.

Communication has a similar ownership problem. If the HMI, historian, and digital twin each open a robot socket, it becomes difficult to identify who sent a command and which state is current.

What a first-time user sees

PC-HMI

The operator opens a Conty program in the PC-HMI and inspects its hierarchy. After a waypoint or motion command is edited, the application checks whether source references remain intact before saving. The connection view brings robot status, the current job, command results, and errors into one place.

Job and error history

Each request receives a command ID so its result can be matched later. Start, completion, and error times are stored in the database, allowing the operator to see where the previous job stopped after a screen or service restart.

Read-only Web Twin

The Web Twin receives MQTT state through WebSocket and draws robot and process status on Canvas. It intentionally has no physical-motion controls. Separating observation from control prevents command authority from spreading across multiple screens.

JSON compatibility layer

Unknown source fields are preserved instead of discarded. The basic test is load → edit → save → reload → compare references. Waypoint, program-tree, and motion-command references are checked separately.

One physical-socket owner

Only the Robot Controller owns the IndyDCP connection. The HMI sends requests; the database and twin consume state. This keeps a display or storage failure from silently becoming another physical-control path.

Separate command and state topics

MQTT command, result, realtime state, connection, and error events have different responsibilities. A command ID connects each request with its outcome. Idempotency and role-based topic permissions remain part of the next validation stage.

What I designed and implemented

  • hierarchical JSON browsing and editing
  • parser and serializer boundaries that preserve the source structure
  • a Robot Controller-centered communication boundary
  • DB Worker responsibilities for job, state, and error history
  • event contracts designed for PLC monitoring and HMI consumers
  • a read-only twin without physical command controls
  • progressive Offline UI, Direct, and Gateway execution modes

The project begins without a physical robot so that JSON and screen behavior can be checked first. Direct communication is added next, followed by the gateway and state consumers. This sequence makes it easier to identify whether a failure belongs to the robot, messaging, database, or UI layer.

Program structure and completion boundary

The system separates screen, robot control, messaging, and status history. The table distinguishes connected functions from the monitoring layer that remains design-only.

The Robot Controller executes commands through IndyDCP and publishes results and state through MQTT. The database and digital twin consume those events without owning the robot socket. The PLC bridge remains a monitoring design rather than a completed integration.

Execution sequence

  1. Check JSON browsing, editing, and screen flow in Offline mode.
  2. Connect the PC-HMI and Indy7 Controller for basic command and state exchange in Direct mode.
  3. Give the Robot Controller sole ownership of the physical connection in Gateway mode.
  4. Publish state, command results, and errors as separate MQTT events.
  5. Add the database and Web Twin one at a time and compare state and display.
  6. Keep the PLC bridge as a separate monitoring follow-up.

Result

The main result is a structure that preserves robot-program compatibility while keeping physical-control ownership in one place. The HMI, database, and twin consume state independently, so visualization and history services do not take over the control socket.

I led the system goal, interfaces, and integration sequence and connected Conty JSON compatibility, PC-HMI, Python control, MQTT, database, and the read-only digital twin. The wider scenario, including vision, was developed with the team; the PLC bridge remains a monitoring design scope.

Next steps

  • regression tests that open and save programs across multiple Indy7 firmware versions
  • long-running reconnect and duplicate-command handling with the physical robot
  • command permissions, user roles, and audit history
  • recovery rules that prevent automatic re-execution after a lost connection
  • an Omniverse USD adapter only after these control and recovery checks are complete

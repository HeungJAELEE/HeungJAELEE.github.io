1. Project background and Technical-PM role

Pain point

Existing robot programs were isolated in teaching pendants and individual JSON files. Task sequence, coordinates, I/O conditions, and physical robot state were separated, preventing PC-HMI editing, full-process integration, 3D state monitoring, and later AI use.

Objective

  • Convert existing Teaching Data into a PC-readable, editable, and reusable data asset
  • Integrate input, completion, and error handshakes across QR → Robot A → Vision 1 → Robot B → Vision 2 → Robot C
  • Connect physical-robot joint, TCP, and execution state to a 3D factory scene
  • Establish interfaces that later simulation and AI-Agent layers can reuse

I served as the Technical PM / Robot and Digital Twin Integration Lead for process and system integration, separate from the team lead’s final reporting role.

2. Legacy-data integration architecture

The team PoC used the PLC as the process-sequence master. The later public code separated HMI and web requests from physical command ownership so that the Robot Controller exclusively owns IndyDCP execution.

Busy·Error·Connection"] RT --> RC --> MQTT["MQTT state bus"] MQTT --> TWIN["3D Digital Twin
read-only Web Twin"] MQTT --> DBW["DB Worker"] --> MYSQL[("MySQL history")] PLC -. "later public code: state read" .-> MQTT

This separates program source, physical command authority, runtime state, history storage, and 3D presentation. Vision, PLC, and database components can integrate through defined state and event contracts without depending on robot-internal code.

3. Core engineering implementation

① [Data Engineering] Teaching-JSON structure analysis and round trip

I analyzed the Conty Teaching JSON program, moveList, wpList, and id/pId relationships and rebuilt flat nodes into an operator-facing task tree.

  • Interpretation of Move, Pick, Place, Wait, If, Loop, and I/O task sequence
  • Links among joint/task coordinates, speed, Tool/TCP, and reference frames
  • Node and waypoint editing in the PC-HMI tree
  • Preservation of unused waypoints and vendor-specific fields while merging edited fields
  • Parent, move–waypoint, unit, and TCP-reference validation before export
Teaching JSON
→ Program-node tree
→ Move·Waypoint·Tool/TCP resolution
→ PC-HMI editing
→ Reference validation
→ JSON save
→ Robot Controller execution request

② [Control Architecture] Robot-Controller command authority

I separated the command queue and runtime state for Robots A, B, and C and traced requests through completion with command_id.

  • robot/accepted: acceptance and queue state
  • robot/result: completion or failure result
  • robot/error: fault, communication, or execution error
  • Motion-command blocking during emergency, collision, or robot-error state
  • Joint/task motion completion and timeout disposition
  • Runtime distribution of J1–J6, TCP, torque, DI/DO, busy, and connection state

The PC-HMI requests execution; the Robot Controller checks connection, fault, queue, and completion conditions before sending the physical command through IndyDCP.

③ [Digital Twin] Forward-kinematics 3D state synchronization

J1–J6 joint values from the physical robot are processed through DH-parameter forward kinematics, then combined with TCP and robot-installation offsets.

J1–J6 joint state
→ DH transformation matrices
→ joint and flange positions
→ TCP offset
→ robot installation offset
→ 3D pose·TCP·trajectory
  • Robot A/B/C 3D pose and TCP display
  • Factory rail, vehicle, and process-station layout
  • Joint, TCP, Busy, Complete, Error, and Connection state linkage
  • TCP trajectory and process-position visualization
  • Read-only Web Twin for state monitoring; physical command execution remains in the PC-HMI and Robot Controller

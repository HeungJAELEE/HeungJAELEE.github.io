Manufacturing automation problem the team addressed

Robot motion alone is not sufficient for automated assembly. The system also has to show which screen sent a command, whether the robot accepted it, what result or error followed, and where product and work history were recorded.

The team demonstrated an automotive assembly scenario with a physical Indy7 and connected robot operation, state, and work history in one flow. I planned the overall project and owned robot motion, controller communication, and the HMI command and state path. The team lead wrote the final report.

Command and state architecture

flowchart LR HMI["PC HMI\nOperation request"] --> CMD["command_id\nCommand message"] --> RC["Robot Controller\nSingle IndyDCP socket"] --> ROBOT["Indy7 robot"] ROBOT --> RC --> STATE["accepted, result, error, and realtime"] STATE --> UI["HMI status"] STATE --> DB["DB worker\nWork history"] STATE --> TWIN["Read-only Web Twin"] PLC["PLC state change"] --> BRIDGE["Read-only bridge"] --> STATE

Why the Robot Controller owned the command path

If several interfaces and services own the robot socket directly, commands and responses can conflict. The Python Robot Controller therefore owned one IndyDCP socket and serialized requests from HMI and MQTT.

  • Each HMI request included a command_id.
  • The controller separated accepted, result, error, and connection states.
  • New commands were rejected under fault or queue-full conditions.
  • Joint, TCP, torque, I/O, busy, error, collision, and emergency state were published repeatedly.
  • The DB worker and Web Twin stored or displayed state and did not command the robot directly.

This structure prevented UI connectivity from being mistaken for successful robot execution.

Why Teaching JSON had to preserve the original structure

Robot job files connect the id/pId program tree, move and waypoint references, tool and TCP, speed, units, and I/O fields. Saving only fields understood by the PC editor can leave the screen looking correct while breaking teaching-pendant references.

  1. Parsed the original JSON.
  2. Edited only the fields required by the interface.
  3. Preserved original fields that the interface did not understand.
  4. Reloaded the saved file and compared the tree, references, and units.

Setting/Teaching, Dry Run Recording, and Auto/Monitor screens were separated by task.

Normal execution and error review

  1. Setting/Teaching prepares job and teaching information.
  2. Auto/Monitor sends an operation request to the controller.
  3. The controller accepts the command or rejects it according to fault and queue state.
  4. Accepted commands execute through IndyDCP and publish results and realtime state through MQTT.
  5. The DB worker stores history, and the Web Twin displays Robot A/B/C state read-only.
  6. Error and connection state remain separate from command result in the interface and records.

Team result and future application

The team connected an automotive assembly scenario to a physical Indy7 demonstration. The personal extension connected the HMI, Robot Controller, MQTT, DB, read-only Web Twin, and JSON round-trip structure. Future work can validate long-duration E2E with a physical PLC, reconnection, duplicate-command handling, authorization, and recovery, then connect Omniverse visualization and AI Teaching to the same command and state contract.

Indy7 Robot and Omniverse Digital Twin Lab

A PC-HMI, event-history, and read-only digital-twin prototype designed around robot-program compatibility and clear control ownership

If one program owns robot commands, current state, history, and the digital twin, failures and authority become ambiguous; separating responsibilities makes the system safer to extend.

Why the shop-floor decision mattered

An Indy7 program is not only a list of positions. Tool and TCP settings, waypoints, motion commands, and the program tree reference one another. If a PC editor drops an unknown field or changes a reference, the file can look correct on screen and still fail on the teach pendant.

Communications ownership creates a related risk. If the HMI, historian, PLC integration, and digital twin each open a robot socket, it becomes difficult to trace command ownership and determine which state is current. Allowing display or storage features to create additional physical-control paths weakens the safety boundary.

Why a digital method was needed

A PC-HMI makes hierarchical JSON easier to inspect and edit, but source compatibility must come before convenience. Unknown fields are therefore preserved, and the basic round-trip check is load → edit → save → reload → compare references.

For communications, one Robot Controller owns the IndyDCP connection. Other functions exchange command requests or consume state events. This keeps visualization and history from independently owning the physical-control socket.

My actual role

In this project, I designed and prototyped the JSON compatibility layer, PC-HMI, Robot Controller-centered communications boundary, and the responsibilities of history and twin services. The design separates:

  • Command: the HMI sends a request with a command ID; only the Robot Controller executes IndyDCP commands.
  • State and result: realtime robot state, connection, errors, and command outcomes are published as separate events.
  • History: the DB Worker stores job, state, and error history without owning physical commands.
  • PLC Bridge: PLC and HMI consumers exchange required state through an event contract; it is not an arbitrary bypass control path.
  • Digital Twin: the twin is a read-only state consumer with no physical command controls.

Data flow

PC-HMI command request → Robot Controller’s single IndyDCP connection → command-result and realtime-state events → DB Worker history / PLC Bridge state exchange / read-only twin observation

Command, result, realtime state, connection, and error are not mixed into one message. A command ID connects each request to its outcome so the path remains traceable.

Implementation sequence

  1. Identify unknown Conty JSON fields and waypoint, program-tree, and motion-command references that must survive a round trip.
  2. Build the hierarchical JSON browser and editor around parser and serializer boundaries that preserve source data.
  3. Use an Offline UI stage to check file behavior and screen flow without a robot.
  4. Add a Direct stage in which the Robot Controller alone owns the IndyDCP connection.
  5. Add a Gateway stage that separates command, result, state, connection, and error events for the DB Worker, PLC Bridge, and twin consumers.
  6. Keep the twin read-only and omit physical command controls.

Verified output and current stage

The current output is a design and prototype joining JSON compatibility with PC-HMI and service ownership. It is not presented as production remote robot operation. Omniverse remains a future adapter direction rather than a completed integration.

The associated repository was reported to contain internal-network, local-path, and default-configuration patterns, so its external link remains withheld. Round-trip tests across Indy7 firmware versions and long-running reconnect and duplicate-command tests with hardware are still open.

Deployment conditions and company value

Field connection requires firmware-specific JSON regression tests, command authentication and authorization, idempotency, MQTT topic permissions, timeout and reconnect behavior, and audit history. Hardware-in-the-loop testing must also confirm that the PLC Bridge and twin cannot bypass the Robot Controller’s single command boundary. Emergency stop and safety interlocks remain the responsibility of validated robot and PLC safety systems.

Under those conditions, the company could reduce the risk of corrupting program references and trace commands, state, and errors through one path. A read-only twin could share current state without creating a new control channel. Any reduction in downtime or editing effort still needs field measurement.

Problem

Partial Conty JSON edits can damage references, while multiple direct IndyDCP clients scatter command ownership and state timing.

Goal

Preserve source JSON round trips and use one Robot Controller so HMI, DB, PLC, and twin consumers share explicit events.

Success

References survive load–edit–save–reload, one service owns the physical socket, and offline/direct/gateway modes are reproducible.

Scope and boundaries

In scope

  • Conty/APK JSON round-trip and reference integrity
  • Single IndyDCP ownership and separate MQTT command/state events
  • CustomTkinter HMI, MySQL worker, PLC bridge, and read-only web twin

Out of scope or unverified

  • Claiming Omniverse is a validated production display
  • Unsupported latency, uptime, or collision-reduction metrics
  • Direct physical robot commands from the digital-twin layer

Implementation and verification

What had to work

  • Preserve unknown JSON fields and references, then reload after save.
  • Only Robot Controller owns a physical IndyDCP socket.
  • Separate command, result, realtime, connection, and error events.

Quality and operating rules

  • Offline UI validates JSON and screen flow without a robot.
  • DB and twin are state consumers, not command paths.
  • Internal-network, local-path, and default-configuration patterns are removed before publication.

Why it was designed this way

  1. Preserve source on round trip

    Unknown vendor fields must survive to retain teach-pendant compatibility.

  2. Use one IndyDCP socket owner

    This prevents concurrent-command races and centralizes physical-control accountability.

  3. Keep the twin read-only

    A visualization failure must not become a physical robot command.

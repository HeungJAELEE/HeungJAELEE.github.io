Overall team project

The team demonstrated an automotive automated-assembly scenario with a physical Indy7 and explored one flow for commands, state, and work history. The assembly scenario and physical demonstration were team results. I led overall planning and owned robot-control and system-interface integration.

Command and state flow

flowchart LR HMI["PC HMI\nMY CORE"] --> CMD["Request and command_id"] --> RC["Robot Controller\nMY CORE"] --> ROBOT["Indy7\nTEAM PHASE"] ROBOT --> RC --> STATE["Result and realtime"] STATE --> UI["HMI status"] STATE --> DB["DB worker"] STATE --> TWIN["Read-only Web Twin"] PLC["PLC state change"] --> BRIDGE["Read-only PLC bridge"] --> STATE

The public-code extension covers the PC HMI, robot controller, MQTT and DB, read-only Web Twin, and Conty JSON compatibility. The Web Twin and DB worker do not command the robot directly; they store or display state.

Why robot-command ownership was centralized

  • Only the Python robot controller owns the IndyDCP socket.
  • HMI requests include command_id, and the controller separates accepted, result, error, and connection states.
  • New commands are rejected under fault or queue-full conditions.
  • This does not claim completed user authorization, long-duration reconnection, all duplicate-command cases, or full recovery.

Teaching JSON preservation

Parser and serializer responsibilities were separated, and unknown original fields were retained. The check sequence was load original → edit part → save → reload → compare tree, references, and units to preserve program-tree and waypoint meaning.

Team result and current stage

The team connected an automotive assembly scenario to a physical Indy7 demonstration. The public snapshot verifies the personal command/state path and read-only Web Twin. Long-duration E2E with a physical PLC, reconnection, duplicate commands, authorization, and recovery remain. Future work can connect Omniverse visualization and AI Teaching to the same command and state structure.

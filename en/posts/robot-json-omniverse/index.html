The problem

A robot program is more than a list of joint positions. Tool and TCP settings, waypoints, motion commands, branches, speed, and I/O fields reference one another. If a PC editor reads only familiar fields and rewrites the file, the result may look correct on screen while failing on the teach pendant.

Communication has a similar ownership problem. If the HMI, historian, and digital twin each open a robot socket, it becomes difficult to identify the command owner and the latest state.

Why the system is divided this way

flowchart LR A["Conty JSON"] --> B["Load, inspect, edit, save"] B --> C["Preserve references and unknown fields"] D["PC-HMI"] --> E["Robot Controller\nsingle IndyDCP owner"] E --> F["MQTT command / result / state"] F --> G["DB Worker\njob and error history"] F --> H["PLC Bridge"] F --> I["Read-only Digital Twin"]

JSON compatibility

Unknown source fields are preserved instead of discarded. The core check is load → edit → save → reload → compare references. Waypoint, program-tree, and motion-command references are inspected separately.

One physical-socket owner

Only the Robot Controller owns the IndyDCP connection. The HMI sends requests; the database and twin consume state. This prevents a display or storage failure from silently becoming another physical-control path.

Separate command and state events

MQTT command, result, realtime state, connection, and error events have different responsibilities. A command identifier should connect each request with its outcome. Idempotency, authentication, and topic permissions remain required before a production-like connection.

What I built and reviewed

  • A hierarchical JSON browser and editor
  • Parser and serializer boundaries that preserve source data
  • A Robot Controller-centered communications design
  • A DB Worker for job, state, and error history
  • Event contracts shared by PLC and HMI consumers
  • A read-only twin without physical command controls
  • Progressive Offline UI, Direct, and Gateway execution modes

The workflow begins without a robot so JSON and screen behavior can be checked first. Direct communication is added next, followed by the gateway and state consumers. This staged path makes failures easier to isolate.

Verified program structure

The current main branch separates presentation, domain logic, and external-device access. The responsibility of each area matters more than the folder names alone.

Area Verified components Responsibility
frontend/presentation Robot HMI, Digital Twin, Virtual Test views operator-facing program, state, and history UI
frontend/core runtime configuration, service manager, robot domain rules and startup order between UI and communications
frontend/infrastructure IndyDCP, Conty executor, MySQL adapter robot, PLC, and database connections
backend/robot_controller robot commands and state publication single owner of the physical robot connection
backend/db_worker work, error, and state persistence convert MQTT events into traceable records
backend/plc_bridge PLC reads and event publication separate PLC observation from robot control
backend/digital_twin MQTT subscription, WebSocket, Canvas twin display current state without command authority

The Robot Controller executes commands through IndyDCP and publishes results and state through MQTT. The DB Worker and Web Twin consume those events without owning the robot socket. The PLC Bridge publishes observation data as a separate event stream. This makes command ownership clear and lets failures be isolated by communication layer.

Result

The result is not presented as “remote robot control.” The project treats file compatibility and physical-control ownership as one engineering problem. It also keeps HMI, history, and visualization functions from independently owning the control socket.

Evidence and limits

The associated repository was reported to contain internal-network, local-path, and default-configuration patterns. Its GitHub and report buttons are withheld until cleanup and a new public review are complete.

  • This is not claimed as a production deployment.
  • Round-trip behavior still needs broader testing across Indy7 firmware versions.
  • Long-running reconnect and duplicate-command tests with hardware remain open.
  • Omniverse is a future adapter direction, not a completed result.
  • The twin remains an observation layer without physical command authority.

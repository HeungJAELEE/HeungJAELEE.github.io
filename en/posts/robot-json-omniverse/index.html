Current stage, before anything else

This case is a training and development prototype exercised with a physical Indy7. It separates a CustomTkinter HMI for reading and editing robot programs from a Robot Controller, MQTT, history storage, PLC monitoring, and a web twin. The public source contains a read-only browser monitor. An NVIDIA Omniverse USD adapter is a future direction, not a completed integration or production deployment.

A robot program is more than a list of positions. Tool and TCP settings, waypoints, motion settings, and the program tree reference one another. If an editor removes an unknown field or changes a reference, the file may look correct on the PC and still fail on the teach pendant. The lab therefore starts with load → edit → save → reload → compare references, not with a polished 3D scene.

The key distinction is that desktop Page 1 and the separate Web Twin are not the same surface. Page 1 remains inside the HMI control boundary. Only the Web Twin and a future Omniverse adapter are intended to be observation-only.

The order a user actually follows

  1. Open the JSON offline first. On Page 2, load a file without connecting a robot and inspect the references across info, wpList, program, and moveList.
  2. Edit nodes and review the order with virtual Play. Selecting a Pick, Place, Loop, DI, or DO node changes the settings and Jog area on the right. This stage reviews the intended sequence and edit scope.
  3. Save, then read the file again. The repository keeps the original blocks that it does not own, rebuilds known fields, and reloads the result to check node IDs and waypoint/move references.
  4. Choose the connection path explicitly. In the operational mqtt mode, the HMI publishes requests and the Robot Controller owns IndyDCP. direct is a separate lab path in which the HMI connects without the Docker gateway; it must not be treated as the same single-controller topology.
  5. Check state before connecting equipment. Robot Settings, Communication Check, and Service Management expose the selected robot, MQTT, DB, and PLC status separately. An open app window does not mean the equipment is connected.
  6. Send a real command only when intended. Page 2 Execute/Jog and Page 1 quick controls are write paths. The on-screen E-STOP is a command button, not a replacement for a validated hardware emergency-stop circuit.
  7. Use Page 3 for diagnostic recording. It can evaluate branches with virtual DI and skip physical DO/tool outputs, but the connected robot still moves and publishes telemetry. It therefore requires a controlled area, reduced-speed procedure, supervision, and explicit stop criteria.
  8. Observe state on Page 1 and the Web Twin. The operator sees control and live state in the HMI, while another viewer sees only the same robot/realtime stream and recent events in the Web Twin.

Basis: a generalized diagram derived from the public communications guide and the HMI, Robot Controller, DB Worker, PLC Bridge, and Web Twin source inspected on July 31, 2026. It is not a fabricated screen or run result.

Separating command, accepted, result, realtime, connection, and error distinguishes “the Broker received a request” from “the robot completed the action.” A command_id alone does not create idempotency. The current Robot Controller has per-robot queues and completion checks, but durable duplicate-command rejection remains to be verified.

Problem

Partial Conty JSON edits can damage references, while multiple direct IndyDCP clients scatter command ownership and state timing.

Goal

Preserve source JSON round trips and use one Robot Controller so HMI, DB, PLC, and twin consumers share explicit events.

Success

References survive load–edit–save–reload, one service owns the physical socket, and offline/direct/gateway modes are reproducible.

Scope and boundaries

In scope

  • Conty/APK JSON round-trip and reference integrity
  • Single IndyDCP ownership and separate MQTT command/state events
  • CustomTkinter HMI, MySQL worker, PLC bridge, and read-only web twin

Out of scope or unverified

  • Claiming Omniverse is a validated production display
  • Unsupported latency, uptime, or collision-reduction metrics
  • Direct physical robot commands from the digital-twin layer

Implementation and verification

What had to work

  • Preserve unknown JSON fields and references, then reload after save.
  • Only Robot Controller owns a physical IndyDCP socket.
  • Separate command, result, realtime, connection, and error events.

Quality and operating rules

  • Offline UI validates JSON and screen flow without a robot.
  • DB and twin are state consumers, not command paths.
  • Internal-network, local-path, and default-configuration patterns are removed before publication.

Why it was designed this way

  1. Preserve source on round trip

    Unknown vendor fields must survive to retain teach-pendant compatibility.

  2. Use one IndyDCP socket owner

    This prevents concurrent-command races and centralizes physical-control accountability.

  3. Keep the twin read-only

    A visualization failure must not become a physical robot command.

Project scope and current stage

This team-based prototype separates the Indy7 command path from the status-monitoring path and brings them into one user flow. The automotive assembly scenario, physical Indy7 demonstration, and vision/PLC/MES expansion concept were team results. I defined the system goal, interfaces, and integration sequence, then implemented the Conty JSON compatibility layer, PC HMI, Python Robot Controller, MQTT/DB history, and read-only Web Twin connection.

User flow from preparation to status monitoring

The user flow is divided into setting and teaching, dry-run recording, automatic operation and monitoring, and read-only status review. AI Teaching remains a separate experimental screen rather than part of the basic operation flow.

Setting/Teaching → Dry Run Recording → Auto/Monitor → Web Twin status view

The four PC-HMI pages separate responsibilities instead of placing every function on one screen.

PageUser task
Auto/MonitorSend robot-operation requests and review key status.
Setting/TeachingManage job settings and teaching information.
Dry Run RecordingRecord the dry-run process and related information.
AI TeachingReview follow-up experiments on a separate page.

Separating command and status paths

If the PC HMI and monitoring services each open their own robot socket, it becomes difficult to trace which component sent a command. The Python Robot Controller therefore owns the only IndyDCP socket. The HMI sends requests to the Robot Controller, while the Web Twin and PLC Bridge do not send robot commands.

flowchart LR HMI["PC HMI\nsetting, teaching, operation requests"] --> RC["Robot Controller\nsole IndyDCP socket owner"] RC --> ROBOT["Indy7"] RC --> MQTT["MQTT\nstatus messages"] MQTT --> DB["DB Worker\nstatus history"] MQTT --> TWIN["Web Twin\nread-only status view"] PLC["PLC signals"] --> BRIDGE["PLC Bridge\nread-only monitoring"] BRIDGE --> MQTT

This structure reduces the number of command paths. It does not claim completed industrial safety control, role-based permissions, or duplicate-command prevention.

Passing, storing, and displaying status

The Robot Controller publishes status through MQTT, the database stores status history, and the Web Twin displays Robot A, B, and C process states in a read-only view.

ComponentResponsibility
Robot ControllerIndyDCP connection and robot command path
MQTTStatus-message delivery
DB WorkerJob, error, and status history storage
Web TwinRead-only display of Robot A, B, and C status
PLC BridgeMonitoring path that reads PLC signals and publishes them to MQTT

The public repository includes read-only PLC monitoring code and Docker configuration. A full E2E test with the physical PLC and robot remains outside the verified scope.

Preserving Conty JSON references

A robot job contains more than joint coordinates. Tool and TCP settings, waypoints, motion commands, branches, speed, and I/O fields reference one another. If a PC editor reads only familiar fields and rewrites the file, the result may look correct on screen while breaking references on the teaching pendant.

The parser and serializer therefore preserve unknown source fields. The basic check is load source → edit selected fields → save → reload → compare references. Exact full-corpus compatibility counts are excluded because the public evidence is inconsistent.

Verified result and next validation

The public repository verifies four HMI pages, sole IndyDCP socket ownership by the Robot Controller, MQTT/DB status-history code, a read-only Robot A/B/C Web Twin, PLC monitoring code, and Docker configuration. I also rendered the public Web Twin locally to verify the current screen.

Next steps are full physical PLC/robot E2E, long-duration operation, reconnect behavior, duplicate-command handling, user and function permissions, and recovery scenarios. Omniverse and AI Teaching remain follow-up work after these core checks.
